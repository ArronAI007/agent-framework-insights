# 事件流与流式输出

> `coworker/events.py` 只有 49 行,定义了一个 `EventType` 枚举和一个 `Event` dataclass——这是 `TurnEngine` 和任何"界面"（GUI、TUI、IDE 插件、Slack 转发)之间唯一的契约。文件头的 docstring 写得很实在："No token streaming in v1, so granularity is per-message/per-tool. Streaming later adds `assistant_delta`/`tool_output_delta` without changing the rest."——这句注释描述的其实是"以后要加"的计划,而读到今天的代码会发现 `assistant_delta` 已经存在了,说明这份文档注释本身也是这个循环演化过程的一份历史记录。这一篇要沿着 `Event` 这条线,看它在 `engine.py` 里是怎么被产生的、经过 `server/app.py`/`server/manager.py` 怎样的转发路径,最终变成 `surfaces/gui` 里用户看到的打字机效果和实时状态卡片。

## 学习目标

- 通读 `EventType` 枚举的完整列表,理解每一种事件对应循环里的哪个时刻,尤其是文本增量（`ASSISTANT_DELTA`/`REASONING_DELTA`)、工具生命周期（`TOOL_PROPOSED`/`TOOL_STARTED`/`TOOL_FINISHED`)、以及各类需要人工介入的审批/提问类事件（`PERMISSION_REQUIRED`/`QUESTION_REQUESTED`/`PLAN_PROPOSED` 等)分别在什么条件下被 `yield`。
- 理解 `Event` 这个 dataclass 本身极度简单（只有 `type` 和 `data` 两个字段)背后的设计考量——契约的稳定性来自枚举值和 `data` 字段的命名约定,而不是类型系统。
- 验证（而非假设)`engine.py` 产生的事件,是怎样经过 `server/app.py` 的 WebSocket 路由和 `server/manager.py` 的 `broadcast_session()`,被转发给所有正在查看这个会话的客户端连接的。
- 用一行真实代码确认 `surfaces/gui` 端如何消费 `assistant_delta` 事件实现打字机效果,同时明确这一部分只做到"确认调用关系存在"为止,不深入 server/gui 内部实现细节。

## 背景与设计动机

一次用户输入触发的循环可能持续几秒到几分钟——期间模型在流式吐字、可能连续调用好几个工具、可能撞上需要人批准的操作、也可能触发一次压缩。如果界面只能等整个循环彻底结束才拿到结果,用户体验会是"发一条消息,然后对着空白等待",完全无法判断当前进展到哪一步、有没有卡住。`openworker` 的应对方式和大多数流式 Agent 系统一样：把循环内部的每个关键时刻都定义成一个轻量的 `Event`,通过 `AsyncIterator[Event]` 一路 `yield` 出来,再由外层的传输层（WebSocket)原样转发给每一个正在看这个会话的连接。

这里真正值得关注的设计选择不是"要不要流式"——几乎所有现代 Agent 引擎都会流式——而是这份契约被刻意做得**极简**：`Event` 只有 `type`（一个字符串枚举)和 `data`（一个自由格式的字典),没有为每种事件类型单独定义 schema class。好处是新增一种事件、或者给已有事件的 `data` 字典新增一个字段,都不需要改动 `Event` 本身的定义,消费端（GUI 的 TypeScript 类型、Slack 转发的字段读取)按约定读取即可——这是一种"契约靠命名和文档约定,而不是靠强类型"的取舍,好处是迭代成本低,代价是消费端必须自己保证按事件类型读取到正确的字段(这一点在 GUI 端通过 TypeScript 的判别联合类型弥补,但那已经是界面层的事,不在这一篇的范围)。

## 核心机制详解

### EventType：循环里每一个值得让界面知道的时刻

```python
# coworker/events.py
class EventType(str, Enum):
    TURN_START = "turn_start"
    ASSISTANT_DELTA = "assistant_delta"
    REASONING_DELTA = "reasoning_delta"  # model thinking text (display-only, never replayed)
    ASSISTANT_MESSAGE = "assistant_message"
    TOOL_PROPOSED = "tool_proposed"
    PERMISSION_REQUIRED = "permission_required"
    DIRECTORY_REQUESTED = "directory_requested"
    TOOL_REQUESTED = "tool_requested"
    QUESTION_REQUESTED = "question_requested"
    PLAN_PROPOSED = "plan_proposed"
    TEAM_PROPOSED = "team_proposed"
    ITEMS_PROPOSED = "items_proposed"
    TOOL_STARTED = "tool_started"
    TOOL_FINISHED = "tool_finished"
    ITERATION_END = "iteration_end"
    TURN_END = "turn_end"
    ERROR = "error"
    INTERRUPTED = "interrupted"
    COMPACTING = "compacting"
    COMPACTED = "compacted"


@dataclass
class Event:
    type: EventType
    data: dict[str, Any] = field(default_factory=dict)
```

对照前三篇读过的 `engine.py`,这些枚举值几乎每一个都能精确对应到 `_loop()`/`_handle_tool_calls()` 里的一行 `yield`：

- **文本增量**：`ASSISTANT_DELTA`/`REASONING_DELTA` 在 `_astream()` 每收到一个 `chunk.text_delta`/`chunk.reasoning_delta` 时就地 `yield`,这是打字机效果的数据源。`REASONING_DELTA` 的注释特别标注"display-only, never replayed"——这是模型的思考过程文本,只用来展示,绝不会被写回 `self.messages` 当作历史重新发给模型(这一点在第 03 篇读 `_outbound_messages()` 时也验证过,`reasoning` 是被剥离的 sidecar 之一)。
- **完整助手消息**：`ASSISTANT_MESSAGE` 在一次模型响应流式接收完毕、`turn` 对象拿到之后触发一次,携带这次响应的完整文本、请求的工具名列表、以及（如果有)token 用量。
- **工具生命周期**：`TOOL_PROPOSED`（模型刚提出这个调用,审批判断还没开始)→（可能有 `PERMISSION_REQUIRED` 等待人工决策)→ `TOOL_STARTED`（审批通过,开始执行)→ `TOOL_FINISHED`（执行完毕,带结果预览)。第一篇读到的 `_handle_tool_calls()` 对并发/串行两条路径都保证了这四个事件按语义顺序出现,不会因为并发执行而错乱。
- **人工介入类事件**：`PERMISSION_REQUIRED`（工具需要审批)、`DIRECTORY_REQUESTED`（`request_directory` 工具触发)、`TOOL_REQUESTED`（`request_tool` 工具触发,对应第一篇提到的 `toolchain.py` 场景——模型发现本地缺一个 CLI,请求安装)、`QUESTION_REQUESTED`（`ask_user` 工具)、`PLAN_PROPOSED`/`TEAM_PROPOSED`/`ITEMS_PROPOSED`（三种不同的审批门,分别对应 plan 模式退出、团队组建、任务分解——这三者共享"提出 → 等待人工决定"的结构,但审批语义各不相同,第 04 章会展开)。
- **循环边界**：`ITERATION_END` 在每一轮"模型响应 + 其工具结果都处理完"之后触发,`TURN_END` 在整个用户输入触发的循环彻底结束时触发（带 `status`：`completed`/`max_iterations_exceeded`),`ERROR`/`INTERRUPTED` 分别对应第 03 篇读过的"不可恢复错误"和"用户主动 Stop"两条终止路径。
- **压缩信号**：`COMPACTING`（压缩开始,可能耗时几秒的摘要调用即将发生)/`COMPACTED`（压缩完成,带一句人类可读的提示文本)——这两个正是第三篇反复出现的事件。

值得强调的是 `PERMISSION_REQUIRED` 这类事件在事件流里的位置：它出现在 `TOOL_PROPOSED` 之后、`TOOL_STARTED` 之前,是"审批"这件事在整条流水线上的挂起点——第一篇读到的 `_authorize()`/`_preconsult_reviewer()` 这些权限判断逻辑,最终都是从这个位置把控制权交还给外部（等待 `approver` 这个注入的异步回调返回决定),循环在这一步真正被挂起,直到人工（或 reviewer)给出裁决才会继续产生后续事件。审批判断本身的门槛设计——hard floor、standing rule、reviewer 自动放行——是第 04 章治理系统的主题,这一篇只需要确认它在事件流时间线上处于这个位置。

### 从 TurnEngine 到 WebSocket：manager.broadcast_session()

`engine.run()`（以及 `engine.retry()`/`engine.resume()`)是一个 `AsyncIterator[Event]`,谁来消费这个迭代器,谁就决定了事件最终怎么被转发。`coworker/server/app.py` 里处理交互式 WebSocket 连接的路由,在收到用户消息后调用它：

```python
# coworker/server/app.py（/ws/session/{session_id} 路由内，节选）
async def run_turn(content, *, retry: bool = False, display=None) -> None:
    events = engine.retry() if retry else engine.run(content, display=display)
    async for event in events:
        await manager.broadcast_session(
            session_id, {"type": event.type.value, "data": event.data}
        )
        if event.type.value in _CHECKPOINTS:  # {"turn_start", "permission_required", ...}
            manager.save(session_id, engine)
```

每个 `Event` 被原样拆成 `{"type": ..., "data": ...}` 这样的 JSON 结构,交给 `manager.broadcast_session()`。同时,`_CHECKPOINTS` 这个集合（包含 `turn_start`、`permission_required`、`directory_requested`、`plan_proposed`、`iteration_end`)决定了哪些事件类型触发一次会话落盘——注意这不是每个事件都存盘,而是只在"这一步之后如果进程被杀掉,历史必须已经是可恢复的状态"这几个关键节点才落盘,这与第二篇读到的 `ConversationStore.save()` 只追加新消息、以及 `_repair_tool_pairing()` 的自愈机制正好衔接起来——落盘节点选得越密,一次意外重启需要自愈的窗口就越小。

`broadcast_session()` 本身在 `server/manager.py` 里的实现非常朴素——一个"会话 id → 已注册的发送回调集合"的映射：

```python
# coworker/server/manager.py
def register_session_client(self, session_id: str, send_cb: Any) -> None:
    self._session_clients.setdefault(session_id, set()).add(send_cb)

async def broadcast_session(self, session_id: str, message: dict) -> None:
    """Fan a turn event out to every socket viewing this session. Best-effort: a dead
    socket is dropped, never fatal to the turn (delivery is socket-independent)."""
    for cb in list(self._session_clients.get(session_id, ())):
        try:
            await cb(message)
        except Exception:
            self.unregister_session_client(session_id, cb)
```

`register_session_client()` 在 WebSocket 连接建立时把 `ws.send_json` 注册成这个会话的一个发送回调;`broadcast_session()` 遍历当前所有注册的回调依次发送,任何一个失败（连接已断开)就静默注销,不影响循环本身的推进——注释里说得很明确："delivery is socket-independent",这意味着**推送失败绝不会反过来影响 `TurnEngine` 的执行**,循环的产出和它有没有观众是两件互不影响的事。这也是为什么同一个会话被两个客户端同时打开时,两边都能实时看到一致的事件流——它们都只是这个"发送回调集合"里的一个成员而已。同样的 `broadcast_session()` 也被 `manager.deliver_to_session()`（后台任务、self-wake、渠道订阅消息触发的非交互式轮次)复用,这说明"事件转发给界面"这条通路和"是谁触发了这一轮循环"是解耦的——不管这一轮是用户在界面上直接发的消息,还是一次定时任务在后台自己跑起来的,产生的事件都走同一条广播路径。

### GUI 端消费：assistant_delta 驱动打字机效果

不深入 `surfaces/gui` 内部实现,只用一处代码确认调用关系确实存在——`surfaces/gui/src/App.tsx` 里对 WebSocket 消息的分发：

```tsx
// surfaces/gui/src/App.tsx（节选）
case "assistant_delta":
  setStreaming((s) => s + (d.text || ""));
  break;
case "reasoning_delta":
  setReasoningStream(reasoningRef.current + (d.text || ""));
  break;
case "assistant_message": {
  if (d.usage) setUsage((u) => addTurnUsage(u, d.usage));
  ...
```

`setStreaming((s) => s + (d.text || ""))` 正是打字机效果的实现方式——每收到一个 `assistant_delta` 事件,就把它的 `text` 字段追加到当前正在展示的流式文本状态上;`assistant_message` 事件（完整消息到达)则把这段流式文本"定型"为一条正式的历史消息条目。`EventType` 枚举里的字符串值和 GUI 端 `case "assistant_delta":` 这样的字符串字面量一一对应,正是前面说的"契约靠命名约定"的具体体现——`coworker/events.py` 和 `surfaces/gui/src/types.ts` 分别用 Python 和 TypeScript 各自维护一份事件类型名称,靠字符串值保持同步,而不是共享一份跨语言的 schema 定义。这一层再往下——GUI 具体怎么渲染工具卡片、审批弹窗、压缩提示——不是这一篇要展开的内容。

## 常见问题/易踩坑

- **`_CHECKPOINTS` 只是落盘时机的优化,不是事件转发的过滤条件**——所有事件都会被 `broadcast_session()` 转发给客户端,只有其中一部分同时触发一次 `manager.save()`。不要把两者混为一谈。
- **`REASONING_DELTA`/`reasoning` 字段是纯展示用途,永远不会进入下一轮请求**——如果需要审计模型的思考过程,应该从事件流或者消息的 `_display`/`reasoning` sidecar 里读取,而不是假设它会出现在发给 provider 的 `_outbound_messages()` 里(第三篇已经确认它会被剥离)。
- **一个事件被广播和这个会话有没有活跃的 WebSocket 连接无关**——`deliver_to_session()` 这类后台触发的轮次一样会产生完整的事件流,只是当时可能没有任何客户端在监听;`broadcast_session()` 对着一个空的回调集合遍历,什么都不会发生,但循环本身照常完整执行并落盘。

## 小结

`Event`/`EventType` 是 `TurnEngine` 对外暴露的唯一契约,刻意保持成一个枚举 + 一个自由字典,把"新增事件类型"“扩展已有事件的字段"的成本降到最低。这份事件流从 `_loop()`/`_handle_tool_calls()` 内部产生,经 `server/app.py` 的 WebSocket 路由或 `server/manager.py` 的后台轮次统一送进 `broadcast_session()`,再原样转发给所有正在查看这个会话的客户端——GUI 端用一行 `setStreaming((s) => s + d.text)` 就实现了打字机效果,審批类事件（`PERMISSION_REQUIRED`/`QUESTION_REQUESTED`/`PLAN_PROPOSED`/`TEAM_PROPOSED`/`ITEMS_PROPOSED`)则是循环真正挂起、等待人工裁决的时间点。

这一章到此为止,已经把 `openworker` 的心脏——引擎循环、会话与数据模型、上下文压缩、事件流——完整拆解了一遍。但事件流里反复出现的 `PERMISSION_REQUIRED`、`TOOL_REQUESTED`、以及 `_authorize()`/reviewer/`readonly.py` 这些只被提了一句"留到下一章"的机制,才是这个项目区别于其他开源 Agent 框架最独特的部分——下一章要深入的正是 openworker 的三层治理系统：从不可逾越的硬性红线,到可以逐步升级为"标准规则"的审批阶梯,再到能自动放行常规操作、又会在拿不准时把决定权交还给人的 auto-approve reviewer。
