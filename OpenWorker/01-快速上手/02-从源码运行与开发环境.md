# 从源码运行与开发环境

> 官方下载页给用户的是一个"双击打开"的桌面应用,但"Run from source"一节把这个应用拆成了三个可以分别单独启动的进程：Python agent server、浏览器版 UI、Tauri 桌面壳。能把这三层拆开跑,本身就是对上一篇那张三层架构图的验证——而 per-launch token 在这三种启动方式下走了两条不同的实现路径（落盘 vs 内存),恰好说明了"本地优先"不是一句口号,而是渗透到每一个实现细节里的约束。

## 学习目标

- 能独立执行 README "Run from source"一节的完整步骤,理解每一步在干什么、为什么要按这个顺序。
- 看懂 `packaging/setup_dev_env.sh` 这个一次性引导脚本具体做了哪几件事,以及它和 `pyproject.toml` 里 `messaging`/`dev` 两个可选依赖组的关系。
- 理解 per-launch token 机制——`<state-dir>/sidecar-8765.token` 文件、`X-OpenWorker-Token` 请求头——以及桌面版为什么选择内存 token 而不落盘。
- 认识仓库里三条测试命令（后端 pytest、前端 vitest、端到端 playwright）分别覆盖什么。
- 知道打包脚本 `build_dmg.sh` / `build_windows.ps1` 存在的原因，以及它们和上一篇提到的"macOS 已签名、Windows 未签名"分发现状是同一件事的两面。

## 背景与设计动机

一个把"本地优先"当作核心卖点的产品,如果只提供一个打包好的桌面应用,这个卖点是没法被验证的——用户没法确认数据到底有没有离开本机,也没法确认那些"connectors"和"model provider"是不是像宣传的那样只用自己的密钥。OpenWorker 的做法是把整条运行链路开放出来：Python 后端可以脱离桌面壳单独跑,浏览器版 UI 可以连接到这个独立跑起来的后端,桌面壳本身也可以在开发模式下直接用 `tauri dev` 启动并观察它如何拉起、监督后端进程。

这条"从源码运行"的路径和上一篇下载页的"双击即用"路径面向的是完全不同的读者：一个是贡献者/研究者,想看清楚每一层到底在做什么；一个是终端用户,只想要一个能用的应用。`packaging/setup_dev_env.sh` 脚本头部的注释直接点出了这条路径服务的三种场景：

```bash
# packaging/setup_dev_env.sh
# One-time dev bootstrap for a fresh checkout: creates the Python venv every
# from-source flow expects at .venv — the browser dev flow runs its
# openworker-server directly, and the Tauri desktop shell falls back to it when
# no packaged sidecar binary is present (src-tauri/src/lib.rs, resolution step 3).
```

这句注释里"falls back to it when no packaged sidecar binary is present"值得留意——即便是运行 `npm run tauri dev` 这条"完整桌面应用"路径,Tauri 壳在找不到打包好的 sidecar 二进制时,依然会退回到用这个开发环境里的 `.venv`。这说明官方发布的桌面应用（预打包 PyInstaller sidecar）和源码开发环境（`.venv` 里的 `openworker-server`）走的是同一套代码,只是二进制的形态不同。

## 核心机制详解

### 前置条件与三步启动顺序

README "Run from source"一节给出的前置条件和步骤是：

```shell
# README.md
# Prerequisites: Python 3.10+, Node 20+, and (for the desktop shell) the Rust
# toolchain via rustup (https://rustup.rs/).

git clone https://github.com/andrewyng/openworker
cd openworker

# 1. One-time bootstrap - creates the Python venv at .venv
#    (on Windows, run from Git Bash or WSL)
bash packaging/setup_dev_env.sh

# 2. Start the local agent server
.venv/bin/openworker-server --cwd ~/some/project --port 8765
#    (Windows: .venv\Scripts\openworker-server.exe)

# 3. In a second terminal, start the UI
cd surfaces/gui
npm install
npm run dev        # browser UI on the Vite dev port
```

三步分别对应三层架构的启动顺序：先搭好 Python 环境（对应"local agent server"层的依赖）,再单独起 server 进程,最后起前端。第 2 步命令行里的 `--cwd ~/some/project` 参数决定了 agent 能访问的工作区目录——这和 `coworker/cli.py` 里 TUI 入口的 `--cwd` 参数（默认 `"."`）是同一个概念,只是这里用的是 HTTP server 入口 `openworker-server`,而不是终端 TUI 入口 `openworker`。

如果要跑完整的桌面应用而不是浏览器版 UI,README 给出的替代方式是：

> To run the full desktop app instead of the browser UI, replace step 3 with `npm run tauri dev` (from `surfaces/gui/`) - the Tauri shell launches the window and supervises the server itself.

也就是说三种运行形态——"手动分别起 server + 浏览器打开 Vite dev 页面"和"用 Tauri 壳自己拉起窗口并监督 server"——的区别只在第 3 步,前两步是共用的。`surfaces/gui/package.json` 里对应的脚本定义印证了这一点：

```json
// surfaces/gui/package.json
"scripts": {
  "dev": "vite",
  "build": "tsc && vite build",
  "preview": "vite preview",
  "test": "vitest run",
  "e2e": "playwright test",
  "e2e:ui": "playwright test --ui",
  "e2e:live": "playwright test -c playwright.live.config.ts",
  "tauri": "tauri"
}
```

`npm run tauri dev` 实际执行的是 `tauri dev`,由 Tauri CLI 接管窗口生命周期和 server 的监督职责,这也是上一篇 README 架构图里"Tauri shell that supervises the server"这句话的具体落地。

### `setup_dev_env.sh`：一次性引导做了什么

完整脚本只有几行,但每一行都对应一个明确的目的：

```bash
# packaging/setup_dev_env.sh
ROOT="$(cd "$(dirname "$0")/.." && pwd)"
VENV="$ROOT/.venv"

python3 -m venv "$VENV"
# The coworker package (server, engine, connectors) + inbound-messaging extras.
# aisuite comes in as a regular dependency (git-pinned in pyproject.toml until
# the next PyPI release).
"$VENV/bin/pip" install --quiet --upgrade pip
"$VENV/bin/pip" install --quiet -e "$ROOT[messaging,dev]"

"$VENV/bin/python" -c 'import aisuite, coworker' # fail loudly if the wiring broke
echo "Ready: $VENV"
echo "  server: $VENV/bin/openworker-server --cwd /path/to/your/project --port 8765"
```

依次拆开看：

1. 在仓库根目录下创建 `.venv` 虚拟环境——这是一个项目本地的虚拟环境,而不是像很多 CLI 工具那样落在用户 home 目录下的固定位置,这样多个从源码 checkout 的副本互不干扰。
2. 以可编辑模式（`-e`）安装 `coworker` 包,并且带上 `[messaging,dev]` 两个 extra。对照 `pyproject.toml` 里 `[project.optional-dependencies]` 的定义：

```toml
# pyproject.toml
[project.optional-dependencies]
dev = ["pytest>=8", "pytest-asyncio", "httpx"]
# Inbound messaging listeners (outbound send_message needs only httpx, already a core dep).
# aiohttp is slack-bolt's Socket Mode transport at runtime (and the FakeSlack test harness
# drives the real handler) — declare it so CI installs it, not just transitively.
messaging = ["python-telegram-bot>=21", "slack-bolt>=1.18", "aiohttp>=3.9"]
# Interactive Cowork browser automation.
browser = ["playwright>=1.44"]
# AWS Bedrock provider (lazy-imported; desktop builds bundle it, pip users opt in).
bedrock = ["boto3>=1.34"]
```

`dev` 分组是测试工具链（`pytest`、`pytest-asyncio`,以及测试里要用的 `httpx`）；`messaging` 分组是 Telegram/Slack 这类"收消息"的监听端依赖——值得注意的是主 `dependencies` 列表里已经有 `httpx` 覆盖"发消息"（`send_message` 工具）的需求,`messaging` extra 只补"收消息"这一侧需要的 `python-telegram-bot`、`slack-bolt` 和 `aiohttp`。脚本默认没有装 `browser`（Playwright 浏览器自动化）和 `bedrock`（AWS Bedrock provider）这两个 extra,这两个能力属于按需开启的可选面。

3. 最后一行 `python -c 'import aisuite, coworker'` 是一个"装完立刻自检"的动作——如果 `aisuite`（git 依赖）或者 `coworker` 包本身的依赖链有问题,这一行会在脚本执行阶段就报错退出,而不是等到用户后面敲 `openworker-server` 才发现环境是坏的。脚本注释里写的"fail loudly if the wiring broke"直接说明了这个用意。

### per-launch token：落盘还是不落盘

README 在讲完三步启动之后，专门用一段说明了鉴权 token 的机制：

> The standalone server creates a per-launch token at `<state-dir>/sidecar-8765.token`; Vite reads that user-only file when it starts. For direct API calls, send its value in the `X-OpenWorker-Token` header. The desktop app uses an in-memory launch token instead and never writes it to disk.

也就是说,同一个 `openworker-server`,在两种启动场景下对 token 的处理方式并不一样：

- **独立运行/浏览器 UI 场景**：token 会以文件形式写在 `<state-dir>/sidecar-8765.token`（文件名里带上了端口号,支持同时起多个实例）,权限限制为仅当前用户可读,浏览器端的 Vite 开发服务器在启动时读取这个文件来获得 token 值,直接调用 API 时则把这个值放进 `X-OpenWorker-Token` 请求头。
- **桌面应用场景**：token 完全在内存里生成和传递,从不写入磁盘。

这个差异不是实现上的随意选择,而是对应两种场景下"谁需要读到这个 token"的真实需求不同：浏览器版 UI 是一个独立进程,必须通过某种进程间可读的媒介（文件）拿到 token；而桌面应用里,Tauri 壳本身就是拉起 server 的那个进程,可以直接在内存里生成 token 并传给自己监督的子进程,没有必要为了传递一个鉴权凭据而把它写到磁盘上增加暴露面。这是"本地优先、能不落盘就不落盘"这条隐私原则在一个具体安全机制上的体现,和第 03 篇要讲的 Privacy 一节、以及第 04 篇治理章节的精神是一致的。

### 测试命令：三层各自的验证方式

README 给出的测试命令覆盖了三个不同的层次：

> Tests: `.venv/bin/pytest` (server), `npm test` and `npm run e2e` in `surfaces/gui` (GUI unit + hermetic end-to-end).

- `.venv/bin/pytest`——对应后端 `coworker/` 包的测试套件,位于仓库的 `tests/` 目录（README"Repository layout"表里注明"Backend test suite"）。`pyproject.toml` 里的 `[tool.pytest.ini_options]` 段落还专门处理了一个路径问题：

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
# The reviewer-eval tests import from the repo-root scripts/ package; the pytest
# console script (CI) does not put the root on sys.path the way `python -m pytest`
# does.
pythonpath = ["."]
asyncio_mode = "auto"
```

这条注释解释了为什么要手动把 `.` 加进 `pythonpath`：CI 环境里直接调用 `pytest` 这个 console script 时,并不会像 `python -m pytest` 那样自动把仓库根目录放进 `sys.path`,而部分"reviewer-eval"测试需要从仓库根目录的 `scripts/` 包里 import 内容,所以必须显式声明。`asyncio_mode = "auto"` 则说明测试套件里大量使用了异步用例,不需要每个异步测试函数单独加装饰器。

- `npm test`——对应 `surfaces/gui/package.json` 里的 `"test": "vitest run"`,是前端的单元测试。
- `npm run e2e`——对应 `"e2e": "playwright test"`,是"hermetic"（隔离、不依赖外部真实服务）的端到端测试；`package.json` 里还有一个 `e2e:live`（`playwright test -c playwright.live.config.ts`）,从命名和单独的配置文件可以看出,这是一套连接真实环境而非隔离环境的端到端测试,和默认的 `e2e` 脚本适用场景不同。

### 打包脚本：为什么不是简单的"打个包"

`packaging/` 目录下的 `build_dmg.sh` 和 `build_windows.ps1` 对应 README 里 macOS/Windows 两个下载渠道的产物构建过程。这两个脚本头部的注释交代了完整的构建链路：

```bash
# packaging/build_dmg.sh
# Build the macOS desktop app + a drag-to-install .dmg.
#
#   1. PyInstaller-bundle the server into a standalone onedir folder (no venv at runtime).
#   2. Stage it at binaries/sidecar/ for Tauri's `resources` slot (+ sign its Mach-Os).
#   3. `tauri build --bundles app` → OpenWorker.app (resources are copied in).
#   4. Wrap the .app in a compressed .dmg via hdiutil (reliable + headless; Tauri's own
#      bundle_dmg.sh uses Finder AppleScript and fails in non-interactive sessions).
```

这个链路解释了官方分发的桌面应用为什么不需要用户单独装 Python：`openworker-server` 会先被 PyInstaller 打包成一个不依赖 `.venv` 的独立可执行目录（对应 `packaging/openworker-server.spec` 里定义的 onedir 打包方式）,再作为资源文件塞进 Tauri 的 `resources` 目录,最终打进 `.app`/`.dmg`。`openworker-server.spec` 的注释里还提到了一个具体的性能取舍：

```python
# packaging/openworker-server.spec
# One-DIR bundle (exe + `_internal/` support folder) shipped via Tauri's `resources`
# slot. It used to be a onefile binary in the externalBin slot, but onefile
# self-extracts its whole archive to a temp dir on EVERY launch — 6-7s of "Starting
# coworker…" splash (measured; the actual Python import is ~0.5s).
```

也就是说,早期用 PyInstaller 的 onefile 模式打包时,每次启动都要先把整个归档解压到临时目录,实测这个解压过程要 6-7 秒,而真正的 Python 导入只需要约 0.5 秒——这是一个用实测数据驱动的打包策略调整,从 onefile 换成 onedir 直接把启动等待时间降了一个数量级。

`build_windows.ps1` 的整体思路和 `build_dmg.sh` 对称,但产物是 NSIS/MSI 安装包而不是 `.dmg`,并且脚本注释里明确写了"The result is UNSIGNED — first launch shows a SmartScreen warning",和上一篇提到的官方 Windows 下载渠道现状完全一致——本地打包出来的产物和官方分发的产物,处在同一个签名状态。

## 常见问题/易踩坑

- **`bash packaging/setup_dev_env.sh` 在 Windows 上要怎么跑**：README 特别标注"on Windows, run from Git Bash or WSL"——这是一个 bash 脚本,不能直接在 PowerShell 里执行,需要 Git Bash 或 WSL 环境。
- **跑完 `tauri dev` 却发现连的还是旧的 Python 代码**：检查 `.venv` 是否是最新的——`setup_dev_env.sh` 用的是可编辑安装（`-e`）,理论上改代码即时生效,但如果切换过分支或者新增了依赖,需要重新执行一次引导脚本。
- **直接调 HTTP API 却拿不到鉴权**：先确认拿到的是哪种 token——独立运行模式下要去 `<state-dir>/sidecar-<port>.token` 文件里读,桌面应用模式下这个 token 只存在于内存,不会有文件可读。

## 小结

这一篇把上一篇的三层架构图变成了三条可以在终端里敲出来的命令：`packaging/setup_dev_env.sh` 搭好 Python 环境,`openworker-server --cwd ... --port 8765` 单独起本地 agent server,再用 `npm run dev` 或者 `npm run tauri dev` 二选一起前端。per-launch token 落盘与否的差异,以及打包脚本对签名状态和启动性能的取舍,都是"本地优先"这条设计原则渗透到具体实现细节里的例子。下一篇《模型与 Provider 配置速览》会回到 README 的"Bring your own model"一节,看看这套跑起来的系统要接哪些模型厂商、`docs/config.example.toml` 里的 `model` 字段怎么配、以及"curated model list"这句话背后对应的是仓库里哪一段真实代码。
