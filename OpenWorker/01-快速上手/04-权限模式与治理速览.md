# 权限模式与治理速览

> README "Governed by design"一节开篇就是一句立场鲜明的话："Governance is the architecture, not a plugin"。这不是修辞——它对应着代码里一个具体的约束：`Mode` 枚举里最激进的自动化模式叫 `BYPASS_APPROVALS`,而不是"bypass-ALL-approvals",代码注释专门解释了为什么不能叫后者——因为即便在这个模式下,一部分"人类专属"的操作依然会拦下来。治理不是一个可以被更宽松模式关掉的开关,而是所有模式共享的底座。

## 学习目标

- 理解 README "Governed by design"一节描述的三层治理结构：硬底线（hard floors）、自主权阶梯（ladder of earned autonomy）、审计追踪（audit trail）。
- 看懂"Unattended runs never self-approve"这条规则在"常驻自动化"场景下的含义。
- 认识 `docs/config.example.toml` 里 `mode`、`allowed_commands`、`auto_allow` 三个字段的字面含义,以及它们各自控制的是"哪一层"权限。
- 通过 `coworker/permissions.py` 里 `Mode` 枚举的真实定义,理解 README 里"一把自主权阶梯"具体对应代码里哪几档模式,以及命名背后的一次重构（"auto"→"bypass-approvals"）说明了什么。
- 明确知道：`permissions.py`/`reviewer.py`/`risk.py`/`audit.py`/`provenance.py`/`overrides.py` 这些模块的具体实现是第 04 章要深挖的内容,这一篇只建立第一手认知。

## 背景与设计动机

上一篇讲到"选模型"这件事几乎没有什么门槛限制——填个 key 就能换。但一个真正会"动手"的 coworker,一旦开始读写文件、跑 shell 命令、连接第三方应用,风险级别就完全不是"选错模型导致回答质量差"能比的了。第 01 篇已经引用过 README 里"before anything consequential ... it checks in"这句话,这一篇要把"consequential"到底意味着什么、"checks in"具体是怎样的机制讲清楚。

OpenWorker 给出的答案不是一个简单的"总开关"（要么全自动、要么全手动）,而是一个分层结构：有一部分操作无论如何都不能被自动化掉,这是最底层的安全网；在这层安全网之上,大部分操作默认需要人批准,但"批准"这件事本身可以被沉淀成规则、被固化进配置,随着用户对系统的信任积累而逐渐减少确认的频率；无论走到哪一层,每一次工具调用都要留下"谁批准的、为什么"的记录。三层叠在一起,才是 README 说的"governance is the architecture"。

## 核心机制详解

### 三层治理：硬底线、自主权阶梯、审计追踪

README "Governed by design"一节把三层结构写得非常清楚：

```text
# README.md
Governance is the architecture, not a plugin - the agent can't grant itself new
permissions, and no prompt can talk it past a gate. Three tiers, all in this repo:

1. **Hard floors.** A set of dangerous and irreversible operations is human-only,
   always. No mode - including full auto-approve - lowers these floors; they
   always escalate to you.
2. **A ladder of earned autonomy.** Actions are approval-gated by default. One-off
   approvals can graduate into standing rules, then into config allowlists - each
   step explicit, visible, and revocable. In auto-approve mode a reviewer model
   lets routine actions through and escalates anything it isn't sure about to you;
   repeated denials trip a circuit breaker that pauses the reviewer and hands
   control back. Reviewer verdicts are judgments, not guarantees - the floors and
   the audit trail are what backstop them.
3. **An audit trail that answers "who did this, and why?"** Every tool call is
   recorded with its approval provenance - auto-approved, user-approved, or
   denied, with the reviewer's reasoning attached - and persisted with the
   conversation.
```

第一句话就定了性："the agent can't grant itself new permissions, and no prompt can talk it past a gate"——权限的授予永远来自人,agent 自己没有能力提升自己的权限,任何 prompt injection 式的话术也无法说服系统跳过一个门槛。这是三层结构共同的前提。

**第一层：hard floors（硬底线）**。一组危险且不可逆的操作被划为"人类专属",无论用户把系统调到多"自动"的模式,这些操作永远会升级给人来决定——注释里特意点名"including full auto-approve"，说明连最激进的自动化模式也不能豁免。

**第二层：a ladder of earned autonomy（一把自主权阶梯）**。这是三层里最有工程细节的一层：默认情况下动作是"approval-gated"（需要审批门槛）的；一次性的批准可以"毕业"成标准规则（standing rules）,标准规则又可以进一步"毕业"成配置层面的白名单（config allowlists）——每一步升级都是显式的、可见的、可撤销的,而不是系统悄悄替用户记住了什么。而在 auto-approve 模式下,不是完全放开,而是引入一个"reviewer model"（审查者模型）替用户先看一遍：明确没问题的常规操作直接放行,拿不准的依然升级给人；如果这个审查者连续被人否决（repeated denials）,会触发一个"熔断器"（circuit breaker）,暂停审查者、把控制权交还给人。最后一句是这一层的免责声明式总结："Reviewer verdicts are judgments, not guarantees"——审查者给出的是判断,不是保证,真正兜底的是第一层的硬底线和第三层的审计追踪。

**第三层：an audit trail（审计追踪）**。每一次工具调用都会带着它的"批准出处"（approval provenance）被记录下来——是自动批准的、用户批准的,还是被拒绝的,如果是审查者模型给出的判断,连它的推理过程（reasoning）也一并附上,并且这些记录和对话本身一起持久化保存。这一层回答的问题是"谁做了这件事、为什么这么做"，是前两层判断出错时唯一能追溯的凭据。

README 紧接着补了一句对"常驻自动化"场景格外重要的规则：

> Unattended runs never self-approve: their asks park in an inbox until a human answers.

这句话呼应第 01 篇 Use cases 里提到的"Standing automations"（晨报、周报、频道监控这类无人值守的定时任务）。一个没有人盯着的自动化任务,一旦遇到需要审批的动作,不会因为"没人在场"就自己放行,而是把这个待批准的请求放进一个"收件箱"（inbox）里,直到有人回来处理为止。这条规则和第一层"硬底线不因模式而降低"是同一种设计哲学的延伸：自动化程度的提升,永远不能变成审批被悄悄跳过的理由。

### `mode`/`allowed_commands`/`auto_allow`：配置文件里的字面含义

`docs/config.example.toml` 给出的示例把"自主权阶梯"落到了三个具体的配置字段上：

```toml
# docs/config.example.toml
mode = "interactive"         # plan | interactive | auto | custom
max_iterations = 12          # max model<->tool iterations per turn before stopping

# Commands auto-allowed without an approval prompt (prefix match).
allowed_commands = [
  "ls", "cat", "pwd", "grep", "find",
  "git status", "git diff", "git log",
  "python3", "pytest", "node", "npm",
]

# In "custom" permission mode, these tools are auto-approved (everything else still
# asks). e.g. auto-accept file edits but keep asking before running shell commands.
auto_allow = ["write_file", "replace_in_file", "apply_patch", "apply_unified_diff"]
```

字面上看,这三个字段控制的是三件不同的事：

- **`mode`**——整体的权限模式,注释给出的候选值是 `plan | interactive | auto | custom`,决定的是"默认情况下,一个动作是直接放行、直接拒绝,还是需要询问用户"这件事的基调。
- **`allowed_commands`**——一份**前缀匹配**的命令白名单（"prefix match"）,命中这份名单的 shell 命令可以不经过审批提示直接运行。示例里给的都是典型的只读/无副作用命令：`ls`、`cat`、`pwd`、`grep`、`find`,以及几个 `git status`/`git diff`/`git log` 这类查看类的 git 子命令,再加上 `python3`、`pytest`、`node`、`npm` 这类开发过程中会频繁调用的可执行文件前缀。
- **`auto_allow`**——只在 `"custom"` 权限模式下生效的**工具**白名单（不是命令,是工具名）,命中的工具会被自动批准,其余工具依然会询问。示例给的四个工具——`write_file`、`replace_in_file`、`apply_patch`、`apply_unified_diff`——都是"编辑文件"这一类动作,注释里给的例子也正是"auto-accept file edits but keep asking before running shell commands"（自动接受文件编辑,但运行 shell 命令时依然询问）,也就是让用户可以对不同风险类别的动作分别设定信任程度。

有意思的是,`coworker/config.py` 里 `Config` 类对 `allowed_commands` 默认值的处理,和示例文件呈现出来的"友好范例"形成了对比：

```python
# coworker/config.py
# Commands auto-run WITHOUT an approval prompt. There is no generally safe executable:
# nominally read-only programs can read secrets outside the workspace, expand
# environment variables, load project-controlled config/plugins, or execute helpers
# (for example `find -exec` and pytest collection). Keep the built-in list empty. A
# user may explicitly opt into command prefixes in their user-owned global config,
# accepting that authority.
DEFAULT_ALLOWED_COMMANDS: list[str] = []
```

代码里真正的内置默认值是**空列表**,而且注释直接反驳了"有些命令天生安全"这种直觉——即便是 `find` 这样看起来"只是查找文件"的命令,配上 `-exec` 参数就能执行任意程序；`pytest` 的用例收集过程本身也可能加载项目里受控的插件或配置。所以 `config.example.toml` 里那份包含 `ls`、`git status`、`pytest` 等命令的列表,是一份**示例配置**,展示用户可以怎么填,而不是系统开箱即用就信任的内容——真正决定信任边界的,永远是用户自己在全局配置里显式写下的选择。`config.py` 里还有一处细节：`allowed_commands` 分全局和工作区两个层级——工作区自己声明的命令前缀（写在 `<workspace>/.coworker/config.toml`）只有在这个工作区被用户"信任"（canonically trusted）之后才会被合并进生效的允许列表,这意味着一个仓库自己没有能力单方面替自己争取到更宽松的命令执行权限,必须先经过用户对这个工作区路径的信任确认。

### `Mode` 枚举：代码里比配置注释更精细的分档

`docs/config.example.toml` 注释里写的候选值是"plan | interactive | auto | custom"四档,而 `coworker/permissions.py` 里 `Mode` 枚举的真实定义要更细一些：

```python
# coworker/permissions.py
class Mode(str, Enum):
    DISCUSS = "discuss"  # read-only conversation: no edits, no planning workflow
    PLAN = (
        "plan"  # read-only + the planning contract (explore → propose_plan → execute)
    )
    INTERACTIVE = "interactive"  # ask for approval (default)
    # Renamed from "auto" (spec §1.5, 2026-08-12): "bypass" names the action —
    # switching a safety system off — and can't be confused with AUTO_APPROVE in a
    # picker. Deliberately NOT "bypass-ALL-approvals": Phase 1's floors (settings
    # files, out-of-root writes, `.git/hooks`) still hold in this mode, so "all"
    # would be a false promise.
    BYPASS_APPROVALS = "bypass-approvals"  # full access (minus the hard floors)
    # Interactive, but an LLM reviewer judges each would-be approval card first:
    # clear allows run without a prompt, everything else still reaches the human.
    # The reviewer can only turn "ask" into "allow", never "blocked" into "allow"
    # (spec §1.2). With no reviewer plugged into the engine this mode behaves
    # exactly like INTERACTIVE.
    AUTO_APPROVE = "auto-approve"
    CUSTOM = "custom"  # interactive + auto-allow the config's `auto_allow` tools

    @classmethod
    def _missing_(cls, value: object) -> "Mode | None":
        # Legacy spelling from configs, saved sessions, and older UIs.
        if value == "auto":
            return cls.BYPASS_APPROVALS
        return None
```

这段代码值得细读的地方有三处：

第一,`DISCUSS` 和 `PLAN` 都是只读模式（`READ_ONLY_MODES = frozenset({Mode.DISCUSS, Mode.PLAN})`）,区别只在于 `PLAN` 额外驱动一套"探索 → 提出计划 → 执行"的规划流程,而配置示例注释里的四档并没有单独提到 `discuss`。

第二,`BYPASS_APPROVALS` 的命名注释是一段非常直白的自我修正记录：这一档原本叫 `"auto"`,后来重命名为 `"bypass-approvals"`,原因是"bypass"这个词准确描述了这档模式在做的事情——关掉一层安全机制,而不会被误解成"跳过所有审批"。注释特别强调"Deliberately NOT bypass-ALL-approvals"，因为"Phase 1's floors（配置文件、workspace 之外的写入、`.git/hooks`）依然在这个模式下生效,叫`all` 会是一个不成立的承诺"。这正是本篇开头引用的那处代码证据：即便是这一档"全权限"模式,依然不能突破硬底线,和 README "no mode - including full auto-approve - lowers these floors"这句话完全对应。

第三,`_missing_` 这个类方法专门处理了向后兼容："auto"这个旧拼法——无论来自旧的配置文件、保存下来的历史会话,还是旧版本的 UI——依然会被识别,并且被映射到重命名之后的 `BYPASS_APPROVALS`。这解释了为什么 `docs/config.example.toml` 的注释里依然写着"auto"而不是"bypass-approvals"：示例文件里保留的是这个配置字段兼容的拼法,而不是内部最新的枚举命名。`coworker/cli.py` 的命令行参数则同时暴露了新旧两种写法：

```python
# coworker/cli.py
parser.add_argument(
    "--mode",
    default=cfg.mode,
    choices=["plan", "interactive", "auto", "bypass-approvals", "auto-approve"],
    help="permission mode",
)
```

`AUTO_APPROVE` 这一档,对应的正是三层结构第二层里"reviewer model"的开关——枚举注释写明"The reviewer can only turn 'ask' into 'allow', never 'blocked' into 'allow'",也就是说审查者模型的权力被严格限定：它只能把"需要询问"降级成"直接放行",绝不能把"本来就该被拦下"的动作放行,这也是为什么第一层硬底线依然凌驾于审查者之上。而 `CUSTOM` 这一档,正是 `auto_allow` 配置字段生效的地方——"interactive + auto-allow the config's `auto_allow` tools"，和上一节配置文件里的注释完全吻合。

另外 `permissions.py` 里 `Decision` 数据类的一个字段,也从代码层面印证了"硬底线不受模式影响"这件事：

```python
# coworker/permissions.py
@dataclass
class Decision:
    allowed: bool
    reason: str = ""
    needs_user: bool = False  # True → surface should prompt the user for approval
    # True → this ask is reserved for a HUMAN: the Auto-Approve reviewer must not be
    # consulted and cannot clear it. ...
    human_only: bool = False
    ...
```

`human_only` 这个布尔字段一旦为真,就意味着这个待批准的动作"连 Auto-Approve 的审查者模型都不会被咨询、也无法清除它"——只有人能处理。这是"三层治理"里第一层"hard floors"在决策层面的具体落点。

## 常见问题/易踩坑

- **以为把 `mode` 调到最"自动"的一档就等于关闭了所有审批**：不成立。`BYPASS_APPROVALS` 的命名本身就是在纠正这种误解——它只关掉了"approval-gated"这一层默认门槛，硬底线（配置文件、workspace 之外的写入、`.git/hooks` 等）依然会拦下来交给人。
- **把 `config.example.toml` 里 `allowed_commands` 的示例列表当作系统默认信任的命令**：不成立。`coworker/config.py` 里真正的内置默认值是空列表,并且专门写了"没有哪个可执行文件是天生安全的"这条注释,示例文件里的列表只是给用户参考的写法样板。
- **认为常驻自动化任务遇到审批会自动放行,因为"反正没人盯着"**：不成立。README 明确写了"Unattended runs never self-approve: their asks park in an inbox until a human answers"——无人值守恰恰是审批不能被跳过的场景,而不是相反。

## 小结

这一篇建立的是治理体系的第一手认知：三层结构——硬底线、自主权阶梯、审计追踪——共同构成"governance is the architecture, not a plugin"这句话；`mode`/`allowed_commands`/`auto_allow` 是这套阶梯在配置文件里暴露出的三个旋钮,分别控制整体基调、命令前缀白名单、和"custom"模式下的工具白名单；而 `Mode` 枚举的真实定义、`BYPASS_APPROVALS` 的命名修正、以及 `Decision.human_only` 字段,则是这三层结构在代码里落地的具体证据。至于 `permissions.py` 里更复杂的判定逻辑（命令拆分、危险参数识别、路径作用域）、`reviewer.py` 里审查者模型的评审流程、`risk.py` 里风险分类、`audit.py` 的审计记录格式、`provenance.py` 的批准溯源、以及 `overrides.py` 里例外规则的管理,都留给第 04 章逐一展开。

到这里,快速上手部分的四篇已经建立起了对 OpenWorker 的第一手直觉：桌面应用怎么下载、三层架构如何跑起来、模型怎么选、以及做事之前的审批边界划在哪里。下一章会退后一步,拆开这个仓库的 monorepo 结构——`coworker/`、`surfaces/gui/`、`stt/`、`packaging/` 几大目录各自的工程边界,以及整个 Agent 引擎和它依赖的 aisuite 库之间到底是怎样的分层关系。
