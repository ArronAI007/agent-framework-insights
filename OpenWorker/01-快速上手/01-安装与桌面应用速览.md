# 安装与桌面应用速览

> README 的 "How it works" 一节把交互流程写成了四步，但真正值得注意的是第 3 步的措辞——"Before anything consequential ... it checks in and you approve or redirect"。这不是一句客套的安全提示，而是在告诉你 OpenWorker 从第一天起就不是"能聊天的助手"，而是"会替你动手、但动手前会停下来"的 coworker。理解这一点，比记住下载链接更重要：它决定了你后面每一次和它交互时，为什么会不断看到"需要你确认"的卡片。

## 学习目标

- 弄清 OpenWorker 官方分发的两个下载渠道（macOS Apple Silicon / Windows 10/11）各自的签名与自动更新状态，知道该对哪个平台的安全提示保持警惕。
- 理解 README "How it works" 描述的四步交互模型，以及它和"提交一个 prompt、等一段文字回复"这类传统 chatbot 交互模型的本质区别。
- 看懂 README 里那张三层 ASCII 架构图——桌面壳、本地 agent server、"文件/工具/模型"三个资源面——各自对应仓库里的哪部分代码。
- 认识 README "Use cases" 一节列出的五类典型场景，理解为什么"安全类专家角色"被放在了第一批交付的位置。
- 建立一个后续章节反复会用到的心智模型："OpenWorker 不是一个程序，是一个受治理的、跨进程的系统"。

## 背景与设计动机

大多数桌面 AI 应用给自己的定位是"一个更聪明的聊天窗口"：你打字，它回复，回复里可能带一段代码或一张表格，但真正"做事"这部分——发消息、改日历、跑命令——还是要你自己动手复制粘贴。OpenWorker 的 README 从第一段就摆明了不走这条路：

> **AI that gets your everyday tasks done.** OpenWorker is an open-source AI coworker that lives on your desktop and delivers **finished work**, not just chat: your code reviewed for vulnerabilities with fixes ready to go, a polished document, a Slack reply with the numbers, a triaged inbox.

"delivers finished work, not just chat"这句话背后是一个架构选择：既然要真的替用户"动手"，系统就不能只是一个和大模型对话的前端，而必须有一层能够访问文件、执行命令、连接外部应用的运行时,并且这层运行时的每一个动作都要能被观察、被拦下、被追责。这就是为什么 OpenWorker 把自己描述成三层结构，而不是一个单体客户端——第一批交付的能力也刻意选在了"安全"这个对"行动可信"要求最高的领域：

> It ships **specialist Security coworkers** first — attackers already use AI, and defenders deserve the same leverage, governed.

"governed"这个词在 README 里反复出现，这不是巧合。一个会替你发邮件、跑 shell 命令的系统,如果没有治理机制,风险和它带来的效率提升是同一个量级的。这也是为什么本篇——课程的第一篇——就要先建立"这是一个会做事、但做事前会确认"的印象,具体的治理实现留到后面专门的章节。

## 核心机制详解

### Download：两个平台，两种信任状态

README 的 "Download" 一节给出的是两条渠道，而不是一个统一的安装包：

```text
# README.md
## Download

[**⬇ macOS (Apple Silicon)**](https://download.openworker.com/mac)
<sub>macOS 12+ · signed & notarized · auto-updates</sub>

[**⬇ Windows 10/11 (x64)**](https://download.openworker.com/windows)
<sub>builds are not yet code-signed, so SmartScreen will warn; signing is in progress</sub>
```

两条渠道的信任状态并不对称：macOS 版本要求 12 及以上,已经完成签名与公证（signed & notarized）,并且具备自动更新能力；Windows 版本目前**尚未代码签名**,这意味着首次运行时 Windows SmartScreen 会弹出警告——这不是安装包损坏或者被篡改,而是项目当前所处的真实状态,README 明确写了"signing is in progress"。这个细节值得记住,因为它会在后面"从源码打包"那一篇里再次出现：`packaging/build_windows.ps1` 生成的产物同样是未签名的,行为和官方分发的 Windows 版一致。

顶部的一句提示也值得留意：

> **Beta** - OpenWorker is in open beta: fully usable, updates itself, and we're actively polishing rough edges. [Issues](https://github.com/andrewyng/openworker/issues) welcome.

"updates itself"呼应了下载区里 macOS 的"auto-updates"标注——这是一个会持续静默升级的产品,而不是一次性安装、之后再也不变的软件包,这个特性也是后面 SECURITY.md 那一句"The app auto-updates, so fixes reach installs quickly - this is also why we don't patch older版本"的前提。

### How it works：四步交互模型

README 用四个步骤描述了一次典型的使用过程：

```text
# README.md
1. Tell OpenWorker the outcome you want - "prepare a customer brief," "untangle my
   calendar," "draft a report," "check where the release stands across Jira and GitHub."
2. It breaks the task into steps and works across your desktop, files, and
   connected apps.
3. Before anything consequential - sending a message, changing a calendar, running
   a command - it checks in and you approve or redirect.
4. You get the finished deliverable, not a to-do list.
```

把这四步拆开看,每一步都在否定一种"更简单"但更受限的设计：

- 第 1 步说的是"结果导向"的输入方式——你描述的是**想要的结果**（"a customer brief"），而不是一步步告诉它"先打开日历,再读邮件,再……"。这意味着任务分解这件事发生在 OpenWorker 内部,而不是由用户手动编排。
- 第 2 步明确了执行发生的位置——"across your desktop, files, and connected apps"。这不是在一个沙盒里模拟,而是真的触达本机文件系统和已连接的第三方应用,这也是为什么第 3 步的确认机制不是可选项。
- 第 3 步是全篇的关键约束："consequential"的动作——发消息、改日历、跑命令——在真正执行前会停下来等待用户表态,用户可以"approve or redirect"（批准或改变方向）,而不只是简单的是/否。这条规则具体怎么实现、什么算"consequential"、有没有例外,是第 04 篇《权限模式与治理速览》的内容,这里只需要记住这条规则本身。
- 第 4 步区分了"交付物"和"待办清单"——传统助手常见的输出是一份"你接下来需要做的事情列表",OpenWorker 追求的是任务本身已经被完成,用户拿到的是可以直接打开、发送、使用的成品。

### 三层架构图：桌面壳、本地 server、资源面

README 在"How it works"一节末尾,用一张 ASCII 图给出了这套交互模型背后的分层结构：

```text
# README.md
┌────────────────────────────────────────────────┐
│              OpenWorker desktop app            │  native shell + GUI
├────────────────────────────────────────────────┤
│           local agent server (Python)          │  engine · tools · connectors - built on aisuite
├───────────────┬────────────────┬───────────────┤
│  your files   │   your tools   │  your model   │  everything runs with your keys,
│  & terminal   │ 25+ connectors │  any provider │  on your machine
└───────────────┴────────────────┴───────────────┘
```

这张图三层分别对应仓库里三个实体：

1. **desktop app（native shell + GUI）**——对应 `surfaces/gui/` 目录,一个 React 前端配合 Tauri 原生壳。它是用户直接看到、点击的部分,但图里特意标注这是"native shell",提示它本身不承载 Agent 的推理和工具调用逻辑。
2. **local agent server（Python）**——对应仓库根目录的 `coworker/` 包,标注里写明了"engine · tools · connectors - built on aisuite"。这是整套系统真正的大脑：任务分解、模型调用、工具执行、审批判断都发生在这一层,并且这一层是独立于桌面壳可以单独启动运行的 Python 进程——这一点在下一篇《从源码运行与开发环境》里会直接体现为"先起 server、再起 UI"的两步启动顺序。
3. **files / tools / model 三个资源面**——分别对应本机文件与终端、25+ 个连接器（GitHub、Slack、Jira 等）、以及用户自己选择并配置密钥的模型 Provider。图右侧的注释"everything runs with your keys, on your machine"点出了这三个资源面共同的前提：无论是文件访问、工具调用还是模型请求,凭据和执行都发生在用户自己的机器上,而不是托管在 OpenWorker 的服务端。

把这张图和"Repository layout"表对照,能看得更清楚：

```text
# README.md
| Directory | What's in it |
|---|---|
| `coworker/` | Python backend - agent engine, model providers, connectors, MCP client, memory, automations |
| `surfaces/gui/` | Desktop app - React UI + Tauri shell that supervises the server |
| `stt/` | Speech-to-text sidecar (Rust) for voice input |
| `packaging/` | Installer builds (macOS DMG, Windows), auto-update manifest, dev bootstrap |
| `docs/` | Design specs and decision logs |
| `tests/` | Backend test suite |
```

值得注意的是 `surfaces/gui/` 这一行的措辞——"Tauri shell that supervises the server"。"supervises"这个动词说明桌面壳和本地 server 不是平级的两个独立程序,而是前者负责拉起、监控、在退出时清理后者。这个监督关系的具体实现（进程生命周期、per-launch token 的下发方式）会在第 02 篇讲"从源码运行"时用真实的启动命令和源码注释来验证。

### Use cases：安全先行的场景清单

README 的"Use cases"一节列出了五类场景,每一类都配了一句说明它"交付什么样的成品",而不是"能聊什么话题"：

```text
# README.md
- **Security review** - scan a codebase and its dependencies for real risk. Findings
  come from deterministic scanners (like semgrep) plus model reasoning; proposed
  fixes are re-scanned and diff-reviewed before you approve them - the fixer is
  never the only checker.
- **Cloud posture** - audit cloud configuration against common misconfiguration
  classes and draft the remediation plan.
- **Incident triage** - work a security or ops incident: gather context across your
  tools, draft the timeline, prepare the report.
- **Everyday work** - prep a customer call from your CRM and inbox, turn scattered
  notes into a shippable plan, produce documents and spreadsheets, keep your
  calendar and Slack threads handled.
- **Standing automations** - a morning brief, a weekly report, a watch over a
  channel - on a schedule, with full transcripts.
```

第一类"Security review"的描述里藏着一个值得记住的设计原则："Findings come from deterministic scanners (like semgrep) plus model reasoning ... the fixer is never the only checker"。也就是说,漏洞发现不是单纯依赖大模型的"感觉",而是先用确定性的扫描工具（如 semgrep）拿到结果,再由模型做推理和归纳；而模型自己提出的修复方案,也不会被它自己盖章通过,而是要重新过一遍扫描、做 diff 审查,才会进入用户审批环节。这是一种"检查者和修复者分离"的思路,和 README"Governed by design"一节强调的整体治理精神是一致的。

紧随其后的"Cloud posture"和"Incident triage"同样是安全/运维向的场景,直到第四类"Everyday work"才转向更通用的日常任务（CRM 客户简报、笔记整理成计划、文档表格生成、日历和 Slack 处理）,第五类"Standing automations"则是"设定好之后不需要再手动触发"的常驻自动化（晨报、周报、频道监控）,并且强调"with full transcripts"——常驻任务同样会留下完整的执行记录,而不是静默运行。README 紧接着解释了为什么安全类场景排在最前：

> Specialist coworkers arrive with the tools, working style, and check-ins for one job already set up. Security coworkers ship first.

"专家角色"在 OpenWorker 里不是一个通用 Agent 换了个开场白,而是自带了一整套针对特定工作预先配置好的工具、工作方式和确认节点（check-ins）。这个"persona/专家角色"背后的实现——`coworker/` 目录下 `personas/` 相关的清单文件——是第 08 篇《Personas 与 Teams 多智能体》要展开的内容,这里先记住"专家角色是预先装配好的,不是从零现场拼凑的"这个事实即可。

## 常见问题/易踩坑

- **Windows 下第一次打开被 SmartScreen 拦截,是不是装错了版本？**：不是。README 明确写了 Windows 分发目前"builds are not yet code-signed",signing 还在推进中,SmartScreen 弹窗是预期行为,不是安装包损坏。
- **把"describe outcome → 自动分解步骤"理解成"完全不需要确认"**：不成立。README 第 3 步已经写明"consequential"的动作一定会停下来等确认,这是贯穿整个产品的规则,不是某个模式下才有的行为——具体的分级规则见第 04 篇。
- **以为"Security coworkers ship first"意味着这是唯一能用的场景**：不成立。"Use cases"一节里"Everyday work"和"Standing automations"同样是官方列出的一等场景,只是安全类专家角色是第一批预配置完成、随版本一起交付的。

## 小结

这一篇建立的是最外层的直觉：OpenWorker 通过两个签名状态不同的下载渠道分发,交互模型是"描述结果 → 跨桌面/文件/连接应用执行 → 关键动作前确认 → 交付成品"的四步循环,底层是"桌面壳 supervise 本地 Python agent server、agent server 连接文件/工具/模型三个资源面"的三层结构,首发场景则集中在安全类专家角色上。这些都还停留在"读 README 能看懂"的层面——下一篇《从源码运行与开发环境》会把这套三层结构真正跑起来：先用 `packaging/setup_dev_env.sh` 搭好 Python 环境,再分别启动本地 agent server、浏览器版 UI,最后用 `npm run tauri dev` 把完整桌面应用跑通,同时会讲清楚 per-launch token 这个安全细节在源码运行和桌面应用两种场景下为什么走了不同的实现路径。
