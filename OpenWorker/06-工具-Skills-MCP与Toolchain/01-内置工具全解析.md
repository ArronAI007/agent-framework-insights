# 内置工具全解析

> `coworker/tools/registry.py` 开头的注释写得很直白："Schema generation is reused from aisuite (`Tools`) so we don't reimplement docstring/type-hint → JSON-schema extraction." OpenWorker 的引擎"built on aisuite"不是一句营销话术——它的工具系统压根没有自己的 `BaseTool` 基类，一个工具就是一个普通的 Python 函数，外挂两个属性：`__aisuite_tool_metadata__`（风险等级、是否需要审批）和可选的 `__coworker_schema__`（显式 JSON Schema，覆盖 aisuite 自动推导的结果）。`ToolRegistry` 本身薄得几乎没有实现——它真正做的事，是把这些裸函数收进一个 `name -> ToolSpec` 字典，然后把审批判断整个甩给上层的 `PermissionEngine`。本篇按四个功能簇过一遍 `coworker/tools/` 目录：文件与代码（files/git/search/directories）、执行（shell）、交互与流程控制（ask/plan/todo）、委派与元工具（subagent 里的 `explore`、toolreq 里的 `request_tool`）。

## 学习目标

- 读懂 `ToolRegistry`/`ToolSpec` 的最小协议，搞清楚一个工具的 JSON Schema 到底从哪来——aisuite 自动生成,还是 `__coworker_schema__` 显式覆盖,两条路径分别在什么场景启用。
- 理解"工具是函数不是类"这个选择,以及它带来的组合方式:大多数工具模块导出的是一个"工厂函数"(`file_tools(workspace)`、`shell_tools(executor)`),按会话上下文现造出闭包,而不是维护一份全局单例。
- 按四个功能簇梳理代表性工具的关键设计取舍,而不是逐个复述"是做什么的"。
- 识别出一种反复出现的模式——"schema carrier"工具:函数体本身几乎不做事,真正的执行发生在 TurnEngine 的拦截逻辑里,函数体只是一个兜底。

## 背景与设计动机

一个工具能不能被模型正确调用,取决于它的 JSON Schema 是否和真实的函数签名对得上。多数 Agent Harness 会为此发明一层协议(类、装饰器、Pydantic 模型),OpenWorker 选择了更省事的路子:直接复用 aisuite 已经实现的"从函数签名/docstring 生成 OpenAI 风格 tool schema"能力,`ToolRegistry.register()` 只在没有更好选择时才回退到这条自动路径。这个选择背后的假设是——工具系统不该是 OpenWorker 自己的地基,aisuite 才是;OpenWorker 的价值在于工具的*内容*(哪些能力、什么风控),不在于工具的*协议*。

这也解释了为什么 `coworker/tools/` 里几乎看不到类:一个工具模块的典型写法是导出一个工厂函数,接收会话相关的上下文(workspace 路径、executor、todo 列表),返回一组绑定好闭包的可调用对象。工具的"状态"(比如 shell 的持久化进程、todo 的当前列表)被闭包捕获,而不是存在工具对象的实例字段里——这样一个工具模块可以被同一个进程里多个并发会话各自实例化一份,互不干扰。

## 核心机制详解

### `ToolRegistry`/`ToolSpec`:schema 从哪里来

```python
# coworker/tools/registry.py
@dataclass
class ToolSpec:
    name: str
    schema: dict[str, Any]  # OpenAI-format function tool schema
    func: Callable[..., Any]
    metadata: Any = None  # aisuite ToolMetadata or None


class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, ToolSpec] = {}

    def register(
        self,
        func: Callable[..., Any],
        *,
        metadata: Any = None,
        schema: Optional[dict[str, Any]] = None,
    ) -> ToolSpec:
        name = getattr(func, "__name__", None)
        if not name:
            raise ValueError("Tool function must have a __name__.")
        meta = metadata or getattr(func, "__aisuite_tool_metadata__", None)
        resolved_schema = (
            schema or getattr(func, "__coworker_schema__", None) or _schema_for(func)
        )
        spec = ToolSpec(name=name, schema=resolved_schema, func=func, metadata=meta)
        self._tools[name] = spec
        return spec
```

`resolved_schema` 这一行的优先级链就是整个工具系统的核心约定:显式传入的 `schema` 参数 > 函数对象上挂的 `__coworker_schema__` 属性 > `_schema_for(func)` 现算。`_schema_for` 只是 `Tools([func]).tools(format="openai")[0]` 的包装——直接调用 aisuite 的 `Tools` 类,靠它读函数签名和 docstring 反推 JSON Schema。这条自动路径能覆盖大部分简单工具(比如 `git_log(path=None, max_count=20)` 这种平坦的关键字参数),但一旦参数形状变复杂——嵌套数组、字符串或对象的联合类型、多选一分组——自动推导就靠不住了,这时候模块会显式挂一个 `__coworker_schema__` 手写 schema。`ask.py` 和 `todo.py` 都是这么做的,后面会看到具体原因。

值得注意的是 `execute()` 这个方法:

```python
def execute(self, name: str, arguments: Optional[dict[str, Any]] = None) -> Any:
    spec = self._tools.get(name)
    if spec is None:
        raise KeyError(f"Tool not registered: {name}")
    return spec.func(**(arguments or {}))
```

没有任何权限检查。模块顶部的注释写得很清楚:"Permission checks live in the PermissionEngine and are applied by the turn engine, not here." `ToolSpec.metadata` 里的 `risk_level`/`requires_approval` 只是**声明**,真正决定一次调用能不能放行的逻辑完全在 engine 层的 `PermissionEngine`(第 04 章的话题,这里不展开)。工具本身只管把事情做完,不管自己该不该被允许做。

### 文件与代码检索簇:files / git / search / directories

`files.py` 的 `read_file` 是对 aisuite 内置 `read_file` 工具的直接替换,模块 docstring 说得很直白:"The toolkit's `read_file` returns raw text (the agent can't cite path:line without counting) and raises outright on large files." 这里的实现返回 `cat -n` 风格的编号行,并且对大文件做窗口化而不是报错:

```python
# coworker/tools/files.py(节选)
selected.append(f"{i:>6}\t{text}")
...
if end < total:
    result["note"] = (
        f"showing lines {start}-{end} of {total}; "
        f"call again with start_line={end + 1} to continue"
    )
```

`note` 字段直接把"怎么继续读"这件事写进结果里,模型不需要自己算下一次该传什么 `start_line`。另一个细节是多根感知:`file_tools(workspace, roots=...)` 接受一个可选的 `roots` 列表,读取时先检查目标路径是否落在主工作区内,不行就依次尝试每个 extra root——这是"universal scratch"设计的一部分,一个会话可能同时拥有主工作区和用户后来临时授权的目录,读文件工具得知道去哪几个地方找。

`git.py` 只提供一个工具——`git_log`——因为 `git_status`/`git_diff` 已经由 aisuite 的 git toolkit 提供了。docstring 交代了一个容易被忽略的设计决定:"no commit/push here (the prompt forbids those without explicit ask, and they'd go through run_shell anyward)"。也就是说 OpenWorker 并没有给 `git commit`/`git push` 做专门工具,这两个操作走的是通用的 `run_shell` + 高风险审批流程,而不是各自独立的、可能有自己审批粒度的工具——一致性换来的代价是模型必须把 commit 命令拼成一行 shell,而不是调用一个结构化的 `git_commit(message=...)`。

`search.py` 的 `grep` 遵循"ripgrep 优先、Python 回退"的常见模式,但有一处非常具体的踩坑记录:

```python
# coworker/tools/search.py(节选)
# Per-OS application data directories. These are not build noise: on macOS 14+ merely
# *descending* into ~/Library/Application Support (other apps' containers) trips the App
# Data TCC protection and macOS shows "would like to access data from other apps" — an
# alarming prompt the user never asked for, reachable whenever the workspace is a home
# directory.
OS_DATA_DIRS = {"Library", "AppData", "Application Data"}
```

这几个目录名被排除,不是因为它们是"构建噪音"(`node_modules`/`dist` 那种常规理由),而是因为在 macOS 14+ 上,`grep` 工具如果真的递归进 `~/Library/Application Support`,会触发 TCC(Transparency, Consent and Control)权限保护,弹出一个用户完全没有预期、也解释不清楚的系统级权限对话框。这是一个只有真实跑过桌面应用、被系统提示"吓到"过才会知道的坑——工具设计里经常藏着这类来自生产环境的教训,而不是纯理论推导。

`directories.py` 的 `request_directory` 是本篇要重点指出的第一个"schema carrier"工具:

```python
# coworker/tools/directories.py(节选)
def request_directory(
    reason: str, path: str = "", writable: bool = False, primary: bool = False
) -> dict:
    # Real handling lives in the engine (it needs the out-of-band GUI round-trip). This body
    # only runs if no requester is wired (e.g. a headless surface).
    return {"granted": False, "error": "directory requests aren't available in this surface"}
```

这个函数体几乎从不会真正执行——TurnEngine 会在检测到这次调用是 `request_directory` 时,发出一个 `DIRECTORY_REQUESTED` 事件,挂起等待用户在 GUI 里选目录,再把结果作为工具调用结果注入回去。函数体里的 `return` 语句只是"没有 requester 接入时"(比如一个纯命令行的无头会话)的安全兜底。这个模式在后面 `ask.py`/`plan.py`/`toolreq.py` 里还会反复出现。

### 执行类:shell(`run_shell` / `shell_task_output` / `shell_task_kill`)

`shell.py` 的核心是 `LocalExecutor`——一个维持长期存活的 shell 子进程(POSIX 上是 `/bin/bash`,Windows 上是 `powershell.exe -Command -` 的 REPL 模式),让 `cd`、`export`、激活的 venv 这些状态能跨多次 `run_shell` 调用保留下来,而不是每次都开一个新的 `subprocess.run`。命令执行完成的检测靠一个唯一 marker:

```python
# coworker/tools/shell.py(节选)
self._proc.stdin.write(command + "\n")
self._proc.stdin.write(self._trailer())
```

`_trailer()` 在命令后面追加一行会打印 `{marker} {exit_code} {cwd}` 的语句(POSIX 用 `printf`,Windows 用 PowerShell 的 `$?`/`$LASTEXITCODE`),`run()` 读到这行 marker 就知道命令跑完了,同时顺手拿到退出码和当前目录(目录会被写回 `self.cwd`,下次respawn 用得上)。超时处理分两步:第一次超时先尝试"打断当前命令、留住 shell"(POSIX 上找子进程发 SIGINT,给 3 秒宽限期等 marker 重新同步),第二次(或 Windows 平台,没有可靠的"只打断一条命令"原语)才 `close()` 硬杀整个 shell 进程——下一次 `run()` 会自动 respawn,会话状态自愈,只是 shell 内的变量/环境丢失。

后台任务(`run_in_background=True`)刻意不复用这个持久 shell,而是各开一个独立的、detached 的子进程:

```python
# coworker/tools/shell.py(节选)
# Background tasks (`run_shell` with `run_in_background`) get their own detached process —
# NOT the persistent shell — so a dev server can run while the session keeps working.
```

这样一个开发服务器可以挂在后台跑,同时会话继续用持久 shell 处理别的命令;后台任务的输出被一个 reader 线程持续读进 buffer,`shell_task_output` 每次只返回"自上次读取以来的新增内容"(游标式增量读取),`shell_task_kill` 显式终止。三个工具里只有 `run_shell` 标了 `risk_level="high", requires_approval=True`,另外两个是低风险——查看已有后台任务的输出或杀掉它,不需要新的审批。

一个容易被忽略的参数是 `description`:

```python
def run_shell(
    command: str,
    description: Optional[str] = None,
    ...
) -> dict:
    # `description` is not used here on purpose: it rides along in the call arguments
    # so approval prompts and the audit log can show intent, not just the raw command.
```

这个字段在函数体内部完全没被用到——它存在的唯一目的,是让审批卡片和审计日志能显示"这条命令是干什么用的"这句人话,而不只是一行晦涩的 shell 命令本身。工具的输入参数不只是给执行逻辑用的,也是给审批 UI 用的——这是理解 OpenWorker 很多工具签名设计的一把钥匙。

### 交互与流程控制簇:ask / plan / todo

`ask.py` 的 `ask_user` 是"schema carrier"模式最丰富的一个例子。模块 docstring 说它"modelled on Claude Code's own AskUserQuestion",支持单问题和分组问题两种形式——分组形式一次最多打包 `MAX_GROUPED_QUESTIONS = 4` 个问题,渲染成一个 stepper,换来一次模型往返而不是四次:

```python
# coworker/tools/ask.py(节选)
"questions": {
    "type": "array",
    "maxItems": MAX_GROUPED_QUESTIONS,
    ...
    "description": (
        f"Grouped form: up to {MAX_GROUPED_QUESTIONS} questions asked in ONE "
        "round-trip, rendered as a stepper. When set, the singular "
        "question/options fields are ignored."
    ),
},
```

选项(`options`)可以是纯字符串,也可以是带 `label`/`description`/`recommended`/`preview` 的富对象——`preview` 字段是给侧边栏展示一段等宽文本用的(代码片段、配置、ASCII 草图),一旦任意一个选项带了 `preview`,卡片就切换成双栏布局。这种"字符串或对象联合类型 + 嵌套数组"的参数形状,正是前面提到的自动 schema 推导会失效的场景,所以 `ask.py` 显式声明了完整的 `_ASK_SCHEMA`。函数体本身和 `request_directory` 一样,只是一个"没有 asker 接入时"的兜底:真正的问答发生在 TurnEngine 把这次调用变成 Inbox 里的一个待办项、挂起会话等用户在(在线会话里内联,或者在无人值守的场景里从 Inbox)作答之后。

`plan.py` 的 `propose_plan` 走的是同一套模式,对应 PLAN_PROPOSED 事件:批准会让 `PermissionEngine` 退出计划模式(同一个会话,之前探索攒下的上下文全部保留),拒绝则把用户的反馈作为结果返回,模型据此修订计划。有意思的是模块 docstring 写着"Registered only when the session starts in plan mode",但在 `coworker/agent.py` 里实际的注册条件是:

```python
# coworker/agent.py(节选)
if agent.team != "lead":
    registry.register(propose_plan_tool())
```

也就是说除了 team lead 角色,几乎每个 persona 在构建时都会拿到这个工具,不管会话一开始是不是计划模式——因为权限模式可以在会话中途切换(`agent.py` 里另一处注释说"mode can flip mid-session; the engine rejects the call outside plan mode")。真正生效的门槛在 engine 层:计划模式之外调用 `propose_plan` 会被直接拒绝。这是一处文档注释("only when...")落后于实际实现的小例子——读代码永远比读模块顶部的一句话总结更可靠。

`todo.py` 的 `todo_write` 藏着一个真实的线上事故记录:

```python
# coworker/tools/todo.py(节选)
# The parameter is `todos`, NOT `items`: a top-level argument key named "items" shadows
# minijinja's `.items()` map method in at least one hosted chat template (Together's
# GLM-5.2, 2026-07-21 — "object is not callable"), 400-ing every request that replays
# the call. Any key name that isn't a minijinja map method is safe; never rename back.
```

参数名从 `items` 改成 `todos`,原因是某个托管聊天模板在渲染工具调用历史时,会把参数名当成 Jinja 模板里的方法名去解析——`items` 恰好和 Python/映射类型的 `.items()` 方法撞名,导致 Together 平台上的 GLM-5.2 模型每次重放这次工具调用都 400。这类"参数名撞了模板引擎方法名"的坑,只有在多 provider、多模型的真实生产环境里跑过才会遇到,注释里特意加了"never rename back"防止未来的人好心地把名字改回更"直觉"的 `items`。函数体里仍然兼容旧的 `items` 参数名,保证旧的排队调用不会因为改名而失败。

### 委派与元工具簇:subagent(`explore`)与 toolreq(`request_tool`)

`coworker/tools/subagent.py` 里唯一的工具是 `explore`——一个只读的研究型子代理。它的构建函数 `build_explorer_engine` 会造一个全新的、内容更窄的 `TurnEngine`:

```python
# coworker/tools/subagent.py(节选)
replaced = {"search_files", "read_file", "read_file_lines"}
registry.register_all(
    [t for t in ai.toolkits.files(root=ws) if getattr(t, "__name__", "") not in replaced]
)
registry.register_all(file_tools(ws))
registry.register_all(ai.toolkits.git(root=ws))  # git_status, git_diff
registry.register_all(git_tools(ws))  # git_log
registry.register_all(search_tools(ws))  # grep
permissions = PermissionEngine(workspace_root=Path(ws), mode=Mode.PLAN)
```

子代理被强制钉死在 `Mode.PLAN`——`PermissionEngine` 在这个模式下硬性拒绝任何写入或 shell 调用,不管子代理自己"想"做什么。因为这个约束是模式层面的硬保证,`explore` 工具本身可以标注 `risk_level="low"`,这又反过来让"一轮里并发调用多个 `explore`"变得安全——多个只读子代理之间没有互相踩踏的风险,engine 可以把它们放进同一批并行执行。子代理的注册表里没有 `explore` 自己,杜绝了无限递归委派。这个工具是 Teams 多智能体体系(第 08 章)里"一个人委派子任务"的最小可用版本——本篇只讲它作为工具怎么触发子引擎,不展开完整的 Teams 协作模型。

`toolreq.py` 的 `request_tool` 存在的理由被写在 docstring 里,是一次具体的生产事故:

```python
# coworker/tools/toolreq.py
"""This exists because of a specific failure mode (OPE-85): with gitleaks absent, a security
review silently dropped its git-history secret scan — the check didn't fail, it vanished
from the report. A missing tool must become a visible decision, never an invisible gap.
"""
```

`gitleaks` 缺失时,一次安全审查曾经悄悄跳过了它的 git 历史密钥扫描——不是报错,是从报告里"消失"了。这个工具把"缺一个 CLI"变成一个必须被看见的决策点。函数签名里明确限定了它只服务于一个很窄的"已固定版本、已做校验和验证"的目录:

```python
def request_tool(name: str, reason: str) -> dict:
    """Ask the user to install one of the PINNED catalog tools you need but can't find
    on this machine. The catalog is a small closed set — currently `gitleaks`,
    `trivy`, `osv-scanner`...
    For ANY other missing CLI (semgrep, jq, kubectl, …) do NOT use this tool: install
    it yourself with the shell (brew/pip/…)
    """
```

`gitleaks`/`trivy`/`osv-scanner` 这三个名字不是随口写的例子——它们正是下一章要讲的 `coworker/toolchain.py` 里 `MANAGED` 字典的三个键。`request_tool` 是模型侧的入口,`toolchain.py` 是背后真正下载、校验、落盘这些二进制文件的实现;这两个模块通过"同一组工具名字"隐式耦合在一起,理解了 `request_tool` 的边界("只认这三个名字,别的都走 shell 自己装"),再看 `toolchain.py` 的 `MANAGED` 注册表就会有一种"原来在这里对上了"的感觉。

## 常见问题/易踩坑

**Q:为什么 `request_directory`/`ask_user`/`propose_plan`/`request_tool` 这几个工具的函数体看起来什么正经事都没做,只是返回一个 error dict?**

因为它们是"schema carrier"工具:注册进 `ToolRegistry` 的目的主要是提供一份 JSON Schema 让模型知道这个工具存在、参数长什么样,真正的执行逻辑在 TurnEngine 里被拦截——一次这类调用会触发一个事件(`DIRECTORY_REQUESTED`/`PLAN_PROPOSED`/`TOOL_REQUESTED`,或是 Inbox 问答),挂起等待某个"requester/approver/asker"完成一次域外(out-of-band)的用户交互,再把结果塞回工具调用结果里。函数体本身的返回值只在没有对应 requester 接入的场景下(比如一个纯无头的自动化 surface)才会真正被返回给模型。四个模块在注释里几乎用一模一样的措辞描述这一点,是一处刻意保持的一致约定。

**Q:`git.py` 为什么没有 `git_commit`/`git_push` 工具?**

这是一处明确的设计取舍:commit/push 走 `run_shell` + 高风险审批流程,而不是各自独立的工具。好处是所有会改变仓库状态的操作共享同一套审批体验(高风险、需要确认),不会因为"提交"和"运行任意命令"分属两套不同粒度的审批规则而产生认知落差;代价是模型必须把 git 命令自己拼成一行 shell 字符串,而不是调用一个带类型参数的 `git_commit(message=...)`。

## 小结

OpenWorker 的内置工具集没有自己的工具协议——`ToolRegistry` 直接复用 aisuite 的 schema 生成器,工具本身是普通函数加两个约定俗成的属性。四个功能簇里最值得记住的不是每个工具具体做什么,而是两种反复出现的模式:一是"schema carrier"——真正的执行发生在 engine 的域外拦截里,函数体只是无头场景的兜底;二是"工厂函数"——工具模块导出的是按会话上下文现造闭包的构建函数,而不是维护全局状态的类实例。这批工具本身管的是"怎么做事",完全不管"能不能做"——风险等级和审批只是挂在函数对象上的元数据,真正的判断权在权限引擎手里。但工具列表本身还不是全部能力面:`skill_tool` 式的按需加载能力藏在另一套机制里——下一篇深入 `coworker/skills/`,看 SKILL.md 格式的技能是怎么被发现、解析,又是怎样和 persona 绑定在一起的。
