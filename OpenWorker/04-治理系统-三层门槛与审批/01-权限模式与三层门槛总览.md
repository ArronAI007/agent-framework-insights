# 权限模式与三层门槛总览

> README "Governed by design" 一节只有四段话,却是整个仓库里分量最重、被反复引用的一段纲领:"治理是架构本身,不是一个插件——agent 不能自己给自己授权,任何 prompt 都无法说服它绕过一道门槛"。紧接着列出三层:①一组危险且不可逆的操作永远只能由人类批准,不管处于什么模式;②一条"自主权阶梯",一次性批准可以升级成常驻规则、再升级成配置里的白名单,每一步都显式、可见、可撤销,auto-approve 模式下还有一个 reviewer 模型帮着放行常规操作、把拿不准的升级给人;③一条能回答"谁做的、为什么"的审计轨迹。本篇是本章的地基,目标是把这三层落到 `coworker/permissions.py` 里 687 行代码构成的真实决策引擎上,建立起后面四篇文章都要用到的心智模型。

## 学习目标

- 逐句对照 README"Governed by design"整节与 `permissions.py` 的实现,建立"三层治理"分别对应哪些代码结构的心智模型。
- 理解 `Mode` 枚举的六个取值(`discuss`/`plan`/`interactive`/`bypass-approvals`/`auto-approve`/`custom`)分别代表什么行为差异,以及它们和历史上的 `auto` 拼写之间的兼容关系。
- 理解 `docs/config.example.toml` 里 `allowed_commands` 与 `auto_allow` 两个字段各自被哪个模式消费、如何从配置文件流入 `PermissionEngine`。
- 理解"仓库自己声明的命令白名单"与"用户全局配置的命令白名单"是两条不同强度的信任链路,前者需要 `workspace_trust.py` 显式信任才生效。

## 背景与设计动机

多数 agent 框架的"安全设计"止步于一句"危险操作会弹窗确认"。OpenWorker 的治理系统之所以值得单独用一整章来讲,是因为它把这句话拆成了三个层次分明、优先级不同、互相独立生效的机制,并且这三层不是文档层面的口号,而是能在 `coworker/permissions.py` 里逐行对应上的真实代码路径。`permissions.py` 顶部的模块 docstring 写得很直接:

```python
# coworker/permissions.py:1-7
"""Permission engine — decides allow / deny / ask-user for each proposed tool call.

Modes: Plan (read-only) · Interactive (auto reads, ask on writes/commands) · Auto
(allow, still path-scoped). Refined by argument patterns (path-under-root, command
prefixes) and a session allowlist. The engine only *decides*; the turn engine routes
`needs_user` decisions to a surface for approval and records the outcome.
"""
```

这句话本身就划清了一条关键边界:`PermissionEngine` 只负责"决策"——allow / deny / ask-user 三选一——把决策路由到人类审批界面、以及把结果记下来审计,是调用方(`coworker/engine.py` 里的 `TurnEngine`)的责任。这个分工在后面几篇会反复出现:风险分类在 `risk.py`,决策链在 `permissions.py`,审批路由和结果记录在 `engine.py` + `audit.py`。本篇先只建立"决策"这一层的完整地图。

## 核心机制详解

### 三层治理各自落在哪段代码上

把 README 的三句话和仓库结构对照,能得到一张清晰的对应表:

| README 里的措辞 | 对应的代码 |
|---|---|
| ① Hard floors——一组操作永远人类批准,任何模式都无法降低 | `permissions.py` 里的 `protected_paths()` / `_touches_protected()` 自我保护红线、`PERSISTENT_AUTHORITY_TOOLS` 常驻授权红线、`_PROTECTED_IN_PROJECT` 项目内延迟执行文件红线(下一篇详细展开) |
| ② 自主权阶梯——一次性批准 → 常驻规则 → 配置白名单,auto-approve 模式下有 reviewer 顶住中间地带 | `session_allow_tools` / `session_allow_commands`(会话级)→ `overrides.py` 的 `RiskOverrideStore.set_trust`(跨会话持久信任规则)→ `config.toml` 的 `allowed_commands` / `auto_allow`(配置白名单);reviewer 部分在 `coworker/reviewer.py` + `engine.py` 的熔断逻辑(第 3 篇详细展开) |
| ③ 审计轨迹——谁做的、为什么 | `coworker/audit.py` 的 `AuditStore` + `engine.py` 里的 `_approval_origins` / `_audit()` 调用(第 4 篇详细展开) |

本篇聚焦第一列里 `permissions.py` 本身,尤其是它的入口——`Mode` 枚举和 `PermissionEngine` 的构造方式。

### `Mode` 枚举:六个取值,不是六级权限

`permissions.py` 定义的模式并不是一条简单的"权限从低到高"的线性刻度,而是几种性质不同的运行姿态:

```python
# coworker/permissions.py:213-236
class Mode(str, Enum):
    DISCUSS = "discuss"  # read-only conversation: no edits, no planning workflow
    PLAN = (
        "plan"  # read-only + the planning contract (explore → propose_plan → execute)
    )
    INTERACTIVE = "interactive"  # ask for approval (default)
    # Renamed from "auto" (spec §1.5, 2026-08-12): "bypass" names the action — switching a
    # safety system off — and can't be confused with AUTO_APPROVE in a picker. Deliberately
    # NOT "bypass-ALL-approvals": Phase 1's floors (settings files, out-of-root writes,
    # `.git/hooks`) still hold in this mode, so "all" would be a false promise.
    BYPASS_APPROVALS = "bypass-approvals"  # full access (minus the hard floors)
    # Interactive, but an LLM reviewer judges each would-be approval card first: clear
    # allows run without a prompt, everything else still reaches the human. The reviewer
    # can only turn "ask" into "allow", never "blocked" into "allow" (spec §1.2). With no
    # reviewer plugged into the engine this mode behaves exactly like INTERACTIVE.
    AUTO_APPROVE = "auto-approve"
    CUSTOM = "custom"  # interactive + auto-allow the config's `auto_allow` tools

    @classmethod
    def _missing_(cls, value: object) -> "Mode | None":
        # Legacy spelling from configs, saved sessions, and older UIs.
        if value == "auto":
            return cls.BYPASS_APPROVALS
        return None
```

几个值得注意的细节:

- **`DISCUSS` 与 `PLAN` 共享同一道只读闸门**,两者的差别只在"意图",不在权限——`PLAN` 额外驱动 agent 走 `propose_plan` 审批流程,但两者在 `READ_ONLY_MODES = frozenset({Mode.DISCUSS, Mode.PLAN})`(`permissions.py:241`)里被同等对待:任何有副作用的调用一律拒绝。
- **`BYPASS_APPROVALS` 特意不叫"bypass-all-approvals"**——注释直接写明这是刻意的克制:哪怕在这个"全权模式"下,第一层的硬性红线(自我保护文件、越界写、`.git/hooks` 这类项目内延迟执行文件)依然生效。"all" 会是一句假承诺,所以命名上就先把这条界线画出来了。
- **`AUTO_APPROVE` 在没有接入 reviewer 时,行为与 `INTERACTIVE` 完全一致**——这是一条重要的降级契约:reviewer 是可插拔的,一旦它缺失或者被禁用,`AUTO_APPROVE` 不会静默地变成"什么都放行",而是原样退回到"一切需要人工确认"的保守状态。
- **`_missing_` 钩子把旧配置里的字符串 `"auto"` 重新映射到 `BYPASS_APPROVALS`**——这是 2026-08-12 那次改名(`spec §1.5`)留下的兼容层:旧的 config.yaml、已保存的会话、旧版 UI 里可能还写着 `"auto"`,枚举构造时会把它当成合法值处理,而不是抛异常。

配合 `MODE_LABELS` 这张人类可读的映射表(`permissions.py:203-210`),UI 上呈现给用户的名字和内部枚举值是两套体系,例如 `bypass-approvals` 对用户展示为"Bypass approvals",`auto-approve` 展示为"Auto-approve"——这也解释了为什么这一节要先把六个取值和它们的历史沿革讲清楚,后面几篇讨论决策链时不会再纠结命名。

### `AUTO_APPROVE_NOTICE`:模式本身自带一份免责声明

`permissions.py` 里还有一段容易被忽略但很能体现治理姿态的常量:

```python
# coworker/permissions.py:191-200
# The transcript's full Auto-Approve explainer (owner copy 2026-08-24). Persisted as a
# `mode_notice` message the FIRST time a session enters Auto-Approve — server-authored so
# it appears exactly once, in place, and survives reloads (the old client-side banner
# re-announced on every restart).
AUTO_APPROVE_NOTICE = (
    "Auto-approve uses a model to let routine actions through without asking; anything "
    "it isn't sure about still comes to you. It cuts interruptions but still carries "
    "some risk i.e. a command it allows still reaches anything you can. These are model "
    "judgments, and not guarantees."
)
```

这段文案和 README 里"Reviewer verdicts are judgments, not guarantees"是同一句话的两个措辞版本,而且被设计成**服务端写入会话记录一次**,而不是客户端每次启动都弹一遍——这本身也是"审计轨迹"思路的延伸:告知用户风险这件事本身也要留痕,而不是变成一条随时可能被划走、下次重新出现的临时通知。

### `allowed_commands` 与 `auto_allow`:两个字段,两条不同的消费路径

`docs/config.example.toml` 里能看到治理系统对外暴露的两个核心配置项:

```toml
# docs/config.example.toml:11-20
# Commands auto-allowed without an approval prompt (prefix match).
allowed_commands = [
  "ls", "cat", "pwd", "grep", "find",
  "git status", "git diff", "git log",
  "python3", "pytest", "node", "npm",
]

# In "custom" permission mode, these tools are auto-approved (everything else still
# asks). e.g. auto-accept file edits but keep asking before running shell commands.
auto_allow = ["write_file", "replace_in_file", "apply_patch", "apply_unified_diff"]
```

这两个字段在 `PermissionEngine` 里走的是完全不同的路径:

- **`allowed_commands`** 面向的是 `run_shell` 这一类命令,消费方是 `PermissionEngine._command_allowed()`——它对每一条(可能是复合)命令做前缀匹配,任何模式下都可能命中(下一篇会详细拆解它的安全边界:为什么是"前缀匹配"而不是简单的字符串包含)。
- **`auto_allow`** 面向的是具体的工具名,只在 `Mode.CUSTOM` 下生效:

```python
# coworker/permissions.py:513-515
# Custom mode auto-approves the configured tools.
if self.mode is Mode.CUSTOM and tool_name in self.auto_allow_tools:
    return Decision(True, "auto-allowed by config")
```

也就是说,`custom` 模式的定位是"interactive 模式 + 一份用户手工挑选的工具自动放行清单",而 `allowed_commands` 这条命令白名单则是所有非只读模式共享的基础设施——它甚至不区分 `interactive` 还是 `custom`,只要命令匹配上前缀规则就会跳过审批卡。这是理解"custom 模式到底 custom 在哪"的关键:它 custom 的是"工具级别"的自动放行,而不是命令级别的白名单本身。

两个字段在 `coworker/agent.py` 构建 `PermissionEngine` 时被分别灌入:

```python
# coworker/agent.py:443-456(节选)
permissions = PermissionEngine(
    workspace_root=ws or (root_list[0].path if root_list else Path.cwd()),
    mode=mode,
    # `[]` is an explicit deny-by-default override, not a request to fall back to config.
    allowed_commands=(
        allowed_commands if allowed_commands is not None else config.allowed_commands
    ),
    auto_allow_tools=set(config.auto_allow),
    allowed_domains=list(config.allowed_domains),
    roots=root_list or None,
    risk_overrides=override_store.resolver(),
    trust_overrides=override_store.trusted,
    grant_trust=override_store.set_trust,
)
```

注意注释里特别澄清的一点:调用方显式传入空列表 `[]` 代表"明确拒绝一切自动放行的命令",而不是"没传值、请回退到配置文件"——这个区分在权限相关代码里反复出现,是一种"宁可保守也不要静默放宽"的写法习惯。

### 仓库能不能自己声明白名单?workspace_trust 的把关

一个容易被忽略但很重要的问题是:如果一个仓库自带 `.coworker/config.toml`,它能不能直接给 agent 声明一份 `allowed_commands`,让克隆下来的每个人都自动获得这份权限?`coworker/config.py` 的答案是明确的"不能,除非你显式信任这个仓库":

```python
# coworker/config.py:100-108(节选)
# only (a repo must not be able to widen the agent's command or network reach).
_GLOBAL_ONLY_FIELDS = {
    "allowed_commands",
    "auto_allow",
    "allowed_domains",
    "auto_approve",
    "auto_approve_shadow",
}
_WORKSPACE_FIELDS = _FIELDS - _GLOBAL_ONLY_FIELDS
```

`allowed_commands`、`auto_allow`、`allowed_domains`、`auto_approve`、`auto_approve_shadow` 这五个字段被划进"只能来自全局配置"的集合——一个仓库自己的 `.coworker/config.toml` 写了这些字段,`load_config()` 会直接忽略它们。但仓库确实可以**声明**一份"建议的"命令白名单,只是它默认只是摆设:

```python
# coworker/config.py:123-129
def workspace_allowed_commands(workspace: str | Path) -> list[str]:
    """Command prefixes requested by repository config; advisory until workspace trust."""
    path = Path(workspace).expanduser() / ".coworker" / "config.toml"
    value = _read(path).get("allowed_commands", [])
    if not isinstance(value, list):
        return []
    return list(dict.fromkeys(v.strip() for v in value if isinstance(v, str) and v.strip()))
```

这份"仓库自己声明的白名单"只有在 `workspace_trusted=True` 时才会被并入生效配置:

```python
# coworker/config.py:145-156(节选)
if workspace:
    w = Path(workspace).expanduser() / ".coworker" / "config.toml"
    if w.is_file():
        for key, value in _read(w).items():
            if key in _WORKSPACE_FIELDS:
                setattr(cfg, key, value)
        if workspace_trusted:
            cfg.allowed_commands = list(
                dict.fromkeys(
                    [*cfg.allowed_commands, *workspace_allowed_commands(workspace)]
                )
            )
```

而 `workspace_trusted` 这个布尔值来自 `coworker/workspace_trust.py` 的 `WorkspaceTrustStore`,在 `coworker/agent.py` 里这样接入:

```python
# coworker/agent.py:265-266
workspace_trusted = bool(ws and WorkspaceTrustStore().is_trusted(ws))
config = load_config(ws, workspace_trusted=workspace_trusted)
```

`WorkspaceTrustStore` 本身很朴素——一个按"规范化绝对路径"存储的信任集合,写入时用临时文件 + `os.replace` 做原子替换,并显式 `os.chmod(tmp, 0o600)` 收紧权限(`workspace_trust.py:54-61`)。它的模块 docstring 把这条设计原则讲得很清楚:

```python
# coworker/workspace_trust.py:1-7
"""User-owned trust decisions for repository-provided command allowances.

A repository may declare command prefixes in `.coworker/config.toml`, but those grants
take effect only after the user trusts that exact canonical workspace root. Trust follows
the path rather than a snapshot of the config: future changes at a trusted path are
accepted until the user revokes trust.
"""
```

这段话里"trust follows the path rather than a snapshot of the config"是一个值得留意的权衡:信任一旦给出,针对同一个规范化路径,未来对 `.coworker/config.toml` 的任何修改都会自动生效,而不需要用户对每一次改动重新确认。换句话说,这不是"审查过这份配置的内容"式的信任,而是"信任这个目录本身"式的信任——粒度更粗,但换来的是不必在每次拉取上游更新后都重新点一次确认。这也是为什么"克隆一个陌生仓库"和"信任一个仓库能自己扩大 agent 权限"在 OpenWorker 里是两个独立的动作:前者只是把代码拉到本地,后者需要用户对着具体路径明确点一次"我信任它"。

## 小结与下一篇

本篇建立的心智模型是:治理系统不是单一的一道审批弹窗,而是①贯穿所有模式的硬性红线、②从会话级到配置级层层升级的自主权阶梯、③记录一切决策的审计轨迹这三层叠加的结果;`Mode` 枚举的六个取值对应的是不同的"运行姿态"而非线性权限级别;`allowed_commands`/`auto_allow` 两个配置字段分别服务命令级和工具级两条不同的自动放行路径,而"仓库自己声明的白名单"必须先经过 `workspace_trust.py` 的显式信任才会生效——这是治理系统里"谁能扩大 agent 权限"这个问题在配置层面的答案。下一篇会深入 `PermissionEngine.evaluate()` 的完整决策链,搞清楚一次工具调用从"模型发起请求"到"被判定为允许/需要审批/直接拒绝",中间究竟经过了哪些检查点,以及"任何模式都无法降低"的硬性红线在代码里到底是怎样一种优先级安排。
