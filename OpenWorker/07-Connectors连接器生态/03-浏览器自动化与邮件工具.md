# 浏览器自动化与邮件工具

> 前两篇看的连接器都有一个共同前提——对方服务愿意开放一个 API。但现实世界里大多数网站不提供 API：内部报销系统、没有公开接口的供应商门户、只能在网页上填的表单。`browser_automation.py` 用 Playwright 顶上这块空白，把"点一下、填一下、截个图"包装成模型可调用的工具。`email_tools.py` 走的是另一个极端——不是"没有 API"，而是"协议古老到几乎不需要 API"：IMAP/SMTP 从上世纪就存在，标准库自带客户端，不需要任何厂商特定的 SDK。这篇文章把这两个文件读透，再顺带看一眼 `attribution.py`——同一个 Slack bot 账号被多个人共用时，回复消息上那个 `[某某]` 前缀是怎么来的。

## 学习目标

- 理解 `browser_automation.py` 为什么用同步的 Playwright API 包一层单线程 `ThreadPoolExecutor`，而不是直接用 Playwright 的异步接口。
- 理解浏览器工具集里"读页面"和"看截图"是两种不同的信息获取方式，以及 `_SNAPSHOT_JS` 如何把页面可交互控件抽取成模型能引用的"选择器提示"而不需要模型自己拼 CSS 选择器。
- 理解 `redirect_refusal()` 解决的具体安全问题——地址守卫只能检查模型提供的原始 URL，页面重定向之后落地的地址需要二次核查。
- 理解 `email_tools.py` 为什么坚持"只读不改"（不提供删除/移动/标记已读工具）以及"单次发送不留副本"这两条克制的设计。
- 理解 `attribution.py` 里 `sender_prefix()` 解决的问题——它是"给人看的署名"，和第 04 章的审批溯源是两回事。

## 背景与设计动机

`descriptors.py` 里的浏览器连接器描述符写得很直白：

```python
# coworker/connectors/descriptors.py:593-607（节选）
ConnectorDescriptor(
    name="browser",
    title="Browser",
    icon="⌕",
    blurb="Let agents navigate, read, and act on websites with approval.",
    auth="none",
    two_way=False,
    fields=[],
    instructions=["No setup required. Browser tools are available to Cowork sessions."],
    available=True,
),
```

`auth="none"`、没有任何字段——浏览器连接器不需要"连接"这个动作,因为它操作的不是某个特定服务的账号,而是一整个浏览器会话本身。这是这套连接器框架里唯一一个"零配置但能力上限最高"的连接器:它不受限于任何单个 SaaS 服务的 API 设计,能做的事情等同于人类在浏览器里能做的事情——也正因为如此,它的每一步操作默认都要审批。

Email 走的是反方向的极端。它既不是"没有 API",也不需要复杂的 OAuth,IMAP/SMTP 是几十年历史的开放协议,Python 标准库自带 `imaplib`/`smtplib`/`email` 客户端,不需要拉任何第三方 SDK。它的克制来自另一个方向——协议本身允许的操作(删除、移动、标记已读)如果暴露给模型,任何一次误判都可能悄悄改变用户真实的邮箱状态,而这种改变很难在事后被注意到。

## 核心机制详解

### `_BrowserController`：单线程 executor 包住 Playwright 的同步 API

`browser_automation.py` 选择了 Playwright 的 `sync_api` 而不是异步 API，但整个连接器工具集本身跑在 aisuite 的异步引擎里。解法是把所有浏览器操作丢进一个只有一个 worker 的线程池，序列化执行：

```python
# coworker/connectors/browser_automation.py:64-74（节选）
class _BrowserController:
    def __init__(self) -> None:
        self._lock = threading.RLock()
        self._playwright = None
        self._browser = None
        self._context = None
        self._page = None
        self._error: Optional[str] = None
        self._executor = ThreadPoolExecutor(
            max_workers=1, thread_name_prefix="coworker-browser"
        )
```

`_submit()` 把每个动作提交给这唯一的 worker 线程执行并同步等待结果：

```python
# coworker/connectors/browser_automation.py:140-141, 200-222（节选）
def _submit(self, fn: Callable[[], dict[str, Any]]) -> dict[str, Any]:
    return self._executor.submit(fn).result()

def call(self, action: str, fn: Callable[[Any], dict[str, Any]]) -> dict[str, Any]:
    def run() -> dict[str, Any]:
        with self._lock:
            page, err = self.page()
            if err:
                return err
            self._touch(last_action=action, last_result="running", last_error="")
            try:
                out = fn(page)
            except Exception as exc:
                out = {"error": str(exc)}
            ...
            return out
    return self._submit(run)
```

`max_workers=1` 这个限制是有意的：Playwright 的一个 `Page` 对象天生不是线程安全的，同一时刻只能有一个操作在跑；用单 worker 的线程池而不是加锁保护并发调用，等于把"这个浏览器会话是单线程独占资源"这条约束写死在结构里，而不是靠调用方自觉。`_state` 字典（`open`/`url`/`title`/`last_action`/`last_error`/`screenshot_data_url`……）在每次动作后更新，供 GUI 实时展示"浏览器现在停在哪一页、上一步做了什么"。

### 读页面 vs 看截图：两种不同的信息获取方式

工具集里 `browser_read_page` 和 `browser_screenshot` 是两条并行的路径,分别面向"文本推理"和"视觉核实"。`browser_read_page` 靠注入一段 JS(`_SNAPSHOT_JS`)提取页面正文和所有可交互控件:

```python
# coworker/connectors/browser_automation.py:288-305（节选，_SNAPSHOT_JS 内嵌函数）
const describe = (el, i) => ({
  index: i,
  tag: el.tagName.toLowerCase(),
  type: el.getAttribute('type') || '',
  id: el.getAttribute('id') || '',
  name: el.getAttribute('name') || '',
  role: el.getAttribute('role') || '',
  aria: el.getAttribute('aria-label') || '',
  label: labelFor(el),
  placeholder: el.getAttribute('placeholder') || '',
  text: (el.innerText || el.value || '').trim().slice(0, 200),
  href: el.getAttribute('href') || '',
  selectorHint: el.getAttribute('id') ? `#${CSS.escape(el.getAttribute('id'))}` : (...)
});
```

每个可见控件都带着一个 `selectorHint`——模型不需要自己去猜"这个按钮的 CSS 选择器是什么"，读一次页面之后，后续的 `browser_click`/`browser_type` 可以直接把这个提示当作 `target` 参数传回来。`_target_locator()` 支持三种目标语法：`text=` 前缀按文本找、`role=` 前缀按 ARIA role + 名称找、以及兜底的原始 CSS 选择器，找不到时再退化成按文本模糊匹配——这一层容错是因为模型给出的目标描述不总是精确的 CSS 选择器。

`browser_screenshot`/`browser_take_screenshot` 走完全不同的路径——直接截图，不做任何结构化提取，用于模型需要"眼见为实"确认页面渲染效果（比如核实一个表单是不是真的填对了）而不是提取文本内容的场景。两者被设计成互补而不是互相替代的工具，文档字符串专门说明了这一点：`browser_read_page` 的 docstring 写着"Not an image — use browser_screenshot for pixels."

### 安全边界：地址守卫 + 重定向二次校验

浏览器工具复用了和 `web_fetch` 一样的地址守卫（`check_url`），但 `browser_open_url` 面对一个 `web_fetch` 不会遇到的问题——Playwright 会真的执行浏览器里的重定向跳转，而地址守卫只检查了模型最初提供的那个 URL：

```python
# coworker/connectors/browser_automation.py:329-343
def redirect_refusal(requested: str, final: str) -> Optional[str]:
    """A refusal reason if navigation LANDED somewhere the address guard would refuse.

    `check_url` vets the URL the model supplied; Playwright then follows redirects, and the
    hop that actually loads is a different address the guard never saw (OPE-124). A public
    shortener can land on the cloud metadata endpoint or a router admin page, and the
    approval the user gave was for the first URL, not this one.

    The request has already gone out by the time this runs — it cannot be prevented here.
    What it prevents is the agent READING the page or interacting with it. Later
    JavaScript- or meta-refresh-driven navigation is still unchecked; only a proxy that
    vets every hop closes that, which is the larger design this defers."""
    if not final or final == requested:
        return None
    return check_url(final)
```

一个公开的短链接服务，表面上是一个无害的域名，重定向之后完全可能落在云厂商的元数据端点或者内网路由器管理页——用户当初批准的是"打开这个短链接"，不是"打开元数据端点"。`browser_open_url` 在导航结束后会拿最终落地的 `page.url` 再走一次守卫检查，命中就把页面导回空白页、拒绝返回内容：

```python
# coworker/connectors/browser_automation.py:392-401（节选）
def _open(page):
    page.goto(url, wait_until=wait_until, timeout=30000)
    landed = redirect_refusal(url, page.url)
    if landed:
        # Leave nothing readable behind: the next snapshot/get_text must not be
        # able to lift content off a page we just refused.
        final = page.url
        page.goto("about:blank")
        return {"error": f"redirected to {final} — {landed}"}
    return {"ok": True, "url": page.url}
```

docstring 里那句"The request has already gone out by the time this runs — it cannot be prevented here"很诚实：网络请求已经发出去了，这层校验挡不住"访问过"这件事本身，它挡住的是"访问之后还能读到内容、还能继续交互"。至于页面加载完之后靠 JavaScript 或 meta-refresh 触发的二次跳转，这层校验完全看不到——文档里明确承认这是一个更大的设计问题（需要一个能审视每一跳的代理层），这里只是把能做的第一道防线做扎实。

另一处容易被忽略的权限细节是文件上传/截图落盘路径的校验。`browser_upload_file`/`browser_screenshot` 表面上是浏览器操作，但本质上分别读取和写入本地文件系统——如果不加约束，模型完全可能诱导它去读 `~/.ssh/id_rsa` 上传到一个网页表单里。这两个工具没有走系统统一的"写本地文件"权限检查（因为它们在工具分类上被标记为 EXTERNAL，不会触发那条检查路径），而是自己实现了根目录范围校验：

```python
# coworker/connectors/browser_automation.py:351-365（节选）
def _readable_source(raw: str) -> tuple[Any, dict[str, Any] | None]:
    """A local file to upload, resolved inside a granted root (OPE-122).

    These tools touch the filesystem but classify EXTERNAL, so the permission engine's
    root scoping — which only runs for WRITE_LOCAL — never sees them. Without this
    check the only thing between `~/.ssh/id_rsa` and a web form is someone reading the
    approval card. Mirrors `email_send`'s attachment rule, which solves the same
    problem for outgoing mail."""
    allowed = [r.path for r in (roots or [])]
    if not allowed:
        return None, {"error": "no session directory is available to upload from"}
    path = Path(str(raw)).expanduser().resolve()
    if not any(path.is_relative_to(root) for root in allowed):
        return None, {"error": f"{path} is outside the session's directories"}
    return path, None
```

注释里那句"the only thing between `~/.ssh/id_rsa` and a web form is someone reading the approval card"点出了问题的本质——审批卡片是最后一道人工防线，但不应该是唯一一道；工具自己在代码层面把可访问范围锁死在会话被授予的根目录里，才是真正兜底的机制。

### email_tools.py：只读不改，发送只走一次

`email_tools.py` 的模块 docstring 把设计原则说得很清楚：

```python
# coworker/connectors/email_tools.py:1-11
"""Email (IMAP/SMTP) connector tools — app-password auth, stdlib only.

One connector covers Gmail, iCloud, Fastmail, and custom IMAP servers: the user enters
an address + app password and servers are inferred from the address domain (advanced
fields override). Credentials are read from the SecretStore at execution time and never
enter prompts. All mailbox reads are non-destructive (read-only SELECT / PEEK fetches,
so the user's unread flags never flip) and v1 ships no delete/move/flag tools. Sending
and attachment download require approval. Sending is deliberately single-shot — SMTP
only, no APPEND-to-Sent afterwards — so a failure can never leave "delivered but looks
failed" state that tempts a retry into double-sending (Gmail saves to Sent server-side).
"""
```

这里有两个值得单独拆开的设计决定：

第一，读邮件用的是 IMAP 的 PEEK 语义（只读 `SELECT`，配合不改变已读标记的 fetch 方式），代码里 `_select_readonly()` 负责这件事——模型去读一封邮件，不应该顺带把用户手机上那个"未读"红点消掉，这是一个真实会打扰到人的副作用，值得在协议层面就避免。v1 版本干脆不提供任何删除、移动、标记已读的工具，这不是"还没做完"，而是刻意的范围收窄：一个只读连接器造成的最坏结果是"读错了信息"，一个能删改的连接器造成的最坏结果是"丢了邮件"，两者的风险不对称。

第二，发送这个动作被设计成"单次提交、不做后续补偿"。大多数邮件客户端在通过 SMTP 发出一封信之后，会再做一次 IMAP `APPEND` 把这封信存进"已发送"文件夹——但 `email_tools.py` 不这么做，理由是一旦 SMTP 发送成功但紧随其后的 APPEND 失败，系统就会处于一种"邮件其实已经送达，但从任何可观察的状态看都像是失败了"的尴尬境地,这种状态最危险的地方在于它会诱使调用方重试,而重试的直接后果是同一封邮件被送达两次。docstring 特别注明"Gmail saves to Sent server-side"——也就是说,对 Gmail 这类会在服务端自动保存已发送副本的邮箱,即使不做本地 APPEND 也不会丢失"已发送"记录;这不是牺牲功能去换安全,而是找到了一个两全的做法。

连接器的校验逻辑也体现了同样的严谨：`validate_email_account()` 要求 IMAP 登录 + INBOX 打开、以及 SMTP 登录**同时**通过才算连接成功——只验证了收信但发信配置有误，或者反过来，都不能算真正连通。

顺带一提，Email（IMAP，`descriptors.py` 里 `name="email"`）和 Gmail（OAuth，`name="gmail"`）是两个完全独立的连接器，覆盖的是同一件事的两种解法：前者用应用专用密码，对任何标准 IMAP/SMTP 服务商都通用（Gmail、iCloud、Fastmail、自建邮件服务器），代价是需要用户自己去邮箱设置里生成一个应用密码；后者是 Google 专属的 OAuth 接入，接入体验更平滑（尤其是走托管一键连接时），但只服务 Google 一家。两者的存在不是冗余，而是覆盖了"要不要绑定 Google 账号"这条分叉路径的两侧。

### attribution.py：Slack 回复上的署名前缀

多个人可能会把同一个 OpenWorker 装进同一个 Slack 工作区，共用同一个 bot 身份对外发消息——如果频道里所有人发出的消息都显示成同一个 `@ocw`，协作起来会很混乱。`attribution.py` 解决的正是这个"谁在替 bot 说话"的展示问题：

```python
# coworker/connectors/attribution.py:1-15
"""Sender attribution for outbound Slack posts (P1, 2026-07-14).

Multiple people can run OpenWorker into the same channel, and every one of their
posts arrives as the same @ocw bot. The managed OAuth install already records WHO
connected each workspace — Slack's `authed_user` — so outbound text carries
"[<their name>] " per workspace: the member id rides the install form-POST into the
`slack:team:<id>` profile, and the display name is resolved once via `users.info`
(scope `users:read`, granted since wave 1) and cached on that profile.

Truthfulness rules: manual Socket-Mode installs have no authed_user, so there is
nothing to attribute and their posts stay bare; DMs skip the prefix (a 1:1 with the
bot has no ambiguity); and attribution NEVER blocks a send — any resolution failure
degrades to no prefix. P2 (chat:write.customize) replaces the text prefix with a
native username override.
"""
```

`sender_prefix()` 只在托管 relay 安装（能拿到 `authed_user`）且目标不是 DM 的场景下才会生效，解析失败一律优雅降级成空前缀——**署名功能本身绝不阻塞发送**，这是一条很明确的取舍：宁可丢一个不影响功能的展示细节，也不能让一个次要特性拖垮核心的消息送达能力。这和第 04 章讲的审批溯源是两件不同的事——`sender_prefix()` 解决的是"这条 Slack 消息显示给频道里的人看时,署名是谁",纯粹是展示层的礼貌;而审批溯源记录的是"这个工具调用是谁批准的、依据是什么",是治理和审计层面的问题。两者都关心"归属于谁",但一个面向消息的读者,一个面向系统的审计员。

## 常见问题/易踩坑

- **浏览器连接器是可选依赖，缺失时不应该让整个引擎崩溃。** `browser` 是 `pyproject.toml` 里单独的 optional-dependency 组（`playwright>=1.44`），`_BrowserController.page()` 在导入 `playwright.sync_api` 失败时会捕获异常，返回一段可读的安装指引而不是让调用栈直接炸穿：`"Interactive browser automation requires Playwright. Install it with 'pip install playwright' and 'python -m playwright install chromium'."`——这和 `descriptors.py` 里浏览器连接器 `blurb` 提到的"Interactive Cowork"呼应：只有装了 Playwright 的浏览器二进制，这个连接器才真正可用。
- **邮件读取的"隐私过滤"发生在工具层，不是协议层。** IMAP 本身不知道什么是"永不显示给 agent 的发件人"，这条规则是 `gmail_accounts.py` 的 `get_filters()`/`sender_matches()` 在 `integration_tools.py` 的工具函数内部执行的一次内容过滤，纯 IMAP 连接器（`email` descriptor）目前没有这层过滤——如果同时接了 `email` 和 `gmail` 两个连接器指向同一个邮箱，隐私规则只对走 `gmail` 连接器的读取生效。
- **署名前缀不是权限控制。** `sender_prefix()` 加的 `[某某]` 只是文本层面的展示，任何人都可以在自己发的消息里手打一段类似格式的文字伪造署名——它解决的是多人协作时的可读性问题，不能被当成身份验证机制使用。

## 小结

`browser_automation.py` 用单线程 executor 包住 Playwright 的同步 API，把"读页面"和"看截图"设计成两条互补路径，并且在地址守卫之外专门处理了重定向落地和本地文件路径两类容易被忽略的风险；`email_tools.py` 用只读 IMAP + 单次 SMTP 发送的克制设计，把"协议允许做的事"主动收窄成"值得暴露给模型的事"；`attribution.py` 用一个绝不阻塞发送的降级策略，解决了多人共用同一个 bot 身份时的可读性问题。这三个文件覆盖的都是"SaaS API 覆盖不到"或者"协议古老到不需要 SaaS API"的场景。下一篇我们回到 README 反复强调的隐私承诺——"本地优先，唯一的云组件是一个代理 OAuth 握手的小型服务"——看这句话在 `cloud.py` 和 `relay_client.py` 里具体是怎么落地的。
