# 无人值守运行与自我唤醒机制

> 上一篇讲完了一个自动化任务怎么被创建、怎么算出下一次触发时间、调度器怎么把它跑起来。这一篇接着往下走:一次执行如果撞见了需要人批准的操作,会发生什么?没有实时 WebSocket 连接盯着的后台会话,要怎么把"请人决定一下"这件事传递出去?`selfwake.py` 这个名字看起来像是某种"自我意识觉醒"的机制,读完代码会发现它其实朴素得多——就是"定时器/等待条件到了,把挂起的会话重新叫醒"。这一篇把 `unattended.py`/`selfwake.py`/`inbox.py`/`inbox_routing.py` 串起来读,主线是"无人值守"这一执行模式的完整链路:触发 → 执行 → 遇到需要批准的操作时不自我批准、转交收件箱 → 产出怎么呈现给用户。

## 学习目标

- 理解 `unattended.py` 里"unattended"这个开关到底改变了什么——它不改变自主权的天花板,只改变"人在哪里被找到"。
- 看懂自动化的定时执行(上一篇)默认走的就是 Inbox 审批路径,和用户手动打开的"无人值守"开关背后其实是同一套 `InboxItem` 状态机在两种触发场景下的复用。
- 弄清楚 `selfwake.py` 的真实含义:它是"挂起-恢复"机制(timer / on-completion / on-event 三种唤醒方式),不是任何形式的自主意识,而是自动化调度器 `extra_tick` 里顺带驱动的另一套挂起队列。
- 理解 `inbox.py` 的状态机契约(`pending → resolved`,一次性、任何入口都能应答)如何同时服务"审批请求"和"自动化产出通知"两种场景。
- 理解 `inbox_routing.py`(出站,把 Inbox 条目镜像到外部频道)和 `subscriptions.py`(入站,订阅某个频道的消息)为什么是两套独立机制,而不是同一件事的两个视角。

## 背景与设计动机

`unattended.py` 模块 docstring 开门见山:

```python
"""Unattended mode — a per-session toggle for *where the human is reached*.

It does **not** change the autonomy ceiling (the permission mode does). When a session is
unattended, anything that would prompt inline (approval / question) is routed to the Inbox and
the agent suspends until answered; the composer is disabled. Turning it on is a one-tap confirm
(enforced at the API/GUI layer). This registry just persists the per-session flag.
"""
```

这句话把"无人值守"和"自主权"这两个容易混淆的概念划清了界限:决定一个 agent **能做多少事而不用问**的是权限模式(第 04 章讲过的那套三层门槛),"无人值守"改变的只是**问的时候去哪问**——正常情况下会在输入框上方弹出的审批卡片或问题,一旦会话被标记为无人值守,就统一路由到 Inbox,agent 挂起等待,直到 Inbox 里的条目被解决。这个设计的价值在于:一个自动化任务定时触发时,压根就不存在一个"正盯着屏幕的人"来看内联提示——所以它天然需要 Inbox 这条路径;而 `unattended.py` 里这个显式的每会话开关,则是把同一套"人不在场"的处理方式,提供给用户主动选择离开电脑、但又希望会话继续推进的场景。二者殊途同归,都落在同一套 Inbox 机制上。

## 核心机制详解

### `UnattendedRegistry`:一个纯粹的持久化标志位

`UnattendedRegistry` 本身非常简单,只做一件事——记住"这个 session_id 现在是不是无人值守":

```python
class UnattendedRegistry:
    def is_unattended(self, session_id: str) -> bool:
        return bool(self._flags.get(session_id, False))

    def set(self, session_id: str, unattended: bool) -> None:
        with self._lock:
            if unattended:
                self._flags[session_id] = True
            else:
                self._flags.pop(session_id, None)
            self._save()
```

没有过期时间、没有和权限模式的联动逻辑——这些判断都发生在别处(`server/manager.py` 里,构建审批回调时二选一)。这个模块本身只是一份 JSON 落盘的字典,`set(unattended=False)` 时直接把 key 删掉而不是写 `False`,这样序列化后的 JSON 文件里只会留下"当前正处于无人值守状态"的那些 session,天然是一份稀疏记录。

真正体现"无人值守改变提示去向"的代码在 `server/manager.py` 构建引擎的地方——`approver`/`question_asker`/`plan_approver` 这些回调的默认值,取决于调用方有没有显式传入(有实时 WS 连接的场景会传入一套走内联提示的回调),没有传入就一律退回 Inbox 版本:

```python
# WS sessions pass mode-aware callbacks (attended → live prompt, unattended → Inbox).
# Background / self-wake / durable-resume runs have no live socket → default to the
# Inbox-based callbacks so a rebuilt engine can still get approvals/answers (and, on
# resume, the already-resolved item returns immediately).
approver=approver or self.inbox_approver(session_id, agent),
```

这条注释点出了一个容易被忽略的事实:**自动化定时执行的会话,从一开始就没有实时 WebSocket 连接**——它是调度器后台起的一次执行,不是用户在界面上敲出来的。所以自动化的执行天然落在"没有传入 approver"这一支,默认就是 `inbox_approver`,不需要额外去检查 `UnattendedRegistry` 这个标志位。换句话说:**用户手动开的"无人值守"开关,和自动化任务天然的"无人值守执行",是同一套 Inbox 路径服务的两种不同触发来源**,只是前者是用户主动选择离开、后者是这个会话从诞生起就没有人守在屏幕前。

### 自动化执行为什么"不自我批准"

上一篇讲到 `_build_task_engine` 会传入一个专门的 `_scheduled_approver`,这里正是"无人值守运行遇到需要批准的操作时怎么办"的具体答案:

```python
def _scheduled_approver(self, task, session_id: str):
    from ..engine import ApprovalOutcome
    from ..permissions import WRITE_TOOLS

    name_allowed = task.name_allowed_tools()

    async def approver(request):
        # Unattended: auto-allow the deliverable writes (path-scoped to the task
        # workspace) + tools the task allows BY NAME (legacy entries). Target-bound
        # rules never reach here — the permission engine matched them already.
        if request.tool_name in WRITE_TOOLS or request.tool_name in name_allowed:
            return ApprovalOutcome.ONCE
        # Anything else parks in the Inbox and suspends the run (§25 graceful
        # degradation — an ungranted automation still works, it just asks). The item
        # carries the task binding so the in-app card can offer "Allow every time";
        # the Slack mirror renders only Approve/Deny buttons.
        item = self.inbox.add_approval(
            session_id,
            f"Run `{request.tool_name}`?",
            body=_approval_body(request),
            inbox=self.inbox_routing.route_for(session_id, task.agent),
            tool_call_id=getattr(request, "tool_call_id", None),
            data=self.approval_prompt_data(session_id, request),
        )
        if item.state == "pending":
            self.persist_session(session_id)
            await self.mirror_inbox_item(item)
        resolution = await self.inbox.wait(item.id)
        return self.approval_outcome(resolution, request, session_id)

    return approver
```

这段代码把"无人值守运行不会自我批准"具体成了两条泾渭分明的路径:

1. **只有两类操作会被自动放行**——写任务自己工作目录里的产出文件(`WRITE_TOOLS`,路径限定在这次任务的工作区)、以及任务记录上以"仅工具名"方式登记过的旧式授权(`name_allowed_tools()`)。上一篇讲的"目标绑定的标准授权"(`always_allowed_tools` 里带具体目标的那些条目)根本不会走到这个函数里——它们在更早的权限引擎匹配阶段就已经被放行了,这里的注释专门写明"Target-bound rules never reach here — the permission engine matched them already"。
2. **其余任何操作,一律挂进 Inbox、挂起这次运行**——这正是"无人值守运行不自我批准"这条规则的字面实现:遇到一个既不在写权限白名单、也没有被预先授权的操作,`_scheduled_approver` 不会替用户做决定,而是造一条 Inbox 条目,把这次运行挂起,等人来点 Approve/Deny。注释里"an ungranted automation still works, it just asks"这句话概括了这套设计的取向——没有被授权覆盖到的操作不会导致自动化失败或者被跳过,只是会多问一句。

这条链路和第 04 章讲的审批机制在概念上是同一套(`ApprovalOutcome`、权限引擎的匹配规则),这里不重复展开;值得强调的是**执行模式**本身——一次自动化触发的运行,从它被 `_build_task_engine` 造出来的那一刻起,就已经绑定了"没有人在实时盯着"这个前提,所以它唯一能做的正确事情就是把决定权交还给 Inbox,而不是自己拍板。

### `selfwake.py`:挂起-恢复,不是自主意识

`selfwake.py` 的模块 docstring 第一句话就消解了这个名字容易引发的联想:

```python
"""Self-wake — tools that let a long-running agent suspend and be re-invoked on a trigger.

Converts an always-on agent into suspend/resume (event-driven, ~zero idle cost): the session
sleeps and the runtime re-invokes it when a wake is due. Two triggers here: a **timer**
(`sleep_until`) and **on-completion** (`wake_on` a backgrounded job). This module
owns the wake records + the due/complete logic; the scheduler tick consumes ``due()`` /
``complete_job()`` and resumes the session (shares the automation scheduler — see
``PERMISSIONS-AND-INBOX.md``).
"""
```

"selfwake"指的是"一个长时间运行的 agent 挂起自己,并在某个触发条件满足时被运行时重新唤起"——本质上是把"一直跑着等结果"这种模式,转换成"睡眠(几乎零闲置成本) + 事件驱动地被叫醒"。这和上一篇讲的调度器 `Scheduler.extra_tick` 是同一条轮询线上的两件事——`Scheduler` 每次 tick 除了检查到期的自动化任务,还会顺手跑一遍 `resume_due_wakes()`(在 `server/manager.py` 里作为 `_scheduler_tick` 传给 `Scheduler(extra_tick=...)`),两套挂起队列共享同一个后台轮询节奏,但记录的对象完全不同——一个是"任务下一次该跑了",一个是"某个已经在跑的会话该被叫醒续接了"。

`Wake` 数据类支持三种触发方式,代码里明确写了第三种(`KIND_EVENT`)是"Phase 3"待完善的能力:

```python
KIND_TIMER = "timer"
KIND_COMPLETION = "completion"
KIND_EVENT = "event"  # wake when a named connector/webhook event fires (Phase 3)
```

三个对应的工具都注册给模型直接调用:

```python
def sleep_until(when_iso: str, note: str = "") -> dict:
    """Suspend and wake this session at an ISO-8601 timestamp (timezone-aware; bare
    timestamps are read as UTC). Use it for polling/waiting without burning context
    while idle — for a relative wait ("check again in 5 minutes"), compute the
    timestamp from the `Now:` line in your context."""
    ...

def wake_on(job_id: str, note: str = "") -> dict:
    """Suspend and wake this session when a backgrounded job (`job_id`) completes."""
    ...

def wake_on_event(event_key: str, note: str = "") -> dict:
    """Suspend and wake this session when a named event (`event_key`) fires — e.g. a
    connector/webhook signal an Ops agent watches for."""
    ...
```

`sleep_until` 的场景是"我需要等一段时间再检查一次"(比如"5 分钟后再看看这个任务跑完没")——模型自己从上下文里的 `Now:` 时间线算出目标时间戳,调用之后这一轮对话就此结束,不会占着一个空转的循环干等;`wake_on` 对应"我后台起了一个作业,等它跑完再继续"这种依赖关系;`wake_on_event` 是留给未来"某个连接器/webhook 触发的具名事件"的扩展点,当前主要作为一个"Ops 类型 agent 监听某个信号"的钩子存在。

调度器侧的消费逻辑(`resume_due_wakes`,在 `server/manager.py`)体现了"挂起-恢复"这四个字的字面含义:

```python
async def resume_due_wakes(self) -> int:
    resumed = 0
    for wake in self.wakes.due():
        try:
            await self._resume_wake(wake)
            resumed += 1
        except Exception:
            pass
        finally:
            self.wakes.mark_fired(wake.id)
    return resumed

async def _resume_wake(self, wake) -> None:
    message = self._wake_message(wake)
    digest = self.team_staleness_digest(wake.session_id)
    if digest:
        message = f"{message}\n\n{digest}"
    await self.deliver_to_session(wake.session_id, message)
```

`_resume_wake` 构造一条"⏰ 唤醒——继续你之前的工作"式的消息,交给 `deliver_to_session` 送回那个会话——`deliver_to_session` 的实现(在上一篇也出现过)会检查这个会话当前是忙(steering 进正在跑的turn)还是闲(起一次新的后台 turn),对一个刚从 `sleep_until` 挂起的会话来说,通常是后者:一次全新的后台 turn,从"⏰ 唤醒"这条消息开始续接。这里没有任何"自主意识"或者"主动觉醒"的成分——纯粹是"一个记录了触发条件的挂起点 + 一次周期性轮询去检查条件是否满足 + 满足了就重新投一条消息进这个会话"的标准挂起-恢复模式,`selfwake` 这个名字里的"self"指的是"agent 自己调用工具把自己挂起",而不是"系统赋予了它某种自主性"。

### `inbox.py`:一份状态机,服务两种完全不同的场景

`inbox.py` 的模块 docstring 把它的定位说得很清楚:

```python
"""The Inbox — the canonical, cross-session human-attention queue.

While a user works in one session (or is away with a session running Unattended), the Inbox
holds what other agents need from them: an **approval**, a **question**, or a **notification**.
It is the store of record; messaging connectors / mobile (Phase 3) are transports of the same
items.
"""
```

`InboxItem` 支持的 `kind` 不止"审批"一种:

```python
KIND_APPROVAL = "approval"
KIND_QUESTION = "question"
KIND_NOTIFICATION = "notification"
KIND_DIRECTORY = "directory"  # agent asks to be granted a folder
KIND_PLAN = "plan"  # agent presents a plan for approval
KIND_TOOL = "tool"  # agent asks for a missing CLI tool to be installed
```

第 04 章已经从"审批请求进收件箱"这个角度讲过 `KIND_APPROVAL`/`KIND_DIRECTORY`/`KIND_PLAN`/`KIND_TOOL` 这几类"需要人做决定"的条目。这一篇要补的是 `KIND_NOTIFICATION`——这一类条目不需要人做任何决定,纯粹是"自动化任务跑完了,把结果通知你一声"这种单向推送。`InboxStore.add_notification` 的签名比 `add_approval`/`add_question` 简单得多,因为它不需要携带任何"决定选项":

```python
def add_notification(
    self, session_id, title, *, body="", inbox="default", visibility=VIS_INBOX
) -> InboxItem:
    return self.add(
        session_id,
        KIND_NOTIFICATION,
        title,
        body=body,
        inbox=inbox,
        visibility=visibility,
    )
```

这就是本篇标题里"自动化任务运行结果需要人工关注的产出"和第 04 章"审批请求"在同一套机制里的分野所在:**它们确实复用了同一个 `InboxItem` 状态机和同一套 `InboxStore` 存储**,区别只在于 `kind` 字段——`approval`/`question`/`directory`/`plan`/`tool` 这几类是"挂起等待,直到有人给出决定"(`InboxStore.wait()` 会真的阻塞在这里),而 `notification` 这一类从被创建的那一刻起就已经"完成了它的使命"(没有代码路径会去 `wait()` 一条通知的解决状态)——只是被塞进同一个队列、走同一套可视化和多端投递逻辑而已。这印证了任务描述里预期的两种可能之一:代码显示这确实是"同一套收件箱机制服务了两种场景"的复用,而不是两套独立机制。

状态机本身的核心契约(`pending → resolved`,一次性,任何入口都能应答)是审批和通知共同依赖的基础设施:

```python
def resolve(self, item_id: str, resolution: str) -> bool:
    """Resolve an item exactly once. First responder wins; later attempts are no-ops
    (return False). Fires any awaiting agent (the suspended inbox_approver)."""
    with self._lock:
        item = self._items.get(item_id)
        if item is None or item.state == STATE_RESOLVED:
            return False
        item.state = STATE_RESOLVED
        item.resolution = resolution
        item.resolved_at = _now()
        self._save()
    waiter = self._waiters.get(item_id)
    if waiter is not None:
        waiter.set()
    return True
```

对一条 `notification` 而言,虽然它同样拥有 `pending`/`resolved` 两种状态,但推动它从 `pending` 变成 `resolved` 的路径,通常只是用户在界面上"已读"或者手动关闭它——不存在挂起等待的一方。这也是为什么它能和真正会阻塞执行的审批类条目安全地共享同一张表:状态机对"谁在等这个结果"完全无感知,等不等待是调用方(`inbox_approver`/`inbox_question_asker` 这些回调 vs. 单纯展示通知的 UI 逻辑)自己决定的事。

### 出站的 Inbox Routing 和入站的 Subscriptions:两个方向,两套机制

`inbox_routing.py` 和 `subscriptions.py` 表面上都在处理"这个会话和一个外部消息频道的关系",但模块 docstring 把方向说得非常明确。`inbox_routing.py`:

```python
"""Multi-inbox routing — named inboxes + delivery bindings.

An inbox is a named queue with optional delivery binding(s): in-app is always the store of
record; a binding can also mirror items to a Slack channel or Telegram chat. ...
"""
```

`subscriptions.py` 则专门在 docstring 里点名和 routing 的区别,生怕读者把两者混为一谈:

```python
"""Channel subscriptions — the INBOUND counterpart of Inbox routing (which is outbound).

...

NOTE: this is *not* Inbox routing. Routing mirrors an agent's approvals/questions OUT to a
DM/channel (request↔reply, `[ow:id]`-correlated); a subscription brings a channel's messages IN
(broadcast). Keep them on different channels — pointing your Inbox at a channel you also subscribe
to conflates the two directions.
"""
```

代码层面这确实是**两套独立的持久化机制**,不是同一件事的两个视角:

- **Inbox Routing(出站)**:一个 `InboxBinding` 把命名的 inbox 和一个外部频道绑定,`deliver()` 把条目镜像出去时,会把条目 id 编码进消息文本(`f"[ow:{item.id}]"`),`resolve_from_reply()` 再从频道回复里正则提取这个 id、判断"同意/拒绝"意图(`_reply_intent` 只看回复**第一个词**或表情符号,这是为了避免"I cannot approve this yet"这种带否定语气的句子被子串匹配误判成同意),最终调回 `InboxStore.resolve`。这条链路服务的是"审批/提问,请求—回复"这种一问一答的语义。
- **Channel Subscriptions(入站)**:`Subscription` 是 `(session_id, channel)` 的持久化记录,代表"这个会话主动订阅了某个频道,希望频道里的消息能推送进来唤醒/续接自己"。`subscription_tools` 里的 `subscribe_channel`/`unsubscribe_channel`/`get_channel_messages` 是模型自己调用的工具——文档里提到的"对某个 Slack 频道保持常驻关注"这一类"standing watch"场景,正是靠这套订阅机制实现:模型主动订阅一个频道之后,该频道后续的消息通过 `ChannelBuffer` 记录、并推动订阅会话被唤醒(复用的正是前面 selfwake 提到的 busy→steer / idle→后台 turn 这条投递路径,而不是走一个独立的实时 socket)。

两个模块甚至互相知道对方的存在,并在代码里做了一次显式的冲突提醒——`subscribe_channel` 工具在订阅时会检查这个频道是不是同时也是当前会话的 Inbox 路由目标:

```python
warn = None
if routing_targets and addr in routing_targets:
    warn = (
        f"heads up: your Inbox is also routed to {addr}. Inbox routing (outbound) and a "
        "subscription (inbound) on the same channel conflate request/reply with broadcast — "
        "consider a dedicated DM/channel for the Inbox."
    )
```

这条提醒印证了 docstring 里"Keep them on different channels"的告诫:如果一个频道既是这个会话审批消息要镜像出去的目的地,又是这个会话订阅进来的信息源,那么"请求—回复"和"广播消息"这两种语义会在同一个频道里混在一起,变得难以区分"这条回复是在批准我的操作"还是"这只是频道里正常的一条聊天消息"。

`mentions.py` 处理的是与订阅相邻但不同的另一种场景——`@OpenWorker` 被提及但当前没有订阅会话覆盖这个话题时,路由器会现场生成一个新会话来"拥有"这条讨论串:

```python
"""Mention-thread → session map for the Slack mention router (UX-DECISIONS §31).

When @OpenWorker is tagged in a channel with no subscribed session, the router spawns a
coworker session that OWNS that thread and replies into it. This store is the
dedupe map: one durable record per thread, keyed by the thread target string...
"""
```

`MentionSessionStore` 的职责很窄——只是"话题串 → 会话"的去重映射,以及"这个会话在这条话题串里的回复已经被预先授权,重启后要能重新种回去"这份持久化凭证(`targets_for` 供引擎重建时把 `send_message` 工具对这条话题串的授权重新种进权限引擎)。它和第 07 章讲 Connectors 时提到的 Slack 集成共享同一个提及事件入口,但这里关注的只是它和"常驻监听"场景的关系——一次提及触发的会话,本质上是订阅机制之外的另一条"按需现开一个会话来接管一个话题串"的路径,不在本篇重复第 07 章已经讲过的连接器细节。

## 常见问题/易踩坑

- **不要把"无人值守开关"当成自主权开关**:`UnattendedRegistry` 只决定审批/提问提示往哪投递,决定"哪些操作不用问就能做"的仍然是权限模式(第 04 章)——一个高权限模式配合无人值守,和一个低权限模式配合无人值守,遇到需要批准的操作时依然都会乖乖挂进 Inbox。
- **自动化任务的执行天然是"无人值守"的,不需要手动打开开关**:它从来就没有过一条实时 WebSocket 连接,`approver` 参数从一开始就没有被传入,默认直接落到 Inbox 版本的审批器上。
- **`selfwake.py` 和"多智能体自主唤醒彼此"没有关系**:它是单个会话"挂起自己、等触发条件满足后被同一个调度循环重新投递消息"的机制,`KIND_EVENT` 目前还是待完善的扩展点(Phase 3),不要因为名字里有"wake"就联想成更复杂的自治行为。
- **Inbox Routing 和 Subscriptions 绝不能简单类比**:前者是把本会话的审批/提问镜像"发出去",后者是把某个频道的消息"接进来",指向同一个频道会造成语义冲突,代码里已经内置了这条冲突检测提醒。

## 小结

"无人值守"这个执行模式在 OpenWorker 里不是一个孤立开关,而是一整条链路共同的落脚点:`unattended.py` 只负责持久化一个每会话的标志位,真正让"不自我批准、转交人工"这件事成立的,是自动化执行天然没有实时连接、因而默认走 Inbox 审批器这一事实,以及 `_scheduled_approver` 里"只放行工作目录写入和已授权工具、其余一律挂起等待"这条明确规则;`selfwake.py` 提供的是纯粹的挂起-恢复能力(定时器/作业完成/具名事件三种触发),和自动化调度器共享同一条后台轮询节奏,但两套记录各管各的;`inbox.py` 一套状态机同时撑起了"审批请求"和"运行结果通知"两种语义,区别只在 `kind` 字段和有没有人在 `wait()`;而 `inbox_routing.py`(出站,审批/提问镜像出去)和 `subscriptions.py`(入站,频道消息拉进来)是两套故意分开、代码里还互相提醒不要用错的独立机制。下一章会离开这些运行时机制,转向桌面应用本身——Tauri 桌面壳怎么把这一整套 server 包装成一个可安装的应用,以及语音输入 sidecar 是怎么接进来的。
