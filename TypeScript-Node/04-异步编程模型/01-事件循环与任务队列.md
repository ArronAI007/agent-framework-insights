# 事件循环与任务队列

> 上一章讲完了 TS 的类型系统，从这一篇开始进入这门课的第二个核心主题：异步编程模型。JS/Node 是单线程执行 JS 代码的——没有你熟悉的那种"多开一个线程去等 I/O"的选项，所有"看起来并发"的行为，靠的都是同一条主线程反复在"跑一段同步代码 -> 检查队列里有没有排队的任务 -> 跑下一段"之间循环，这套循环机制就是事件循环（event loop）。这一篇先不讲 `Promise`/`async`，只讲事件循环本身，以及几种任务在队列里的优先级顺序——这是后面所有异步内容的地基，也是"为什么这段代码打印顺序和我以为的不一样"这类困惑的根源。

## 学习目标

- 理解调用栈（call stack）、宏任务（macrotask）、微任务（microtask）三者的关系
- 搞清楚 `setTimeout`/`setImmediate`（宏任务）和 `Promise.then`/`queueMicrotask`（微任务）的执行顺序
- 认识 Node 特有的 `process.nextTick`，以及它在 ESM 和 CommonJS 下优先级表现不一致这个容易被忽视的坑
- 对 Node 事件循环的六个阶段建立一个概览性的认识（不深挖每个阶段的底层源码）

## 单线程 + 事件循环：JS/Node 并发模型的起点

如果你之前写的是有原生线程、有阻塞 I/O 的语言，第一次接触 JS 时最容易产生的误解是：以为 `setTimeout`、网络请求这些"异步"操作是靠另开一个线程去执行的。实际情况是——**JS 代码本身永远只在一条主线程上跑**，`setTimeout` 的回调、Promise 的 `.then`、网络请求收到响应后的处理逻辑，全部都要排队等主线程"闲下来"才会被执行。真正做了"多线程/多进程"工作的，是 Node 底层的 libuv 库（负责文件 I/O、DNS 解析等）和网络协议栈本身，JS 这一层只是在合适的时机被"通知一下、请回来执行"。

调用栈（call stack）是这套机制里最基础的概念：任何一段同步代码在执行期间都会占据调用栈，只要调用栈不空，事件循环就不会去处理任何排队中的任务——这也是为什么"写一个死循环会让整个 Node 进程卡死，连 `setTimeout` 都不会触发"：调用栈永远不会空出来，事件循环压根没有机会去看队列。

排队等待被执行的任务分成两大类，理解这两类之间的优先级关系，比记住具体哪个 API 属于哪一类更重要：

- **宏任务（macrotask）**：`setTimeout`/`setInterval` 的回调、`setImmediate`（Node 专属）、I/O 完成后的回调（比如文件读取完成、网络请求收到响应）。每一轮事件循环通常只会从宏任务队列里取**一个**任务出来执行。
- **微任务（microtask）**：`Promise.then`/`.catch`/`.finally` 的回调、`queueMicrotask()` 注册的回调。微任务队列的优先级高于宏任务——**每次调用栈清空之后，事件循环会先把微任务队列里的所有任务全部跑完，才会去看宏任务队列**，哪怕这个过程中微任务队列里又产生了新的微任务（比如一个 `.then` 里又注册了另一个 `.then`），也会先跑完这条链，再轮到宏任务。

## 用真实代码验证执行顺序

光靠文字描述容易记混，直接跑一段混合了各种任务类型的代码，看真实的打印顺序最直观。完整代码见 `examples/04-异步编程模型/01-事件循环与任务队列/event-loop-order.ts`，核心部分：

```ts
console.log("[sync] 第 1 行");

setTimeout(() => {
	console.log("[macrotask] setTimeout(fn, 0)");
}, 0);

setImmediate(() => {
	console.log("[macrotask] setImmediate（check 阶段）");
});

Promise.resolve().then(() => {
	console.log("[microtask] Promise.resolve().then()");
});

queueMicrotask(() => {
	console.log("[microtask] queueMicrotask()");
});

process.nextTick(() => {
	console.log("[nextTick] process.nextTick()");
});

console.log("[sync] 最后一行（仍在同一轮调用栈中）");
```

用 `npx tsx` 跑出来的真实打印顺序：

```text
[sync] 第 1 行
[sync] 最后一行（仍在同一轮调用栈中）
[microtask] Promise.resolve().then()
[microtask] queueMicrotask()
[nextTick] process.nextTick()
[macrotask] setImmediate（check 阶段）
[macrotask] setTimeout(fn, 0)
```

这个顺序印证了前面讲的核心规则：两行 `console.log`（同步代码）最先跑完；调用栈清空后，微任务队列先被清空——但这里有一个真实跑出来才会发现的意外，下一节专门拆解。

## 意料之外的发现：`process.nextTick` 在 ESM 下并不"最优先"

Node 官方文档里反复强调 `process.nextTick` 的优先级高于 Promise 微任务队列——每当一个操作完成，Node 会先清空 `nextTick` 队列，再清空 `Promise` 微任务队列。按这个说法，上面例子里 `[nextTick]` 那一行应该打印在两行 `[microtask]` 之前。但实际跑出来的顺序是 `[microtask]` 两行在前，`[nextTick]` 排在它们后面——这不是巧合，也不是代码写错了，而是**这份代码运行在 ESM 模块**（本项目 `package.json` 里配了 `"type": "module"`）下才会出现的行为差异。

用同样的代码分别存成 `.mjs`（ESM）和 `.cjs`（CommonJS）跑一遍做对比，能清楚看到差异确实来自模块系统，而不是随机波动：

```text
# node xxx.mjs（ESM）真实输出
A: sync
A2: sync2
C: promise.then
D: queueMicrotask
B: nextTick
F: setImmediate
E: setTimeout

# node xxx.cjs（CommonJS）真实输出
A: sync
A2: sync2
B: nextTick
C: promise.then
D: queueMicrotask
F: setImmediate
E: setTimeout
```

CommonJS 下的顺序和文档描述完全一致：`nextTick` 排在 Promise 微任务之前。ESM 下则反过来。合理的解释是：ESM 模块的顶层求值本身是按 JS 规范"模块执行是一个异步任务"的方式跑的（这也是 ESM 支持顶层 `await` 的基础），V8 在完成"当前模块顶层同步代码"这一步之后，会先按标准 JS 引擎自己的微任务清空规则（自动 drain 微任务队列），这一步发生在 Node 自己的 `processTicksAndRejections`（负责按"先 nextTick、后 Promise 微任务"的顺序交替清空两个队列）真正被调度到之前。CommonJS 模块没有这层"模块本身是一次异步求值"的包装，所以能严格走 Node 文档描述的那套顺序。

这个发现对写代码的实际影响：**不要假设 `process.nextTick` 一定比所有 Promise 微任务先执行**——这个保证在 CommonJS 下成立，但本项目和现在大多数新项目默认使用的 ESM 下不成立。如果代码逻辑真的依赖"必须比任何 Promise 微任务更早执行"这个精确顺序（比如某些底层库需要在用户的 `.then` 回调跑之前先完成一次内部状态初始化），需要额外测试验证，不能只凭文档里针对 CommonJS 场景写的说明。

## `setImmediate` 与 `setTimeout(fn, 0)` 的顺序：不总是确定的

上面的例子里，`setImmediate` 的回调打印在 `setTimeout(fn, 0)` 之前，连续跑三次结果一致。但这个顺序**不是**一个可以依赖的保证——Node 官方文档明确说明：如果这两个调用发生在"主模块的顶层"（不在任何 I/O 回调内部），它们谁先执行取决于进程的性能表现，是不确定的；只有当两者都是在**同一个 I/O 回调内部**注册时，`setImmediate` 才保证一定先于 `setTimeout(fn, 0)` 执行（因为 I/O 回调发生在 poll 阶段，poll 阶段的下一站正是 check 阶段——`setImmediate` 专属的阶段——而 `setTimeout` 要等下一轮循环的 timers 阶段）。这是本篇特意选的一个"看起来有固定顺序、实际上要看上下文"的例子：如果代码逻辑依赖 `setImmediate` 一定先跑，得先确认自己是不是真的在 I/O 回调里调用它。

## Node 事件循环的六个阶段（概览）

事件循环每一轮会按固定顺序依次经过几个阶段，每个阶段维护自己的一个回调队列：

| 阶段 | 处理什么 |
|------|---------|
| timers | `setTimeout`/`setInterval` 到期的回调 |
| pending callbacks | 上一轮循环里被延后到这一轮的系统级回调（比如某些 TCP 错误） |
| poll | 检索新的 I/O 事件、执行 I/O 相关的回调（文件读写完成、网络数据到达等），这是事件循环里通常耗时最长的阶段 |
| check | `setImmediate` 的回调，紧跟在 poll 阶段之后 |
| close callbacks | `socket.on("close", ...)` 这类"关闭"事件的回调 |

每完成一个阶段的一批回调、以及每完成一个单独的回调之后，Node 都会先把 `process.nextTick` 队列和 Promise 微任务队列清空，再进入下一个阶段——这就是为什么无论宏任务处于事件循环的哪个阶段，微任务永远能"见缝插针"地在两个宏任务之间执行。这一篇不深入每个阶段内部的实现细节（那部分属于 libuv 的范畴），只需要建立"事件循环是分阶段的、微任务在阶段之间见缝插针执行"这个整体图景。

## 小结

JS/Node 用单线程 + 事件循环实现"看起来并发"的效果：调用栈清空之前，任何排队的任务都不会被执行；调用栈清空之后，微任务队列（`Promise.then`/`queueMicrotask`）总是先于宏任务队列（`setTimeout`/`setImmediate`/I/O 回调）被清空。Node 特有的 `process.nextTick` 按文档应该比 Promise 微任务优先级更高，但这个顺序只在 CommonJS 下严格成立——本项目使用的 ESM 下，顶层同步代码跑完后，Promise 微任务反而先于 `nextTick` 执行，这是本篇用真实代码验证出来的、容易被文档误导的一个细节。`setImmediate` 和 `setTimeout(fn, 0)` 的相对顺序只有在 I/O 回调内部注册时才有确定的保证。事件循环按 timers/pending callbacks/poll/check/close callbacks 几个阶段循环，微任务队列在每个阶段之间都会被清空一次。下一篇进入 `Promise` 和 `async`/`await` 的状态机与语义细节，会大量用到这一篇建立的"宏任务 vs 微任务"这套心智模型。
