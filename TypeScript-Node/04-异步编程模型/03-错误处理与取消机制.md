# 错误处理与取消机制

> 上一篇讲完了 `Promise`/`async`/`await` 的核心语义，这一篇讲异步代码里的错误处理和取消。JS 原生的 Promise 有一个经常让人意外的设计缺失：**没有内置的取消机制**——一个 Promise 一旦创建，唯一能左右它命运的就是它自己内部的逻辑，外部代码没有"我不要这个结果了、把它中止掉"的原生手段。这一篇会讲清楚 `try`/`catch` 在 `async` 函数里到底捕获了什么、如何用自定义 `Error` 子类做结构化的错误分类，以及 `AbortController`/`AbortSignal` 这套后来补上的、跨越多个 Web/Node API 的统一取消方案。

## 学习目标

- 理解 `try`/`catch`/`finally` 在 `async` 函数里的语义边界
- 学会用自定义 `Error` 子类做结构化错误分类，配合 `instanceof` 精确处理
- 掌握 `AbortController`/`AbortSignal` 这套跨 API 统一的取消机制，能用它给一个"天然不会结束"的操作实现超时
- 了解 `unhandledRejection`/`uncaughtException` 这两个进程级兜底事件的用途和边界

## `try`/`catch`/`finally` 在 `async` 函数里的语义

前一篇提到过：`await` 本质上是把"Promise reject"转换成"同步风格的 throw"。这意味着在 `async` 函数内部，`try`/`catch` 能同时捕获两类错误：函数体里同步 `throw` 出来的异常，以及 `await` 到的 rejected Promise——对写代码的人来说，这两类错误可以用完全相同的一套 `try`/`catch` 心智去处理，不需要区分"这个错误是同步抛出的还是异步来的"。

```ts
class ValidationError extends Error {
	constructor(message: string, public readonly field: string) {
		super(message);
		this.name = "ValidationError";
	}
}

function validateAge(age: number): void {
	if (age < 0 || age > 150) {
		throw new ValidationError(`age 取值不合法: ${age}`, "age");
	}
}

async function demoTryCatchFinally(): Promise<void> {
	try {
		validateAge(-5);
	} catch (error) {
		if (error instanceof ValidationError) {
			console.log(`[try/catch] 捕获到 ValidationError，字段=${error.field}，消息=${error.message}`);
		}
	} finally {
		console.log("[try/catch] finally 块执行——无论成功失败都会跑到这里");
	}
}
```

真实输出：

```text
[try/catch] 捕获到 ValidationError，字段=age，消息=age 取值不合法: -5
[try/catch] finally 块执行——无论成功失败都会跑到这里
```

`finally` 块的语义和同步代码里完全一致：不管 `try` 块是正常结束、`throw` 了异常、还是提前 `return`，`finally` 都会执行——这对异步代码里"无论请求成功还是失败都要释放某个资源"（关闭数据库连接、清理临时文件、释放一个锁）的场景非常有用，不需要在成功和失败两条分支里各写一遍清理逻辑。

## 自定义 `Error` 子类：让错误携带结构化信息

JS 里 `throw` 语句理论上可以抛出任意值（字符串、数字、普通对象），但生产代码应该始终 `throw` 一个 `Error`（或它的子类）实例——`Error` 自带 `message`、`stack`（调用栈信息，调试时非常关键）等标准字段，是运行时和调试工具（比如 Node 的错误堆栈打印）默认能正确识别和展示的形态。

在 `Error` 的基础上，用 `class XxxError extends Error` 定义自己的错误子类，能让 `catch` 块用 `instanceof` 精确区分"这是哪一种错误"，比在错误消息字符串里做子串匹配可靠得多——字符串匹配一旦错误消息的措辞被后续改动就会静默失效，`instanceof` 检查的是类型，不受消息文案变化影响：

```ts
class NotFoundError extends Error {
	constructor(public readonly resourceId: string) {
		super(`资源不存在: ${resourceId}`);
		this.name = "NotFoundError";
	}
}
```

这个例子里额外挂了一个 `resourceId` 字段——自定义 `Error` 子类不仅能分类错误类型，还能携带类型系统能追踪的结构化上下文数据，调用方 `catch` 到之后可以直接访问 `error.resourceId`，不需要从错误消息字符串里再解析一遍。

## `AbortController`/`AbortSignal`：跨 API 统一的取消机制

前面提到过，Promise 本身没有取消能力——`AbortController` 是后来补上的、跨越多个 API（`fetch`、部分 `fs` API、以及大量用户自定义的异步函数）的统一约定：一个函数只要接受一个 `signal: AbortSignal` 参数，就意味着它支持被这套机制取消。`AbortController` 负责"发起取消"（调用 `.abort(reason)`），它的 `.signal` 属性是一个只读的 `AbortSignal`，被取消的操作靠监听 `signal` 上的 `"abort"` 事件（或检查 `signal.aborted` 布尔值）来响应。

下面的例子用它给一个"永远不会自己 resolve 的 Promise"实现超时取消——这是一个很实用的通用模式：包装任何一个可能长期挂起的操作，用 `AbortController` + `setTimeout` 强制它在超时后失败。

```ts
function neverResolves(signal: AbortSignal): Promise<never> {
	return new Promise((_resolve, reject) => {
		if (signal.aborted) {
			reject(new Error("任务尚未开始就已经被取消"));
			return;
		}
		signal.addEventListener("abort", () => {
			reject(new Error(`任务被取消，原因: ${String(signal.reason)}`));
		});
	});
}

const controller = new AbortController();
const timeoutMs = 50;
setTimeout(() => controller.abort(`超过 ${timeoutMs}ms 未完成，主动超时`), timeoutMs);

const startedAt = Date.now();
try {
	await neverResolves(controller.signal);
} catch (error) {
	const elapsed = Date.now() - startedAt;
	console.log(`[AbortController] ${elapsed}ms 后捕获到取消错误 -> ${(error as Error).message}`);
}
```

真实输出：

```text
[AbortController] 51ms 后捕获到取消错误 -> 任务被取消，原因: 超过 50ms 未完成，主动超时
```

51ms（略超过设定的 50ms 超时，属于定时器本身的正常调度误差）之后，`neverResolves` 返回的 Promise 被强制 reject。注意这里 `neverResolves` 内部的 Promise executor 除了 abort 事件之外没有任何其他会让它 settle 的途径——它是被"外部强制终结"的，而不是自己算出了什么结果。这正是 `AbortController` 相比"自己手写一个 race 定时器"更规范的地方：`signal.reason` 能携带取消的原因，同一个 `signal` 可以同时传给多个函数，一次 `abort()` 能同时取消所有监听了它的操作，而 `fetch` 这类内置 API 也接受同样的 `signal` 参数，取消逻辑可以在整条调用链上保持一致。

## `unhandledRejection` 与 `uncaughtException`：进程级的兜底

如果一个 Promise reject 了，但没有任何 `.catch()` 或 `try`/`await` 去处理它，Node 会在事件循环的某个时机判定这是一次"未处理的 rejection"，并触发 `process` 上的 `unhandledRejection` 事件；类似地，如果一个同步抛出的异常一路冒泡到调用栈顶都没有被任何 `try`/`catch` 捕获，会触发 `uncaughtException` 事件。

```ts
function triggerUnhandledRejection(): void {
	Promise.reject(new Error("故意制造的未处理 rejection，用来演示 unhandledRejection 事件"));
}

process.once("unhandledRejection", (reason) => {
	console.log(`[unhandledRejection] 捕获到未处理的 rejection -> ${(reason as Error).message}`);
});
triggerUnhandledRejection();
```

真实输出：

```text
[unhandledRejection] 捕获到未处理的 rejection -> 故意制造的未处理 rejection，用来演示 unhandledRejection 事件
```

这两个事件的正确定位是**兜底监控**，不是"正常的错误处理手段"——生产代码应该保证每一条 Promise 链、每一个可能抛异常的路径都有对应的 `catch`/`try`，`unhandledRejection`/`uncaughtException` 的监听器通常只用来做最后一层防线：记录日志、上报监控系统、然后 `process.exit(1)` 让进程崩溃重启（尤其是 `uncaughtException`——触发它意味着程序已经处于未知的不一致状态，继续运行比直接退出更危险，Node 官方文档也明确建议不要试图在 `uncaughtException` 里"恢复"程序继续运行）。如果发现日志里频繁出现这两个事件，说明的是代码里存在没有被正确 `catch` 的路径，应该去修复那个路径本身，而不是长期依赖这层兜底。

## 小结

`try`/`catch`/`finally` 在 `async` 函数里能同时捕获同步 `throw` 和 `await` 到的 rejected Promise，`finally` 无论成败都会执行，适合做资源清理。自定义 `Error` 子类配合 `instanceof` 能做比字符串匹配更可靠的错误分类，还能携带结构化的上下文数据。`AbortController`/`AbortSignal` 是 JS 生态里跨 API 统一的取消方案，`fetch`、部分 `fs` API 和大量用户自定义函数都遵循这个约定，用它可以给任何"天然不会结束"的操作实现超时取消。`unhandledRejection`/`uncaughtException` 是进程级的兜底事件，用于监控和最后一道防线，不能替代代码里本该写的 `catch`/`try`。下一篇讲并发控制——当需要同时发起大量异步任务（比如批量调用外部 API）时，如何限制真正同时在跑的任务数量，避免打垮下游服务或本机资源。
