# 并发控制模式

> 这一章的最后一篇，讲一个前三篇都刻意回避的问题：`Promise.all` 启动的所有任务，是**同时**全部开始的。这在任务数量少的时候没什么问题，但如果任务是"批量调用外部 API"、"批量读取几千个文件"，一次性把它们全部同时扔出去，很可能触发对方的限流、打满本机的连接数，甚至直接把内存写爆。这一篇讲清楚为什么需要限制并发、如何自己实现一个不依赖第三方库的受限并发执行器。

## 学习目标

- 理解为什么"天真并发"（naive concurrency）在批量任务场景下是危险的
- 掌握一种不依赖第三方库、自己实现"限制同时运行任务数"的常见思路
- 能用真实的时间戳日志证明并发数确实被限制住了，而不是凭直觉相信代码"应该"生效

## 为什么需要限制并发

`Promise.all([task1(), task2(), ..., task100()])` 这行代码本身有一个容易被忽视的细节：**数组里的每一项在被求值的那一刻就已经启动了**——`task1()` 到 `task100()` 这 100 次函数调用是同步、依次立刻执行的，`Promise.all` 只是负责"等它们都完成"，它本身不控制"什么时候启动"。这意味着如果这 100 个任务是"调用同一个外部 API"，代码运行到这一行的瞬间，100 个 HTTP 请求会几乎同时被发出去。

真实场景下这通常是个问题：外部 API 大概率有限流策略，瞬间 100 个并发请求很可能直接触发 429（Too Many Requests）；即便对方没有限流，本机的 TCP 连接数、内存里同时缓存的 100 份响应数据，也可能成为瓶颈。**天真并发**（把所有任务一次性全部启动）在任务数量小的时候是无害的简化，任务数量一大就需要换成**受限并发**——限制"任意时刻真正同时在跑的任务数不超过某个阈值"。

## `runWithConcurrencyLimit`：自己实现一个任务队列

思路并不复杂：维护一个共享的"下一个待领取任务"指针，同时启动 `limit` 个"worker"（更准确地说是 `limit` 个并发执行的 `async` 循环），每个 worker 不停地"领取下一个任务 -> 等它跑完 -> 再领取下一个"，直到任务耗尽。因为同时只有 `limit` 个 worker 在跑，任意时刻真正在执行的任务数量自然就被限制在 `limit` 以内——不需要引入任何第三方任务队列库。

```ts
async function runWithConcurrencyLimit<T>(tasks: Array<() => Promise<T>>, limit: number): Promise<T[]> {
	const results: T[] = new Array(tasks.length);
	let nextIndex = 0;

	async function worker(): Promise<void> {
		while (nextIndex < tasks.length) {
			const currentIndex = nextIndex;
			nextIndex += 1;
			results[currentIndex] = await tasks[currentIndex]!();
		}
	}

	const workerCount = Math.min(limit, tasks.length);
	const workers = Array.from({ length: workerCount }, () => worker());
	await Promise.all(workers);

	return results;
}
```

这里有两个实现细节值得注意：第一，`tasks` 数组里的元素是**函数**（`() => Promise<T>`），而不是已经调用过的 Promise——如果传进来的是已经调用过的 Promise，任务在数组构造的那一刻就已经全部启动了，"限制并发"就无从谈起，必须让调用方把"启动任务"这个动作也延后到 worker 真正领取到它的那一刻。第二，`nextIndex` 是所有 worker 共享的同一个闭包变量，`nextIndex += 1` 这一行虽然看起来有"多个并发读写同一个变量"的既视感，但因为 JS 单线程执行、这行代码本身是同步的，不存在传统多线程语言里的竞态条件——不需要加锁。

## 天真并发 vs 受限并发：用真实时间戳日志对比

用几个 `setTimeout` 模拟的异步任务，分别跑一次 `limit=Infinity`（等价于天真并发，全部同时开始）和 `limit=2`，记录每个任务真正开始执行时的相对时间戳，能直接从日志上看出并发数是否被限制住。完整代码见 `examples/04-异步编程模型/04-并发控制模式/concurrency-limit.ts`。

`limit=Infinity` 真实输出：

```text
===== limit=Infinity（等价于 Promise.all 的天真并发，全部同时开始）=====
任务 T0 开始，相对时间 +0ms
任务 T1 开始，相对时间 +0ms
任务 T2 开始，相对时间 +0ms
任务 T3 开始，相对时间 +0ms
任务 T4 开始，相对时间 +0ms
全部完成 -> T0 完成, T1 完成, T2 完成, T3 完成, T4 完成
```

5 个任务全部在 `+0ms` 开始——完全符合"天真并发"的定义，没有任何节流。

`limit=2` 真实输出：

```text
===== limit=2（受限并发，同时最多 2 个任务在跑）=====
任务 T0 开始，相对时间 +0ms
任务 T1 开始，相对时间 +0ms
任务 T2 开始，相对时间 +32ms
任务 T3 开始，相对时间 +32ms
任务 T4 开始，相对时间 +64ms
```

每个模拟任务耗时 30ms。可以看到 T0、T1 在 `+0ms` 同时开始（两个 worker 各领了一个任务），T2、T3 要等到 `+32ms`（约等于一个任务的耗时之后）才开始——这正是因为 T0/T1 跑完释放出 worker 之后，T2/T3 才被领取到；T4 又要再等一轮，在 `+64ms` 才开始。日志清楚地证明了：**任意时刻真正在跑的任务数确实被限制在了 2 个以内**，不是靠猜测或者"代码逻辑看起来应该没问题"，而是用真实的时间戳数据验证出来的。

## 小结

`Promise.all` 本身不控制任务的启动时机——数组里的任务在被求值那一刻就已经全部同时启动，这就是"天真并发"，任务数量大、下游又有限流/资源限制时会成为隐患。自己实现一个受限并发执行器的核心思路是"共享一个待领取任务指针 + 启动固定数量的 worker 循环领取任务"，不需要引入第三方库。判断并发限制是否真的生效，不能只靠"代码逻辑看起来对"，要用真实的时间戳日志去验证——`limit=Infinity` 下所有任务同时开始，`limit=2` 下任务分批、按约等于单个任务耗时的间隔依次开始，这种可观测的证据才是可信的验证方式。到这里，第 04 章「异步编程模型」全部结束——从事件循环的任务队列优先级，到 Promise/async-await 的状态机和组合方法，到错误处理与 AbortController 取消机制，最后落到并发控制这个真实工程里绕不开的问题。下一章转向 Node.js 运行时核心，会讲模块系统、文件系统、Stream、网络编程、子进程与 Worker Threads、进程生命周期——这些是 Node 区别于"纯 JS 语言标准"的、真正让它成为一个服务端运行时的部分，而这一章讲的异步模型，正是理解它们全部工作原理的基础。
