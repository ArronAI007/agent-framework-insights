# 高级类型：映射类型、条件类型与模板字面量类型

> 这一篇开始，TS 类型系统会明显区别于你熟悉的那些语言的类型系统——这里讲的不是"给变量标个类型"，而是"用类型去计算类型"：根据一个已有类型，生成一个新的、规则化变换过的类型。映射类型、条件类型、模板字面量类型是这套"类型计算"能力的三块地基，下一篇的"类型体操"全部建立在这三者之上。

## 学习目标

- 理解映射类型语法 `[K in keyof T]`，知道内置的 `Partial`/`Readonly`/`Pick`/`Record` 是怎么实现的
- 理解条件类型 `T extends U ? X : Y` 的语义
- 理解分布式条件类型：为什么对联合类型用条件类型会"逐个成员分发"
- 知道 `[T] extends [U]` 这种元组包裹写法如何阻止分布式行为
- 理解模板字面量类型，会用它拼接出受约束的字符串字面量类型

## 映射类型：`[K in keyof T]`

映射类型的语法是 `{ [K in keyof T]: 某种基于 T[K] 的类型表达式 }`——遍历 `T` 的每一个属性名 `K`，为新类型生成一个同名属性，属性值类型由你在冒号后面写的表达式决定。

```ts
type MyPartial<T> = {
	[K in keyof T]?: T[K];
};

interface Draft {
	title: string;
	body: string;
	tags: string[];
}

const partialDraft: MyPartial<Draft> = { title: "草稿标题" };
const builtinPartialDraft: Partial<Draft> = { title: "草稿标题" };
```

真实输出：

```text
partialDraft={"title":"草稿标题"}
builtinPartialDraft={"title":"草稿标题"}
```

`MyPartial<T>` 遍历 `keyof T`（`Draft` 的话就是 `"title" | "body" | "tags"`），对每个属性名 `K`，生成一个类型为 `T[K]` 但加了 `?` 修饰符的属性——`?` 让这个属性变成可选。这正是 TS 内置工具类型 `Partial<T>` 的完整实现原理，两者结构完全等价：`partialDraft` 和 `builtinPartialDraft` 都只填了 `title` 一个字段，两边都能通过类型检查。

同样的思路可以照搬出另外几个常用内置工具类型：

```ts
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };
type MyRecord<K extends string | number | symbol, V> = { [P in K]: V };
```

真实输出：

```text
readonlyDraft.title=t
pickedDraft={"title":"t","body":"b"}
draftCountByTag={"tech":3,"life":1}
```

`MyReadonly<T>` 只是把 `?` 换成 `readonly` 修饰符——遍历每个属性名，把对应属性标记为只读，属性值类型不变。`MyPick<T, K extends keyof T>` 稍有不同：它不遍历 `keyof T`，而是遍历调用方传入的 `K`（`K` 被约束为 `keyof T` 的子集），也就是"只挑出 `K` 里指定的那几个属性名"，实现"从 `T` 里挑出一部分字段"的效果。`MyRecord<K, V>` 则是遍历一个跟 `T` 完全无关的类型参数 `K`（通常是一个字符串字面量联合类型），给每个 `K` 里的成员统一生成类型为 `V` 的属性——常用来描述"键的集合已知、但值都是同一种类型"的对象，比如按标签统计文章数量的 `draftCountByTag`。

## 条件类型：`T extends U ? X : Y`

条件类型的语法长得像三元表达式，但工作在类型层面：`T extends U ? X : Y` 的意思是"如果类型 `T` 可以赋值给类型 `U`（也就是 `T` 是 `U` 的子类型），结果类型是 `X`，否则是 `Y`"。第 03 篇写的穷尽性检查其实已经用到了条件类型的近亲——`never` 判断，这一篇正式展开。

## 分布式条件类型：联合类型会被逐个分发

条件类型有一个不太直观、但在类型体操里极其重要的行为：**当被判断的类型参数 `T` 是一个"裸类型参数"（没有被数组、元组、Promise 等结构包裹），且调用时传入的是一个联合类型，TS 会把这个联合类型拆开，对每个成员分别执行一次条件判断，再把所有结果重新联合起来**——这叫分布式条件类型（distributive conditional type）。

```ts
type MyExtract<T, U> = T extends U ? T : never;

type Mixed = string | number | boolean;
type OnlyStrings = MyExtract<Mixed, string>; // 分布式展开：string | number | boolean 逐个判断，只留下 string
const onlyStringsExample: OnlyStrings = "kept";
```

真实输出：

```text
onlyStringsExample=kept
```

`MyExtract<Mixed, string>` 展开时，TS 并不是把整个 `Mixed`（`string | number | boolean`）作为一个整体去判断"是否可以赋值给 `string`"，而是拆成三次独立判断：`string extends string ? string : never`（结果 `string`）、`number extends string ? number : never`（结果 `never`）、`boolean extends string ? boolean : never`（结果 `never`），再把三个结果联合起来：`string | never | never`。`never` 在联合类型里会被自动"吸收"（联合一个 `never` 等于什么都没加），所以最终结果化简为单纯的 `string`。这正是 TS 内置工具类型 `Extract<T, U>` 的实现原理——`MyExtract` 就是它的手写版本。

## 用 `[T] extends [U]` 阻止分布

分布式行为不是任何时候都想要——有时候你恰恰想把联合类型当成一个**整体**去判断，而不是逐个成员分发。把类型参数包进一个单元素元组（`[T] extends [U]`），就能关闭分布式行为，因为这时候被判断的不再是"裸类型参数" `T`，而是"包含 `T` 的元组类型" `[T]`：

```ts
type IsStringNonDistributive<T> = [T] extends [string] ? true : false;
type MixedIsString = IsStringNonDistributive<Mixed>; // Mixed 整体不满足 extends string，结果是 false

type IsStringDistributive<T> = T extends string ? true : false;
type EachIsString = IsStringDistributive<Mixed>; // 分布式展开后是 false | true | false，联合化简为 boolean
```

真实输出：

```text
mixedIsStringExample=false
eachIsStringExample=true
```

`IsStringNonDistributive<Mixed>` 里，`[T]` 和 `[string]` 都是"包裹过"的元组类型，TS 不会拆开 `Mixed` 这个联合类型，而是直接判断"`[string | number | boolean]` 这个元组类型，能不能赋值给 `[string]` 这个元组类型"——显然不能（`Mixed` 本身包含了 `number`/`boolean`，不是纯 `string`），所以结果直接是 `false`，这才是"判断整个联合类型是不是 string"这个问题的正确答案。

对比 `IsStringDistributive<Mixed>`：因为 `T extends string` 里的 `T` 是裸类型参数，分布式行为会把 `Mixed` 拆开逐个判断——`string extends string` 是 `true`，`number extends string` 是 `false`，`boolean extends string` 是 `false`——三个结果联合成 `true | false | false`，化简后就是 `boolean` 类型。示例里把 `eachIsStringExample` 声明为 `EachIsString`（也就是 `boolean`）并赋值 `true` 能通过检查，恰好说明了分布式版本给出的不是"`Mixed` 是不是 string"这一个确定答案，而是"每个成员各自是不是 string"的逐个判断结果重新联合——这两种写法回答的是完全不同的问题，混淆它们是类型体操里常见的错误来源。**记住这条经验法则：想要"逐个成员判断"用裸类型参数，想要"整体判断"就用 `[T] extends [U]` 包一层元组。**

## 模板字面量类型：在类型层面拼字符串

模板字面量类型的语法和 JS 的模板字符串几乎一样，区别是它工作在类型层面：如果模板里代入的是字符串字面量联合类型，TS 会生成"所有组合"的字面量类型联合。

```ts
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";
type Resource = "users" | "orders";
type Route = `${HttpMethod} /${Resource}`; // "GET /users" | "GET /orders" | "POST /users" | ...

const route: Route = "GET /users";
// const badRoute: Route = "PATCH /users"; // 如果取消注释会编译报错：PATCH 不在 HttpMethod 里

function buildRoute<M extends HttpMethod, R extends Resource>(method: M, resource: R): `${M} /${R}` {
	return `${method} /${resource}`;
}
const built = buildRoute("POST", "orders");
```

真实输出：

```text
route=GET /users
built=POST /orders
```

`Route` 类型由 `HttpMethod`（4 个成员）和 `Resource`（2 个成员）通过模板字面量拼接而成，TS 会把两个联合类型的所有组合都展开，一共生成 8 个字面量类型的联合（`"GET /users"`、`"GET /orders"`、`"POST /users"` ……）。`route` 变量的值必须是这 8 种字符串之一，写成其他字符串（比如方法名拼错、资源名拼错）都会在编译期报错——这比单纯用 `string` 类型精确得多，能在编译期堵住"路由字符串拼写错误"这类问题。

`buildRoute` 更进一步：它的返回类型 `` `${M} /${R}` `` 直接引用了函数自己的类型参数 `M` 和 `R`。调用 `buildRoute("POST", "orders")` 时，TS 从实参推断出 `M` 是字面量类型 `"POST"`、`R` 是字面量类型 `"orders"`，代入模板后返回类型精确到字面量 `"POST /orders"`——这种"返回类型由入参的具体值决定"的能力，是模板字面量类型和泛型结合后特有的，在设计类型安全的路由表、事件名、CSS 属性名这类"字符串里编码了结构信息"的场景里很常用。

## 小结

映射类型 `[K in keyof T]` 遍历一个类型的所有属性名，逐个生成新属性，配合 `?`/`readonly` 修饰符和自定义的值类型表达式，能重新实现 `Partial`/`Readonly`/`Pick`/`Record` 这些内置工具类型。条件类型 `T extends U ? X : Y` 在类型层面做分支判断；当被判断的类型参数是"裸类型参数"且传入联合类型时，会触发分布式条件类型，把联合类型拆开逐个判断再重新联合，这是很多内置工具类型（比如 `Extract`）的实现基础；用 `[T] extends [U]` 把类型参数包进元组能阻止分布、转而对整个联合类型做一次性判断。模板字面量类型能在类型层面拼接字符串字面量联合类型，配合泛型函数可以让返回类型随着具体入参精确到字面量。下一篇是"类型体操实战"，会把这三种能力（映射、条件、模板字面量）叠加起来解决真实场景的问题。
