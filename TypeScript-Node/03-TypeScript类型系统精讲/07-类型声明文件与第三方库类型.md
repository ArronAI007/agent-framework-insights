# 类型声明文件与第三方库类型

> 这一篇是第 03 章的收尾。前面六篇讲的都是"怎么用 TS 自己的类型系统描述类型"，但真实项目里你迟早会依赖某个没有类型、甚至压根没打算支持 TS 的第三方 JS 库——这时候需要的不是类型体操，而是知道 `.d.ts` 文件到底是什么、TS 怎么找到它、以及怎么给一个"裸" JS 库手写一份类型声明。

## 学习目标

- 理解 `.d.ts` 文件的作用：只声明类型、不包含任何运行时代码
- 知道 `declare module`/`declare function` 的用法
- 了解 DefinitelyTyped（`@types/*`）生态解决的是什么问题
- 学会给一个没有类型的第三方 JS 库手写声明文件
- 理解同名 `.js` 源文件和 `.d.ts` 声明文件共存时，TS 是怎么把两者配对的

## `.d.ts` 文件的作用

`.d.ts`（declaration）文件只包含类型声明，不包含任何可执行的运行时代码——它不会被编译成 JS 输出，纯粹是给 TS 编译器和编辑器看的"类型说明书"。当你 `npm install` 一个包，`import` 它的某个函数时，TS 需要知道这个函数的参数类型、返回类型才能做类型检查、给出自动补全——这些信息要么来自这个包自带的 `.d.ts` 文件，要么来自你（或社区）额外提供的 `.d.ts` 文件，要么就是没有类型信息，TS 只能把它当成 `any` 处理（如果开了 `noImplicitAny`，这种情况还会直接报错，除非显式豁免）。

`declare` 关键字是 `.d.ts` 文件里的核心语法：`declare function foo(x: number): string` 只声明"存在一个叫 `foo` 的函数，签名长这样"，不需要（也不允许）给出函数体——因为真正的实现代码在别处（通常是对应的 `.js` 文件），`.d.ts` 只是把这份实现的类型"外挂"上去。类似地 `declare module "some-package" { ... }` 用来声明"某个模块（通常是一个没有自带类型的 npm 包）导出了哪些东西"，常见于给第三方库补类型声明。

## DefinitelyTyped（`@types/*`）生态

很多广泛使用的 JS 库本身是用纯 JS 写的、没有自带类型声明，社区维护了一个叫 [DefinitelyTyped](https://github.com/DefinitelyTyped/DefinitelyTyped) 的仓库，专门收录第三方库的类型声明文件，发布到 npm 上时统一带 `@types/` 前缀——比如给 `lodash` 补类型就装 `@types/lodash`，给 `express` 补类型就装 `@types/express`。这些包只包含 `.d.ts` 文件，不包含任何运行时代码，装上之后 TS 会自动找到对应的类型声明，`import` 原始的库（`lodash`、`express`）时就能获得完整的类型提示，即便这些库自己的源码是纯 JS。这也是为什么第 00-02 章安装依赖时，有的包需要额外装一个 `@types/xxx`（比如这门课本身依赖的 `@types/node`，给 Node.js 内置模块提供类型声明），有的不需要——取决于这个库本身是用 TS 写的（自带 `.d.ts`）还是纯 JS 写的（需要单独找社区维护的 `@types` 包，或者干脆没人维护、需要自己手写）。

## 给一个没有类型的遗留 JS 库手写声明文件

真实场景中，你可能会遇到一个内部维护的老工具库，纯 JS 写的，DefinitelyTyped 上也没人给它写过类型——这时候就需要自己动手。示例用一个假想的"格式化货币"函数模拟这种情况：

```js
// legacy-lib.js —— 没有任何类型信息，用 CommonJS 的 module.exports 导出
function formatCurrency(amount, currency) {
	if (typeof amount !== "number" || Number.isNaN(amount)) {
		throw new TypeError("amount 必须是合法数字");
	}
	return `${amount.toFixed(2)} ${currency}`;
}

module.exports = { formatCurrency };
```

```ts
// legacy-lib.d.ts —— 手写的声明文件，给上面这个纯 JS 函数外挂类型
export declare function formatCurrency(amount: number, currency: string): string;
```

```ts
// consumer.ts —— 像使用一个原生 TS 模块一样使用它
import { formatCurrency } from "./legacy-lib.js";

console.log(`formatCurrency(1999, "CNY") -> ${formatCurrency(1999, "CNY")}`);
console.log(`formatCurrency(9.9, "USD") -> ${formatCurrency(9.9, "USD")}`);
```

真实输出：

```text
formatCurrency(1999, "CNY") -> 1999.00 CNY
formatCurrency(9.9, "USD") -> 9.90 USD
```

`legacy-lib.d.ts` 里的 `export declare function formatCurrency(amount: number, currency: string): string` 精确声明了参数和返回值类型——`declare` 表明这只是类型声明，没有函数体；`export` 让 `consumer.ts` 能用 `import { formatCurrency } from "./legacy-lib.js"` 这种具名导入语法拿到它。运行时执行的是 `legacy-lib.js` 里 `module.exports` 导出的那个真实函数（本例的这个子目录额外放了一份 `package.json`，把 `type` 设为 `"commonjs"`，这样 `module.exports` 才能在运行时正常工作——课程主项目整体是 `"type": "module"`，但 Node 支持按目录就近覆盖模块类型，这也是"新项目全用 ESM、个别遗留模块保留 CommonJS"这种混合场景的标准做法）。类型检查阶段读的是 `legacy-lib.d.ts`，两者各司其职：**`.js` 负责"怎么跑"，`.d.ts` 负责"长什么样"**。

## 类型不匹配时，`tsc` 的真实报错

给 `formatCurrency` 补上类型声明之后，它就不再是一个"传什么都不会报错"的黑盒函数——传错参数类型会在编译期直接暴露，这是本节要验证的地方：临时把调用改成传字符串而不是数字，跑一次 `tsc --noEmit`：

```ts
formatCurrency("1999", "CNY"); // amount 参数被声明为 number，这里传的是 string
```

真实报错（用 `tsc --noEmit` 跑出来的原始信息）：

```text
examples/03-TypeScript类型系统精讲/07-类型声明文件与第三方库类型/consumer.ts(9,16): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
```

如果没有 `legacy-lib.d.ts` 这份声明文件，`formatCurrency` 对 TS 来说就是彻底的"未知"（在 `noImplicitAny` 关闭的项目里会被当成隐式 `any`，这门课的 `strict` 模式下会直接报错说找不到模块的类型声明），`formatCurrency("1999", "CNY")` 这种参数类型错误只能在运行时才会暴露——而且运行时暴露的方式还未必是直接报错，取决于库内部有没有做参数校验，很可能是悄悄产生一个错误结果，过很久才在别的地方被发现是这里传错了类型。补上声明文件之后，这类错误在保存文件、`tsc --noEmit` 跑起来的那一刻就会被抓住，错误信息精确到"哪个文件哪一行哪一列、期望什么类型、实际传了什么类型"——这正是给无类型第三方库手写声明文件最直接的收益。

## 同名 `.js` 源文件与 `.d.ts` 声明文件共存时的解析规则

TS 在 `NodeNext`/`Node16` 这类现代模块解析策略下，对同一目录下"文件名相同、扩展名分别是 `.js` 和 `.d.ts`"的一对文件有专门的配对规则：`import ... from "./legacy-lib.js"` 里写的是 `.js` 后缀（这是 ESM 规范要求的——ESM 的相对导入路径必须带上真实的文件扩展名，不能像 CommonJS 那样省略），但 TS 在做类型检查时，会自动去找同目录下文件名去掉 `.js` 后缀、加上 `.d.ts` 后缀的文件（也就是 `legacy-lib.d.ts`），把它的类型声明和 `legacy-lib.js` 的运行时代码"绑定"在一起——写 `import` 语句时看到的是 `.js`，类型检查阶段实际生效的类型却来自 `.d.ts`。这条配对规则不需要任何额外配置，只要两个文件同名（仅扩展名不同）且在同一目录下，TS 就会自动识别；这也是为什么手写声明文件时，`.d.ts` 的文件名必须和它要描述的 `.js`/`.mjs`/`.cjs` 文件严格对应,命名对不上，TS 就找不到这份声明,只能把对应的导入当成没有类型信息处理。

## 小结

`.d.ts` 文件只包含类型声明、不含运行时代码，`declare` 关键字用来声明"这里存在什么，但实现在别处"。DefinitelyTyped（`@types/*`）是社区维护的第三方库类型声明仓库，解决"库本身是纯 JS、但你想要类型提示"这个问题。给没有类型的遗留 JS 库手写声明文件，只需要一份和源文件同名的 `.d.ts`，把参数和返回值类型声明清楚，之后这个库在 TS 里用起来就和原生 TS 模块几乎没有区别——包括参数类型传错会在编译期就报错，而不是留到运行时才暴露。TS 会自动把同目录下同名的 `.js` 源文件和 `.d.ts` 声明文件配对，`import` 语句里写 `.js` 后缀是 ESM 规范要求，类型检查阶段实际使用的是配对的 `.d.ts`。
