# 基础类型与类型推断

> 从这一篇开始进入本课程分量最重的一章：TypeScript 类型系统。你已经会写 TS 的语法（第 02 章），但类型系统是另一回事——它决定了 TS 到底能帮你挡住多少 bug，以及会不会在你没意识到的地方悄悄放水。这一篇先把地基打牢：原始类型怎么分、`any` 和 `unknown` 差在哪、字面量类型和 `as const`、类型推断到底在什么时候会把类型"变宽"或"变窄"。

## 学习目标

- 知道 TS 的原始类型有哪些，以及它们和运行时 `typeof` 的对应关系
- 理解 `any` 和 `unknown` 的本质区别，以及为什么生产代码里应该几乎不用 `any`
- 理解字面量类型（literal type）是什么，`as const` 如何利用它
- 搞清楚类型宽化（widening）规则：`let` 为什么会丢失字面量类型，`const` 为什么不会
- 理解上下文类型推断（contextual typing）：为什么回调参数经常不需要手写类型注解

## 原始类型一览

TS 的原始类型和 JS 的运行时类型是一一对应的，`typeof` 在运行时能拿到几种值，TS 在类型层面就有几种对应的类型：

| TS 类型 | 对应的运行时 `typeof` 结果 | 说明 |
| --- | --- | --- |
| `string` | `"string"` | 字符串 |
| `number` | `"number"` | 双精度浮点数，TS 不区分整数和浮点数 |
| `boolean` | `"boolean"` | `true` / `false` |
| `bigint` | `"bigint"` | 任意精度整数，字面量写作 `123n` |
| `symbol` | `"symbol"` | 唯一标识符，常用作对象属性的"隐藏"键 |
| `undefined` | `"undefined"` | 变量已声明但未赋值 |
| `null` | `"object"`（这是 JS 的历史遗留 bug，`typeof null` 永远是 `"object"`） | 显式的"空值" |

这几个类型本身没什么好展开的——真正容易踩坑的是 `null`/`undefined` 在 `strict` 模式下如何参与联合类型（下一篇会细讲可辨识联合），以及 `any`/`unknown` 这对经常被混用的类型。

## `any` vs `unknown`：几乎总该用 `unknown`

`any` 和 `unknown` 都表示"这个值的类型我们暂时不知道"，但它们在**能对这个值做什么**这件事上完全相反：

- `any` 会**关闭**这个值上的所有类型检查。一旦一个值是 `any`，你可以对它调用任意方法、访问任意属性、把它赋值给任意类型的变量——TS 完全不会拦你，错误会一路传播到运行时才爆炸。更危险的是 `any` 有"传染性"：`any` 参与的任何表达式，结果类型通常也会变成 `any`，相当于在类型系统里开了个洞，洞会顺着数据流蔓延。
- `unknown` 同样表示"类型未知"，但 TS 会**强制你先收窄类型**才能使用它——不做任何检查就调用方法或访问属性，编译期直接报错。

```ts
function decodeWithAny(payload: any): string {
	// payload.toUpperCase() 即便 payload 实际上是个 number，这里也不会报错，
	// 只会在真正运行到这一行时抛出运行时异常。
	return payload.toUpperCase();
}

function decodeWithUnknown(payload: unknown): string {
	if (typeof payload === "string") {
		// 进入这个分支后，TS 已经把 payload 的类型从 unknown 收窄成 string
		return payload.toUpperCase();
	}
	if (typeof payload === "number") {
		return payload.toFixed(2);
	}
	return String(payload);
}
```

真实输出：

```text
decodeWithAny("boom") -> BOOM
decodeWithUnknown(42) -> 42.00
decodeWithUnknown("boom") -> BOOM
```

从签名上看，`decodeWithAny` 和一个没有类型注解的 JS 函数没有本质区别——`any` 参数拿到手就是"随便用"，编译器完全没帮你做任何事。`decodeWithUnknown` 则强制调用方（也就是函数内部的你自己）在使用前先用 `typeof` 做**类型收窄（narrowing）**，收窄之后 TS 才会在对应分支里把 `payload` 当成具体类型对待。这就是为什么 `unknown` 几乎总是比 `any` 更合适的选择：它保留了"类型确实未知"这个诚实的信号，同时强制你处理这种不确定性，而不是假装什么都知道。`any` 应该被当成极少数场景下的"逃生舱"（比如迁移遗留 JS 代码的过渡期），而不是默认选项。

## 字面量类型与类型宽化（widening）

TS 里，字符串、数字、布尔值不仅可以作为"类型"存在（比如 `string`），单个具体的值本身也可以是一个类型——这就是**字面量类型（literal type）**。`"hello"` 既是一个值，也可以是一个只包含这一个值的类型。

字面量类型在 `let` 和 `const` 声明时的推断结果不一样：

```ts
let widenedGreeting = "hello"; // 推断类型：string
const literalGreeting = "hello"; // 推断类型：不是 string，而是 "hello" 这个字面量类型

widenedGreeting = "world"; // 合法，widenedGreeting 的类型是 string
// literalGreeting = "world"; // 如果取消注释会编译报错：不能将类型“"world"”分配给类型“"hello"”
```

真实输出：

```text
widenedGreeting=world, literalGreeting=hello
```

这就是**类型宽化（widening）**：`let widenedGreeting = "hello"` 里，TS 知道 `widenedGreeting` 之后随时可能被重新赋值成任何字符串，如果把它的类型死死固定成字面量类型 `"hello"`，那连 `widenedGreeting = "world"` 这种最正常的操作都会报错，这明显不是我们想要的行为。所以 TS 会把字面量类型主动"放宽"到它所属的基础类型 `string`——这就是"宽化"这个名字的由来。而 `const literalGreeting = "hello"` 不存在"之后被重新赋值"的可能（`const` 变量赋值后不能再变），TS 就没有理由做这次放宽，直接保留最精确的字面量类型 `"hello"`。

这条规则可以总结成一句话记住：**`let` 推断出的类型会被宽化成基础类型，`const` 推断出的类型会保留字面量类型的精确度**。理解这一点对读懂后面泛型推断、函数重载选择哪个签名都有帮助——TS 的很多"意料之外"的推断结果，根源都是宽化规则在起作用。

## `as const`：把字面量类型"钉"住，把数组变成只读元组

有时候即便用的是 `let`，或者面对的是数组/对象字面量，你也想让 TS **不要**做宽化，保留最精确的字面量类型——这时候就该用 `as const`（const 断言）。

```ts
const mutableRoles = ["admin", "editor", "viewer"]; // 推断类型：string[]

const readonlyRoles = ["admin", "editor", "viewer"] as const;
// readonlyRoles.push("guest"); // 如果取消注释会编译报错：类型“readonly ["admin", "editor", "viewer"]”上不存在属性“push”
// readonlyRoles[0] = "editor"; // 如果取消注释会编译报错：无法分配到 "0" ，因为它是只读属性

type Role = (typeof readonlyRoles)[number]; // "admin" | "editor" | "viewer"：从值反推出联合类型，避免手写重复的类型定义
const currentRole: Role = "editor"; // 合法：属于联合类型里的一员
```

真实输出：

```text
mutableRoles=[admin,editor,viewer], readonlyRoles=[admin,editor,viewer], currentRole=editor
```

注意 `mutableRoles` 和 `readonlyRoles` 运行时的值完全一样（都是 `["admin", "editor", "viewer"]`），`as const` 不改变任何运行时行为，它纯粹是给 TS 编译器看的标注。但类型层面差别很大，`as const` 同时做了三件事：

1. **数组变成只读元组类型**：`string[]`（长度可变、顺序无关紧要）变成 `readonly ["admin", "editor", "viewer"]`（固定长度为 3，每个位置的类型都精确固定）。
2. **每个元素的类型从基础类型收窄成字面量类型**：`string` 变成 `"admin"` / `"editor"` / `"viewer"` 各自对应的字面量类型。
3. **数组本身变成只读**：`push`/`pop`/下标赋值这些会修改数组的操作，在编译期直接报错。

`type Role = (typeof readonlyRoles)[number]` 这一行是个很实用的惯用法：用 `typeof` 拿到 `readonlyRoles` 这个值的类型（也就是那个只读元组类型），再用 `[number]` 索引访问语法取出"元组里所有元素的类型的联合"，得到 `"admin" | "editor" | "viewer"`。这样就只需要维护 `readonlyRoles` 这一份运行时数据（比如用来做下拉框选项、遍历校验等），类型是从数据自动推导出来的，不需要额外手写一份重复的 `type Role = "admin" | "editor" | "viewer"`——第 05 篇会更系统地讲这类"从值推导类型"的技巧。

## 上下文类型推断（contextual typing）

到目前为止的例子都是"从值推断类型"，但 TS 还有一种方向相反的推断：**根据变量/参数被使用的位置（上下文），反过来推断出它应该是什么类型**，最常见的场景就是回调函数的参数。

```ts
const scores = [88, 92, 76, 100];
const grades = scores.map((score) => (score >= 90 ? "A" : score >= 80 ? "B" : "C"));
const doubled = scores.map((score) => score * 2);
```

真实输出：

```text
grades=[B,A,C,A]
doubled=[176,184,152,200]
```

`scores` 的类型是 `number[]`，数组的 `.map()` 方法签名大致是 `map<U>(callback: (value: T, index: number, array: T[]) => U): U[]`。当我们调用 `scores.map((score) => ...)` 时，TS 从 `scores` 的类型 `number[]` 知道 `T` 是 `number`，于是**反推**出这里传入的回调函数的参数 `score` 应该是 `number` 类型——这就是"上下文类型推断"：`score` 的类型不是从它自己的声明推断出来的（它根本没有类型注解），而是从"它被用在 `.map()` 的回调参数这个上下文位置"推断出来的。

这也是为什么 TS 代码里，回调函数的参数通常不需要手写类型注解，代码依然能类型安全——`score * 2` 如果误写成 `score.toUpperCase()`，TS 一样会在编译期报错，因为上下文推断已经确定了 `score` 是 `number`。同样的机制也适用于事件监听器回调、`Promise.then()` 回调、数组的 `.filter()`/`.reduce()` 等场景，本质都是"函数签名的参数类型位置"给出了足够的类型信息，让 TS 不需要你重复标注。

## 小结

TS 的原始类型和运行时 `typeof` 基本一一对应，其中 `null` 由于历史遗留原因 `typeof` 结果是 `"object"`。`any` 关闭类型检查且有传染性，`unknown` 强制先收窄再使用——生产代码里遇到"类型未知"的场景应该默认选 `unknown`。字面量类型让单个具体值也能作为类型存在，`let` 声明会把字面量类型宽化成基础类型，`const` 声明会保留字面量类型的精确度；`as const` 可以在不改变运行时行为的前提下，把字面量类型"钉"住并把数组变成只读元组，配合 `typeof ... [number]` 能从一份运行时数据反推出对应的联合类型，避免维护两份重复定义。上下文类型推断让回调函数的参数在很多场景下不需要手写类型注解，TS 会根据调用点的类型信息自动反推。下一篇进入接口、类型别名和联合/交叉类型，会用到这一篇打下的推断基础。
