# 接口、类型别名与联合交叉类型

> `interface` 和 `type` 该用哪个？很多从其他语言过来的人会下意识地把 `interface` 当成 Java/C# 里的接口、把 `type` 当成"随便起个别名"，但 TS 里这两者的边界和你熟悉的语言完全不是一回事。这一篇讲清楚它们的真实差异，再讲 TS 里最重要的建模工具之一——联合类型和可辨识联合模式。

## 学习目标

- 理解 `interface` 和 `type` 的实际差异：声明合并、可扩展性
- 掌握联合类型（`|`）和交叉类型（`&`）的语义
- 学会用可辨识联合（discriminated union）给"一组互斥的形状"建模
- 学会用 `never` 做穷尽性检查（exhaustiveness check），让编译器帮你盯住"新增分支忘记处理"这种 bug

## `interface` vs `type`：声明合并是关键分野

`interface` 和 `type` 在描述对象形状这件事上，能力高度重叠——大多数情况下两者可以互换。但有一个能力上的本质差异：**`interface` 支持声明合并（declaration merging），`type` 不支持**。

```ts
interface Window {
	appVersion: string;
}
interface Window {
	buildTime: string;
}
// 合并后的 Window 同时拥有 appVersion 和 buildTime 两个属性
const appWindow: Window = { appVersion: "1.0.0", buildTime: "2026-09-16" };
console.log(`appWindow=${JSON.stringify(appWindow)}`);
```

真实输出：

```text
appWindow={"appVersion":"1.0.0","buildTime":"2026-09-16"}
```

同名的 `interface Window` 声明了两次，TS 不会报错，而是自动把两次声明的成员**合并**成一个接口——最终 `Window` 同时要求 `appVersion` 和 `buildTime` 两个属性。如果把两个 `interface` 换成 `type Config = { a: string }` 和 `type Config = { b: string }`，第二次声明会直接编译报错："标识符 Config 重复"——`type` 别名一旦声明，这个名字就被"用掉"了，不能再声明第二次，更谈不上合并。

声明合并看起来是个冷知识，但它是很多第三方库"模块扩展"能力的基础：比如给 Express 的 `Request` 类型加一个自定义字段、给全局 `Window` 对象加一个第三方 SDK 挂载的属性，本质都是在利用 `interface` 的声明合并——在你自己的代码里补一份同名 `interface` 声明，TS 就会把新字段合并进去，不需要修改库的源码或类型定义。这也是社区里"能用 `interface` 描述对象形状就优先用 `interface`，需要联合类型/交叉类型/元组这些 `interface` 表达不了的形状才用 `type`"这条经验法则的来源——不是因为 `interface` "更正确"，而是因为保留声明合并这个扩展点，在写库或大型项目时价值更高。

## 联合类型（`|`）与交叉类型（`&`）

```ts
type Id = string | number; // 联合类型：值只要满足其中一种即可
type WithTimestamps = { createdAt: string } & { updatedAt: string }; // 交叉类型：必须同时满足两边的形状

const numericId: Id = 42;
const stringId: Id = "user_42";
const record: WithTimestamps = { createdAt: "2026-01-01", updatedAt: "2026-09-16" };
```

真实输出：

```text
numericId=42, stringId=user_42, record={"createdAt":"2026-01-01","updatedAt":"2026-09-16"}
```

**联合类型（`|`）** 表示"或"：一个值只要满足联合类型里任意一个成员的形状即可。`Id` 可以是 `string`，也可以是 `number`，二者选一。联合类型在集合论意义上是**并集**——`Id` 类型包含的值，是"所有 `string`"和"所有 `number`"的并集，因此联合类型的成员越多，这个类型能接受的值范围**越大**。

**交叉类型（`&`）** 表示"且"：一个值必须**同时**满足所有成员的形状。`WithTimestamps` 要求一个值既有 `createdAt` 又有 `updatedAt`。交叉类型是集合论意义上的**交集**——对于对象类型来说，交叉的直观效果通常是"把多个类型的字段合并到一起"，成员越多，要求越苛刻，能满足条件的值范围**越小**。这一点经常和"联合类型成员越多越宽松"搞反，容易搞混，记忆的关键是：`|` 是"任选其一"，`&` 是"全部都要"。

## 可辨识联合（discriminated union）：给"互斥的形状"建模

真实业务里经常会遇到"这个值可能是几种形状之一，具体是哪种要看某个字段"的场景——比如一个几何图形可能是圆形、正方形或三角形，不同形状需要的字段完全不同。这正是**可辨识联合**（也叫标签联合、tagged union）要解决的问题：让联合类型的每个成员都带一个共同的字面量类型字段（约定俗成叫 `kind` 或 `type`），TS 就能根据这个字段的值，把联合类型精确收窄到某一个具体成员。

```ts
interface Circle {
	kind: "circle";
	radius: number;
}
interface Square {
	kind: "square";
	side: number;
}
interface Triangle {
	kind: "triangle";
	base: number;
	height: number;
}
type Shape = Circle | Square | Triangle;

function area(shape: Shape): number {
	switch (shape.kind) {
		case "circle":
			return Math.PI * shape.radius ** 2;
		case "square":
			return shape.side ** 2;
		case "triangle":
			return (shape.base * shape.height) / 2;
		default: {
			const _exhaustive: never = shape;
			throw new Error(`未处理的 shape.kind: ${JSON.stringify(_exhaustive)}`);
		}
	}
}
```

真实输出：

```text
area(circle) = 12.57
area(square) = 9.00
area(triangle) = 10.00
```

`Circle`、`Square`、`Triangle` 各自都有一个 `kind` 字段，取值分别是字面量类型 `"circle"`、`"square"`、`"triangle"`——注意这里的关键是每个 `kind` 字段的类型都是**具体的字符串字面量**，而不是宽泛的 `string`（如果写成 `kind: string`，三个接口的 `kind` 类型就完全一样，TS 就无法用它来区分成员了）。`Shape` 是这三者的联合类型。

在 `switch (shape.kind)` 的每个 `case` 分支里，TS 会自动把 `shape` 的类型从整个联合类型 `Shape`**收窄**到匹配那个 `kind` 值的具体成员——在 `case "circle":` 分支里，`shape` 的类型被收窄成 `Circle`，这时候访问 `shape.radius` 是合法的，但如果误写成 `shape.side`（`Square` 才有的字段），会直接编译报错。这就是可辨识联合最大的价值：**不需要任何类型断言，TS 单靠一个字段的字面量值就能精确推断出当前分支里值的完整形状**。

## 用 `never` 做穷尽性检查（exhaustiveness check）

`default` 分支里的 `const _exhaustive: never = shape;` 是一个很实用的惯用法，叫**穷尽性检查**。它利用的是：如果 `switch` 已经处理了 `Shape` 联合类型的所有成员（`"circle"`、`"square"`、`"triangle"`），那么走到 `default` 分支时，TS 能推断出 `shape` 已经不可能是任何一种已知类型——这种"不可能出现的类型"在 TS 里就是 `never`。`never` 类型的变量只能被赋值 `never` 类型的值，所以 `const _exhaustive: never = shape` 在"确实穷尽了所有分支"的情况下能顺利通过类型检查。

穷尽性检查真正的价值体现在**未来有人往 `Shape` 联合类型里新增一个成员，却忘记在 `switch` 里补上对应的 `case` 分支**这种场景——这是本篇设计要求必须真实验证的地方：临时删掉 `"triangle"` 这个 `case` 分支，跑一次 `tsc --noEmit`：

```ts
function area(shape: Shape): number {
	switch (shape.kind) {
		case "circle":
			return Math.PI * shape.radius ** 2;
		case "square":
			return shape.side ** 2;
		// case "triangle" 被临时删掉
		default: {
			const _exhaustive: never = shape;
			throw new Error(`未处理的 shape.kind: ${JSON.stringify(_exhaustive)}`);
		}
	}
}
```

真实报错（用 `tsc --noEmit` 跑出来的原始信息）：

```text
examples/03-TypeScript类型系统精讲/02-接口类型别名与联合交叉类型/union-intersection.ts(57,10): error TS2322: Type 'Triangle' is not assignable to type 'never'.
```

删掉 `"triangle"` 分支之后，走到 `default` 分支时，`shape` 剩下的可能类型不再是"空"，而是还没被处理掉的 `Triangle`——因为 `Circle` 和 `Square` 已经在前两个 `case` 里被排除，`Triangle` 是唯一没被排除的成员。这时候 `shape` 在 `default` 分支里的类型是 `Triangle`，而不是 `never`，把 `Triangle` 类型的值赋给声明为 `never` 的 `_exhaustive` 就会触发上面这条 `TS2322` 报错，明确指出"有一个 `Triangle` 类型的值没有被处理"。这正是穷尽性检查的意义：**它把"忘记处理新增的联合类型成员"从一个只有运行时才会暴露的 bug，变成了编译期就会失败的错误**——只要你新增一个形状却忘了补分支，`tsc` 就会在这一行报错，而不是等到线上某个用户传了个三角形，代码默默走到 `default` 分支抛出一个语焉不详的运行时异常。

## 小结

`interface` 和 `type` 的核心差异在于 `interface` 支持声明合并、`type` 不支持——这也是社区惯用法"优先 `interface`、必要时才用 `type`"的真正原因。联合类型（`|`）是并集、代表"任选其一"，交叉类型（`&`）是交集、代表"全部都要"，二者语义相反，成员数量对"接受范围"的影响也相反。可辨识联合用一个共同的字面量类型字段（如 `kind`）让 TS 能在 `switch`/`if` 分支里精确收窄联合类型到具体成员，是给"互斥形状"建模的标准做法。穷尽性检查（在 `default` 分支里把值赋给 `never` 类型变量）能把"新增联合类型成员却忘记处理"变成编译期错误，是可辨识联合模式里值得养成的一个习惯。下一篇进入泛型编程——你会发现泛型和这一篇的联合/交叉类型经常配合使用，一起构建更灵活的类型。
