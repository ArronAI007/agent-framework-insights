# 值类型、引用类型与相等性

> 这一章开始进入 JS/TS 语言本身。第一篇就啃一个几乎所有语言都有、但 JS 的坑特别多的话题：值 vs 引用、`===`/`==` 的区别、`Object.is` 和 `===` 那两处容易被忽略的差异，以及浅拷贝导致的别名 bug。

## 学习目标

- 理解原始值按值复制、对象按引用复制的行为差异
- 说清楚 `===` 和 `==` 的本质区别，以及为什么几乎总该用 `===`
- 掌握 `Object.is` 与 `===` 的两处已知差异：`NaN` 和 `+0`/`-0`
- 识别浅拷贝导致的别名（aliasing）bug，并用 `structuredClone` 做真正的深拷贝

## 原始值 vs 对象引用

JS 的类型分成两大类：**原始值**（`number`/`string`/`boolean`/`null`/`undefined`/`bigint`/`symbol`）和**对象**（普通对象、数组、函数等一切非原始值）。区别不在语法层面，而在**赋值语义**上：

```ts
let a = 1;
let b = a;
b = 2;
console.log(`原始值：a=${a}, b=${b}`);
```

真实输出：

```text
原始值：a=1, b=2
```

`b = a` 复制的是**值本身**，`a` 和 `b` 从此互不相干。但对象完全不同——变量里存的从来不是对象本体，而是对这个对象的**引用**：

```ts
const objA = { count: 1 };
const objB = objA; // 没有发生拷贝，objB 只是 objA 的别名
objB.count = 2;
console.log(`对象引用：objA.count=${objA.count}, objB.count=${objB.count}`);
```

真实输出：

```text
对象引用：objA.count=2, objB.count=2
```

`const objB = objA` 只是让 `objB` 指向和 `objA` 完全相同的那块内存，之后通过任意一个变量修改对象内容，另一个变量看到的都是同一份修改。这一点如果你写过 Python，会觉得很熟悉（Python 里的列表/字典赋值同理）；如果你更习惯 Go 里"结构体默认按值传递"的心智，需要格外注意 JS 对象类型永远是引用语义，没有"按值传递结构体"这回事。

## `===` vs `==`

```ts
function looseEquals(x: unknown, y: unknown): boolean {
	return x == y;
}
function strictEquals(x: unknown, y: unknown): boolean {
	return x === y;
}
console.log(`1 === "1" -> ${strictEquals(1, "1")}`);
console.log(`1 == "1" -> ${looseEquals(1, "1")}`);
```

真实输出：

```text
1 === "1" -> false
1 == "1" -> true
```

`===`（严格相等）不做任何类型转换：**类型不同直接返回 `false`**，类型相同再比较值。`==`（宽松相等）在类型不同的时候会先按一套相当复杂的规则做隐式类型转换，再比较——上面例子里 `"1"` 被转换成数字 `1` 之后才和 `1` 比较。这套转换规则本身有大量反直觉的边界情况（比如 `[] == false` 是 `true`，`"" == 0` 是 `true`），社区和几乎所有 lint 规则集的共识是：**除非你明确知道自己需要隐式转换、并且这么写是有意为之，否则永远用 `===`**。TypeScript 项目里 `==` 几乎不应该出现，ESLint 的 `eqeqeq` 规则就是用来强制这一点的。

> 上面代码里用 `strictEquals`/`looseEquals` 这两个接收 `unknown` 参数的辅助函数做中转，是因为 TypeScript 对写死的字面量比较会在编译期直接拦下。直接写 `1 === "1"` 会报 **`TS2367`**："This comparison appears to be unintentional because the types 'number' and 'string' have no overlap."（这处比较类型不同、没有交集，编译器认为大概率是笔误）——这是编译器能提前发现的真错误，但会打断我们想在运行时演示这个行为的目的，所以这里包一层函数绕开静态检查，实际比较逻辑和裸写完全一致。注意这和后面 `NaN === NaN` 触发的 `TS2845` 是两种不同的诊断：`TS2367` 针对的是**两侧类型本身就不重叠**（比如 `number` 和 `string`），`TS2845` 针对的是**同类型下静态可判定恒为 false/true 的比较**（比如 `NaN === NaN`），两者报错文案和触发条件都不一样。

## `Object.is` 与 `===` 的两处差异

`Object.is` 常被简单理解为"更严格的 `===`"，但准确的说法是：**两者几乎完全一样，只有两处已知的差异**。

```ts
console.log(`NaN === NaN -> ${strictEquals(NaN, NaN)}`);
console.log(`Object.is(NaN, NaN) -> ${Object.is(NaN, NaN)}`);
console.log(`Object.is(0, -0) -> ${Object.is(0, -0)}`);
console.log(`0 === -0 -> ${strictEquals(0, -0)}`);
```

真实输出：

```text
NaN === NaN -> false
Object.is(NaN, NaN) -> true
Object.is(0, -0) -> false
0 === -0 -> true
```

**差异一：`NaN`**。`NaN` 是 IEEE 754 浮点数标准里唯一一个"不等于自身"的值，`NaN === NaN` 永远是 `false`——这也是为什么判断一个值是不是 `NaN` 不能写 `x === NaN`，只能用 `Number.isNaN(x)` 或 `Object.is(x, NaN)`。`Object.is` 对这一情况做了修正，认为 `NaN` 和自己是"相同值"。

**差异二：`+0` 与 `-0`**。JS 里 `+0` 和 `-0` 是两个不同的二进制表示，但 `===` 认为它们相等（这是 IEEE 754 的常规行为）；`Object.is` 则能区分出它们不同。这个差异日常业务代码里几乎碰不到，但在一些数值计算、金融相关的边界场景（比如需要区分"结果为零"和"结果从负数方向趋近于零"）里是有意义的。

实践建议：日常判等继续用 `===`；只有在明确需要区分 `NaN`/`+0`/`-0` 这两种边界情况时（比如写一个通用的深度比较函数），才用 `Object.is`。

## 浅拷贝导致的别名 bug

引用语义最容易在"拷贝"场景下引发隐蔽 bug。展开运算符 `...` 做的是**浅拷贝**——只复制容器本身的这一层，容器里的对象元素仍然是原来的引用：

```ts
interface CartItem {
	name: string;
	qty: number;
}

const original: CartItem[] = [{ name: "apple", qty: 1 }];
const shallowCopy = [...original]; // 只拷贝了数组这一层，元素对象仍然是同一个引用
const shallowItem = shallowCopy[0];
if (shallowItem) {
	shallowItem.qty = 99;
}
console.log(`浅拷贝后修改 shallowCopy，original[0].qty 也被改成了 ${original[0]?.qty}`);
```

真实输出：

```text
浅拷贝后修改 shallowCopy，original[0].qty 也被改成了 99
```

`[...original]` 确实创建了一个新数组，但数组里的每个元素——`{ name: "apple", qty: 1 }` 这个对象——地址完全没变。修改 `shallowCopy[0].qty` 实际上修改的是 `original[0]` 指向的同一个对象，导致"明明只改了副本"却"原始数据也变了"这种典型的别名 bug。这类问题在状态管理（比如 Redux/Zustand 的 reducer）、缓存实现里非常常见，往往表现为"莫名其妙的数据污染"，排查起来很痛苦。

顺带一提：上面代码里 `shallowCopy[0]` 需要先判空才能访问 `.qty`，这是因为 `tsconfig.json` 开启了 `noUncheckedIndexedAccess`——数组索引访问的结果类型是 `CartItem | undefined` 而不是 `CartItem`，TypeScript 强制你处理"取不到元素"的可能性，这是上一章 02 篇提到过的严格性选项在这里的实际体现。

## `structuredClone`：真正的深拷贝

要彻底避免别名问题，需要**深拷贝**——递归地为对象和它内部的所有对象都创建全新的副本。现代 JS 运行时（包括 Node.js 17+、所有主流浏览器）原生提供了 `structuredClone`，不需要再手写递归拷贝函数或引入 `lodash.cloneDeep`：

```ts
const deepCopy = structuredClone(original);
const deepItem = deepCopy[0];
if (deepItem) {
	deepItem.qty = 1;
}
console.log(`深拷贝后修改 deepCopy，original[0].qty 仍然是 ${original[0]?.qty}，deepCopy[0].qty=${deepCopy[0]?.qty}`);
```

真实输出：

```text
深拷贝后修改 deepCopy，original[0].qty 仍然是 99，deepCopy[0].qty=1
```

修改 `deepCopy[0].qty` 完全不影响 `original`，因为 `structuredClone` 递归创建了全新的对象树，两者不再共享任何引用。需要知道的限制：`structuredClone` 基于[结构化克隆算法](https://developer.mozilla.org/zh-CN/docs/Web/API/structuredClone)，能处理大部分内置类型（`Date`、`Map`、`Set`、`RegExp`、`ArrayBuffer` 等），但**不能克隆函数、DOM 节点，也不能克隆带 `Symbol` 属性的对象**——遇到这些情况会直接抛出 `DataCloneError`。日常业务数据（JSON 兼容的对象/数组）用它完全够用。

## 小结

原始值按值复制，赋值后两个变量互不影响；对象按引用复制，赋值只是复制了一份指向同一块内存的"指针"。`===` 不做隐式类型转换，`==` 会做，几乎所有场景都该用 `===`。`Object.is` 和 `===` 只有两处已知差异：`Object.is(NaN, NaN)` 是 `true` 而 `NaN === NaN` 是 `false`，`Object.is(0, -0)` 是 `false` 而 `0 === -0` 是 `true`。展开运算符 `...` 只做浅拷贝，容器内的对象元素仍然是共享引用，容易引发别名 bug；需要真正的深拷贝时，用运行时原生提供的 `structuredClone`，不需要手写或引入第三方库。
