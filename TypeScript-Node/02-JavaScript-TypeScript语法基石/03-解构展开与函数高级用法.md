# 解构、展开与函数高级用法

> 解构和展开语法在 JS/TS 代码里几乎无处不在，写起来很直观，但嵌套解构、合并顺序、重载签名这些细节经常被忽略。这一篇把这些细节过一遍，顺带讲清楚可选参数和默认参数在类型层面的真正差异。

## 学习目标

- 掌握数组/对象解构的嵌套写法、默认值、重命名
- 分清剩余参数（收集）和展开运算符（打散）的方向差异
- 理解对象展开合并时"后写的覆盖先写的"这条顺序规则
- 能写出并使用函数重载签名
- 理解可选参数（`?`）和默认参数在类型推断上的差异

## 嵌套解构 + 默认值 + 重命名

```ts
interface UserProfile {
	id: number;
	name: string;
	address?: {
		city: string;
		zip?: string;
	};
}

const profile: UserProfile = {
	id: 1,
	name: "Ada",
	address: { city: "Shanghai" },
};

const {
	name: userName, // 重命名：把 name 解构成 userName
	address: { city, zip = "unknown" } = { city: "N/A" }, // 嵌套解构 + 整体默认值 + 字段默认值
} = profile;
console.log(`userName=${userName}, city=${city}, zip=${zip}`);

const guest: UserProfile = { id: 2, name: "Guest" }; // 没有 address 字段
const {
	address: { city: guestCity } = { city: "N/A" },
} = guest;
console.log(`guestCity=${guestCity}`);
```

真实输出：

```text
userName=Ada, city=Shanghai, zip=unknown
guestCity=N/A
```

这段代码里三种解构技巧叠在一起，容易搞混，拆开看：

- **重命名**：`address: { city, zip = "unknown" }` 里的 `address:` 不是"取出 `address` 属性再重命名"，而是"进入 `address` 这一层继续解构"；`name: userName` 才是纯粹的重命名语法——从 `profile.name` 取值，赋给一个叫 `userName` 的新变量。
- **字段默认值**：`zip = "unknown"` 表示如果解构出来的 `zip` 是 `undefined`（包括属性完全不存在的情况），就用 `"unknown"` 兜底。
- **整体默认值**：`address: { city, zip = "unknown" } = { city: "N/A" }` 末尾那个 `= { city: "N/A" }` 针对的是**整个 `address` 属性**——只有当 `profile.address` 本身是 `undefined` 时才会生效，回退成 `{ city: "N/A" }` 再继续解构。`guest` 对象没有 `address` 字段的例子验证了这一点：`guestCity` 落到了整体默认值里的 `"N/A"`，而不是抛出"无法解构 undefined 的属性"这种运行时错误。这是嵌套解构里最容易被忽略、也最容易在处理"可能不存在的可选字段"时踩坑的地方。

## 展开运算符：数组合并与对象合并

```ts
const left = [1, 2, 3];
const right = [4, 5, 6];
const merged = [...left, ...right];
console.log(`merged=[${merged.join(",")}]`);
```

真实输出：

```text
merged=[1,2,3,4,5,6]
```

数组展开的合并语义很直观：把每个数组"打散"后按顺序拼接。对象展开的合并语义容易让人下意识按"数组那样拼起来"去理解，但实际规则是**属性名冲突时，后写的覆盖先写的**：

```ts
const defaults = { theme: "light", fontSize: 14 };
const overrides = { fontSize: 18 };

const settings = { ...defaults, ...overrides }; // overrides 在后，fontSize 取 18
console.log(`settings=${JSON.stringify(settings)}`);

const reversedOrder = { ...overrides, ...defaults }; // defaults 在后，fontSize 被覆盖回 14
console.log(`reversedOrder=${JSON.stringify(reversedOrder)}`);
```

真实输出：

```text
settings={"theme":"light","fontSize":18}
reversedOrder={"fontSize":14,"theme":"light"}
```

`{ ...defaults, ...overrides }` 里，`fontSize` 先被 `defaults` 的 `14` 写入，再被 `overrides` 的 `18` 覆盖，最终是 `18`；把展开顺序反过来，`fontSize` 就变回了 `14`。这条规则在"合并默认配置和用户自定义配置"这类场景里天天用到——**默认值永远写在前面，用户覆盖值写在后面**，是这类合并代码的标准写法，写反顺序是一个隐蔽但常见的 bug 来源。

## 剩余参数 vs 展开运算符：方向相反的一对语法

同样是 `...`，出现在函数参数位置和出现在函数调用位置，含义完全相反：

```ts
function sum(...nums: number[]): number {
	// nums 是剩余参数：调用方传入的多个实参被收集成一个数组
	return nums.reduce((acc, n) => acc + n, 0);
}
console.log(`sum(...left, ...right)=${sum(...left, ...right)}`);
```

真实输出：

```text
sum(...left, ...right)=21
```

**剩余参数（rest parameter）**出现在函数定义处的参数列表里，作用是"打包"——把调用时传入的、数量不确定的多个实参**收集**成一个数组。**展开运算符（spread operator）**出现在函数调用处的实参列表里，作用是"拆包"——把一个数组**打散**成多个独立的实参。两者字面上都是三个点，方向却正好相反，区分它们唯一可靠的办法是看这个 `...` 出现在函数定义侧还是调用侧。

## 函数重载：一个实现，多个对外签名

```ts
function format(value: string): string;
function format(value: number): string;
function format(value: string | number): string {
	// 这一行是唯一的实现签名，不对外暴露；调用方只能看到上面两条重载签名
	return typeof value === "number" ? value.toFixed(2) : value.trim();
}
console.log(`format("  hello  ") -> "${format("  hello  ")}"`);
console.log(`format(3.14159) -> "${format(3.14159)}"`);
```

真实输出：

```text
format("  hello  ") -> "hello"
format(3.14159) -> "3.14"
```

TypeScript 的函数重载是纯粹的**编译期特性**：写在前面的多条签名（`function format(value: string): string;` 和 `function format(value: number): string;`）只是声明，不带函数体，用来告诉调用方"这个函数接受哪几种参数组合、对应哪种返回类型"；紧接着带函数体的那一条叫**实现签名**，它的参数类型必须能兼容前面所有重载签名（这里用联合类型 `string | number` 覆盖两种情况），且**不会**出现在调用方看到的类型提示里。调用方在编辑器里输入 `format(` 只会看到 `(value: string): string` 和 `(value: number): string` 两条提示，看不到实现签名里的 `string | number`。相比直接写一个 `(value: string | number): string` 的函数，重载签名的价值在于能表达"传字符串一定返回字符串场景的字符串、传数字一定是数字场景的字符串"这种**输入决定输出形态**的精确关系——虽然这个例子里返回类型都是 `string`，重载在返回类型也随输入变化时（比如传 `string` 返回 `string`、传 `number[]` 返回 `number`）价值会更明显。

## 可选参数 vs 默认参数：类型推断上的差异

```ts
// tag 是可选参数，类型会被推断为 string | undefined，调用方必须自己处理 undefined
function logOptional(message: string, tag?: string): void {
	console.log(`[optional] tag=${tag ?? "(none)"} message=${message}`);
}
// level 是默认参数，类型直接就是 number（不带 undefined），因为不传时会用默认值兜底
function logDefault(message: string, level = 1): void {
	console.log(`[default] level=${level} message=${message}`);
}
logOptional("hello");
logDefault("world");
```

真实输出：

```text
[optional] tag=(none) message=hello
[default] level=1 message=world
```

两者从调用方角度看都是"这个参数可以不传"，但在函数**内部**，TypeScript 推断出的参数类型不一样：`tag?: string` 的 `tag` 在函数体内类型是 `string | undefined`——TypeScript 只是允许调用方省略这个参数，函数体内部依然要自己处理"可能是 `undefined`"这个事实（上面用 `??` 兜底）。`level = 1` 的 `level` 在函数体内类型直接就是 `number`，不带 `undefined`——因为 TypeScript 知道，一旦调用方没传，默认值 `1` 就会立刻顶上，函数体内部**永远不可能**观察到 `undefined`。这个差异决定了两种写法的适用场景：**只是"允许不传、不传就是没有这个东西"（比如一个可选的回调、一个可选的元数据字段），用可选参数；"不传就该有一个具体默认行为"（比如一个默认的重试次数、默认的日志级别），用默认参数**——默认参数能少写很多不必要的 `?? 兜底值` 判断。

## 小结

嵌套对象解构里，属性名前的重命名和默认值可以同时作用于"整体"和"字段"两个层级，可选字段（如 `address?`）的解构必须搭配整体默认值才能安全处理"字段整体缺失"的情况。展开运算符做对象合并时遵循"后写覆盖先写"的顺序规则，默认配置永远写在前、用户覆盖写在后是标准写法。剩余参数（定义处）和展开运算符（调用处）字面相同但方向相反，一个收集、一个打散。函数重载让一个实现对外暴露多条精确的类型签名，实现签名本身不对调用方可见。可选参数在函数体内类型带 `undefined`，默认参数不带——这决定了该用哪一种取决于"不传时到底有没有一个具体的默认行为"。
