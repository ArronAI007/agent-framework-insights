# 进程生命周期与优雅关闭

> 这一章、也是这门课到目前为止最偏"生产运维视角"的一篇：一个 Node 进程从启动到退出，中间会经历哪些可以被代码感知和响应的节点，以及收到终止信号时应该怎么做才不会在"正在处理中的请求"上留下烂摊子。这个话题看起来简单，但几乎每个把 Node 服务部署到容器编排系统（Kubernetes、ECS 等）的团队都会在某个时间点踩到这个坑——版本发布时进程被粗暴杀死，导致一批正在处理的请求收到连接被重置的错误。

## 学习目标

- 理解 `process.on("exit")` 的限制：只能做同步收尾工作
- 掌握 `SIGINT`/`SIGTERM` 两个终止信号的含义和触发场景
- 实现一个标准的优雅关闭模式：停止接收新连接 -> 等现有请求处理完 -> 退出
- 理解为什么优雅关闭还需要一个兜底超时

## `process.on("exit")`：只能做同步收尾

`"exit"` 事件在 Node 进程即将退出、事件循环已经没有更多工作要做的那一刻触发——这个时间点上，**不能再注册任何新的异步操作**：这个回调里调用 `setTimeout`、发起一个 Promise 链，都不会被执行，因为事件循环本身已经在关闭过程中，不会再给这些新任务留出运行的机会。`"exit"` 事件的回调只适合做纯同步的收尾工作，比如打印一条最终日志、同步写一行统计数据到文件。

这个限制直接决定了：**"等待现有 HTTP 请求处理完再退出"这种本质是异步的逻辑，不能放在 `"exit"` 事件里做**——必须在进程刚收到终止信号的那一刻就开始异步处理，把"真正退出"这个动作推迟到异步收尾工作完成之后。

## `SIGINT` 与 `SIGTERM`：两个最常见的终止信号

- **`SIGINT`**：在终端里按 `Ctrl+C` 时，操作系统发送给前台进程的信号，语义是"用户主动请求中断"。
- **`SIGTERM`**：`kill <pid>`（不带任何信号参数）默认发送的信号，语义是"请求进程正常终止"——这也是容器编排系统（Kubernetes 在删除/重启一个 Pod 前、Docker 在 `docker stop` 时）通知进程"你该退出了"所使用的标准信号，通常会给进程一个宽限期（Kubernetes 默认 30 秒），如果进程在这个宽限期内没有自行退出，才会用更粗暴的 `SIGKILL`（无法被捕获或忽略，直接强制杀死进程）兜底。

这两个信号都可以通过 `process.on("SIGINT", handler)`/`process.on("SIGTERM", handler)` 监听并自定义处理逻辑——这正是实现优雅关闭的入口点。

## 标准优雅关闭模式：停止接收新连接 -> 等现有请求完成 -> 退出

```ts
import http from "node:http";

const server = http.createServer((req, res) => {
	// ...处理请求
});

server.listen(0, "127.0.0.1");

function shutdown(signal: NodeJS.Signals): void {
	console.log(`[graceful-shutdown] 收到信号 ${signal}，开始优雅关闭...`);

	server.close(() => {
		console.log("[graceful-shutdown] 所有连接已关闭，进程正常退出");
		process.exit(0);
	});

	const FORCE_EXIT_TIMEOUT_MS = 5000;
	setTimeout(() => {
		console.log(`[graceful-shutdown] 超过 ${FORCE_EXIT_TIMEOUT_MS}ms 仍未正常关闭，强制退出`);
		process.exit(1);
	}, FORCE_EXIT_TIMEOUT_MS).unref();
}

process.on("SIGINT", () => shutdown("SIGINT"));
process.on("SIGTERM", () => shutdown("SIGTERM"));
```

`server.close()` 是这套模式的核心：调用它会让服务器**立刻停止接受新的连接**（新请求会被操作系统层面拒绝，而不是被 Node 接收后再拒绝），但**不会**强行打断已经在处理中的请求——它的回调只有在"所有已建立的连接都已经处理完并关闭"之后才会触发。这正好符合优雅关闭的直觉：不接新单，但手上的单要做完。

完整代码见 `examples/05-Node.js运行时核心/06-进程生命周期/graceful-shutdown.ts`。这个文件设计为**手动交互式测试**，不是自动化跑一次就结束的脚本：启动之后需要手动按 `Ctrl+C`（或者在另一个终端用 `kill -TERM <pid>`）才会触发关闭逻辑，所以这一篇特意没有把它纳入本章末尾"跑一遍所有示例文件"的自动化验证列表，只用 `npm run typecheck` 覆盖它的类型正确性。

即便不写进自动化列表，这段逻辑本身的行为还是做了真实验证——手动用 `kill -TERM` 给运行中的进程发送信号（模拟"先有一个正在处理的请求，请求处理到一半时进程收到终止信号"这个最容易出问题的场景），得到的真实日志：

```text
[graceful-shutdown] 服务器已启动 -> http://127.0.0.1:50347
[graceful-shutdown] 收到请求 /inflight-test，当前处理中的请求数 -> 1
[graceful-shutdown] 收到信号 SIGTERM，开始优雅关闭...
[graceful-shutdown] 请求 /inflight-test 处理完成，剩余处理中的请求数 -> 0
[graceful-shutdown] 所有连接已关闭，进程正常退出
[graceful-shutdown] process exit 事件，最终退出码 -> 0
```

可以看到：`SIGTERM` 信号到达时，`/inflight-test` 这个请求还在处理中（模拟了 3 秒的处理耗时）；`server.close()` 被调用之后，进程**没有**立刻退出，而是等这个请求真正处理完（打印"处理完成"）之后，才触发 `server.close()` 的回调、进而调用 `process.exit(0)`。这正是"停止接收新连接、但不打断正在处理的请求"这套逻辑在真实场景下工作的证据。

## 为什么还需要一个兜底超时

`server.close()` 的回调依赖"所有现有连接都关闭"这个条件——如果某个请求处理逻辑本身有 bug（比如卡在一个永远不会 resolve 的 Promise 上）、或者客户端建立了一条连接但既不发送数据也不主动断开（长连接场景下这种情况并不罕见），`server.close()` 的回调可能永远不会被触发，进程会无限期挂起，既没有正常退出也没有继续正常服务——这比"直接被 `SIGKILL` 强制杀死"更糟糕，因为它可能会悄悄拖慢整个发布/重启流程。

代码里额外设置的 `setTimeout(..., FORCE_EXIT_TIMEOUT_MS).unref()` 就是应对这种情况的兜底：给优雅关闭设一个明确的时间上限，超时后不再等待、直接 `process.exit(1)` 强制退出。`.unref()` 这个调用容易被忽略但很重要——它告诉 Node "这个定时器不应该单独阻止进程退出"：如果 `server.close()` 在超时之前就正常完成了，进程会正常退出，不会被这个兜底定时器额外拖住等到 5 秒超时才退出。

## 小结

`process.on("exit")` 只能做同步收尾，不能在里面发起任何新的异步操作——依赖异步逻辑的关闭流程必须在收到 `SIGINT`/`SIGTERM` 信号的那一刻就开始处理。`SIGINT` 对应终端 `Ctrl+C`，`SIGTERM` 是 `kill` 默认信号、也是容器编排系统通知进程退出的标准方式。标准的优雅关闭模式是：收到信号后调用 `server.close()` 停止接受新连接、等现有连接全部处理完再退出，这个行为已经用真实的 `kill -TERM` 测试验证过——正在处理的请求确实会被等到处理完才关闭。因为 `server.close()` 依赖"所有连接关闭"这个可能永远不满足的条件，需要额外配一个兜底超时，超时后强制 `process.exit(1)`，并用 `.unref()` 保证这个兜底定时器本身不会在正常关闭时拖慢进程退出。到这里，第 05 章「Node.js 运行时核心」全部结束——从模块解析、文件系统与 Buffer，到 Stream、网络编程、子进程与 Worker Threads，最后落到进程生命周期管理，这一章覆盖的是 Node 区别于"纯 JS 语言标准"、真正让它成为一个生产级服务端运行时的核心能力。下一章转向工程化实践，会把前面几章学到的语言和运行时基础，用到真实项目需要的测试、构建、部署这些工程化环节里。
