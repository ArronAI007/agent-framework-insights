# 模块解析与包系统机制

> 上一章讲完了异步编程模型，这一章开始进入 Node.js 运行时本身——这一章讲的东西，是 Node 之所以是 Node（而不只是"一个能跑 JS 的地方"）的核心：模块怎么被找到并加载、文件系统和二进制数据怎么处理、Stream 怎么工作、怎么写网络服务、怎么开子进程和线程、进程的生命周期怎么管理。第一篇讲模块解析——`import "some-package"` 这行代码背后，Node 到底做了哪些事情才找到对应的文件，以及 `package.json` 的 `exports` 字段如何决定一个包"愿意公开哪些入口"。

## 学习目标

- 理解 Node 模块解析算法的整体流程：相对路径、裸模块说明符、`node_modules` 逐级向上查找
- 掌握 `package.json` 的 `exports` 字段如何控制包的公开入口，包括子路径导出和条件导出
- 明确 ESM 下 `__dirname`/`__filename` 不存在，学会用 `import.meta.url` + `fileURLToPath` 替代

## Node 模块解析算法概览

`import` 或 `require` 一个模块说明符时，Node 按说明符的形态分三种情况处理：

- **相对路径**（以 `./` 或 `../` 开头）：直接相对当前文件所在目录解析，找不到就报错，不会去 `node_modules` 里找。
- **绝对路径**（以 `/` 开头，或 Windows 下的盘符路径）：直接按这个路径查找。
- **裸模块说明符**（既不以 `./`、`../` 开头，也不是绝对路径，比如 `"typescript"`、`"node:path"`）：先检查是不是 Node 内置模块（`node:` 前缀或者内置模块白名单里的名字），如果不是，就从当前文件所在目录开始，依次查找 `./node_modules/包名`，如果找不到就退到父目录再查找 `../node_modules/包名`，如此逐级向上，直到文件系统根目录——这正是"为什么 `npm install` 一个包之后，项目里任何深度嵌套的文件都能 `import` 到它"的原因：只要某一级祖先目录的 `node_modules` 里有这个包，就能被找到。

## `package.json` 的 `exports` 字段：包的公开入口

`exports` 字段是相对新的机制（Node 12+），在它之前，一个包对外暴露什么完全由 `main` 字段（或者干脆没有限制、任何深层文件路径都能被 `import`）决定。`exports` 字段把这件事变成**显式声明**：只有 `exports` 里列出的路径才允许被外部 `import`/`require`，没列出的路径即便文件真实存在于包目录里，也会被解析算法直接拒绝——这是包作者"收紧公开 API 边界"的手段，避免使用方依赖了包内部的实现细节文件，导致包作者以后想调整目录结构就会破坏使用方的代码。

本项目 `node_modules` 里已经安装的 `typescript` 包，`package.json` 里的 `exports` 字段是一个很典型的"只声明少数几个子路径"的例子：

```json
{
  "./package.json": "./package.json",
  ".": "./lib/version.cjs",
  "./unstable/sync": "./dist/api/sync/api.js",
  "./unstable/async": "./dist/api/async/api.js",
  "./unstable/fs": "./dist/api/fs.js",
  "./unstable/proto": "./dist/api/proto.js",
  "./unstable/ast": "./dist/ast/index.js"
}
```

`"."` 对应的是 `import "typescript"` 这个最基础的写法，会被解析到 `./lib/version.cjs`；`"./unstable/sync"` 对应 `import "typescript/unstable/sync"` 这种子路径导出。除了这几个路径，`typescript` 包目录里实际上还有大量其他文件（比如 `lib/typescript.js`），但因为它们没有出现在 `exports` 字段里，直接 `import "typescript/lib/typescript.js"` 会被 Node 拒绝解析——这就是子路径导出收紧公开面的效果。

## 条件导出：同一个入口，不同场景下解析到不同文件

`exports` 字段的每个路径还可以不是一个简单的字符串，而是一个"条件 -> 文件"的映射对象，Node 会根据当前的加载方式（ESM `import` 还是 CommonJS `require`）、以及消费方（TS 编译器读取类型时）选择匹配的那个分支。本项目 `node_modules` 里的 `vitest` 包给出了一个真实的条件导出例子：

```json
{
  ".": {
    "import": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    },
    "require": {
      "types": "./index.d.cts",
      "default": "./index.cjs"
    }
  }
}
```

同一个 `import "vitest"`，如果发起方是 ESM（`import` 语句）就解析到 `./dist/index.js`（配 `.d.ts` 类型声明）；如果发起方是 CommonJS（`require("vitest")`）就解析到 `./index.cjs`（配单独的 `.d.cts` 类型声明）。这就是**条件导出**存在的意义：一个包可以同时对 ESM 和 CommonJS 消费者提供不同格式的实际产物，且各自搭配正确的类型声明文件，而不需要使用方关心"我这边是哪种模块系统、该 import 哪个具体文件"——解析算法会自动帮你选对。

## ESM 下 `__dirname`/`__filename` 不存在：`import.meta.url` 是替代方案

CommonJS 模块里，`__dirname`（当前文件所在目录的绝对路径）和 `__filename`（当前文件自身的绝对路径）是模块加载器在执行每个模块之前自动注入的两个"隐藏变量"。但 ESM 规范里根本没有这两个变量——ESM 用 `import.meta.url` 代替，它是一个形如 `file:///Users/xxx/foo.ts` 的 URL 字符串，需要用 `node:url` 提供的 `fileURLToPath` 转换成操作系统原生的文件路径格式，才能配合 `node:path` 的 API（`path.dirname`、`path.join` 等）正常使用。

```ts
import { fileURLToPath } from "node:url";
import path from "node:path";

const currentFilePath = fileURLToPath(import.meta.url);
const currentDirPath = path.dirname(currentFilePath);
```

真实输出：

```text
import.meta.url        -> file:///Users/arron/Desktop/ArronAI/agent-framework-insights/TypeScript-Node/examples/05-Node.js%E8%BF%90%E8%A1%8C%E6%97%B6%E6%A0%B8%E5%BF%83/01-%E6%A8%A1%E5%9D%97%E8%A7%A3%E6%9E%90%E4%B8%8E%E5%8C%85%E7%B3%BB%E7%BB%9F%E6%9C%BA%E5%88%B6/resolve-demo.ts
fileURLToPath 得到的路径 -> /Users/arron/Desktop/ArronAI/agent-framework-insights/TypeScript-Node/examples/05-Node.js运行时核心/01-模块解析与包系统机制/resolve-demo.ts
当前文件所在目录         -> /Users/arron/Desktop/ArronAI/agent-framework-insights/TypeScript-Node/examples/05-Node.js运行时核心/01-模块解析与包系统机制
```

值得注意的一个细节：`import.meta.url` 打印出来的路径里，目录名里的中文字符被自动做了 URL 百分号编码（`05-Node.js%E8%BF%90...`）——这是因为 URL 规范不允许非 ASCII 字符直接出现在 URL 里，必须编码；而 `fileURLToPath` 转换回文件路径之后，中文目录名又变回了正常可读的形态。这也是为什么不能直接把 `import.meta.url` 字符串当作文件路径使用（比如直接拼接进 `fs.readFile`）——必须先用 `fileURLToPath` 转换，否则遇到路径里有中文、空格这类需要编码的字符时会得到错误的路径。

## 用 `import.meta.resolve` 解析一个真实模块

ESM 标准提供了 `import.meta.resolve(specifier)`，同步返回这个模块说明符实际会被解析到的 URL——这是本篇要求验证的另一个 API，用当前 Node 版本（v26.5.0）实测确认可用：

```ts
const resolvedBuiltin = import.meta.resolve("node:path");
const resolvedTypescript = import.meta.resolve("typescript");
```

真实输出：

```text
import.meta.resolve("node:path") -> node:path
import.meta.resolve("typescript") -> file:///Users/arron/Desktop/ArronAI/agent-framework-insights/TypeScript-Node/node_modules/typescript/lib/version.cjs
```

这里有个容易被"resolve 出来的一定是文件路径"这个直觉误导的地方：解析内置模块 `"node:path"` 得到的结果**就是它自己**（`node:path`），而不是磁盘上某个 `.js` 文件的路径——因为内置模块是编译进 Node 二进制本身的，根本不对应文件系统里的任何一个文件，"解析"对它们来说没有"查找文件"这一步，只是确认这个说明符本身合法。解析第三方包 `"typescript"` 则如预期般得到了一个真实文件路径 `.../node_modules/typescript/lib/version.cjs`——这正好对应上一节看到的 `exports` 字段里 `"."` 声明的入口文件，验证了 `exports` 字段确实在解析过程中生效。

作为对照，用 `node:module` 的 `createRequire` 在 ESM 里桥接出一个 `require` 函数，`require.resolve("typescript")` 返回的是普通文件系统路径（不带 `file://` 协议头），这是 CommonJS 解析 API 和 ESM 解析 API 在返回值形态上的差异，语义是一致的：

```text
require.resolve("typescript")     -> /Users/arron/Desktop/ArronAI/agent-framework-insights/TypeScript-Node/node_modules/typescript/lib/version.cjs
```

## 小结

Node 的模块解析按说明符形态分三条路径：相对路径直接按目录解析，绝对路径直接查找，裸模块说明符先判断是否内置模块，否则从当前目录开始逐级向上查找 `node_modules`。`package.json` 的 `exports` 字段把包的公开入口从"没有限制、任何文件都能被 import"收紧成"只有显式声明的路径才允许被外部访问"，还能通过条件导出（`import`/`require`/`types`）让同一个说明符在不同消费场景下解析到不同的实际文件——`typescript` 包用简单字符串声明子路径导出，`vitest` 包用对象形式声明了完整的条件导出，两者都是本项目 `node_modules` 里真实安装的包。ESM 下没有 `__dirname`/`__filename`，替代方案是 `import.meta.url`（一个 URL 字符串，中文等非 ASCII 字符会被自动编码）配合 `node:url` 的 `fileURLToPath` 转换回原生文件路径；`import.meta.resolve` 能同步解析出一个模块说明符对应的 URL，内置模块解析后得到的是它自身而非文件路径，第三方包则会解析到 `exports` 字段声明的真实入口文件。下一篇讲文件系统和 Buffer，会用到这一篇提到的 `fs/promises` API 风格，正式开始操作真实的文件和二进制数据。
