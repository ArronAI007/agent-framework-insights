# 调试、性能剖析与内存泄漏排查

> 上一篇讲的是"怎么确认代码符合预期"（测试），这一篇讲"代码不符合预期/跑得比预期慢/占用内存比预期多的时候，怎么找到问题在哪"。这四件事——用 DevTools 单步调试、用 CPU Profile 找热点函数、用 `process.memoryUsage()` 观察内存趋势、用堆快照定位泄漏——是几乎所有语言的运行时诊断工具都会提供的能力，这一篇不重复"什么是调试器"这种通用概念，重点放在 Node 具体怎么把这些能力暴露出来、命令怎么用。本篇不新建示例文件，内存泄漏排查这一节会引用第 07 章「内存模型与垃圾回收」的 `gc-demo.ts`，把它当作一个真实的排查对象来演示思路。

## 学习目标

- 掌握 `node --inspect`/`--inspect-brk` 配合 Chrome DevTools 的连接流程
- 会用 `node --prof` 生成 CPU profile，并用 `node --prof-process` 把它转成可读报告
- 理解 `process.memoryUsage()` 各个字段的含义，会用它观察内存增长趋势
- 理解堆快照（heap snapshot）定位内存泄漏的基本思路，会用 `v8.writeHeapSnapshot()` 生成一份

## `--inspect`/`--inspect-brk` 配合 Chrome DevTools

给 `node` 命令加上 `--inspect`，Node 会在启动时打开一个 WebSocket 调试端口（默认 `9229`），并打印出连接信息：

```bash
node --inspect your-script.js
```

真实输出：

```text
Debugger listening on ws://127.0.0.1:9229/88d710cd-587d-4111-8d37-7fb0838ecbc2
For help, see: https://nodejs.org/learn/getting-started/debugging
```

这时候用 Chrome 打开 `chrome://inspect`，在"Remote Target"列表里能看到这个正在运行的 Node 进程，点击"inspect"就会打开一个专门为 Node 定制的 DevTools 窗口——和调试网页时用的是同一套 DevTools 界面（Sources 面板打断点、单步执行、查看调用栈和作用域变量；Memory 面板做堆快照；Profiler 面板录制 CPU Profile），只是调试的对象从浏览器里的 JS 换成了 Node 进程里的 JS。

`--inspect` 和 `--inspect-brk` 的区别只有一点，但很关键：`--inspect` 启动后脚本立刻正常执行，如果调试器还没来得及连接上，脚本可能已经跑完了；`--inspect-brk` 会在执行**第一行代码之前**暂停，等待调试器连接上之后再继续——这在调试"启动阶段就会出问题"的脚本，或者需要在任何业务代码跑起来之前就设好断点的场景下是必需的：

```bash
node --inspect-brk your-script.js
```

对于长期运行的服务进程（不是跑一次就退出的脚本），还可以在进程运行过程中动态开启调试——给进程发送 `SIGUSR1` 信号（`kill -USR1 <pid>`），Node 会在不重启进程的前提下开启 inspector（这一点在第 05 章讲过的 `SIGINT`/`SIGTERM` 之外，是 Node 对信号的另一处扩展用法）。

## `--prof` + `node --prof-process`：生成并解读 CPU Profile

`--inspect` 配合 DevTools 适合交互式地单步调试，但要回答"这段代码整体上时间花在哪个函数里"这类问题，更适合用统计式的 CPU profiler。加上 `--prof` 运行：

```bash
node --prof prof-test.mjs
```

运行结束后，当前目录会多出一个 `isolate-0x....log` 文件——这是 V8 按固定采样间隔记录下来的原始调用栈样本，人不能直接读，需要再用 `node --prof-process` 转成可读的统计报告：

```bash
node --prof-process isolate-0x7d140c000-34038-v8.log
```

用一段递归计算斐波那契数列（`fib(35)`，故意选一个足够慢、能采集到有效样本量的计算量）实测跑出的真实报告节选：

```text
Statistical profiling result from isolate-0x7d140c000-34038-v8.log, (41 ticks, 0 unaccounted, 0 excluded).

 [Shared libraries]:
   ticks  total  nonlib   name
      7   17.1%          /opt/homebrew/Cellar/node/26.5.0/lib/libnode.147.dylib

 [JavaScript]:
   ticks  total  nonlib   name
     34   82.9%  100.0%  JS: *fib file:///private/tmp/prof-test.mjs:1:13

 [Summary]:
   ticks  total  nonlib   name
     34   82.9%  100.0%  JavaScript
      0    0.0%    0.0%  C++
      0    0.0%    0.0%  GC
      7   17.1%          Shared libraries

 [Bottom up (heavy) profile]:
  Note: percentage shows a share of a particular caller in the total
  amount of its parent calls.
  Callers occupying less than 1.0% are not shown.

   ticks parent  name
     34   82.9%  JS: *fib file:///private/tmp/prof-test.mjs:1:13
```

报告分几个区块：`[Summary]` 给出宏观占比（这次采样里 82.9% 的时间花在 JavaScript 执行本身，0% 花在 GC 上，说明这段代码不是内存密集型而是纯计算密集型）；`[JavaScript]` 列出按耗时排序的具体函数（`fib` 一家独大，符合预期，因为整个脚本基本就在递归调 `fib`）；`[Bottom up (heavy) profile]` 是"从最耗时的叶子函数往上看它是被谁调用的"，适合排查"这个热点函数是从哪条调用路径触发的"。真实项目里排查性能问题，通常就是先看 `[Summary]` 判断问题大类（JS 计算 / GC / C++/系统调用），再到 `[JavaScript]` 区块找到耗时最高的具体函数，作为优化的起点——这也是下一章「性能优化实战」强调"先测量再优化"的具体工具支撑：没有这份报告之前，任何"我觉得是这里慢"的猜测都只是猜测。

## `process.memoryUsage()`：观察内存增长趋势

`process.memoryUsage()` 返回当前进程的内存使用快照，几个关键字段：

- `rss`（Resident Set Size）：进程占用的物理内存总量，包含 V8 堆、C++ 对象、代码本身等所有部分，是操作系统层面"这个进程用了多少内存"的最直观指标。
- `heapUsed`/`heapTotal`：V8 堆里**当前正在使用**/**当前已分配**的字节数——只统计 JS 对象、字符串、闭包等 V8 管理的内存，不包含 Buffer 等堆外分配。
- `external`：C++ 侧绑定到 JS 对象上的内存，典型的例子就是较大的 `Buffer`——Node 出于性能考虑，会把比较大的 `Buffer` 的实际数据分配在 V8 堆**之外**，`heapUsed` 完全看不出这部分内存的变化，要看 `external`。这也是第 07 章 `gc-demo.ts` 在设计"内存泄漏"演示时特意选择用普通 JS 对象/字符串而不是 `Buffer.alloc` 的原因——用 `Buffer` 演示反而在 `heapUsed` 上看不出明显增长。
- `arrayBuffers`：`external` 里专门属于 `ArrayBuffer`/`Buffer` 的那部分，是 `external` 的一个子集细分。

排查内存问题最基本的手法就是在代码的关键节点打印这几个字段、对比前后差值，观察增长趋势是"用完就回落"（正常的临时占用）还是"持续只增不减"（疑似泄漏）。下一节会具体演示。

## 用堆快照定位泄漏的基本思路

如果 `process.memoryUsage()` 已经确认内存在持续增长，下一步需要知道"具体是什么对象在占着内存不放"，这时候需要堆快照（heap snapshot）——把某一时刻 V8 堆里所有存活对象的完整快照导出成文件，用 Chrome DevTools 的 Memory 面板打开分析。生成快照最直接的方式是调用 `node:v8` 模块的 `writeHeapSnapshot()`：

```ts
import v8 from "node:v8";

const file = v8.writeHeapSnapshot();
console.log(`堆快照已写入 -> ${file}`);
```

真实执行结果：

```text
snapshot written to Heap.20260916.194715.37085.0.001.heapsnapshot
size bytes: 4985177
```

（这里生成的示例快照约 4.9MB，验证完就删除了，不属于本课程需要保留的产物；`--inspect` 连接 DevTools 之后，Memory 面板本身也能直接点按钮生成快照，效果等价，不需要写代码调用 `writeHeapSnapshot()`。）

排查泄漏最常用的技巧是**对比两份快照**：在怀疑发生泄漏的操作前后各生成一份（比如"处理 1000 个请求之前"和"处理 1000 个请求之后"），在 DevTools 里用 Comparison 视图对比两份快照，重点看哪些对象的**数量**在两次快照之间明显增长、且增长量和"请求数"这类操作次数成比例——这种"数量随操作次数线性增长、且增长的对象都指向同一处代码"的模式，就是内存泄漏的典型信号。找到可疑对象之后，DevTools 还能展示这个对象的**保留路径**（retaining path，即"从 GC Root 到这个对象之间经过了哪些引用"），沿着这条路径往回看，通常就能定位到具体是哪一行代码忘记断开了引用。

## 实操对象：用 `gc-demo.ts` 演示排查思路

第 07 章 `examples/07-进阶主题与总结/01-内存模型与垃圾回收/gc-demo.ts` 里专门写了一个"故意制造内存泄漏"的函数 `leakSomeMemory`，配合 `printHeapUsed` 在泄漏前后打印 `heapUsed`。运行它（真实输出，运行方式和第 07 章第 01 篇给出的命令一致）：

```text
===== 内存泄漏模拟：全局数组不断 push =====
[gc-demo] 泄漏前 -> heapUsed = 8.33MB
[gc-demo] 泄漏后（已 push 200000 条记录，每条 payload 长度 50） -> heapUsed = 53.54MB
[gc-demo] leakedRecords.length = 200000 —— 这些对象只要还挂在这个数组上，就永远不会被 GC 回收，这正是内存泄漏的本质：不是「GC 不工作」，而是「代码里还有一根引用没断」。
```

`heapUsed` 从 8.33MB 涨到 53.54MB，这正是上一节说的"用完不回落"的信号（如果在真实的长期运行服务里、每处理一批请求就重复观察到类似的单调增长，而不是"涨一点、GC 一次、回落一些"的正常波动，就该怀疑存在泄漏）。对照 `gc-demo.ts` 的源码，泄漏点其实一目了然：`leakedRecords` 是一个模块作用域的全局数组，`leakSomeMemory` 只有 `push`、没有任何清理逻辑——这也正是真实项目里内存泄漏最常见的形态：一个本该是"临时缓存"或"当前批次处理中的数据"的容器，被挂在了模块作用域甚至全局对象上,长期存活、只增不减。如果这是一个更复杂的真实排查场景（而不是像 `gc-demo.ts` 这样已经知道泄漏点在哪的教学示例），下一步就是照上一节的方法：在 `printHeapUsed("泄漏前")` 和 `printHeapUsed("泄漏后")` 对应的两个时间点分别生成堆快照，对比出"数量随 `push` 次数同步增长"的对象类型，再顺着保留路径找到具体是哪个数组/Map/闭包在攥着这些对象不放。

## 小结

`--inspect`/`--inspect-brk` 让 Chrome DevTools 能直接连上 Node 进程调试，区别在于是否等待调试器连接后再执行第一行代码；长期运行的服务可以用 `SIGUSR1` 信号动态开启调试而不需要重启。`--prof` 采集 CPU 使用样本，`node --prof-process` 把原始日志转成可读报告，`[Summary]` 区块判断问题大类、`[JavaScript]`/`[Bottom up]` 区块定位具体热点函数，这是"先测量再优化"这条原则在工具链层面的具体落地。`process.memoryUsage()` 的 `heapUsed`/`heapTotal` 只反映 V8 堆内内存，较大的 `Buffer` 走 `external` 字段，观察内存问题时不能只盯着 `heapUsed` 一个数字。堆快照能给出"某一时刻堆里到底有什么对象"的完整快照，对比操作前后两份快照、找到数量随操作次数同步增长的对象类型、再顺着保留路径回溯，是定位内存泄漏的标准流程——`gc-demo.ts` 里 `heapUsed` 从 8.33MB 涨到 53.54MB 且只增不减，正是这套诊断方法要捕捉的典型信号。下一篇是第 06 章最后一篇，讲构建打包与 NPM 包发布，会用 `tsc` 把一个 TS 库编译成可发布的产物，并走一遍 `npm pack --dry-run` 到 `npm publish` 的完整流程。
