# 项目结构与代码组织

> 第 05 章讲完了 Node 运行时本身——模块、文件系统、Stream、网络、子进程、进程生命周期。这些是"引擎"层面的能力，但一个真实项目能不能长期维护下去，往往不取决于引擎强不强，而取决于代码怎么组织。这一章转向工程化实践，先从最基础也最容易被低估的一环开始：目录怎么分、文件怎么放、模块之间怎么互相引用。这一篇不需要配套的可执行示例——它讨论的是项目骨架层面的约定，用真实项目里常见的目录树对比就足够说明问题。

## 学习目标

- 理解"按技术层组织"和"按业务域组织"两种目录结构的本质区别，以及为什么后者在项目变大后更容易维护
- 知道 `src/`+`tests/`（或就近放置测试文件）这两种测试文件组织惯例各自的取舍
- 理解桶文件（`index.ts` re-export）能带来的便利，以及它在编译性能和循环依赖上隐藏的代价
- 掌握 `tsconfig.json` 里 `paths` 别名的用法，以及什么情况下不该用它

## 按技术层组织 vs 按业务域组织

刚接触一个多层 Web 框架的人，几乎都会本能地写出这样的目录结构：

```text
src/
├── controllers/
│   ├── user.controller.ts
│   ├── order.controller.ts
│   └── product.controller.ts
├── models/
│   ├── user.model.ts
│   ├── order.model.ts
│   └── product.model.ts
├── views/
│   └── ...
└── services/
    ├── user.service.ts
    ├── order.service.ts
    └── product.service.ts
```

这叫"按技术层组织"（organize by layer）：顶层目录是 MVC 里的角色分类，同一个业务概念（比如"订单"）被拆散成 `order.controller.ts`、`order.model.ts`、`order.service.ts` 三个文件，分别躺在三个不同的顶层目录里。这种结构在项目很小、模块数量不多的时候看起来很整齐——毕竟"所有 controller 长得都差不多"，放在一起似乎更方便横向对比。

但项目一旦长到几十个业务概念、上百个文件，这套结构的问题就会暴露出来：想搞清楚"订单"这个业务到底涉及哪些代码，得同时打开 `controllers/`、`models/`、`services/`，甚至可能还有 `validators/`、`dto/`、`repositories/` 好几个目录，来回切换；想删除一个不再需要的业务功能时，得在每个技术层目录里分别找到对应文件删掉，稍不注意就会漏掉一个孤儿文件。更麻烦的是团队协作——两个开发者同时改"订单"和"用户"两个不相关的业务，如果都要碰 `services/` 目录（哪怕改的是完全不同的文件），"服务层这个目录最近改动很频繁"这种感知上的耦合，会让代码评审和 merge 冲突的心理负担都变大。

对比"按业务域组织"（organize by feature/domain）：

```text
src/
├── order/
│   ├── order.controller.ts
│   ├── order.model.ts
│   ├── order.service.ts
│   └── order.test.ts
├── user/
│   ├── user.controller.ts
│   ├── user.model.ts
│   ├── user.service.ts
│   └── user.test.ts
└── product/
    ├── product.controller.ts
    ├── product.model.ts
    └── product.service.ts
```

顶层目录变成了业务概念，同一个业务的所有代码（包括它自己的测试）都放在一起。想理解"订单"业务，打开 `order/` 一个目录就够了；想删除整个功能，删掉一个目录、检查一下有没有被其他目录 import 就基本完事；两个开发者分别改 `order/` 和 `user/`，物理上就不会有文件冲突。这不是说技术层分类完全没有价值——文件命名里依然保留了 `.controller.ts`/`.service.ts` 这样的后缀，一眼能看出某个文件在业务内部扮演什么角色，只是不再用它作为顶层的组织维度。这也是很多现代框架（Nest.js 的 module 系统、前端领域的 feature-based 目录）默认推荐的组织方式，本质上是把"高内聚、低耦合"这条通用工程原则落到目录结构上。

## `src/` 与测试文件的位置：集中 vs 就近

Node/TS 项目常见的顶层布局是把源代码放进 `src/`，和 `node_modules/`、`dist/`（编译产物）、配置文件区分开，避免构建工具需要遍历整个仓库去找哪些文件是"真正的源码"。这一层约定基本没有争议。

真正有取舍的是测试文件放哪：

- **集中放在独立的 `tests/` 目录**，镜像 `src/` 的目录结构（`src/order/order.service.ts` 对应 `tests/order/order.service.test.ts`）。好处是打开项目根目录能立刻看到"这是一个有完整测试目录的项目"，`src/` 目录本身保持纯粹，不会被测试文件"稀释"；坏处是改一个源文件时，对应的测试文件在另一棵目录树上，需要额外跳转，两边的目录结构也容易在重构时逐渐"失步"（改了 `src/` 里的目录名，忘了同步改 `tests/` 里的）。
- **就近放置**，测试文件和被测文件挨在一起（`order.service.ts` 旁边就是 `order.service.test.ts`）。好处是改代码和改测试之间的心理距离最短，目录结构天然保持同步，不存在"两棵树对不上"的问题；坏处是每个功能目录里源文件和测试文件混在一起，文件列表看起来更"吵"。

这门课第 06 章第 02 篇的 `math.ts`/`math.test.ts` 用的就是就近放置——这也是 Vitest、Jest 这类现代测试框架的默认推荐做法，本课程后续也会延续这个约定。两种方式都能落地成规范的工程实践，关键是**团队内统一**，不要一部分模块就近放、一部分模块集中放，那样谁都找不到测试文件在哪。

## 桶文件（`index.ts` re-export）：便利与代价

"桶文件"（barrel file）指的是一个只做 re-export、不包含实际逻辑的 `index.ts`，常见写法：

```ts
// order/index.ts —— 桶文件
export { OrderService } from "./order.service.js";
export { OrderController } from "./order.controller.js";
export type { Order } from "./order.model.js";
```

有了它，外部代码可以写 `import { OrderService } from "../order/index.js"`（或者利用模块解析规则省略成 `"../order"`），而不需要知道 `OrderService` 具体定义在哪个文件里——这是桶文件最直接的好处：**把"目录内部怎么拆文件"这件事对外部调用方隐藏起来**，内部重构（比如把 `order.service.ts` 拆成两个文件）不需要动外部所有的 import 语句。

但这份便利是有代价的，而且代价会随着项目变大被放大：

- **编译/打包性能**：一个桶文件把整个目录的导出聚合成一个入口，只要外部代码 `import` 了这个桶文件里的任意一个符号，打包工具在做静态分析时经常需要把整个 `index.ts` 及其背后引用的所有文件都拉进依赖图——哪怕外部只用到其中一个函数。项目里桶文件层层嵌套（`a/index.ts` re-export `b/index.ts` re-export `c/index.ts`）会让这个问题指数级放大，是大型 TS/JS 项目里增量编译变慢、打包体积异常膨胀的常见根源之一。
- **循环依赖风险**：桶文件让"目录 A 依赖目录 B 的桶文件、目录 B 的桶文件又（间接）依赖目录 A"这种循环变得更容易在不经意间发生——因为开发者引用的是一个聚合入口，很难直觉地意识到"我只是想用 B 里的一个工具函数，但这个桶文件实际上重新导出了半个项目"。ESM 环境下循环依赖不一定会直接报错，但会导致"模块的某些绑定在初始化阶段还是 `undefined`"这类隐蔽 bug，排查成本很高。

实践上的折中：桶文件适合用在**目录对外的公共 API 边界**（比如一个发布为 npm 包的库的根 `index.ts`，见本章第 04 篇），不适合在应用内部大量、多层嵌套地使用。应用内部模块间的 import，直接写具体文件路径（`import { OrderService } from "./order.service.js"`）虽然看起来啰嗦一点，但依赖关系是显式、可追踪的，也是本课程 `examples/` 目录里所有文件之间互相引用时采用的方式。

## `tsconfig.json` 的 `paths` 别名

`paths` 让你给深层的相对路径起一个短别名：

```json
{
	"compilerOptions": {
		"baseUrl": ".",
		"paths": {
			"@order/*": ["src/order/*"],
			"@shared/*": ["src/shared/*"]
		}
	}
}
```

配置好之后，原本可能要写 `import { formatMoney } from "../../../shared/format.js"` 的深层相对路径，可以写成 `import { formatMoney } from "@shared/format.js"`——不再需要数有几层 `../`，文件被移动到目录树的其他位置时，这行 import 语句也不需要跟着改。

`paths` 好用，但也容易被滥用，什么时候不该用：

- **`tsc` 本身不会重写这些路径**：`paths` 只影响 TypeScript 做类型检查时如何解析模块，编译产物里这些别名原样保留——运行时（Node、打包工具）需要额外的机制才能认得 `@shared/*` 这种路径，比如 `tsx`/`ts-node` 借助各自的 loader、打包工具借助各自的 alias 配置、纯 `tsc` 编译产物则完全不支持，运行时会直接报"找不到模块"。引入 `paths` 之前，必须确认项目实际的运行方式（是直接跑 `tsx`，还是先 `tsc` 编译再跑 `node`）能不能让这些别名在运行时也生效，否则就是"类型检查通过、运行时报错"的陷阱。
- **单体小项目不需要**：如果项目本身没有深层嵌套的目录结构，相对路径最多两三层 `../`，引入别名带来的认知开销（团队新人得先知道 `@shared` 对应哪个真实目录）可能比它省下的几个字符还大。
- **跨包边界不该用 `paths` 冒充**：在 npm workspaces/monorepo 里，如果两个包之间真的存在"库"和"使用方"的关系，应该通过正常的包依赖（`package.json` 的 `dependencies` + workspace 协议）互相引用，而不是用 `paths` 把另一个包的源码路径直接映射进来——那样会让两个本该独立发布、独立管理版本的包在类型检查层面产生一种"看起来是同一个项目"的假象，掩盖了它们实际上是两个独立发布单元这个事实。

## 小结

目录组织优先按业务域划分而不是按技术层划分——同一个业务概念的所有代码放在一起，高内聚、低耦合，删功能、防冲突都更省心；技术层信息（controller/service/model）保留在文件名后缀里就够了，不需要提升到目录结构。测试文件可以集中放在 `tests/` 目录镜像 `src/` 结构，也可以就近放置在被测文件旁边——本课程后续统一采用后者。桶文件（`index.ts` re-export）适合用在对外发布的公共 API 边界，但在应用内部大量嵌套使用会拖慢编译/打包、并增加循环依赖的风险，内部模块间引用建议写具体文件路径。`tsconfig.json` 的 `paths` 别名能省掉深层相对路径的麻烦，但要先确认项目实际运行方式支持这些别名在运行时被正确解析，单体小项目和跨包边界的场景都不适合引入它。下一篇进入测试体系，会讲 Node 内建的 `node:test` runner 和 Vitest 各自的定位，并用一对真实的 `math.ts`/`math.test.ts` 示范怎么给自己的代码写测试。
