# 开发工具链与调试环境

> 环境、编译器、包管理器都就位后，最后一块拼图是"日常写代码时用什么工具保证质量、出问题时怎么调试"。这一篇讲清楚 ESLint 和 Prettier 的分工、VS Code 最小可用的调试配置，以及 Node.js 内置调试器的基本用法。

## 学习目标

- 分清 ESLint 和 Prettier 各自解决什么问题，为什么通常两者一起用
- 能写出一份最小可用的 VS Code `launch.json`，直接对 TypeScript 项目下断点调试
- 了解 `node --inspect` 配合 Chrome DevTools 的基本调试流程

## ESLint 与 Prettier：两个经常被混为一谈的工具

刚接触 JS/TS 生态的人很容易把 ESLint 和 Prettier 当成"两个都是用来格式化代码的工具，随便选一个"，但它们解决的实际上是两类不同的问题：

**ESLint 是代码质量检查工具（linter）**，关注的是"这段代码逻辑上有没有问题"。比如：声明了从未使用的变量、`==` 和 `===` 混用、`Promise` 没有 `catch`、条件表达式恒为真/假。ESLint 依赖抽象语法树（AST）分析代码结构，规则是可配置、可扩展的，社区有大量针对特定框架（React、Vue）或特定风格（Airbnb、Standard）的规则集。

**Prettier 是代码格式化工具**，只关心"这段代码长什么样"——缩进用几个空格、字符串用单引号还是双引号、每行最多多少字符、逗号要不要拖尾。Prettier 的设计哲学是"**尽量不给你选择**"：它的可配置项远少于其他格式化工具，目的就是消灭团队里关于代码风格的无谓争论。

两者的分工边界应该是：**Prettier 管"长什么样"，ESLint 管"对不对"**。如果让 ESLint 的格式类规则（比如 `indent`、`quotes`）和 Prettier 同时生效，两者的判断经常互相打架，产生"保存文件后被两个工具来回改"的抓狂体验。业界标准做法是用 `eslint-config-prettier` 这类配置**关闭 ESLint 里所有和格式相关的规则**，让 ESLint 只做纯逻辑/质量检查，格式化完全交给 Prettier 一个工具负责。

一个典型的分工配置（以 flat config 为例）大致是这样的结构：

```js
// eslint.config.js（示意，不是本课程脚手架的实际配置）
import eslintConfigPrettier from "eslint-config-prettier";

export default [
	// ...你的 ESLint 规则集
	eslintConfigPrettier, // 放在最后，关闭所有和 Prettier 冲突的格式类规则
];
```

日常工作流通常是：编辑器保存时自动跑 Prettier 格式化，提交前（或 CI 里）跑 `eslint .` 做质量检查,两个工具各司其职，谁也不越界。

## VS Code 调试配置：`launch.json`

VS Code 对 Node.js/TypeScript 有开箱即用的调试支持，核心是项目根目录 `.vscode/launch.json` 里的调试配置。一份能直接对本课程 `examples/` 目录里的 TypeScript 文件下断点调试的最小配置：

```json
{
	"version": "0.2.0",
	"configurations": [
		{
			"type": "node",
			"request": "launch",
			"name": "调试当前 TS 文件（tsx）",
			"runtimeExecutable": "npx",
			"runtimeArgs": ["tsx"],
			"args": ["${file}"],
			"console": "integratedTerminal",
			"internalConsoleOptions": "neverOpen"
		}
	]
}
```

几个字段的含义：

- **`type: "node"`**：使用 VS Code 内置的 Node.js 调试适配器（较新版本的 VS Code 已经把 JS/TS 调试能力直接内置，不需要额外装插件）。
- **`runtimeExecutable`/`runtimeArgs`**：不直接用 `node` 启动，而是通过 `npx tsx` 启动——这样调试器实际调试的是 `tsx` 即时转译后的代码，同时保留了源码映射（source map），断点仍然能精确落在你写的 `.ts` 源码行上。
- **`args: ["${file}"]`**：`${file}` 是 VS Code 的内置变量，指向"当前在编辑器里打开的文件"，意味着这份配置对任意一个 `.ts` 文件都通用，不需要给每个示例文件单独写一份配置。
- **`console: "integratedTerminal"`**：让程序的标准输入输出走 VS Code 内置终端，而不是调试控制台——对需要读取命令行输入或希望看到彩色终端输出的场景更友好。

配置好之后，在源码里点击行号左侧设置断点，切到"运行和调试"面板选中这份配置、按 F5，代码执行到断点处就会自动暂停，可以查看调用栈、变量值、逐行单步执行。这是日常开发中最高频使用的调试方式，比反复插入 `console.log` 更适合定位复杂的状态和调用链问题。

## `node --inspect` 与 Chrome DevTools：不依赖编辑器的调试路径

VS Code 的调试功能，底层实际上依赖的正是 Node.js 自带的 **Inspector 协议**。这意味着即便不用 VS Code，任何时候都能直接用 Chrome 浏览器调试 Node.js 进程，这条路径在"远程服务器上的进程需要调试"或"想要更专业的性能分析面板"时尤其有用：

```bash
node --inspect your-script.js
```

执行后终端会打印一行提示，包含一个 `chrome://inspect` 或 `devtools://` 形式的调试地址。打开 Chrome 浏览器访问 `chrome://inspect`，在 "Remote Target" 列表里能看到这个正在运行的 Node.js 进程，点击 "inspect" 就会打开一个和调试网页几乎一模一样的 DevTools 窗口——Sources 面板能下断点、单步执行，Console 面板能直接对着运行中的进程执行任意表达式。

另一个常用变体是 `node --inspect-brk`，区别在于**进程会在第一行代码执行前就暂停**，适合需要从最开始就单步调试（比如排查模块加载顺序问题）的场景，而不是等程序跑到某个断点才暂停。

这里只建立"存在这条路径、大致怎么用"的印象。结合 Chrome DevTools 的 Memory 面板做堆快照对比、定位内存泄漏的完整实战流程，会在第 06 章《调试性能剖析与内存泄漏排查》里详细展开——那一篇会用一个真实会泄漏的示例程序，走一遍从发现问题到定位根因的完整过程。

## 小结

ESLint 负责代码逻辑质量检查，Prettier 负责代码格式化，两者不应该在格式化规则上重叠，业界标准做法是用 `eslint-config-prettier` 关闭 ESLint 里和格式相关的规则，让分工彻底清晰。VS Code 的 `launch.json` 通过 `runtimeExecutable: "npx"` + `runtimeArgs: ["tsx"]` 就能对 TypeScript 源码直接下断点调试，不需要额外的编译步骤。`node --inspect`/`--inspect-brk` 配合 Chrome DevTools 是不依赖编辑器、随时可用的调试手段，尤其适合远程环境或需要更专业性能面板的场景；更深入的内存剖析实战留到第 06 章。
