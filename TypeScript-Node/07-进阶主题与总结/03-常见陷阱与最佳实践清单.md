# 常见陷阱与最佳实践清单

> 这一篇不是新知识，是一份"错题本"——把这门课程从第 01 章到这里反复强调、但实践中依然最容易被忽略的坑，集中成一份可以对照检查的清单。每一条都配了"❌ 错误写法 / ✅ 正确写法"，其中至少 4 条附带了`pitfalls.ts` 里真实可运行的代码：两种写法都会真的跑一遍、打印出结果，用输出证明"这两种写法的行为确实不一样"，而不是停留在"大家都这么说"的层面。

## 学习目标

- 建立一份可以在代码评审时对照检查的常见陷阱清单
- 理解每一条陷阱背后的根本原因，而不是死记"不能这样写"的规则
- 通过 `pitfalls.ts` 的真实运行结果，验证错误写法和正确写法在行为上确实存在差异

## 1. `==` 隐式转换陷阱

- ❌ 用 `==` 比较，触发 JS 的隐式类型转换规则（字符串转数字、`null`/`undefined` 互相宽松相等、布尔值先转数字……），规则本身复杂到没人能完整背下来。
- ✅ 永远用 `===`/`!==`，类型不同直接判定为不相等，不做任何隐式转换。

`pitfalls.ts` 真实输出：

```text
[❌ ==] "0" == 0 -> true
[❌ ==] "" == 0 -> true
[❌ ==] false == "0" -> true
[✅ ===] "0" === 0 -> false
[✅ ===] "" === 0 -> false
[✅ ===] false === "0" -> false
```

有意思的是，如果这两个操作数在编译期就是 TypeScript 能确定的具体类型（比如直接写 `"0" == 0` 这种字面量），`tsc` 在 `strict` 模式下会直接报错拒绝编译（`This comparison appears to be unintentional`）——`pitfalls.ts` 里特意把这些值存进 `unknown` 类型的字段才规避了这个检查。这本身就是一个值得记住的事实：**TypeScript 的类型系统已经替你挡掉了很大一部分 `==` 的陷阱，真正有风险的永远是类型信息已经丢失（`unknown`/`any`）之后的比较**——第 5 条陷阱会继续展开这个话题。

## 2. 忘记 `await` 导致悬空 Promise（silently swallowed rejection）

- ❌ 调用一个返回 Promise 的函数但不 `await`，函数内部一旦 reject，这个错误没有任何地方会显式处理它，只能被 `process.on("unhandledRejection")` 这个全局兜底事件捕获——业务代码完全感知不到这里发生过错误。
- ✅ 用 `await` + `try`/`catch`，错误在调用处就被显式处理。

`pitfalls.ts` 真实输出：

```text
[❌ 悬空 Promise] 函数调用后的代码已经继续往下跑了，错误只能靠 unhandledRejection 事件兜底捕获到 -> 写入 id=2 失败（模拟）
[✅ 正确 await] 错误在调用处被直接捕获 -> 写入 id=2 失败（模拟）
```

两种写法最终都"捕获"到了同一个错误消息，但捕获的方式天差地别：❌ 的那次是靠一个全局兜底监听器碰巧接住的（真实项目里如果没有全局监听 `unhandledRejection`，这类错误默认会让 Node 进程直接崩溃退出，或者在旧版本 Node 里只打印一条警告后被彻底吞掉）；✅ 的那次错误在调用发生的当下就被处理了，出错的上下文（哪次调用、传了什么参数）都还在作用域里，排查起来完全不是一个量级的成本。

## 3. `for...in` 遍历数组的隐患

- ❌ 用 `for...in` 遍历数组：它遍历的是对象的"可枚举属性名"，不是"数组索引"——如果数组对象上被挂了额外的自定义属性（第三方库、框架的响应式实现有时会这么做），这些非索引属性也会被一起遍历进来，而且遍历顺序不保证和索引顺序一致。
- ✅ 用 `for...of` 或 `.forEach`，只关心数组的元素值，不受额外挂载的属性影响。

`pitfalls.ts` 真实输出（给数组挂了一个 `source` 属性之后）：

```text
[❌ for...in] 遍历到的 key -> ["0","1","2","source"]（混入了非索引属性 "source"）
[✅ for...of] 遍历到的元素 -> [10,20,30]
```

## 4. 可变默认参数/闭包共享可变状态

- ❌ 工厂函数返回的对象内部闭包引用的是外部共享变量，或者误把一个已有实例的引用当成"新建了一份"传来传去——一个持有者的操作会"泄漏"影响到其他所有持有同一个引用的调用方。
- ✅ 每次调用工厂函数都创建全新的、互不共享的局部状态，闭包只捕获这份局部状态。

`pitfalls.ts` 真实输出：

```text
[❌ 共享闭包] wrongA.increment() 两次后又被 wrongShared.reset() -> 1
[✅ 独立闭包] counterA.value() -> 2，counterB.value() -> 1（互不影响）
```

❌ 的例子里 `wrongShared` 其实和 `wrongA` 是同一个对象引用（`const wrongShared = wrongA`），调用 `wrongShared.reset()` 意外清空了 `wrongA` 的计数——这是一类极容易在重构、复制粘贴代码时无意间引入的 bug：变量名不同，但底层引用的是同一份可变状态。✅ 的例子里 `counterA`/`counterB` 是两次独立调用 `makeCounter()` 分别创建的，互不影响。

## 5. `any` 类型逃逸导致类型系统形同虚设

- ❌ 用 `any` 接收外部数据（`JSON.parse` 的结果、第三方库没有类型声明的返回值、图省事直接标 `any` 的函数参数），类型检查器对后续所有基于这个值的操作完全失去约束力，一个拼写错误的字段名在编译期不会被发现,只有运行时才会暴露。
- ✅ 用具体类型（或者至少用 `unknown` + 显式类型收窄），拼写错误在 `typecheck` 阶段就会被直接拒绝。

`pitfalls.ts` 真实输出：

```text
[❌ any 逃逸] wrongTotal(order) -> 0（拼写错误被 any 悄悄放过了）
[✅ 具体类型] correctTotal(order) -> 5000（字段名错误会在 typecheck 阶段报错）
```

`wrongTotal` 内部把 `totalCents` 拼错成了 `totlaCents`，因为参数类型是 `any`，`tsc` 对 `order.totlaCents` 这个不存在的属性访问完全不会报错，运行时静默地拿到 `undefined`、再被 `?? 0` 兜底成 0——这是一个远比抛异常更危险的失败模式：代码"看起来正常运行"，但结果是错的，如果这是一个真实的订单金额计算，这个 bug 可能要等到财务对账时才会被发现。

## 6. 浮点数精度问题

- ❌ 直接用 `===` 比较两次浮点数运算的结果——IEEE 754 双精度浮点数无法精确表示大多数十进制小数，`0.1 + 0.2` 的实际二进制表示并不精确等于 `0.3`。
- ✅ 用一个足够小的误差范围（epsilon）判断"足够接近"，涉及金额等场景更推荐直接用整数（比如"分"而不是"元"）做计算，从根本上避开浮点精度问题。

`pitfalls.ts` 真实输出：

```text
[❌ 浮点比较] 0.1 + 0.2 === 0.3 -> false（实际值是 0.30000000000000004）
[✅ 误差范围比较] Math.abs(0.1 + 0.2 - 0.3) < 1e-10 -> true
```

## 7. 同步阻塞操作出现在请求处理路径里

- ❌ 在请求处理逻辑里使用同步阻塞 API（典型的如 `fs.readFileSync`），它会独占 Node 单线程的事件循环，期间**任何**其他工作——包括本该在这段时间内触发的定时器、其他请求的 I/O 回调——全部无法被处理，直接拖垮整个服务的吞吐。
- ✅ 全程使用异步 API（`fs.promises.readFile`），把真正的重计算丢给 Worker Thread（第 05 章「子进程与 Worker Threads」有过完整讨论），避免独占主线程。

`pitfalls.ts` 用一段耗时的同步循环模拟阻塞操作，真实输出：

```text
[❌ 同步阻塞] blockingWork 跑了 25.14ms；理论上 0ms 后就该触发的 setTimeout，在它跑完之前 timerFired 仍然是 -> false（哪怕这个定时器在 0.00ms 前就已经被注册）
```

这个例子里"阻塞"只持续了 25ms 左右，`timerFired` 依然是 `false`——一个理论上应该"立刻"触发的 `setTimeout(fn, 0)`，硬是被同步计算多拖了 25ms 才有机会执行。真实生产服务里如果这类阻塞操作出现在每个请求的处理路径上，在高并发下的后果不是"慢一点"，而是所有并发请求排队等着这条 JS 主线程轮流处理，吞吐量断崖式下跌。

## 8. 忘记处理 `AbortSignal`/超时导致资源泄漏

- ❌ 用 `Promise.race` 实现"给请求加超时"，但从不清理那个没有胜出的、依然在后台运行的任务——它占用的定时器、网络连接等资源会一直挂着，直到自己原本的耗时结束才被动释放。
- ✅ 用 `AbortController` 把"外部不再关心这个结果了"显式传递给正在执行的任务，任务内部监听 `signal` 主动清理自己持有的资源。

`pitfalls.ts` 真实输出：

```text
[❌ 无 AbortSignal] race 结果 -> "超时"，耗时 10.59ms；但那个 50ms 的 slow 定时器依然在后台占用着资源，直到它自己触发才会被回收，无法提前释放。
[✅ 使用 AbortSignal] 结果 -> "超时（已主动中止，底层定时器已被清理）"，耗时 10.90ms；10ms 超时后 controller.abort() 会让 delay() 内部主动清理自己的定时器，不会留下悬空资源。
```

两种写法的"表面结果"看起来差不多（都在 10ms 左右因为超时返回），但底层资源的命运完全不同：❌ 的那个 50ms 定时器依然在后台占用资源，直到它自己触发才会被回收；✅ 的写法里，`node:timers/promises` 的 `setTimeout` 支持传入 `signal` 选项，`controller.abort()` 之后它会主动清理自己的定时器，不留下悬空资源。真实服务里如果每个请求都发起这样一次"不清理"的竞速，在高并发、超时频繁触发的场景下，这些悬空的定时器/连接会持续累积，是内存增长和资源耗尽问题的常见根源——和第 07 章第 01 篇「内存模型与垃圾回收」里讲的"内存泄漏本质是有一根引用没断"是同一类问题的不同表现形式。

## 小结

这八条陷阱背后其实只有几个共通的根本原因：**隐式转换/隐式丢弃类型信息**（`==`、`any`）让代码在编译期看起来没问题、运行时的实际行为却和预期不一致；**忘记显式处理异步结果**（悬空 Promise、未清理的竞速）让错误和资源泄漏被悄悄地推给了不存在的兜底机制；**对底层实现细节的错误假设**（`for...in` 遍历的是属性名不是索引、浮点数不能精确表示十进制小数、同步调用会独占事件循环）让"看起来正确"的代码在特定输入或负载下才暴露问题。代码评审时如果能对照这份清单快速过一遍，很多问题能在合并之前就被拦下来，成本比线上排查低得多。到这里，第 07 章只剩最后一篇——课程总结与进阶方向，会回顾整门课程的知识地图，并给出几个具体的、和这个仓库其他课程内容相关联的进阶学习建议。
