# 内存模型与垃圾回收

> 第 06 章讲完了工程化实践，这一篇往下钻一层，回到运行时本身——V8 的内存管理到底是怎么工作的。上一章「调试性能剖析」那一篇已经用过 `process.memoryUsage()`、也提到了堆快照，这一篇补上背后的原理：V8 堆为什么要分代、标记-清除具体在做什么、`WeakRef`/`FinalizationRegistry` 这两个 ES2021 才加入语言的 API 解决什么问题。不需要讲到 V8 源码级别的细节，重点是建立一个"内存什么时候会被回收、什么时候不会"的正确心智模型。

## 学习目标

- 理解 V8 堆分代假设的基本思路：新生代（Young Generation）与老生代（Old Generation）
- 了解标记-清除（Mark-Sweep）算法的基本步骤，以及增量/并发 GC 要解决的问题
- 掌握 `WeakRef`/`FinalizationRegistry` 的用途，理解"不要依赖 GC 时机做业务逻辑"这条告诫的含义
- 会用 `--expose-gc` 手动触发 GC 做调试，理解为什么生产代码不该这么做

## V8 堆的分代假设：新生代与老生代

V8 的垃圾回收器建立在一个经验观察之上，叫**分代假设**（generational hypothesis）：绝大多数对象都是"朝生夕死"的——一个函数内部创建的临时对象、一次请求处理过程中产生的中间结果，往往在很短时间内就变得不可达，能被回收；只有少数对象会存活很长时间（比如全局配置对象、长期持有的缓存、模块级别的单例）。既然大部分对象活不长，V8 把堆划分成两个区域，分别用不同频率、不同算法处理：

- **新生代（Young Generation）**：容量较小，新创建的对象几乎都先分配在这里。因为区域小、存活对象比例低，V8 用一种叫 Scavenge 的算法频繁地做小规模 GC（把新生代再分成两半，每次 GC 只把还存活的对象从一半复制到另一半，非常快）——这种"频繁但便宜"的策略正好匹配"大部分对象活不过一次 GC"这个假设。
- **老生代（Old Generation）**：容量大得多。一个对象如果在新生代里经历了几轮 Scavenge 都还存活（说明它大概率是长期存活的对象），会被"晋升"（promotion）到老生代。老生代的 GC 频率低得多，但每次要处理的对象数量和总内存量都大得多，用的是下一节要讲的标记-清除算法。

这个"先假设大部分对象短命、只有少数长期存活的才需要用更重的算法处理"的设计,本质上是拿"大多数场景下的平均性能"去换"极端场景下也不会太差"，是几乎所有现代高性能 GC（不只是 V8，Java 的 JVM 也是同样的分代思路）共享的核心权衡。

## 标记-清除与增量/并发 GC

老生代用的标记-清除（Mark-Sweep）算法分两个阶段：

1. **标记（Mark）**：从一组"GC Root"（全局对象、当前调用栈上的变量、闭包捕获的变量等明确可达的起点）出发，沿着引用关系遍历整个对象图，把所有能到达的对象标记为"存活"。
2. **清除（Sweep）**：遍历堆里的所有对象，把上一步没有被标记的对象（也就是从任何 Root 都到达不了的对象）内存回收掉。

这个过程听起来简单，但如果整个标记和清除阶段都是**一次性、不间断**完成的（叫 Stop-The-World GC），意味着 GC 运行期间整个 JS 主线程必须完全暂停——堆越大，需要标记和清除的对象越多，暂停时间就越长，对于需要低延迟响应的服务（比如一个 HTTP 服务器，GC 暂停期间没法处理任何请求），这种暂停是不可接受的。

V8 用两种手段缓解这个问题：**增量 GC**（incremental GC）把一次完整的标记工作拆成很多个小步骤，穿插在正常的 JS 代码执行之间断续完成，而不是一口气做完；**并发 GC**（concurrent GC）更进一步，把标记这类不需要暂停 JS 执行也能安全进行的工作，挪到后台线程去做，和主线程的 JS 执行并行（只有清除阶段、以及标记的极少数收尾步骤才需要真正短暂地暂停主线程）。这两种手段共同的目标，是把"必须暂停用户代码"的时间从"一大段连续暂停"拆分/挪移成"很多次几乎无感的短暂停顿"，这也是过去多年 V8 在垃圾回收上的主要优化方向（从早期版本明显可感知的 GC 卡顿，到现在多数场景下用户几乎感知不到）。

## `WeakRef` 与 `FinalizationRegistry`

正常的对象引用（无论是变量、对象属性还是数组元素）都是**强引用**——只要一个对象能通过强引用链从 GC Root 到达，它就不会被回收，哪怕这个引用早就不再被业务逻辑实际使用。`WeakRef`（ES2021 加入）提供了一种**弱引用**：持有一个 `WeakRef` 不会阻止它指向的对象被 GC 回收，通过 `.deref()` 方法可以尝试取出这个对象——如果对象还活着就返回它，如果已经被回收就返回 `undefined`。

`WeakRef` 典型的适用场景是"缓存"：想缓存一些计算代价较高的对象，但又不希望这个缓存本身成为阻止对象被回收的理由（"缓存不应该是内存泄漏的合法借口"）——用 `WeakRef` 包裹缓存的值，内存压力大的时候 GC 可以自由回收这些对象，缓存未命中时重新计算就是了。

`FinalizationRegistry`（同样是 ES2021）能在一个对象被 GC 回收**之后**收到一次异步通知，用来做一些收尾清理（比如"这个包装了原生资源句柄的 JS 对象被回收了，顺便把对应的原生资源也释放掉"）。

这两个 API 都带着标准里反复强调的同一条告诫：**不要依赖 GC 的具体触发时机做任何业务逻辑**。GC 什么时候运行、`FinalizationRegistry` 的回调什么时候（甚至是否）被调用，完全是引擎的实现细节和调度决策，规范只保证"最终会发生"，不保证"什么时候发生"、也不保证"一定会发生"（如果进程在对象变得不可达之后很快就退出了，回调完全可能永远不会被调用）。这意味着 `FinalizationRegistry` 只适合"锦上添花"式的收尾优化，绝不能是唯一的资源释放路径——文件句柄、网络连接这类真正需要确定性释放的资源，永远应该有一条显式的 `close()`/`dispose()` 调用路径（比如 `try`/`finally`），`FinalizationRegistry` 顶多是"万一忘记显式释放，起码还有一层兜底"，不能本末倒置。

## `--expose-gc`：手动触发 GC 做调试

正常情况下，V8 什么时候运行 GC 完全由引擎自主决定，业务代码无法（也不应该）手动干预。但在调试内存问题、需要让"对象被回收"这件事变得确定性、可观察时，Node 提供了一个调试专用的开关：给 `node` 命令加上 `--expose-gc` 参数，会在全局暴露出一个 `global.gc()` 函数，调用它会立刻触发一次同步的全量 GC。**这个 API 只应该出现在调试脚本和测试代码里，绝不应该出现在生产代码的正常执行路径上**——生产代码里手动调用 `global.gc()` 不仅完全没必要（V8 的自动调度已经根据实际的内存压力做了优化），反而可能因为触发了不合时机的 Stop-The-World 阶段而制造出人为的延迟毛刺。

## 实操：`gc-demo.ts`

`examples/07-进阶主题与总结/01-内存模型与垃圾回收/gc-demo.ts` 把这一篇的几个概念串起来做了一个可运行的演示，包含两部分：

第一部分模拟一次典型的内存泄漏——一个模块作用域的全局数组 `leakedRecords`，`leakSomeMemory` 函数只管往里 `push`，没有任何清理逻辑，配合 `process.memoryUsage().heapUsed` 在 push 前后打印对比。

第二部分演示 `WeakRef`：`createWeaklyHeldObject` 函数内部创建一个对象、用 `WeakRef` 包裹它，函数返回前把局部变量置为 `undefined`（断开这个作用域内唯一的强引用），配合 `--expose-gc` 手动触发的 `global.gc()`，观察 `weakRef.deref()` 从"能拿到对象"变成 `undefined`。

运行方式（实测在 Node v26.5.0 + tsx v4.23.13 下验证可用）：

```bash
node --expose-gc --import tsx "examples/07-进阶主题与总结/01-内存模型与垃圾回收/gc-demo.ts"
```

`--expose-gc` 是给 `node` 可执行文件本身的 flag，必须写在 `--import tsx` 前面——`--import tsx` 只是告诉 Node 用 tsx 提供的 loader 把 `.ts` 转译成可执行的 JS，不影响 `--expose-gc` 这类直接由 V8/Node 自身处理的启动参数。真实运行结果：

```text
===== 内存泄漏模拟：全局数组不断 push =====
[gc-demo] 泄漏前 -> heapUsed = 8.33MB
[gc-demo] 泄漏后（已 push 200000 条记录，每条 payload 长度 50） -> heapUsed = 53.54MB
[gc-demo] leakedRecords.length = 200000 —— 这些对象只要还挂在这个数组上，就永远不会被 GC 回收，这正是内存泄漏的本质：不是「GC 不工作」，而是「代码里还有一根引用没断」。

===== WeakRef 演示：失去强引用后 deref() 变成 undefined =====
[gc-demo] 创建后立刻 deref() -> { id: 1, payload 长度: 1000 }
[gc-demo] 手动 global.gc() 之后 deref() -> undefined（已被回收）
[gc-demo] deref() 变成 undefined，说明那个对象已经被回收——它的唯一强引用（函数内的局部变量 entry）在 createWeaklyHeldObject 返回前就已经被置空。

[gc-demo] 演示结束，已清空 leakedRecords，脚本正常退出。
```

有一个实测中发现的细节值得记下来：**只调用一次 `global.gc()` 往往观察不到 `deref()` 变成 `undefined`**——实测发现需要先调用一次 `global.gc()`，再显式让出一次**宏任务**（用 `await new Promise(resolve => setImmediate(resolve))`，只用 `Promise.resolve()` 这样的微任务不够），然后再调用第二次 `global.gc()`，才能稳定复现。这背后的原因是 `WeakRef` 的清理是在 GC 收尾阶段异步排入的，不一定在同一次 `global.gc()` 调用同步返回时就完成——这个实测细节本身就是这一篇反复强调的那条告诫的具体例证：GC 的确切时序是引擎实现细节，连"手动触发一次全量 GC"这种看似确定性的操作，具体生效的时机都还需要多一步观察和等待，业务逻辑更不应该假设自己能预测或依赖这些时序。

## 小结

V8 堆按"分代假设"分成新生代（频繁、便宜的 Scavenge）和老生代（低频、成本更高的标记-清除），是几乎所有现代 GC 共享的核心权衡。标记-清除分标记和清除两阶段，增量/并发 GC 把原本连续的 Stop-The-World 暂停拆分、挪移到后台，减少对主线程的可感知影响。`WeakRef` 提供不阻止对象被回收的弱引用、`FinalizationRegistry` 能在对象被回收后收到异步通知，两者都只适合"锦上添花"的缓存/收尾场景，绝不能作为需要确定性释放的资源（文件句柄、网络连接）的唯一释放路径。`--expose-gc` 暴露的 `global.gc()` 只应该用于调试，`gc-demo.ts` 的实测还证明了一点：即便手动触发 GC，`WeakRef` 的清理时机依然不是立即、确定的，这正是"不要依赖 GC 时机做业务逻辑"这条告诫最直接的证据。下一篇是性能优化实战，会讲"先测量再优化"的方法论，用 `benchmark.ts` 里两组真实的基准测试，验证几个"直觉但错"的性能陷阱。
