# 性能优化实战

> 上一篇讲了 GC 的原理，这一篇讲性能优化——但重点不在"教一堆孤立的优化技巧"，而在一个更重要的态度：**先测量，再优化**。没有实测数据支撑的"优化"经常是白费功夫甚至反效果，尤其是现代 JS 引擎的 JIT 编译器已经做了大量自动优化，很多"我觉得应该更快"的直觉早就不成立了。这一篇会用 `performance.now()` 手写的基准测试，实测验证几个常见的"直觉但错"的性能陷阱，所有数字都是本机真实跑出来的——正文会反复提醒：具体数字因机器、Node 版本、甚至同一台机器不同时刻的负载而异，真正有参考价值的是**相对趋势**，不是某个具体的毫秒数。

## 学习目标

- 建立"先测量、再优化"的工作方法，理解为什么直觉判断经常不可靠
- 掌握 `performance.now()`、`console.time`/`console.timeEnd` 两种计时方式的用法
- 通过实测理解字符串拼接 `+=` vs `Array.push`+`join("")` 的性能差异
- 通过实测理解高频查找场景下普通对象 vs `Map` 的性能差异
- 知道"不必要的深拷贝"这类隐藏的性能陷阱该怎么识别

## 先测量，再优化

性能优化最容易踩的坑不是"优化得不够狠"，而是**优化错了地方**——凭直觉猜"这里应该是瓶颈"，花大力气重写，实测下来对整体性能毫无影响,因为真正的瓶颈在别处（很可能是一次网络请求、一次同步文件 I/O，而不是某个 JS 函数本身的计算耗时）。这也是上一章「调试性能剖析」讲 CPU Profile 的意义所在：`node --prof-process` 生成的报告会诚实地告诉你时间到底花在哪个函数上，不需要靠猜。

这一篇聚焦的是更细粒度的"写法级别"优化——同一个逻辑目标，用不同的语言特性/数据结构去实现，性能差异有多大。这类优化的正确姿势永远是：**先写一个能复现真实场景规模的基准测试，测出当前写法的耗时基线，换一种写法后再测一次，用实测数字决定要不要保留这次改动**——而不是"读了一篇博客说 A 比 B 快"就直接全项目替换,不同的 Node/V8 版本、不同的数据规模，同一个"最佳实践"完全可能得出相反的结论。

## `performance.now()` 与 `console.time`/`console.timeEnd`

`performance.now()` 返回一个高精度的时间戳（单位毫秒，精度通常能到微秒级），本身不代表任何"真实世界的时间点"，只在两次调用的差值有意义——这正是手写基准测试最基础的构件：

```ts
const start = performance.now();
doSomeWork();
const end = performance.now();
console.log(`耗时 ${(end - start).toFixed(2)}ms`);
```

`console.time(label)`/`console.timeEnd(label)` 是这个模式的语法糖封装，效果等价，只是不需要自己管理开始时间变量：

```ts
console.time("doSomeWork");
doSomeWork();
console.timeEnd("doSomeWork");
```

两者选择上没有对错之分：`console.time`/`console.timeEnd` 写起来更省事，适合临时调试、快速看一眼某段代码耗时；`performance.now()` 手动管理起止时间，更适合写进正式的基准测试代码里（能拿到具体的数字做比较、统计、存档，而不是只打印一行文本）。本篇配套的 `benchmark.ts` 两组正式基准都用 `performance.now()`，额外演示了一次 `console.time`/`console.timeEnd` 的等价用法。

## 陷阱一：字符串拼接 `+=` vs `Array.push` + `join("")`

JS 里的字符串是不可变的——从语义上说，`str += "x"` 每次都要生成一个新的字符串对象，而不是在原字符串后面"追加"。这个语义上的事实,催生了一个流传很广的说法："大量字符串拼接应该用数组收集、最后 `join`，避免反复创建新字符串的开销"。这个说法**部分正确，但被过度泛化了**——现代 V8 对连续的字符串拼接做了名为 rope（绳）的内部优化，不是每次 `+=` 都真的整体拷贝一遍，很多简单场景下两种写法的差距很小,甚至可以忽略不计。

`benchmark.ts` 里对拼接 20 万次的实测（本机三次运行的真实数字）：

```text
[benchmark] += 拼接 200000 次 -> 5.00ms
[benchmark] Array.push + join 拼接 200000 次 -> 2.04ms
```

```text
[benchmark] += 拼接 200000 次 -> 4.18ms
[benchmark] Array.push + join 拼接 200000 次 -> 1.97ms
```

三次实测里 `Array.push` + `join` 都稳定地比直接 `+=` 快了一倍以上——具体数字会因机器而异，但"数组收集+join 更快"这个相对趋势是稳定的。这里的教训不是"以后所有字符串拼接都要用数组"（对于只拼接几次、或者拼接发生在不是热路径的地方，这点差异完全不值得为了"性能"牺牲代码可读性），而是**在真正的热路径（比如循环体内、高频调用的函数里）遇到大量字符串拼接时，这是一个值得实测验证的优化方向**，本篇的数字给出了具体的量级参考。

## 陷阱二：高频查找，普通对象 vs `Map`

另一个常见直觉："对象字面量本质上不就是一张哈希表吗，查找性能应该跟 `Map`差不多"。这个直觉忽略了普通对象额外承担的开销：**原型链查找**（`obj[key]` 找不到时还要沿着原型链继续找，`Map.get` 没有这层负担）、**隐藏类（hidden class）转换**（V8 为对象的属性布局做了大量假设和优化，属性是运行时动态添加的、键的数量很大时，这些优化的收益会打折扣）。`Map` 是专门为"键值查找"这一个用途设计的数据结构，没有这些额外包袱。

`benchmark.ts` 里对 5000 个 key 做 200 万次查找的实测（预先生成好查找用的 key 序列，避免字符串拼接的开销混进计时区间，只测查找本身）：

```text
[benchmark] 普通对象查找 2000000 次（5000 个 key） -> 13.52ms
[benchmark] Map 查找 2000000 次（5000 个 key） -> 8.69ms
```

```text
[benchmark] 普通对象查找 2000000 次（5000 个 key） -> 13.76ms
[benchmark] Map 查找 2000000 次（5000 个 key） -> 8.79ms
```

两次实测里 `Map` 都比普通对象快 35%～40% 左右。这个差距在键的数量较小（比如几个到几十个固定的字面量键）时通常不明显甚至可以忽略——真正值得关注 `Map` 的场景是**键的数量大、且是运行时动态确定**的查找表（比如按用户 ID 缓存会话数据、按请求路径缓存编译好的正则），这类场景下把普通对象换成 `Map` 是一个有实测数据支撑、值得采纳的优化。

## 陷阱三：不必要的深拷贝

前两个陷阱是"这个写法看起来一样快，实测发现有差距"，第三个陷阱方向相反："这个操作看起来无害，实测发现代价很大"。深拷贝（`structuredClone(obj)`、`JSON.parse(JSON.stringify(obj))`，或者手写的递归拷贝）的复杂度和对象的属性数量、嵌套深度成正比——对一个层级很深、字段很多的对象做深拷贝，哪怕只是想"确保调用方不会意外改到原对象"，这个防御性拷贝本身的开销可能远超实际需要。

真实项目里最容易滥用深拷贝的场景是：函数签名上写着"不会修改传入的参数"（遵循这门课程一直强调的不可变性原则），但实现上偷懒直接对入参做一次深拷贝再操作，而不是只在真正需要修改的那一小部分数据上做浅拷贝/局部拷贝。多数场景下，**只需要拷贝到实际会被修改的那一层**——比如只改了一个对象最外层的某个字段，`{ ...original, field: newValue }` 这种浅拷贝就足够保证不可变性，不需要把整棵对象树都递归复制一遍。判断"这里需不需要深拷贝"同样应该遵循"先测量"的原则：如果这段代码不在热路径上、对象也不大，深拷贝的开销完全可以忽略，不值得为了这点性能牺牲代码的简单和安全；如果确实在热路径上、且实测发现深拷贝占了明显的耗时占比，才值得考虑换成更精确的浅拷贝或者干脆调整数据结构避免拷贝。

## 小结

性能优化的第一步永远是测量，不是凭直觉猜。`performance.now()` 适合写进正式的基准测试代码，`console.time`/`console.timeEnd` 适合临时调试。三个实测验证的陷阱：字符串拼接在大量拼接的热路径场景下 `Array.push` + `join` 比 `+=` 更快（本机实测快一倍以上）；高频查找场景下键数量大、动态确定时 `Map` 比普通对象更快（本机实测快 35%～40%）；深拷贝的代价和对象复杂度成正比，很多场景下只需要浅拷贝到实际被修改的那一层，滥用深拷贝换不可变性是不必要的性能损耗。再次强调：本篇给出的所有具体毫秒数都是本机实测结果，换一台机器、换一个 Node 版本，具体数字必然不同，但"哪种写法更快"这个相对趋势通常是稳定可复现的，这也是为什么"自己动手实测"永远比"抄一份网上的性能对比表格"更可靠。下一篇是一份常见陷阱与最佳实践清单，用"❌ 错误写法 / ✅ 正确写法"成对的可运行代码，覆盖类型转换、异步处理、遍历方式等至少 8 类容易踩的坑。
