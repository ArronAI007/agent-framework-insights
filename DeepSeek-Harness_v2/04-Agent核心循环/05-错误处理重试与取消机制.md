# 错误处理、重试与取消机制

这一篇回答：模型请求失败时，`dsh` 怎样决定"要不要再试、等多久"；用户点了停止之后，取消信号怎样一路传到底；工具并发又受什么约束。

结论先行。`dsh` 把失败的分类和处理策略彻底分开：任何来源的失败都被规约成带稳定 `code` 的 `LlmFailure`，`llm-retry` 插件只按 `code` 决定退避，而且重试决策本身先写进会话日志，进程重启后轮次也不会归零。取消靠一根 `AbortSignal` 贯穿到 `fetch` 和工具滚动池，被取消而没来得及执行的工具调用也会补一条合成失败结果，保证调用与结果永远配对。至于 provider 级的主动限流，课程材料明确说明代码库里没有找到实现。

## 失败为什么要先收敛成一种形状

一次请求可能死在很多地方：DNS、连接被拒、TLS 握手（这些在 Node 的 `fetch` 里常被统一包成语义模糊的 `TypeError: fetch failed`）；HTTP 返回非 2xx，body 有没有结构化错误信息不一定；SSE 流中途断线；流看似正常却违反协议，比如 EOF 前没有 `[DONE]`；空闲太久触发本地看门狗；调用方主动取消。如果每层各自处理，上层重试策略就得针对每种情况写一套规则。

`dsh` 的做法是让每个可能失败的层次都收敛到 `LlmFailure`，一个只有 `message`、`code`、`status?`、`providerRetryAfterMs?`、`requestId?` 五个字段的普通对象。重试、压缩恢复、UI 展示都只认这一份结构。

这条链有三层。最底层是 `HarnessError`，整个代码库自定义错误的公共基类，比标准 `Error` 多一个 `code` 字段。`LlmError` 继承它，额外带一份冻结的 `failure` 快照，可序列化，可写入日志。第三层是 `normalizeLlmFailure()`，处理不是从 `LlmError` 抛出的任意值，比如第三方 SDK 的错误或一个裸字符串：只有当错误对象自带的 `failure` 快照与它自带的 `code` 互相印证一致时才直接复用；否则退化成只有 `message` 和 `code` 的对象，不是 `HarnessError` 就记为 `UNKNOWN`。这是"不信任外部抛出的、未经验证的结构"在错误路径上的体现。

`code` 的来源是 adapter 层。DeepSeek adapter 的 `httpErrorCode()` 把 401/403 映射成 `AUTH`，429 映射成 `RATE_LIMIT`，配额相关文案（正则匹配）映射成 `QUOTA`，上下文超限文案映射成 `CONTEXT_WINDOW_EXCEEDED`，5xx 映射成 `SERVER`，其余 4xx 映射成 `HTTP_${status}`。代码注释反复强调的规则是：按 `code` 路由，绝不解析 `message` 文本。这样上一篇的压缩恢复只需要认 `CONTEXT_WINDOW_EXCEEDED`，重试插件只需要认它的可重试集合，都不必关心失败来自 fetch 的哪一层。

## 退避算法与默认值

`llm-retry` 挂在 `agent/request-error` 钩子上，与上一篇的溢出恢复同处一个钩子，各自只处理自己认得的失败，不认得的 `next()` 放行。延迟计算很短：

```typescript
function localDelay(config, retry, random): number {
  const exponent = Math.min(retry - 1, 1024)
  const exponential = Math.min(config.initialDelayMs * 2 ** exponent, config.maxDelayMs)
  const jitter = 1 - config.jitterRatio + 2 * config.jitterRatio * random()
  return Math.min(exponential * jitter, config.maxDelayMs)
}
```

指数增长的基础延迟乘上一个围绕 1 浮动 `jitterRatio` 的随机系数，最后仍不超过 `maxDelayMs`。`Math.min(retry - 1, 1024)` 是防止重试轮次极大时 `2 ** exponent` 算出 `Infinity`。默认值在 `retry-policy.ts`：`initialDelayMs = 500`，`maxDelayMs = 10_000`，`jitterRatio = 0.1`，普通模式 `maxRetries = 5`（材料记录早期这里是 2，后来调大了）。默认可重试的 `code` 是 `EMPTY_RESPONSE`、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`。`AUTH`、`INVALID_CREDENTIAL`、`CONTEXT_WINDOW_EXCEEDED` 不在其中，道理很直接：这类失败不会因为多试一次就自己变好。

如果失败里带有 `providerRetryAfterMs`，`recover()` 优先采用 provider 给的等待时间而不是本地算出的值；但若这个等待超过 `maxDelayMs`，`normal` 模式直接放弃（`return next()`）。框架不会为了一个超长的等待把会话挂住。

## 重试轮次为什么从日志里折叠

重试到了第几轮，一般会想用一个内存计数器。`llm-retry` 没这么做，而是向 `ctx.sessionProjections` 注册了一个 `llmRetry` 投影：遇到 `step/start` 或 `turn/end` 就重置为空，遇到 `llm/retry` 事件就以 `provider + policyKey` 为键记录最新的 `retry` 和 `retryId`。`recover()` 直接读这份投影：取出上一轮的 `retry`，普通模式下已达 `maxRetries` 就放手，否则加一，沿用已有的 `retryId`，没有就生成一个新的。

两个细节值得注意。一是 `retryPolicyKey()` 把当前生效的策略（mode、maxRetries、retryableCodes、退避参数）序列化成字符串，也参与键的匹配。所以请求之间如果策略被改动，旧策略下累计的轮次不会被新策略沿用。二是 `retryId` 在同一串重试之间保持稳定，日志里的多条 `llm/retry` 因此可以关联成一次恢复序列。整体的效果是进程重启后重新走到同一个 step，重试计数不会凭空归零，它和会话历史一样是从日志派生的状态。这里用的是框架提供的投影注册通道，带 `stateVersion` 和 zod schema 校验，与上一篇提到的 `RuntimeContextProjection` 手工维护快照是同一种思路的两种写法。

## 先落盘、再等待、再确认

真正执行等待的 `backoff()` 分三段。先把两个信号（传入的 `signal` 与插件自己的 `lifetime.signal`）用 `AbortSignal.any` 融合，若已中止就直接返回；然后写入 `llm/retry` 事件，记录 retryId、turn、step、provider、mode、policyKey、retry、`delayMs` 和 `failure`；接着 `cancellableDelay` 等待；等待正常结束后再写 `llm/retry-started`，最后返回 `{ kind: 'retry' }` 交给 `step()` 的重试循环。

先落决策的价值体现在回放。如果进程在等待期间崩溃，日志里能看到"决定重试、计划等多久、但没等到确认"这个完整过程，不会留下无法解释的空白。`cancellableDelay` 是标准的可被 `AbortSignal` 提前打断的定时器封装：已中止直接返回 false，否则定时器到点返回 true，中止时清除定时器并返回 false。融合信号里包含插件的 `lifetime.signal`，所以插件被卸载时，正在进行的等待也会随之结束，这是上一部分"注册必须可逆"原则在异步等待上的落实。

另有 `mode: 'always'` 策略：无限重试直到成功、取消或插件被卸载，面向"网络抖动我不管，重试到底"的部署。它的处理顺序是先让 `next()` 里更外层的监听器（比如压缩恢复）有机会处理，只有 `next()` 明确判定不重试时，`always` 才接手。

## 取消信号怎样一路传到底

取消从 `Agent.cancel(cause, options)` 开始：默认先清空收件箱，并把非空闲状态下的 `wakeRequested` 置为 false，然后对当前活动专属的 `phase.abort` 调用 `abort(cause)`。`keepInbox` 选项可以保留已排队的消息。因为 `phase.abort` 只属于当前这一次活动，取消不会误伤下一次唤醒；`turn()` 每次进入下一轮都会换一个新的 `AbortController`。

`AgentCancelCause` 是四种判别值：`user`（用户主动停止）、`parent`（父会话或子代理被取消而连带）、`hook`（某个插件钩子主动中断，带人类可读的 `reason`）、`disposed`（agent 生命周期被销毁）。这个原因会被写进 `turn/end`。

写入前有一步归一化，材料强调容易漏看：`turn()` 的异常收尾和 `wakeDriver()` 不直接使用 `signal.reason as AgentCancelCause`，而是经过 `abortedCancelCause()` 按 `kind` 逐字段拷贝成一个干净的普通对象。原因是 Node 的 `fetch` 会往 abort 原因对象上动态挂一个 `stack` 属性，原样交给 `Session.append()` 要么被日志拒收，要么把非持久化数据写进日志。持久化在 `turn/end` 里的类型是 `TurnEndCancelCause`，比运行时的多一个 `{ kind: 'legacy' }`，只用来容纳从旧格式迁移来的、当年没有记录取消原因的日志，运行时代码永远不会产生它。

信号继续向下：`step()` 的 `signal` 进入 `GenerateOptions.signal`，`LlmRuntime.stream()` 原样转发给 adapter，`DeepSeekAdapter.stream()` 把它和空闲看门狗的信号用 `AbortSignal.any()` 融合后交给 `fetch()`。所以取消是真正中断进行中的 HTTP 请求，而不是逻辑上假装取消、底层连接还挂着。

工具侧同理。`executeToolCalls()` 收到的信号一旦中止，`runGroup()` 停止启动新调用，等已在运行的调用排空，并对每一个"模型发起了但根本没机会执行"的调用，通过 `appendSkippedToolCall` 写一条 `tool/call` 加一条合成的 `tool/result`：内容是 "Error: tool call aborted before dispatch"，`isError` 为真，错误信息里带 `AbortError` 和 `TOOL_ABORTED_BEFORE_DISPATCH` 码。这样每条 `tool/call` 在日志里都能找到配对的 `tool/result`。悬空的调用会让回放时出现"这个 callId 到底有没有结果"的歧义，也会让派生给模型的历史出现没有结果的调用，补一条合成结果就是为了避开这两件事。

## 工具并发是另一个问题

工具并发上限和 provider 限流没有关系，它限制的是同一个 step 里同时运行的工具调用数量。默认 `DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10`，作为部署级配置项，`resolveMaxParallelToolCalls` 要求它是正整数，否则抛错。

`runGroup()` 用它维护一个滚动池：`fillPool` 在 `inFlight` 数量未达上限时不断从待启动队列拉调用。特别之处是每次启动下一个之前，会重新用 `ctx.tools.executionMode()` 检查该调用当下的并发分类，如果从可并行变成了需要独占，池子就停止填充，等当前批次排空后再把这个独占调用当作屏障处理。

分类由工具自己声明。`ToolExecutionMode` 只有 `parallel` 和 `exclusive` 两种，默认是 `exclusive`：工具必须显式实现 `isConcurrencySafe(arguments)` 并且针对这次具体参数返回 `true` 才算可并行。它是基于参数的谓词而不是静态标记，同一个工具不同参数可以有不同分类，材料举的例子是读文件总是安全，写文件要看是不是同一路径。谓词抛异常也按最保守的 `exclusive` 处理。这是典型的 fail-safe：拿不准就串行。

## 没有实现的东西

很多人会想当然地认为，既然有重试就该有主动的 QPS 或并发限流器，避免把 provider 的速率限制打爆。材料的检索结论是：在 `packages/llm` 全目录里找 `rate limit`、`QPS`、`throttle` 相关实现，能找到的只有 `RATE_LIMIT` 这个被动的错误码，它是 provider 返回 429 后被识别、进而触发退避重试的结果，没有任何预测超限、提前放慢发送速度的组件。当前策略完全是被动响应式的。需要主动限流的话，得自己在 provider adapter 或更上层封装里补，不能指望框架里有隐藏机制。

## 我的看法

以下是判断，均以上述材料为依据。

`always` 模式加上"先落盘 `llm/retry`"意味着长时间的无限重试会在日志里不断追加事件。材料没有说明这类事件的体量控制，也没有说明 `always` 模式下 `maxRetries` 是否参与判断（材料中 `llm/retry` 的 `maxRetries` 字段在代码里标为可选）。用 `always` 的部署值得单独观察日志增长。

被动限流的取舍也不是缺陷本身：对单个交互式 agent，429 后指数退避通常够用。但材料同时提到一个 step 内工具可以并发到 10 个，并且子代理会连带产生请求，多个 agent 共享同一个 provider 额度时，被动退避会让各自独立地撞墙再退避。这是我基于"没有全局限流器"这一事实做的推断，材料没有讨论多 agent 场景下的实际表现，需要实测。

## 小结

- 失败先规约成 `LlmFailure`，路由只认 `code`；`llm-retry` 用指数退避加抖动，默认最多 5 次，轮次由日志里的 `llm/retry` 事件折叠而来，决策按"落盘、等待、确认"三段执行，可回放。
- 取消由 `AbortSignal` 贯穿 `Agent.cancel()`、adapter 的 `fetch` 和工具滚动池；取消原因经归一化后写入 `turn/end`，没来得及执行的工具调用补合成失败结果，保证调用与结果配对。
- 工具并发由 `maxParallelToolCalls`（默认 10）与参数级的 `isConcurrencySafe` 共同决定，默认保守；provider 主动限流在当前代码库中没有实现，只有被动的 `RATE_LIMIT` 重试。
