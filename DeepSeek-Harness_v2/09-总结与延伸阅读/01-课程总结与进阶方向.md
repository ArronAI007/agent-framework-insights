# 课程总结与进阶方向

这一篇回答三个问题：前八章讲的东西怎样合成一个整体，DeepSeek Harness（`dsh`）放在 Claude Code、Codex CLI、`pi` 这个坐标里有什么不同，以及这套重框架路线要付出什么代价、读完之后往哪里走。简短的答案是：`dsh` 先把 Cordis 插件框架立起来，再用同一种"座、实现、消费者"结构组织几十个能力域，Agent 循环只是框架里的一个消费者；它与 `pi` 的分野是复杂度放在哪里，这一点有源码依据，与 Claude Code、Codex CLI 的对照则只能停留在推断；代价是真实的，主要落在学习曲线、构建流程、治理门槛和导航成本上。

## 八章的主线

第 01 章从入口讲起。CLI 与 Web UI 看起来只是界面，背后已经在做 Profile 装配、Provider 配置和权限预设，这是理解后面所有章节的第一道门槛：几乎所有能力都是"按 Profile 决定装不装"，而不是写死在代码里。模型每一轮的请求配置，也是在这一章里作为日志里的请求头快照出现的。

第 02 章是地图。仓库里有 307 个可发布叶子包，分布在 54 个能力分类目录下（这两个数字仍在增长），两级目录不是随意的文件组织，而是"能力座与实现分离"在文件系统上的投影。这一章还讲了 pnpm workspace、Host 与 Client 的双面构建、CI 门禁，以及把 Cordis 生态源码放进 `vendor/` 的治理：框架是地基，出了问题要自己能看、能改。

第 03 章是基石，Cordis 的 Context、Service、Plugin 和 Typed Events。一旦这几个词在脑子里成型，后面看到的 `ctx.xxx` 就不再是魔法，而是"某个服务契约被某个 Provider 满足了"。最关键的一条规矩是注册即副作用：所有贡献都通过 `ctx.effect()` 或 `ctx.on()`，撤销是自动、逆序的，热重载、测试销毁和子代理退出才能干净。

第 04 章是 Agent 核心循环。`ReactLoopAgent` 用 `kick`、`turn`、`step` 三层嵌套回答"用户插话何时处理、崩溃后从哪续、停止只打断哪一件事"。会话是只追加的事件日志，`deriveMessages()` 从日志派生历史，压缩通过 Surface 的 `replace` 只改视图不删日志。这一章贯穿全课程的不变量是：模型看到的一切，都必须能从日志重建。

第 05 章是能力扩展范式 CapabilitySeam。抽象座（Service Definition）、实现（Provider）、消费者（工具）三元结构，在这一章从抽象概念变成几十个包里反复出现的代码形态；权限被拆成 `sandbox/mode`、`approval/policy`、`permission/preset` 三个旋钮，沙箱在找不到可用后端时选择不执行（fail closed）。

第 06 章是跨语言边界与部署形态。边界不是"抛个 JSON 过去"：native 侧是手写系统调用的独立可执行文件，Python 侧把整套 Node 运行时打成单文件可执行程序当子进程用，Host 与 Client 之间用 Typert 生成类型安全的 RPC，并兼容 Claude Code、Codex 一类的 Hooks 生态。

第 07 章是多智能体与工作流。子代理、Workflow、Skill 三者回答同一个问题：一个 Agent 不够用时，复杂度以什么形式被组织。答案分别是再开一个 Agent、写一段编排脚本、按需加载一份技能包。

第 08 章是治理：逐文件 100% 覆盖率、Verify the World 的测试哲学、`AGENTS.md` 站规、postmortem 与防御性清单。它是前七章灵活性的配套设施，没有强制规则，几十个能力域各自演化又互相插拔，很容易退化成表面模块化、实际到处耦合。

把八章压成一句话：注册必须可逆，模型可见必须留痕，其余都是围绕这两条纪律展开的。

## 与 pi、Claude Code、Codex CLI 对比

先说边界。课程系统读过 `dsh` 和姊妹课程里 `pi` 的源码，但没有拿到 Claude Code 和 Codex CLI 的源码，因此对后两者的判断只基于公开可观察的行为、官方文档描述的扩展机制（hooks、MCP、subagent、skills 等），以及 `dsh` 主动兼容它们生态这一事实。这部分确定性明显低于前者，下面凡涉及它们的地方都应当读作推断，请读者自行核实。

和 `pi` 的对比最有把握。`pi` 的 Agent 运行时本身就是最小稳定核心，能力通过 TypeScript 扩展在生命周期节点挂钩；`dsh` 先立 Cordis 框架，Agent 循环只是其中一个消费者，每个能力域拆成座、Provider、消费者三段。多模型差异两边都收敛成一层统一适配，只是在 `dsh` 里 LLM 只是几十个能力座中的一个，不是特例。安全隔离上，`pi` 不做进核心，交给外部容器化；`dsh` 把它做成核心的一部分，用三个旋钮表达。会话持久化上，`pi` 是 JSONL 追加写入、天然支持分支，`dsh` 是只追加事件日志加派生视图，压缩靠替换区间。规模上，`pi` 十余个包基本能整体记住，`dsh` 需要专门的导航约定。

两条路线没有对错，是对"复杂度放在哪里"的不同回答。`pi` 把复杂度推出核心，核心能一次读完；`dsh` 把"如何组织复杂度"本身框架化，代价是必须先学会这套框架，好处是几十个能力域被迫用同一种语言描述，新增能力域时"怎么拆"已经被框架回答了。选哪条取决于更看重新人多快能看懂核心，还是多人同时改多个能力域时会不会互相踩脚。

和 Claude Code、Codex CLI 的对照，能确定的只有一点：`dsh` 选择主动兼容它们的 Hooks 生态约定，而不是要求生态迁移到自己的插件写法。由此可以推断，这两个产品对外暴露的扩展面更接近"在相对封闭的核心外开若干标准化钩子"，而 `dsh` 是"整个运行时都是插件"。但这只是从集成层设计做出的推断，课程没有验证它们内部是否也有类似 Cordis 的插件内核，它们完全可能在内部有自己的抽象层，只是没有暴露成用户可直接替换任意能力域的形态。这一点不下结论。

## 代价

彻底的重框架不能只讲好处，下面几项在前面各章基本是顺带提及，这里集中说。

Cordis 的学习曲线是第一道门槛。对只想加一个工具的开发者，Context、Service、Plugin、Typed Events 是额外的一层抽象；`pi` 的读者理论上可以直接从主循环源码读起，`dsh` 的读者必须先吃透第 03 章，否则后面每一段能力扩展代码都只是"看起来像依赖注入"。课程用一整章打这个基础，本身就是这个代价的证明。

Host 与 Client 强制类型分离，换来干净的边界，也换来额外的构建流程。两个独立的 TS Program 避免 Cordis Context 类型污染浏览器端，但任何跨边界的新功能都要走"定义 RPC 契约、用 Typert 生成代码、两侧各自实现"这一整套。项目还处于 developer preview，这更像提前为规模化付的一笔保险费，在包和团队还小的阶段性价比不一定划算。

逐文件 100% 覆盖率的门槛，连它自己都要开例外。`AGENTS.md` 规定 `pnpm run test:coverage` 是 CI 门禁，`packages/*/*/src` 逐文件 100%，但 `vitest.config.ts` 引用的 `scripts/coverage-exempt.ts` 维护了一份重量级测试套件的豁免名单。这说明规则并非免费午餐，集成性强、跑起来很重的测试很难塞进逐文件 100%，团队得持续维护"哪些确实该豁免，哪些是在偷懒"的边界，这本身是一项治理成本。

导航成本是隐性的认知负担。想找一个具体实现，要先弄清楚该去哪个分类目录、`-local`、`-sandbox`、`tool-*` 这类后缀对应哪种实现。当前具体沙箱后端只剩 local 与 windows-acl 两个（此前存在过的远程沙箱后端已不在仓库中）。工具链完善且熟悉命名规则的团队里问题不大，对新人则需要适应期，这也是第 02 章存在的原因。

最后是 developer preview 的现实。`CONTRIBUTING.md` 很坦白：项目处于早期，暂不接受外部 PR，鼓励的方式是写插件、写教程、在生态层参与。所以学完之后想给核心提交代码，目前走不通；更现实的路径是把设计范式用到自己的项目里，或者在 `dsh-plugin` 生态标签下做事。`dsh` 现阶段的重框架投入，更多是团队为未来规模化下注，外部读者暂时只能旁观和借鉴。

## 我的看法

这一节是判断，依据都来自上面的材料。`dsh` 的治理规则和它的架构是互相依赖的：注册可逆靠 HMR 安全测试强制，模型可见留痕靠"未知事件默认拒绝"强制，循环改动靠架构文档预算约束。如果只借用其中的插件化而不引入这些机械化的配套，材料里描述的那种"表面模块化、实际耦合"就是最可能的结局。因此把它当作参考答案时，更值得带走的是"每条设计原则都配一个能让违反者变红的机制"这一做法，而不是具体的能力域拆分。至于重框架是否比精简核心更优，材料只给出了两种路线各自成立的证据，我没有看到足以定论的对比数据。

## 延伸阅读

一手资料集中在几处。仓库根目录的 `AGENTS.md`（强制规则）、`CONTRIBUTING.md`（贡献边界）和 `THIRD_PARTY_NOTICES.md`。Cordis 本身在 `vendor/cordis` 源码，以及 `docs/cordis-tutorial/`、`docs/cordis-api/` 两组文档。`docs/subsystems/*.md` 是子系统级的类型定义与语义，覆盖 core、session、approval、typert、goal、attachment 等几十个子系统，由脚本与源码同步。`docs/cookbook/` 里有 `adding-a-tool.md`、`adding-a-package.md`、`adding-a-vendored-package.md`、`adding-an-llm-adapter.md`、`extension-cookbook.md`，回答"我要做 X，该动哪些文件"。`docs/postmortem/` 的四篇，涵盖 ACP 默认导出丢失注入、JS 表达式意外关闭文件系统工具、Web Agent GUI 反馈闭环、Landlock 部分通知误判子进程失败。跨语言边界的落地代码在 `native/system`（纯 C11，覆盖 Landlock 启动器与 POSIX flock 绑定）、`python/sdk` 与 `python/sdk-runtime`。安全模型相关包是 `packages/sandbox/{sandbox,sandbox-local,sandbox-policy,sandbox-windows-acl}` 和 `packages/interaction/{permission-presets,user-approval}`。

## 按兴趣分流的阅读路径

不建议所有人从头读到尾，第 05 章之后的很多细节课程只挑了有代表性的路径讲透，没有覆盖 307 个叶子包。

想写新工具的人：先回看第 05 章的三元结构在一个具体能力域（例如 `packages/fs`）里的落地，再打开 `docs/cookbook/adding-a-tool.md`，它按"写一个工具要动哪些文件"的顺序组织。

想理解安全模型的人：读 `packages/sandbox/` 下几个叶子包，对照 `native/system` 里的纯 C 实现，感受为什么这个后端要单独手写系统调用；再读 `docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md`，它比任何设计文档更能说明安全边界条件有多难界定。

想理解权限审批交互的人：看 `packages/interaction/permission-presets` 与 `packages/interaction/user-approval`，配合前端的 `packages/client/ui-permission-presets`，能看到"一次性升级授权"从后端到前端如何串起来。

想把类似架构引入自己产品的人：不要直接抄能力域拆分，先在一个小项目里把 Context、Service、Plugin 用透，再考虑套三元结构；跨语言边界则以 `packages/typert` 作为理解编译期生成类型安全 RPC 的最小切入点。

想知道 `dsh` 怎么变成现在这样的人：把 `docs/postmortem/` 读完，很多看起来"故意设计成这样"的防御性代码，是从某次真实故障里长出来的。

可以动手的练习有几个：凭记忆画一张 `kick → turn → step` 的事件溯源时序图，再回头对照代码查漏（重试、取消、压缩触发时机）；选一个能力域，读它的抽象座包，列出新增一个假想 Provider 必须实现的方法；追一次跨 Host 与 Client 的调用链，从 `packages/client` 一路跟到 Typert 生成的契约再到 `packages/host` 的实现；选一篇 postmortem，用自己的话还原"设计假设、触发条件、症状、根因、修复"的因果链；最后在本地跑一次 `pnpm run test:coverage`，对某个故意改动的文件看它怎么报告缺口，体会逐文件 100% 在真实项目里是什么感觉。

## 小结

一、`dsh` 的整体形态是：Cordis 框架打底，座、实现、消费者结构铺到几十个能力域，Agent 循环只是消费者，治理层靠强制规则撑住这一切。
二、与 `pi` 的分野是复杂度放核心之外，还是把组织复杂度的方式框架化，有源码依据；与 Claude Code、Codex CLI 的对照只是基于公开行为和 `dsh` 的兼容选择做出的推断，课程没有验证它们的内部结构。
三、代价真实存在，包括学习曲线、Host 与 Client 的构建流程、覆盖率门槛及其豁免维护、导航成本，以及暂不接受外部 PR 的现状，后续阅读可按兴趣从工具、安全、权限、架构借鉴、故障史几条路径分流。
