# Postmortem 与防御性编程模式

这一篇回答两个问题：一次事故怎样变成一条永久生效的规则，以及一个长期运行、不断拉起子进程、频繁热重载插件的 agent 进程，为什么需要一份专门的防御性编程清单。结论有三点：`postmortem/` 是文档体系里唯一允许讲事故叙事的层级，要解释的不是修复，而是所有安全网为什么集体失灵；四篇复盘反复出现的共同模式是"确定性不等于正确性"，信号被压缩后会丢失区分度；`docs/defensive-patterns.md` 把这些教训蒸馏成不带故事的规则，并被 `AGENTS.md` 列为改动生命周期、并发、子进程和清理代码前的强制阅读项。

## 什么样的 bug 值得一篇 postmortem

`docs/postmortem/README.md` 划了明确的准入线。postmortem 不是 Agent Note：后者记录一个主动做出的设计决定及被否决的备选方案，面向未来；前者是面向过去的失败记录，包括什么坏了、机制是什么、为什么每层安全网都没接住、以及加了哪些具体守卫让同类 bug 下次大声失败。写不写取决于三个条件同时成立：机制不显然（subtle）、暴露的是测试、工具或约定上的缺口而不是一次笔误（systemic）、以及重新发现的成本很高（costly to rediscover）。每篇要以一段三十秒能读完的执行摘要开头，并且必须链接这次复盘催生的守卫，包括测试、`AGENTS.md` 规则和 ADR。

到目前为止有四篇：ACP 服务器加载崩溃、文件系统工具被永久禁用、Web agent 验收了错误的服务器、Landlock 部分强制执行通知被误判为子进程失败。下面精读机制最典型的 0001 和 0004，再用 0002、0003 补出共同模式。

## 0001：100% 覆盖率，第一秒崩溃

标题是 ACP server crashed on connect：`export default` 丢掉了插件的 `inject`。摘要写得很直接：两个集成错误在单元测试全覆盖的情况下仍导致 ACP 崩溃，一个是默认导出使 Loader 丢弃 `inject`，一个是经可追踪代理的可选服务查找在 shadow 边界上失败，手动挂载的测试绕过了这两条路径。

第一个根因在上一篇测试哲学里已经拆过：`packages/acp/acp/src/index.ts` 多写了一行 `export default apply`，`unwrapExports` 于是优先取 `.default`，整个命名空间连同 `inject` 声明一起被丢弃，`apply` 在一个没有任何注入的 fiber 里运行，第一行读 `ctx.agents` 就抛异常。

第二个根因更隐蔽，修完第一个之后才浮出来：`session/load` 仍在读取 `sessionPersistence` 时崩溃。这个服务有意没有放进 `AgentLoop` 的 `static inject`，因为注入它会让非持久化的演示场景永远等一个不会加载的后端，所以代码用属性读取机会性地访问它。但 Cordis 的上下文代理在通过可追踪代理调用服务方法时，会把 `this` 重新绑定到一个 shadow 对象，属性访问的 fiber 遍历只朝祖先方向进行，`sessionPersistence` 所在的 fiber 是兄弟分支，不在祖先链上，遍历到根之后只能抛错。内存测试从未触发它，是因为测试从 fiber 外部直接调用 `ctx.agents.resume(...)`，此时 `ctx.fiber.runtime` 为 `null`，代理走了另一条基于 isolate symbol 的全局 store 直查路径，根本不做那次会失败的祖先遍历。

两个互不相关的 bug 被同一条错误信息（`cannot get property "X" without inject`）绑在了一起，复盘用专门一节回答"为什么所有测试都没抓住"：两个 bug 都源于同一个流程缺口，没有任何测试通过插件的真实加载路径或真实调用拓扑来驱动它。内存 harness 用 `ctx.plugin({ name, inject, apply })` 手工挂载 bridge，手工提供了 `inject`，所以永远复现不了 bug 一；同一个 harness 把所有服务平铺在根上下文上，恢复流程要么运行在顶层，要么经由 origin 仍解析到 root 的 shadow，掩盖了 bug 二的祖先遍历失败。所以复盘的结论不是"补一个测试"，而是改写测试基础设施的搭建方式，并把教训写进 `docs/testing.md` 的"测试真实入口路径"规则。

经验教训里有一句方法论提醒：相信跟踪结果，不要迷信理论。优雅的 shadow 解释是真的，但它是第二个 bug；第一个只是一行导出错误，在数小时看似合理实则错误的推理之后，是一个 fiber 遍历里的 `console.error` 在几分钟内找到了它。

## 0002 与 0003：确定性不等于正确性

0002 讲的是文件系统快照工具被永久禁用。事故发生时，Cordis 只在插件 `config` 字段内对 `!!js` 表达式求值，而 ACP 示例把 `disabled: !!js ...` 写在了 Loader 配置项元数据上，字段永远读到一个 truthy 的表达式对象，文件系统插件在所有模式下都被禁用。它逃过检测的方式才是重点：快照框架把任何确定性的 transcript 都视为有效行为；header pin 验证了组合后的工具 schema，但文件系统场景共享默认组合的 pin，没有独立证明自己需要的工具已注册；刷新快照的动作先于任何语义断言拒绝缺失工具，就把预期的 stdout 和会话日志重写了。工具确实一直返回同一个 `UNKNOWN_TOOL` 结果，它是确定的、可回放的，快照的字面职责（同样输入输出不漂移）被满足了，但"不漂移"和"正确"是两回事。复盘的原话是：快照刷新是 fixture 的生产过程，不是正确性审查；已注册工具缺失这类语义上不可能的结果，需要独立于预期输出的断言。这和测试哲学里"覆盖率证明代码跑过，不证明跑对"是同一个逻辑结构在不同测试层级上的重演。

顺带说明，这条边界今天已经重画：当前 Loader 也会在每次挂载决策时对配置项的 `disabled` 字段做插值，规则因此表述为"`!!js` 在插件 `config` 与配置项 `disabled` 内有效，其余元数据保持字面量"。postmortem 记录的是事故当时的行为。

0003 是变体：Web agent 验收了一个替代服务器，而不是用户正在看的 GUI。agent 依次观察到源码修改成功、构建成功、HTTP 200、注入的启动 manifest，每个信号单独成立，没有一个指向"用户正在看的那个页面确实更新了"。结论是：HTTP 就绪、构建成功和启动 manifest 是不同的事实，验收必须明确指定确切的 origin，并从外部观察所请求的改动是否在该 origin 生效。这与"验证外部世界"是同一原则在产品验收场景里的翻版。

## 0004：共享前缀不是协议

这篇处理沙箱子进程的失败归因。摘要：在 Landlock ABI 较旧的内核上，launcher 会在执行每个子进程前打印一条无害的部分强制执行通知；harness 把共享的 `landlock-run:` 前缀与任意非零子进程退出组合起来，判定为 launcher 失败，于是 ripgrep 在没有匹配项时退出 1 这种普通结果，呈现成了 `SANDBOX_UNAVAILABLE`。

原生 launcher 的约定本来区分得清楚：内核只能部分强制执行时，打印一条精确的信息性文本（partial enforcement, older Landlock ABI）然后继续执行子进程；launcher 真正失败时，打印另一行诊断，以退出码 125 结束，根本不执行子进程。消费这个约定的 harness 却把两种情况压缩成同一个判断：stderr 里出现 `landlock-run: ` 子串，且子进程退出码非零。ripgrep 用退出码 1 表示"搜索完成但没有匹配"，是完全正常的结果，恰好同时满足两个条件，就被误判成基础设施故障。

复盘把根因上升到表示能力的缺陷：公开的沙箱结果类型只能表达一组子字符串，无法表示"Landlock 失败必须使用退出码 125""证据必须出现在一行致命诊断内""同一前缀下有一行精确文本属于信息性通知"。消费方的布尔判定于是把来自不同进程、互不相关的事实拼在一起。修复是把丢失的区分度找回来：`RunnerFailureRule` 携带可选的允许退出码、不区分大小写的逐行致命签名，以及按不区分大小写的整行精确匹配排除的信息性行。教训也被浓缩成两句：进程归因需要多项独立证据同时成立，共享前缀不是协议；信息性与致命诊断可以共享命名空间，所以排除规则必须精确且范围狭窄，同时对未知的致命行保持失败关闭（fail closed）。这个模式适用面很宽：只要判定逻辑图省事，只看某个标志串是否出现，而不看位置、伴随的退出码、是否属于已知的有限清单，就可能重演这次事故，无害信号被误判成故障，真正的故障也可能因缺了那个串而被漏判。

## 从故事到规则的闭环

把三篇放在一起，闭环有固定的三步。第一，bug 逃过了所有现有测试，原因不是测试少，而是搭建方式或判定逻辑有系统性盲区：0001 的手工挂载绕开真实加载，0002 的快照刷新把语义上不可能的结果当作新预期，0004 的子串匹配丢失了区分度。第二，新增一个能让回归真的变红的守卫，并验证它有效：0001 验证恢复 `export default apply` 时测试失败，0004 新增了原生边界回归用例和组装后的快照组合，覆盖"信息性通知后跟非零子进程退出"这个原本矩阵里完全没有的组合。第三，把一般性教训写成规则，放进它归属的那一层文档：0001 催生 `docs/testing.md` 的真实入口规则，0002 催生 `AGENTS.md` 与 `docs/cordis-primer.md` 关于 `!!js` 范围的说明，以及新的静态检查 `verify-cordis-config`，0004 催生更精确的 `RunnerFailureRule`。

这也是上一篇"一个事实只有一个家"的体现：postmortem 负责故事和机制，催生出来的规则不留在里面复述，而是搬去 `docs/testing.md`、`AGENTS.md`、包 README 或具体测试文件。

## docs/defensive-patterns.md：蒸馏后的规则

如果 postmortem 是故事，`docs/defensive-patterns.md` 就是规则清单。它的自我定位是：每条模式都是本项目实际发布或差点发布的一类缺陷，以防复发的规则形式陈述，在编写生命周期、并发、子进程或清理代码前先读。这些模式在 agent 进程里格外重要，是因为它不是跑完就退出的脚本，而是长期存活、持续接收消息、动态挂载卸载插件、不断启动又必须清理子进程的常驻服务。材料里列出的有七条。

正交结果独立上报：进程可能已经超时，却仍以退出码 0 结束，因为它捕获了终止信号。`timedOut`、`signal`、`exitCode` 各自独立上报，不要把一个标志的上报嵌套在另一个标志的分支里。这与 0004 是同一问题的两面，0004 里退出码与输出字符串被错误绑定，这里是提醒不要在设计阶段制造耦合。

公共约定两侧都要遵守：实现收到同一结果的多种表示时，应在通过公共 API 返回前规范化。`LlmAdapter.stream()` 的实现可以抛出异常，也可以发出 `finish {kind:'error'|'aborted'}`，而 `LlmRuntime.stream()` 只通过终止型 finish 分片暴露请求失败。这是能力座内部的纪律：不在座的公共边界统一，Consumer 就得为每种表示各写一遍处理。

异步状态不是同步状态：`agent.followup()` 没有逐消息的完成状态或结果，后台任务的完成与轮次边界存在竞争，不要把 `agent/status` 或 `whenIdle()` 当作某次 `followup()` 的结果。inbox 里可以同时排着多条消息、后台任务和 steering 注入，共享同一个"运行中"区间。

dispose 必须达到完全停稳，而不仅是请求停止：清理只发出终止或中止信号就返回，会留下孤儿进程。这几乎是为"agent 会用 bash 工具拉起真实子进程"量身定做的，测试篇里 `afterEach` 的注释就是它的落地。

在分发器中隔离回调异常：用户提供的监听器抛出异常，不得导致其所在的 promise 被 reject，也不得饿死排在它后面的监听器。在"一切皆插件"的架构里，不隔离的话，一个写得不好的插件就足以让清理逻辑本身中途中断。

不要把环境变量或可预测路径暴露给不可信输出：清理 `*KEY*`、`*SECRET*`、`*TOKEN*`、`*PASSWORD*` 一类环境变量，临时文件放在 0700 权限的私有目录，用随机文件名并以独占方式打开。这是唯一带安全属性的一条，因为 agent 会执行模型生成的命令，一次 `env` 就可能把 harness 自己的凭证泄漏出去。

用 unlink 删除链接形态的路径：teardown 时被删路径可能是符号链接或 Windows junction，先判断再用 `unlinkSync` 只删链接本身，不要对它做递归删除并跟进目标。

## 代价与边界

材料明确的边界有三处。第一，不是所有 bug 都写 postmortem，滥用只会稀释真正值得反复读的几篇。第二，防御性清单只收本项目实际发布或差点发布的缺陷类别，因此全文不到 40 行，而不是通用最佳实践大全，这也是它每条都有分量的原因。第三，0004 要求多项证据同时成立，看起来更复杂，其实是让判断的复杂度匹配现实的复杂度，代价是使用者要理解每个失败规则各字段的含义。

## 小结

一、postmortem 的价值在于解释安全网为什么失灵，而不是修复本身：0001 是测试路径系统性绕开真实入口，0002 是快照把确定性当作正确性，0004 是信号被压缩成子串后丢了区分度。
二、每次事故都走同一个闭环：加一个能让回归变红的守卫，验证它有效，再把一般性教训写进归属的文档层，故事留在 postmortem，规则搬走。
三、`docs/defensive-patterns.md` 把生命周期、并发、子进程和清理这几类教训写成短清单，因为常驻 agent 进程会不断拉起子进程、热重载插件，这些坑在这里比在一次性脚本里更容易出事。
