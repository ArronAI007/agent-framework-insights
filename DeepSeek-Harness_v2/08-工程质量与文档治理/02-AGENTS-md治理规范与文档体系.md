# AGENTS.md 治理规范与文档体系

这一篇回答的问题是：一个有三百多个可发布叶子包、几十个能力座的 monorepo，靠什么让所有贡献者（包括驱动开发的 agent 本身）守住同一套规矩。答案分两层。根目录的 `AGENTS.md` 有严格的字数预算，只放"每次会话都得带在上下文里"的站规（standing order），每条一到三行，把展开的道理链接到别处；`docs/AGENTS.md` 则规定了文档体系本身的分层，原则是"一个事实只有一个家"。两层合起来的结果是，规则足够短，能留在上下文里，又不随时间互相矛盾。

## 为什么彻底插件化需要一份站规

`docs/architecture.md` 对项目的定位是：模型适配器、工具注册表、会话日志乃至 agent loop 本身，都是可以从配置替换的插件。这带来一个治理难题：既然任何东西都可以被替换，任何贡献都可以来自任何一个包，那么"什么该做、什么不该做"就没法靠代码结构约束，只能靠一份人和 agent 都会读到的规范兜底。`AGENTS.md` 就承担这个角色，`CLAUDE.md` 是指向它的符号链接，所以它会进入每一次会话的模型上下文。

篇幅因此是硬约束。字数预算集中定义在 `scripts/doc-budgets.manifest.json`，由 `pnpm run verify-doc-budgets` 强制，当前根 `AGENTS.md` 上限是 1950 词，大多数子树的 `AGENTS.md` 不超过 600 词。篇幅越紧，每条规则背后压缩的教训就越多，下面四条最有代表性。

规范还有一个前提要先交代，就是当前处于预发布阶段（pre-stable）。公开 API 允许随意重命名、重新分包，代价是必须在同一个 PR 里更新所有消费方。但已经随发布版本落到用户磁盘上的会话数据，不再是"拒绝旧格式"，而是通过相邻迁移逐版本向前搬：`packages/session/` 下的 `session-format-v0-to-v1` 到 `session-format-v3-to-v4`，每个包负责一步 `vN → vN+1`，已提交的历史世代永远不移动、不覆盖、不删除，`SESSION_FORMAT_VERSION` 当前为 4。SQLite 用单调递增的 `SCHEMA_VERSION`。也就是说，代码可以激进，用户数据必须被抬着往前走。

## Registrations are effects

条款只有一行：每个贡献都必须经过 `ctx.effect()` 或 `ctx.on()`，注册表的 `register()` 返回撤销函数。它要解决插件化架构里几乎必然出现的一类 bug：插件往某个注册表里塞了数据，却没留下撤销路径，卸载或热重载后就留下指向已不存在的插件的孤儿条目，轻则内存泄漏，重则已卸载插件的行为在新会话里复活。`docs/cordis-primer.zh.md` 的说法是，提示词片段、工具 schema、适配器、提供方和监听器都通过 `ctx.effect()` 或 `ctx.on()` 安装，reload 和 teardown 时按预期撤销；如果 teardown 有顺序要求，就把相关工作放进同一个 effect。

这条规则的分量在于它被机械强制：每个注册表都有 HMR 安全测试，对贡献者的 fiber 执行 dispose 并断言清理完成。忘了正确处理卸载的注册表，会在这项测试里直接暴露。放回整体设计看，agent preset 按会话动态组装能力、插件开发时反复热重载、子代理被创建又被销毁，全都依赖这条规则；没有它，"卸载一个插件"就会变成一句谎话。

## Model-visible ⟺ logged

条款原文：抵达模型请求的一切，都必须能从会话日志重建；新增模型可见输入，需要一个会话事件。`docs/architecture.zh.md` 还补了一句，这一点由运行时不变量断言，修改现有消息内容的插件则注册纯消息投影（pure message projection），独立读取器显式传入相同的处理器。用双向箭头而不是单向箭头，是因为两边都要成立：日志里的东西模型能看见，模型能看见的东西也必须在日志里。一旦某段影响了模型上下文的内容没有落盘，fork、resume、transcript、遥测这些以日志为唯一来源的功能就会悄悄与真实发生的事情不一致。

支撑它的是一组具体机制，记录在 `.agents/notes/implemented/architecture/2026-08-10-session-log-version-mechanism.md`。最关键的是默认值的选择：读取器遇到不认识的事件类型时拒绝解读日志，除非该事件的信封带 `ignorable: true`。默认必需而不是默认可忽略，是因为两种错误的代价不对称：忘写标记的后果是把一个本可恢复的会话拒绝过头，是体验问题；默认可忽略则会让同样的疏忽静默地恢复出一个残缺会话，是安全事故。架构保证了这条规则成立：模型可见内容只通过四种带 `surfaceOp` 标记的 surface 事件，再加 `request/header`、`request/context` 折叠进入重建，真正危险的未知事件，恰好是那些不进 surface、却改变日志其余部分解读方式的事件，`session/end-seed` 是现存的例子。相应地，`SESSION_FORMAT_VERSION` 只在结构性变更时递增，普通新增事件靠 `ignorable` 吸收，版本号和这条不变量各管不同粒度的兼容性。

## Plugins, not loop changes

第三条把 `agent-loop` 钉成一份稀缺契约：新行为放在文档化的扩展点上，改动 `agent-loop` 必须同步更新 `docs/architecture.md`。`agent-loop` 是驱动每个会话每个 turn 的核心，如果每个新需求都可以往里加分支，它很快会膨胀成没人能完整理解的巨石。规则的做法是把"要不要改循环"这个危险问题，提前转化成"我的需求对应文档里哪一行"这个安全问题。`docs/architecture.zh.md` 的扩展点表大意如下：

| 目标 | 机制 |
|---|---|
| 添加面向模型的能力 | 在 `ctx.tools` 上注册，schema 加入提示词组装 |
| 拦截请求、工具或轮次 | 使用 `agent/*` 或 `tools/*` 事件；`agent/turn-stopping` 会停止轮次 |
| 添加模型可见上下文 | 调用 `agent.inject()`，落到下一次获准的请求中 |
| 添加持久会话状态 | 扩展 `SessionEventMap`，从日志渲染和回放 |

事件的调用语义也是先定好的：`agent/pre-step`、`agent/request`、`llm/stream` 和三个 `tools/*` 事件是瀑布式（waterfall），监听器必须调用 `next()` 才能继续往下传；`agent/turn-stopping` 是串行（serial）事件，没有 `next()`。这和第 04 章讲的循环设计是一回事。

真正绕不开、必须改循环的场景，规则并不禁止，而是附加一个连带成本：同步更新架构文档。这个文档本身有字数预算，改动者无法把细节无限堆进去，反过来促使他先想能否用现有扩展点表达。它与"capability seam 三角色完整性"规则（一个 seam 同时具备 Service Definition、Service Provider、Consumer 三个角色，拆分只在角色需要独立演化时才发生）配合，共同表达一个态度：新能力的入口是稀缺资源，不能靠在核心循环里打补丁图方便。

## Trust TypeScript at typed same-process boundaries

第四条是在"少做一件通常被当作最佳实践的事"。原文：不要仅仅为了静态接口已经要求的值，增加运行时校验、fallback 行为或恶意输入测试；校验应放在 parser/config、queued、model/tool JSON、durable/file、worker、process、wire 这些边界。

多数工程师习惯在类型已经约束好的函数里再补一层 `if (!value) throw`。在同进程、同一次编译里互相检查过的模块之间，这是重复劳动，还有两个隐蔽的坏处：真正的业务逻辑被防御代码淹没，而 fallback 行为可能悄悄掩盖一个本该在类型层面暴露的真实 bug，让程序在错误状态下继续跑。

规则同时划定了不适用的范围，这份清单本身就是"什么算真正的边界"的教材。它们的共性是值从"编译器能证明形状"的世界跨进了"编译器管不到"的世界：配置文件来自磁盘，排队消息可能是另一次运行留下的旧格式，模型生成的工具调用 JSON 不受静态类型约束，落盘数据可能来自旧版本或被手改过，worker、子进程和线上协议的另一端可能是任何版本。第二条规则里的"未知事件类型默认拒绝"就是这套判断的应用：会话日志是 durable/file 边界，必须运行时校验；同一次编译里的内部调用则不用。所以这条规则不是鼓励少写校验，而是把校验预算从"到处都加一层以防万一"重新分配到真正跨越信任边界的地方。

## docs/ 的分层：一个事实只有一个家

前面四条解决代码层面的问题，`docs/AGENTS.md` 解决文档本身的腐化问题。它的核心原则是：Each fact has one home，事实归属于职责所在的那一层，其他地方只链接过去。文档体系被拆成十多个层级，每层都写明职责和"不该出现在这一层"的内容，挑几个有代表性的：

| 层级 | 职责 | 不属于这里 |
|---|---|---|
| 根 `AGENTS.md` | 站规，每条一到三行，链接其归属 | 故事、示例、从别处复述的内容 |
| `architecture.md` | 有序地图：组合、核心包、循环、seam、扩展点 | 类型定义、单包细节、决策理由 |
| `subsystems/` | 每个子系统一页：类型定义、语义、生成的 Cordis API | 行为叙事 |
| Agent Notes | 活跃的决策记录：为什么、放弃了什么、需要什么验证 | 已落地后的迁移计划、验收清单、"应该……"式的规格语气 |
| `postmortem/` | 事故叙事，唯一允许讲故事的层级 | - |
| 包 README | 单包契约：配置、语义、限制、扩展点 | 对 JSDoc 或生成目录的重复 |

`subsystems/` 是其中长得最明显的一层，现在有六十多个页面（`core.md`、`session.md`、`subagent.md`、`workflow.md`、`skills.md`、`sandbox.md` 等），基本覆盖了本课程各章讲到的子系统。它不是纯手写：`verify-type-equiv` 这类脚本校验页面里粘贴的类型片段与源码是否漂移，配套的 Agent Note（`2026-08-03-package-anchored-subsystem-pages.md`）规定了"一个类型该挂在哪个页面"，页面里的 "cordis-surface" 区域由源码生成，不允许手改。

防腐化的规则有两条。一是 "Document current state"：历史留在 commit、PR、Agent Note、postmortem 里，其他文字只谈仍然存在的机制，不谈变更和"栈上位置"。二是文档异味清单里排第一的 Duplicated rules：搜一个有特征的短语，只保留一个家，其余改成链接。`docs/` 有七十多项内容，还叠加了 `.md`、`.zh.md`、`.i18n.yaml` 三件套的中英双语负担，没有强制的唯一归属，文档会比代码更快陷入重复与漂移。

字数预算和唯一归属是同一件事的两面：篇幅被限死，作者就没有空间重复别处已经讲过的内容，只能把细节搬到归属层。预算不够时，`docs/AGENTS.md` 规定的顺序是先迁移内容到正确层级，其次压缩表达，最后才提高预算，而且提高必须在 PR 里对预算清单的改动作出说明。当前预算清单里，根 `AGENTS.md` 为 1950 词，`architecture.md` 为 2410 词，侧面反映项目本身还在持续变大。

## 代价与边界

站规的代价是每条规则背后的推理被压缩掉了，读者必须顺着链接去找 `docs/architecture.md`、`docs/testing.md` 或某篇 Agent Note 才能还原道理，这也是为什么本篇要把每条规则的背景展开来讲。字数预算能防膨胀，却可能逼着作者把内容"迁移"到别的层，读者需要在多层之间跳转，"一个事实只有一个家"是以查找成本换一致性。另外，预稳定阶段的"代码可以激进"和"用户数据必须向前迁移"是两套不同的纪律，同时维护，成本并不低：每一次结构性格式变更都要多一个迁移包。

材料里还有一个小的不一致：同一份材料中 `architecture.md` 的预算一处写作不超过 1800 词，另一处写作 2410 词，应以 `scripts/doc-budgets.manifest.json` 中的当前数字为准，课程材料中未展开具体数字的演变过程。

## 小结

一、站规靠篇幅预算保持简短，四条规则各对应一个具体机制：注册可逆由 HMR 安全测试强制，模型可见留痕由默认拒绝未知事件保证，循环改动被收窄到文档化的扩展点，运行时校验只花在七类真实边界上。
二、文档体系同样被当作工程产物治理，每个事实只有一个归属层，靠预算、生成工具和检查清单防止重复与漂移。
三、预稳定阶段的分层前提是"公开 API 可改、已发布的会话数据必须迁移"，理解这个前提才能理解这些规则为什么这样设计。
