# 权限预设与个性化配置

这一篇回答的问题是：用户在界面上点一下"workspace-write"或"danger-full-access"，背后到底改了什么。三句话概括：`dsh` 把"工具能碰哪些文件"（`SandboxMode`）和"敏感操作要不要先问人"（`ApprovalPolicy`）拆成两个互相独立的旋钮，各自活在自己的包里；`permission-presets` 只是把几种常见组合打包成可切换的名字，是体验糖衣，切一次预设最多写三条独立的会话事件；默认值不写死在包里，而是由 `dsh-base` 的补丁层按环境变量算出来。

## 为什么要拆成两个旋钮

一个能执行 shell 命令、改写文件的编码 Agent，如果"允许它做什么"和"做之前要不要问"绑在同一个开关上，能表达的组合就很少：要么完全信任，要么完全不信任。"允许随便读写工作区，但超出工作区的必须先问我"这种中间状态，单一等级表达不了。CI 是另一个反例：没人值守、不想弹窗，但仍要把破坏限制在项目目录里。

`dsh` 的做法是把这两个维度拆给两个独立的 Seam：`packages/sandbox/sandbox` 只回答这次执行的文件效应范围，`packages/interaction/user-approval` 只回答要不要先问人。两个包互不 import，只有 `permission-presets` 同时认识两者。

沙箱模式只有三个值：`read-only` 只允许 `/dev/null` 这类必需的输出目的地；`workspace-write` 额外允许工作区和后端定义的临时区；`danger-full-access` 绕过隔离。它只管文件效应，网络访问和进程可见性不在这套词汇表里。执行隔离的是抽象类 `SandboxProvider` 的 `confine(argv, policy)`，契约要求它要么返回真正强制生效的受限命令，要么拒绝；没有可用后端（缺 bubblewrap、Landlock 内核支持或 `sandbox-exec`）时必须抛 `SandboxUnavailableError`，不允许悄悄退化成不隔离直接跑。这是 fail closed。审批策略更简单：`ask`（默认）把问题交给已组合进来的应答者，一个都没有时落到 `'unavailable'`；`never` 对每次询问都确定性地返回 `'rejected'`，从不打扰任何人，是 CI 和无人值守的严格立场。

## 预设：把两个旋钮打包

`PermissionPresetService` 的模块注释把关系讲清楚了：一次切换先记录选中的预设，再通过各自规范的 setter 写入发生变化的旋钮；执行、提示词陈述和回放依然读旋钮本身。一个预设只有两个必填字段 `sandbox` 和 `approval`，另有可选的 `name` 与 `description`。包自己内置了 `workspace-write`（沙箱 `workspace-write`、审批 `ask`）和 `danger-full-access`（沙箱 `danger-full-access`、审批 `never`）两个默认项。

实际运行的 `dsh-base` 在这之上又叠了一层：

```yaml
- id: sandbox-policy
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
- id: approval
  config:
    policy: !!js "(process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'"
- id: permission
  config:
    presets:
      read-only:  { sandbox: read-only,  approval: ask }
      workspace-write: { sandbox: workspace-write, approval: ask }
      danger-full-access: { sandbox: danger-full-access, approval: never }
```

这段配置最直接地证明了"预设只是糖衣"：`sandbox-policy` 与 `approval` 两个底层服务各自读同一个环境变量 `DSH_PERMISSION_MODE` 算出自己的默认值，进程刚启动时用哪个组合完全由它们决定；`permission` 这一行只声明了三个"名字对应组合"的映射，供运行时切换。`!!js` 表达式在这一行对应的插件被激活时求值，所以能读到 `process.env`。

## 切一次预设发生了什么

`PermissionPresetService.apply` 的逻辑是：先解析预设，读出当前会话里两个旋钮的生效值，如果当前预设名不是目标就追加一条 `permission/preset` 事件，然后只对与目标不一致的旋钮写事件，沙箱不同就写 `sandbox/mode`，审批不同就写 `approval/policy`。所以最多三条，且只有真的变化的旋钮才落事件。`permission/preset` 是纯审计记录，不进入模型可见的上下文；真正被执行侧读取的是后两条。想知道"这次执行到底是什么权限"，应读它们折叠出的结果，而不是 `permission/preset`。

反过来，"当前处于哪个预设"不是存储值，而是推导结果。`derive` 先看记录的预设名对应的规格是否与当前旋钮匹配，匹配就返回它；否则遍历预设表找第一个匹配项；都不匹配就返回保留名 `custom`，界面上显示为 Custom。比如用户把沙箱设成 `read-only`、审批设成 `never`，表里没有这个组合，系统不报错，只是标成 `custom`。这是两个旋钮独立可调的必然结果，预设表只覆盖常见组合，并不是全部合法状态。

`auto` 是另一个保留名，留给实验性的 Auto review 集成：只有该集成在运行时通过 `registerAuto()` 注册后，它才出现在可切换列表里，绑定固定的 `danger-full-access` 加 `never` 组合，仅对当前会话有效，写入前还要同步跑一次准入检查。`custom` 与 `auto` 都不允许用作配置表里的条目名，构造函数会直接抛错。

会话内切换的入口是 `/permission` 命令：不带参数时打印当前预设（可能是 `custom`）和所有可选项，带预设名则走 `apply`，未知名字返回错误并列出可选项。Web UI 设置页的权限控件，最终提交的也是这条命令。

## 审批服务的决策路径

`ApprovalService.request()` 只能在已打开的 turn 内调用，否则直接抛错，原因是 `approval/asked` 和 `approval/decided` 这对审计事件必须被 turn 包住。每次询问都在日志里留下这一对事件，即使审批结果本身不进入模型上下文，也必须能从日志回放，这是"模型可见留痕"规则的延伸。

决策在 `decide()` 里。先看信号是否已取消，取消返回 `'cancelled'`；然后是关键的一行：`effectivePolicy(session) === 'never'` 时立刻返回 `'rejected'`，发生在分发任何事件之前。代码注释解释了为什么不把它做成一个高优先级监听器：后注册且带 `prepend: true` 的监听器可能排到它前面，"`never` 无视注册顺序、确定性拒绝"的承诺就守不住，只有服务自己的调用路径能做到。

只有 `ask` 才会走 `ctx.waterfall('approval/request', ...)`。waterfall 是 Cordis 的环绕式派发：监听器可以调用 `next()` 交给下一个，也可以直接返回结果短路。没有应答者时链条落到默认的 `'unavailable'`，返回值不在合法结果集合里也归一化为 `'unavailable'`，抛异常同理。没人能回答的问题，结果是拒绝，不是放行，这是第二处 fail closed。

## 我的看法

三个旋钮加一个推导出来的预设名，模型很干净，但也有一处容易让人误判：界面显示的预设名只是当前组合的一个"反查结果"，而 `permission/preset` 事件记录的是"用户当时选了什么"。两者在旋钮被单独调整之后会不一致，`derive` 用匹配优先来消除这个矛盾，但阅读日志时需要知道这条差别，否则可能把审计事件当成生效权限。这个判断只来自 `apply` 与 `derive` 的代码逻辑。另外，`!!js` 表达式让默认权限随环境变量变化，好处是不改源码就能锁定部署；代价是同一份补丁在不同机器上的默认值可能不同，用 `--dump-config` 也看不到求值结果（见第 03 篇）。

## 部署侧怎么覆盖

默认值可以在两个层面覆盖：包内置的两个默认预设，和 `dsh-base` 补丁层重新声明的三项表。它们靠的是第 03 篇讲的补丁叠加机制，每一行用 `id` 定位到已装配的插件行并整体替换它的 `config`。原课程材料提到部署方可以在 `$DSH_HOME/cordis.patch.yml`（Home 级用户层）针对 `permission` 那一行覆盖 `defaultPreset`；具体补丁支持哪些操作，本篇材料中未展开，可参考仓库里 `docs/architecture.md` 与 `docs/cordis-primer.md`。

## 小结

1. `SandboxMode` 管文件效应、`ApprovalPolicy` 管是否问人，是两个互不依赖的 Seam；预设只是打包，切换预设最多写 `permission/preset`、`sandbox/mode`、`approval/policy` 三条事件，只写变化的旋钮，当前预设由旋钮推导，对不上就是 `custom`。
2. `never` 在 `ApprovalService.request()` 自己的路径里、分发之前短路拒绝，不依赖监听器顺序；`ask` 走 waterfall，没有应答者就是 `unavailable`，与沙箱后端缺失即拒绝一样，全程 fail closed。
3. 默认值由 `dsh-base` 补丁层用 `DSH_PERMISSION_MODE` 等环境变量算出，模型如何申请临时升级权限，见后续章节。
