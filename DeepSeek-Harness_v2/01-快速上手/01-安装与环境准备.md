# 安装与环境准备：把约束前移到安装这一步

这一篇回答的问题是：在一个有三百多个叶子包的 monorepo 里，怎样让每个贡献者装出一致的环境，并且不把 API Key 装进仓库。`dsh` 的做法是把约束前移到安装阶段，而不靠文档提醒或 code review 兜底。具体是三件事：用 `packageManager` 和 `engines` 把 pnpm 与 Node 版本钉死，用 `postinstall` 自动接管 git hooks，把凭证与用户设置拆成两个互不相干的能力座（Seam）。此外 pnpm 的 `allowBuilds` 白名单，把"依赖在安装时执行脚本"这条供应链攻击面也收了起来。

## 版本钉死

根目录 `package.json` 开头几行就锁定了运行环境：

```json
{
  "name": "@deepseek-ai/dsh-root",
  "version": "0.1.7-alpha.1",
  "packageManager": "pnpm@11.7.0",
  "engines": {
    "node": "^22.19.0 || >=24.0.0"
  }
}
```

`engines.node` 的写法是有意的：Node 22 系列必须不低于 22.19.0，这是一条精确下限，不是笼统的"22.x 都行"；Node 24 及以上不设上限。`docs/development.md` 说明 CI 会在 22.19、24、26 三条版本线上跑。`packageManager` 则是一个精确到补丁号的 pnpm 版本，由 Corepack 强制校验。pnpm 版本不一致会让 lockfile 解析或 `allowBuilds` 的语义出现细微差异，"在我机器上能装"就成了一句空话。

`docs/development.md` 的环境要求可以直接当清单用：Node 22.19+ 或 24+；启用了 Corepack 的 pnpm（`pnpm --version` 如果没有经过 Corepack 解析，先执行 `corepack enable`）；Git 2.26 或更新；可选的 DeepSeek API Key，用于 Web、headless、ACP 的自动化演示和真实 API 的 e2e 测试。第三条看上去与包管理无关，下一节会看到它是 hooks 安装脚本的硬前提。

```sh
corepack enable
pnpm install
```

## pnpm install 之后发生了什么

`package.json` 的 `scripts` 里有一个会被 pnpm 自动触发的生命周期脚本：

```json
"postinstall": "node scripts/install-lefthook.mjs"
```

所以跑过一次 `pnpm install`，git hooks 就已经装好，不需要贡献者记得去读文档。这个脚本并不是简单调用 `lefthook install`。它把 hooks 装在 worktree 本地的 `dsh-hooks` 目录，而不是污染整个仓库的全局 hooks 路径；这依赖 Git 2.26 才有的 worktree 级独立配置，脚本里 `MINIMUM_GIT = [2, 26, 0]` 就对应文档里那条 Git 版本要求。它还会写一个带版本号的所有权标记文件 `.dsh-lefthook-owned`，下次安装先检查标记，避免覆盖贡献者手工配置的、不属于 `dsh` 的 hooks 目录；并有一把跨进程安装锁（超时 30 秒），避免并发安装互相踩踏。

`postinstall` 只是默认路径，不是唯一入口。依赖从缓存恢复时它可能被跳过，这时手动补一次即可：

```sh
node scripts/install-lefthook.mjs
```

装好之后，`lefthook.yml` 的分工很克制。`pre-commit` 只对暂存文件做增量 lint（oxlint，带 `--fix`）并检查空白问题；完整的 `typecheck` 放到 `pre-push`。`docs/development.md` 明确说，hooks 有意不跑测试、快照、文档检查、构建和卫生检查，贡献者只需针对改动跑一次相关检查，穷尽式的覆盖交给 CI。这个取舍的理由很朴素：本地检查点必须够快，否则大家会用 `--no-verify` 绕开它，反而没有检查点。

## 凭证从哪里读

真实调用 DeepSeek API 的测试和演示需要一个 Key。`docs/development.md` 的写法很朴素，在环境变量或仓库根目录的 `.env` 里放 `DEEPSEEK_API_KEY`，可选的 `DEEPSEEK_BASE_URL`。`AGENTS.md` 补了一条纪律：不要提交凭证，CI 的 e2e 在没有 Key 时会跳过。

但"读取 `.env`"只是最后一层。`packages/credentials/credentials-local` 的模块注释给出了完整的优先级，从高到低是：

1. 启动进程继承来的环境变量（只读，最高优先级）；
2. `$DSH_HOME/.credentials.yaml`（由 provider 管理，唯一可写的一层）；
3. 调用时工作目录下的 `.env`（只读兜底）；
4. `$DSH_HOME/.env`（只读兜底）。

继承环境变量排在最前，理由写在注释里：`DEEPSEEK_API_KEY=… dsh`、CI secret、容器的 `-e` 参数，都是"这一次运行"的显式意图，进程内部无法编辑它，所以必须"可见地只读"，而不是让写入被静默遮蔽。代码里对应 `assertUnshadowed`：一旦某个引用在继承环境里存在，任何 `set` 或 `unset` 都会直接抛错，错误信息还告诉你该去启动 `dsh` 的那个 shell 里取消这个变量。这比"写成功了但不生效"好排查得多。

## 凭证与设置为什么是两个 Seam

`dsh` 里几乎每一种可替换的能力都按"契约、实现、消费者"三段组织。凭证走的是 `packages/credentials/credentials` 里的 `ctx.credentials`，用户设置走的是 `ctx.settings`，两者刻意分开。

关键约定是：`cordis.yml` 和设置里出现的从来不是密钥本身，而是一个引用，也就是环境变量名，比如字符串 `DEEPSEEK_API_KEY`。真正的值由 `CredentialProvider` 在每次操作发生时解析。这个抽象类有四个方法：`resolve`、`describe`、`set`、`unset`。其中 `describe` 最能说明设计意图：它返回的 `CredentialInfo` 只有 `configured`、`source`、`writable` 三个字段，永远不含值本身。于是 Web 的 Models 页面可以显示"这个 Key 已配置，来自 `.env`，可覆盖"，却没有任何路径能把密钥渲染进 DOM。

这样拆的收益有两点。其一，因为每次操作才解析，改了凭证之后下一次操作立刻生效，不需要重启插件。其二，如果凭证和设置共用一条读写路径，任何把 `settings.get()` 结果整体序列化给前端的代码都可能顺带泄漏密钥；分开之后，这类风险由结构排除，而不是靠开发者小心。

## allowBuilds：默认拒绝安装脚本

`pnpm-workspace.yaml` 里有一段 `allowBuilds`。pnpm 10 起默认策略反转：依赖若带安装或构建脚本，未经审查就直接让安装失败（`strictDepBuilds` 默认为 `true`）。`dsh` 把这份审查清单写了出来，而且每一项都带理由：`esbuild` 要下载平台原生二进制，`lefthook` 要写 git hooks，`node-pty` 要编译 PTY 绑定（含 Windows 的 ConPTY），`koffi` 用于 Windows 下 JSONL 的写穿式持久化。反过来，`@google/genai`、`protobufjs` 这些声明了脚本、但脚本对 `dsh` 没有用的包被显式标为 `false`，安装依然成功，只是脚本不会跑。

这份清单还在增长。仓库新增 `apps/desktop`（基于 Electron 的桌面壳）之后，打包相关依赖也被逐一审查，`electron-winstaller: false` 就是其中一条：桌面端 Windows 走 NSIS，那个辅助脚本不属于构建的一部分。

这与凭证 Seam 是同一种思路：任何隐式、未经审查的行为路径都不被信任，必须显式声明。

## 我的看法

`allowBuilds` 的"逐项注明理由"是好习惯，但它也是一份需要人维护的清单。材料里能看到它随桌面壳的加入而扩张，而新增依赖是否带脚本，只有在安装失败时才会暴露。在 `dsh plugin add` 装 git 来源插件失败时，CLI 会专门提示去 Profile 的 `pnpm-workspace.yaml` 里补 `allowBuilds`（见第 03 篇），说明这条摩擦在用户侧也确实存在。至于这份清单是否有自动化的过期检查，课程材料中未展开。

## 小结

1. 版本、hooks、凭证三类容易被忽略的问题，被前移到工具链层面：精确的 `packageManager` 与 `engines`，`postinstall` 加幂等安装脚本，本地 hooks 只做快速检查点、完整覆盖交给 CI。
2. 凭证有明确的四层优先级，继承环境只读且最高；配置里只放引用，值由 `credentials` Seam 在每次操作时解析，`describe` 不回显值。
3. `allowBuilds` 让"安装时执行脚本"从默认放行变成默认拒绝，逐项注明理由。
