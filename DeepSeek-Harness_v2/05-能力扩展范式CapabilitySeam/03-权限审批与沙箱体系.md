# 权限审批与沙箱体系

这一篇回答：一条命令想写文件，dsh 怎么决定放不放行，被拒之后模型怎样才能拿到更宽的权限，以及不同操作系统上“沙箱”到底能保证到什么程度。概览已经讲过三个旋钮的分工，这里往下走一层：策略在哪里解析，沙箱在哪里兑现，各平台的实现差在哪，升级请求经过哪几道检查。

结论有三句。第一，策略解析和策略执行被拆在两个 seam 里：`ctx.sandboxPolicy` 只算出这次调用用哪个模式，`ctx.sandbox` 负责把模式兑现成受限的 argv，找不到可用后端就拒绝执行。第二，四个运行器用完全不同的内核机制兑现同一份三档契约，并且诚实地区分 `full` 与 `partial` 强制完整性。第三，升级是严格单向递增加一次性人工批准，批准只对当前这一次调用生效。

## 策略解析：三层优先级与投影

`SandboxPolicyService`（`packages/sandbox/sandbox-policy/src/index.ts`）不做任何沙箱包装，只回答“这次调用该用哪个模式、工作区根在哪”。`resolve()` 的优先级链是：调用带的显式 `mode`（经审批的 override），其次会话自己的 `sandbox/mode` 事件历史，最后是部署配置的 `defaultMode`。配置里 `mode` 默认为 `read-only`，`workspaceRoot` 缺省时取会话头里的 `cwd`。一个没有明确声明可写的部署，永远从最保守的状态起步。

会话事件历史现在通过会话投影服务读取：构造函数里向 `ctx.sessionProjections` 注册一个名为 `sandboxMode` 的投影单元，`init` 是 `null`，`apply` 遇到 `sandbox/mode` 事件就把状态换成事件载荷，查询时一行 `stateOf(session, 'sandboxMode')`。投影带版本号和状态 schema，回放时增量更新，查询直接读快照。旧版是每次调用时把事件列表当场折叠，语义一样，性能和复用方式不同。

`SandboxProvider`（`ctx.sandbox`）是兑现这一步的 seam，契约只有一个方法：

```typescript
export abstract class SandboxProvider extends Service {
  abstract confine(argv: readonly string[], policy: SandboxPolicy,
                   signal?: AbortSignal): Promise<ConfinedArgv>
}
```

`confine` 拿到调用方即将 spawn 的 argv，异步返回包裹后的新 argv。异步是因为包装可能要跑一次探测、创建目录 ACL 或连接远程 helper；`signal` 让执行方取消时能中途打断包装。JSDoc 强调必须返回强制生效的 argv，否则在包装或运行时 fail closed，绝不静默直通未加沙箱的原命令，`SandboxUnavailableError` 就是这条承诺的载体。

## 审批：为什么 never 不能是一个监听器

`ctx.approval`（`packages/interaction/user-approval/src/index.ts`）的策略只有 `ask` 和 `never`。`ask` 是默认，交给注册的回答者，没有回答者时 fail closed 成 `unavailable`。`never` 则是确定性拒绝：`decide()` 里先判断 `signal?.aborted` 返回 `cancelled`，再判断 `effectivePolicy(session) === 'never'` 直接返回 `rejected`，之后才进入 `approval/request` 瀑布。

这个检查必须写在服务自己的请求路径里，而不能是一个监听器，源码注释给了理由：以 `prepend: true` 注册、排在检查之前的监听器，会破坏 `never` 无条件拒绝这个文档化承诺，只有服务自己的路径能保证。无人值守的 CI 场景需要的正是这种无法被后加载插件绕过的强保证。

`ApprovalOutcome` 只有四个取值：`allowed-once`、`rejected`、`cancelled`、`unavailable`，没有“永久允许”。每次需要审批的操作都要重新走一遍。这是这套体系里最刻意的立场，后面升级机制的一次性也是它的推论。

## Preset 是糖衣，但有一个诚实的 custom

`ctx.permissionPresets` 的默认表里，`workspace-write` 对应沙箱 `workspace-write` 加审批 `ask`，`danger-full-access` 对应沙箱 `danger-full-access` 加审批 `never`。切换 preset 时，`apply` 先在当前 preset 名不同的情况下追加一条 `permission/preset` 事件，再仅在实际取值不同时分别调用两个旋钮的 setter。也就是说 preset 事件只记录用户意图，真正生效的是紧随其后的 `sandbox/mode` 与 `approval/policy` 事件。当前状态同样从 `sessionProjections` 的 `permissions` 投影读取。

还有一个实验性的 `auto` preset（沙箱 `danger-full-access` 加审批 `never`，由 Auto 审核集成在运行时发布），选中前要先过 `autoAdmit()` 准入回调。`derive()` 在两个旋钮的组合凑不出表里任何一行时返回 `custom`，例如沙箱被手动调回 `read-only` 而审批仍是 `never`。它不是可切换的目标，只是对“当前无法归类”的如实汇报。

## 四个运行器，一份契约

`LocalSandboxProvider`（`packages/sandbox/sandbox-local`）按平台选择运行器链：

| 平台 | 候选链 | 强制完整性 |
| --- | --- | --- |
| linux | `bwrap`，退到 `landlock` | full |
| darwin | `seatbelt` | full |
| win32 | `windows-acl` | partial |

Linux 有两个候选，按顺序做功能性探测，即真的 spawn 一次极简进程验证内核或工具是否可用：优先 bubblewrap，它基于 mount namespace，语义最贴近三档模式的词汇；探测失败才退到 `landlock-run`，它基于 Landlock LSM，不需要 mount 权限，适合受限容器。macOS 和 Windows 各只有一个候选，选中即用，执行期失败再 fail closed。

两种典型 profile 很能说明“同一契约、不同语言”。bwrap 用 `--ro-bind / /` 把整个根文件系统只读挂载，`workspace-write` 时再加 `--tmpfs /tmp` 和把工作区 bind 成可写。seatbelt 反过来，SBPL profile 先 `(allow default)`，再 `(deny file-write*)`，只对 `/dev/null` 和工作区等可写根用 `subpath` 开白名单。一个是默认只读再开洞，一个是默认放行再禁写再开洞，最终都收敛成 read-only、workspace-write、danger-full-access。

Windows 是最复杂的一个。`windows-acl` 用受限令牌运行子进程，配合 ACL 显式授予工作区写权限。设计笔记里记录了一次实战加固：仅受限令牌只覆盖“对象自身安全描述符上的访问检查”，而 Windows 允许经父目录的 `FILE_DELETE_CHILD` 权限删除，`cmd /c del` 能删掉工作区外的文件；受限列表里必须保留的 `Everyone` 组还意味着本来对 Everyone 可写的外部对象依然可写。修复是叠加强制完整性控制：一次 `SetNamedSecurityInfoW` 里同时做三件事，能力 SID 的允许 ACE（原有授权），对 world SID 在 `FILE_DELETE_CHILD` 上挂一个仅容器继承的 DENY ACE，给工作区根贴 Low 完整性标签（`S-1-16-4096`，`SYSTEM_MANDATORY_LABEL_NO_WRITE_UP`），并通过 `SetTokenInformation(TokenIntegrityLevel)` 把受限令牌降到 Low。这样无论写权限来自对象自身还是父目录的 delete-child，内核先过完整性策略，Medium 级别的工作区外对象就写不进也删不掉。

代价也写得清楚：Low 标签和 ACE 一样要常驻在工作区根上，撤销时机是该目录上不再有任何完好的能力授权，不能按会话挂撤。所以 `windows-acl` 在 `STATIC_ENFORCEMENT` 里仍标为 `partial`：NTFS 硬链接仍能把已授权文件别名到工作区外的路径，读取完全不受约束（方案只管写），被 AppContainer ACL 化的目录树对子进程整个不可读。源码注释的原话是，后端把剩余 ACL 能管到的面都管住，但不能宣传成绝对承诺。

## 进程内还有一道围栏

沙箱运行器管的是进程能不能碰某个路径，`fs-sandbox` 在进程内又叠了一道：`isPathUnder`（`packages/fs/fs-sandbox/src/containment.ts`）。先做词法前缀比较；不匹配再沿目标路径逐级祖先做文件身份（`dev` 加 `ino`）比较，用来识别 Windows 上 8.3 短文件名或大小写差异造成的路径别名。一个在内核层拦截，一个在 Node 进程里对“目标到底是不是工作区内路径”做二次校验，两者叠加才是对 `workspace-write` 的完整承诺。

## 拒绝方言与模型的处境

上层要区分“沙箱拒绝了文件操作”和“命令自己失败了”，靠的是每个运行器 stderr 里的拒绝签名：`bwrap` 是 `read-only file system`，`landlock` 是 `permission denied`，`seatbelt` 是 `operation not permitted`，`windows-acl` 有 `access is denied`、`access to the path` 等几条，部署方自带运行器（`runnerCommand` 配置）单独登记一档。只有命中对应签名，模型看到的结果才会附加 `[sandbox: file access denied under <mode> mode]`。`runnerCommand` 会复用 bwrap 的 profile 参数，拼在自定义命令之前。

模型知道自己处在什么模式，靠的是 `sandbox:policy` 动态上下文，每次装配按当前策略重新生成。`read-only` 分支最后一句是让模型不要仅凭这条策略拒绝必要的修改，要正常尝试工具并遵循返回的拒绝与升级指引；`approval:policy` 在 `never` 时则明确告诉模型不要设置 `sandbox_permissions`，因为升级请求必然被确定性拒绝。提示词只告知，判断权留在执行时的沙箱和审批手里。

## 升级流程逐步走一遍

工具被沙箱拒绝后，模型可以在同一轮里带升级参数重试同一个调用。`packages/sandbox/sandbox/src/escalation.ts` 里 `approveEscalation` 的判定顺序如下。

第一步，请求的模式等于当前生效模式：直接放行，不走审批。这让模型带着 `sandbox_permissions` 无害地重放当前模式时不会吃到多余的弹窗。

第二步，严格单向递增校验：`WIDER_MODES` 规定 `read-only` 只能升到 `workspace-write` 或 `danger-full-access`，`workspace-write` 只能升到 `danger-full-access`。不满足直接抛错，连审批都不问。这张表是执行期才查的，故意不写进工具 schema 的枚举：schema 枚举用的是静态并集 `ESCALATION_TARGETS`，是注册表级共享的；“从哪个模式升”是每次调用的运行期事实，两者必须分开校验。

第三步，检查审批服务和调用方 agent 是否存在，缺任何一个都拒绝。第四步，发起 `approver.request`，`reason` 形如 `escalate sandbox to <mode>: <justification>`。结果映射：`allowed-once` 返回目标模式；`rejected`、`cancelled`、`unavailable` 各自抛出带专属文案的错误。

批准的结果只是这一次调用的 `mode` override，不写回会话级的 `sandbox/mode` 事件，下一次同样的命令再被拒绝还要重来。想要“以后都用更宽的模式”，正确路径是通过 `/permission` 命令或 `PermissionPresetService.set()` 显式切换，让变更成为一条独立可审计的事件，而不是依附在某次工具调用的批准上。同文件导出的 `validateEscalationArgs()` 校验 `sandbox_permissions` 与 `justification` 必须成对出现且理由非空，`tool-bash` 与 `tool-fs` 共用它，模块文档说明这样做是为了让两个家族的审批顺序和错误文案不漂移。

`bash` 工具描述里给模型的指引很直接：不要先去聊天里问权限，重试时触发的审批弹窗就是用户同意的方式；一次被拒绝的升级对这条命令是终局，应该停下来解释，不要绕路。

审批和升级是两件事，但升级最终借用审批 seam：审批是通用的“问人”基础设施，任何工具都能在 `tools/pre-execute` 返回 `ask` 触发；升级是它在沙箱场景下的专用封装。

## 远程执行：一次撤退与当前形态

早期这里有 `packages/e2b`，把 `ctx.fs` 和 `ctx.subprocess` 换成云端 microVM 实现。这条路径已于 2026-09-11 整体移除，设计笔记 `2026-09-11-remove-e2b-providers.md` 给出的原因不是速度或成本，而是传输约束：PTC 的 Node 后端需要一条独立于程序 stdin/stdout/stderr 的双向控制通道，而当时锁定的 `e2b@2.29.1` SDK 只暴露标准进程流和 PTY 输出；要自己搭带鉴权的中继流，就得独立解决背压、有界内存、断线清理，笔记的说法是继续做下去会变成一个独立的远程传输项目。

移除的只是一个 provider 家族，笔记同时写明 remote execution remains an intended capability。当前落地的远程形态是 `packages/ssh` 下的 SSH 助手族：`ctx.ssh` 持有认证的 OpenSSH 连接，其上挂 `fs-ssh`、`subprocess-ssh`、`sandbox-ssh`。

## 边界与我的看法

`workspace-write` 不等于工作区里什么都能随便改，写入前还有“先读后写”的版本检查（下一篇展开），它与沙箱模式是独立的两层；也不等于工作区外绝对不可写，要看运行器的 `SandboxEnforcement`。

以下是判断。模式名字与实际强制完整性是两回事，这一点在 Windows 上最明显：用户看到的仍是同一个 `workspace-write`，但保证力度由后端决定，我认为部署时应该把 `partial` 当成需要在文档里单独说明的差异，而不是等同 Linux 与 macOS。这有直接材料支撑：源码里 `windows-acl` 的注释就明确拒绝宣传绝对承诺。另外课程材料提到，dsh 的 `ApprovalOutcome` 没有永久允许，编辑工具没有 `undo_edit`，这两点源码注释没有说明是否有意，课程本身也只陈述现象，我这里同样不推测原因。

## 小结

- 三个旋钮各自持久化并由投影服务提供快照，策略解析在 `ctx.sandboxPolicy`，兑现在 `ctx.sandbox`，找不到后端就 fail closed；`never` 写在审批服务自己的路径里，任何插件都绕不过。
- 四个运行器用 bwrap、Landlock、Seatbelt、受限令牌加 Low 完整性标签兑现同一份契约，Windows 方案仍是 `partial`。
- 升级先查等于当前模式、再查严格递增、再走审批，批准只对一次调用有效。
