# 内置工具全解析

这一篇回答：dsh 自带的二十多个工具包分别管什么，其中最常用的两组，命令执行和文件编辑，在实现层面凭什么可靠。先按类别把工具版图讲清楚，再深入 `bash` 的进程管理与输出处理，以及 `edit` 的字面量替换、原子写和乐观并发。

结论有三句。第一，工具包本身通常很薄，真正的实现在背后的 seam 里，工具目录不是手写的，而是脚本启动每个插件后读 `ctx.tools.schemas()` 生成的。第二，`bash` 的可靠性来自三层正交机制：进程树管理、两级信号升级、内存尾部窗口加落盘 spill。第三，编辑安全靠“写之前用版本号拦住过期认知”，而不是“写之后可撤销”，仓库里没有 `undo_edit`。

## 工具目录为什么可信

`docs/tool-catalog.md` 由生成器产出，生成器会真的启动每个工具插件、挂到真实 context 上读取 `ctx.tools.schemas()`。原因是工具的 schema 不能静态推断：有运行时展开的枚举、拼接的描述文本、配置驱动的名称，以及 MCP 工具的原始 JSON Schema。一个完整性守卫还会扫描 `packages/*/tool-*`，任何没进入生成器启动清单的包都会让生成报错，所以新工具不会被悄悄漏掉文档。也因此，下面提到的每个工具都能对照仓库里的包找到。

## 工具版图：按类别看

执行命令是最核心的一类。`dsh-tool-bash` 提供 `bash`，一次性执行、支持后台运行、超时迁移和沙箱升级，背后是 `ctx.shell`；`dsh-tool-pwsh` 是它的 PowerShell 方言版。想要跨调用保留 cwd 和环境，有两条路：`dsh-tool-bash-persistent` 和 `dsh-tool-pwsh-persistent` 基于 PTY，各只暴露一个同名工具；`dsh-tool-terminal` 暴露六个精细操作（如 `terminal_open`），管理持久 PTY 会话。后两者走的是 `ctx.terminals`，而不是 `ctx.shell`。目录表里 `tool-bash` 与 `tool-bash-persistent` 的模型可见名称都是 `bash`，部署时应只选一套，或按材料所说同时加载多套供模型按场景挑选，具体同名冲突如何处理，课程材料中未展开。这三个家族不是重复建设，而是“要不要跨调用保留 shell 状态”在三种粒度上的具体化。统一的后台任务由 `dsh-tool-jobs` 的 `job_kill`、`job_list`、`job_output` 控制，它对具体任务类型无感，bash 后台命令、`terminal_send(run_in_background: true)` 和 subagent 委派只要都通过 `ctx.jobs.start()` 登记，就能被同一套工具读取和终止。

文件类分两组。`dsh-tool-fs` 提供 `edit`、`read`、`read_image`、`write`，其中 `read_image` 需要 `ctx.attachments`，执行时还要求所选路由声明支持图像输入。`dsh-tool-str-replace-editor` 提供 Anthropic 风格的 `str_replace_editor`，`command` 是 `view`、`create`、`str_replace`、`insert` 四选一。二者共用 `ctx.fs` 和同一套原子写与乐观并发机制，只是模型可见的 schema 不同，这是“能力 seam 与模型工具是多对多关系”的典型例子。检索则是 `dsh-tool-fs-search` 的 `glob` 和 `grep`，后面单说。

代理与协作类：`dsh-tool-subagent` 提供 `subagent`（可配置别名 `subagent_fork`）和固定配对的 `list_subagent_models`，后者专门回答“这个会话里可选哪些模型”；`dsh-tool-subagent-control` 提供 `interrupt_agent`、`list_agents`、`send_message`；`dsh-experimental-tool-agent-team` 提供 `spawn_teammate`、`team_task_*`、`wait_agent` 等九个实验性工具，围绕共享任务清单协作。工作流类有 `ralph`（固定的全新 agent 循环）、`workflow`（通用脚本引擎入口）、`todo_write`（会话自有任务清单）、`create_goal` 等三个会话级持久目标工具，以及 `schedule_create` 等三个为未来根 Agent 创建一次性或周期性调度的工具。

外部世界与知识类：`web_fetch`、`web_search` 背后是可插拔的 `ctx.web`；`lsp` 通过语言服务器做四种标准化查询；`skill` 加载技能正文；`session_search` 等五个工具只读地检索和追踪历史会话事件；`list_mcp_resources`、`read_mcp_resource`、`list_mcp_resource_templates` 读取 MCP 资源。交互与管理类：`ask_user_question` 暂停当前调用等待人工回答，`exit_plan_mode` 结束计划模式并提交计划，`present` 把交付物呈现给会话，`plugin_manager` 安装和启停插件，`load_workspace_dependencies` 按需加载工作区依赖视图，`run_code` 是 PTC 的传输通道。

最近一次目录再生成带来三处调整，值得当作“面向模型的工具面”与“内部机制面”解耦的证据。`dsh-tool-cordis` 从七个动态定义与运行工具缩成两个只读检视工具 `cordis_inspect_list` 和 `cordis_inspect_query`，可以查询活插件的 Config schema，持久变更收敛到 `plugin_manager` 这一个入口；独立包 `dsh-tool-subagent-report` 被整体移除，汇报改由委派链路自己投递；`dsh-tool-subagent` 附带了固定的 `list_subagent_models`。

## bash：三层机制叠在一起

执行链路是 `tool-bash`，经 `ctx.shell`，再经 `ctx.subprocess`，最后是 `subprocess-local` 的真实 `spawn`。前两层在 shell 一篇里讲过，这里看最底层 `packages/subprocess/subprocess-local/src/spawn.ts`。

进程树管理。`spawnSubprocess` 把子进程当作一棵树：POSIX 上 `detached: true`，子进程自成一个进程组；Windows 上 `windowsHide: true` 并用 `taskkill /T` 按根 pid 终止整棵树。命令自己再 fork 出孙进程也不会成为孤儿。传入的 `env` 是先经 `childEnv(spec.env)` 按平台键语义合并，再由 `controlEnvironment(...)` 按 spec 附加上下文 FD 用的环境标记，是两步而不是一次普通 merge。

两级信号升级。取消或超时后，`terminateWithReason` 先发 `SIGTERM`，同时启动 `graceMs` 计时器（`bash-local` 默认 3000ms，与 OpenCode 的默认值保持一致），宽限期结束进程树仍在，才升级成 `SIGKILL`。信号不再直接 `process.kill(-pid, ...)`，而是经 `launch.owner.signal(sig, cancellationReason)` 发出。`BoundProcessOwner` 是一个抽象，具体有 `fallbackOwner`、`linuxScopeOwner`、`windowsJobOwner` 等实现，把 POSIX 进程组、Windows Job 对象、Linux cgroup scope 的差异藏在一个方法后面，并且把取消原因随信号带下去，最终落进结果分类。“进程树是否还活着”也不再靠重读进程表，而是 `observeRangeExit()` 通过 `launch.owner.waitForExit()` 等整棵树蒸发。`rangeExitObserved` 一旦置位，就成为第一个确认的死亡边界，任何迟到或陈旧的 pid 信号都不再发出，宽限计时器同步清掉，避免把信号发给 pid 复用之后的新进程。

输出的尾部窗口与 spill。stdout、stderr 各由一个 `OutputCollector` 收集，内存里只保留尾部窗口，`bash-local` 默认上限 64000 字节；`push()` 在超限时持续丢弃头部、保留尾部，保证模型看到的是最新输出。超限后打开 spill 文件，把完整输出流式落盘：

```typescript
this.spillFile = join(this.spillDir,
  `dsh-subprocess-${process.pid}-${++spillCounter}-${randomBytes(6).toString('hex')}-${this.label}.log`)
this.spillFd = openSync(this.spillFile, 'wx', 0o600)
```

文件名混入 PID、自增计数和 6 字节随机十六进制串，`'wx'` 等价于 `O_CREAT | O_EXCL`，目标路径已存在（无论是普通文件还是符号链接）就直接失败，权限 `0o600`。这个组合专门防御共享临时目录里的符号链接攻击：攻击者预先在可预测路径放一个指向敏感文件的链接，诱使进程写穿。spill 自身也有上限 `maxSpillBytes`，`bash-local` 默认 64MiB，超过就主动停止并删除文件，承认这个流太大记不全。

超时和输出收集是两条独立机制。收集器从 spawn 起持续工作，与是否超时无关，所以即便命令被 `SIGTERM` 或 `SIGKILL` 结束，已有的内存窗口与 spill 文件依然可读，结果里的 `timedOut: true` 与 `stdout`、`stderr` 是分开的字段。这三层合起来的效果是：失控命令不会拖垮宿主，海量输出不会撑爆上下文也不会真丢。沙箱是在此之外再加一层文件访问限制，二者正交叠加。

## glob 与 grep：为什么绕开 ctx.shell

`glob`、`grep` 直接走 `ctx.subprocess`，不经 `ctx.shell`，`search-core.ts` 的模块文档给出了原因。ripgrep 二进制随 npm 包（`@vscode/ripgrep`）分发，不依赖宿主装了系统 `rg`；argv 向量与 ripgrep 之间没有 shell 层，搜索模式里的引号、反斜杠、`$` 不需要转义，也没有被 shell 意外展开的注入风险。`bash` 走 `ctx.shell` 是因为它本就要执行任意 shell 语法，而搜索只需要“spawn 一个固定可执行文件，传一份确定的参数列表”，用更底层的 seam 更贴合。

`glob` 对超限结果有一个部署级配置 `sampleOverCapGlobResults`：`false` 时直接截断保留前 N 条；`true` 时对超限结果抽样展示，并把完整格式化列表存进可选的 `ctx.spillStore`，返回一个之后可读可搜的定位符。这与 bash 的 spill 是同一个思路：不因为一次输出过大就丢信息，只是把完整内容移到上下文之外，留一个可取回的入口。

## edit：字面量替换、原子写、乐观并发

编辑输入不是统一 diff。全仓库搜索 `apply_patch`、`applyPatch`、`multi_edit` 均无命中。`edit` 和 `str_replace_editor` 的 `str_replace` 共用 `applyLiteralEdit`（`packages/fs/fs-local/src/fsio.ts`）：`old_string` 先做换行归一化，空串报 `FS_EDIT_NOT_FOUND`，匹配零次同样报 `FS_EDIT_NOT_FOUND`，匹配多次且没设 `replace_all` 报 `FS_AMBIGUOUS_EDIT`，错误信息里附带“提供更具体的 `old_string` 或设置 `replace_all`”的指引，最后 `content.split(oldNorm).join(newNorm)`。匹配是纯字符串精确匹配，不折叠大小写或空白，只统一 CRLF 与 LF，读入时记录原换行风格，写回时还原。这把“编辑是否精确命中”的校验前置到了应用补丁之前，模型不需要懂 hunk 语法，只需要引用足够独特的原文。

真正的 diff 是结果时才算的展现产物。`computeHunkDiffs`（`packages/fs/tool-fs/src/diff.ts`）用 `diff` 库的 `structuredPatch` 从前后文本反推 hunk，放进 `tool/result` 的 `meta.diffs`，只服务 UI 与重放，不参与修改。

写入落盘走 `writeFileAtomic`：在目标目录旁建私有暂存子目录（`0o700`），用 `'wx'` 以 `0o600` 写临时文件，`sync` 之后再发布。发布分两条：普通替换用 `rename`，同文件系统内原子，任何时刻看到的都是完全旧或完全新，进程中途被杀也没有半截状态；`write` 工具“只创建原本不存在的文件”（`createIfAbsent`）用硬链接 `link()` 发布，目标已存在必然失败，并发创建者之中谁赢由文件系统原子裁决，败者得到 `FS_NOT_OBSERVED` 提示先读再写，赢家已写好的内容原样保留，这比先检查再写的 TOCTOU 做法更稳。几处加固值得记：`mkdir` 和 `open` 之后都紧跟显式 `chmod`，因为 mode 参数会被 umask 收窄，`chmod` 是让指定权限严格落地的双保险；Windows 替换路径在写内容前先把原文件的 DACL 复制给暂存文件，发布用 `ReplaceFile` 风格的 API 而不是 `rename`，保证新文件继承原文件的安全描述符，而不是目标目录的默认 DACL。

并发安全网是乐观版本控制，由 `fs-observation-policy` 强制“先读后写”。它按会话这个 owner、按文件 `targetKey` 记录上一次观察到的版本。`editIntent` 在会话从没读过该文件时抛 `FS_NOT_OBSERVED`，上次观察是“不存在”时抛 `FS_NOT_FOUND`，否则返回读到的版本作为比较并交换的基准；`writeIntent` 在读过时给出 `replaceIfVersion`，没读过时只能 `createIfAbsent`。版本 `FsVersion` 由 `dev:ino:size:mtimeNs:ctimeNs` 拼成的不透明字符串，任一项变化版本就变。底层 Provider 只有当磁盘上的版本与基准完全一致才执行替换，否则说明文件在读与写之间被别人改过，写入必须失败，而不是覆盖。

这也解释了没有 `undo_edit`：dsh 选择在写入前拦住基于过期认知的修改，而不是写入后提供撤销。前者防的是覆盖别人刚写的内容，后者防的是模型自己判断错误造成的破坏。源码里能确认的只是选择了前者、没有实现后者，具体权衡原因注释里没有说明。另外，写文件类工具通常不声明 `isConcurrencySafe`，调度器默认视为独占，同批里不会并发执行，所以 CAS 真正防的是跨调用、跨会话的过期写入，比如两个会话在不同时间读过同一文件，后写的一方版本已过期。

`str_replace_editor` 的四个命令中，`view` 既可看文件（可选行区间）也可看目录，是唯一能作用于目录的；`create` 遇到已存在路径直接拒绝，不会误伤旧内容；`str_replace` 参数名是 `old_str` 和 `new_str`，其余与 `edit` 同源；`insert` 在指定行号之后插入，不需要匹配已有文本。

## 后台任务上的两处近期演进

`job_kill` 对 subagent job 的归属栅栏已被撤掉，现在唯一规则是这个 job 所属的会话你能看见，子会话自己的 job 从它自己的列表里就能杀。另外，人为停止与模型要求的停止被区分：从 Web 或界面侧调用 `JobController.kill` 时，注册表以 `cancelled by the user` 为原因记录，因为不是模型请求的杀停，所以拥有该 job 的 agent 仍会照常收到完成通知，而正在等待它的 `bash`（前台命令启动时就已登记为 job）会在结果里读到原因，渲染成 `[stopped: <reason>]`。

## 我的看法

以下是判断。持久终端家族按 owner agent 隔离，`terminal_list`、`terminal_read` 只能看到自己名下的终端，这在多 agent 场景下是必要的，但课程材料没有说明子 agent 与父 agent 之间能否共享终端，这类跨 agent 的场景我在材料里没有看到说法。同理，`fs-observation-policy` 的观察状态按会话记录，委派出去的子 agent 是否继承父会话已观察的版本，课程也没有给答案，只能列为待确认点，而不应假设继承。

## 小结

- 工具目录由脚本运行真实插件生成，工具包薄、能力在 seam 里；命令执行有 `bash`、持久终端、`pwsh` 三个家族，按是否保留 shell 状态选择。
- `bash` 靠进程树管理、`SIGTERM` 到 `SIGKILL` 的升级（由 owner 抽象屏蔽平台差异）和内存尾部窗口加落盘 spill，做到不拖垮宿主、不撑爆上下文、不丢输出。
- `edit` 用字面量精确匹配前置校验，原子写保证无半截文件，先读后写的版本 CAS 拦住过期修改，因此没有 `undo_edit`。
