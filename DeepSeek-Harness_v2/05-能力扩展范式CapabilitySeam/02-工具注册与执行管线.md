# 工具注册与执行管线

这一篇回答：模型返回的一条 `toolCall`，只是一个工具名加一段 JSON，它凭什么被执行、按什么顺序执行、结果怎样回到会话里。答案是一条固定的流水线：`tools/pre-execute` 瀑布，单调 Guard，`tools/execute` 瀑布，`tools/post-execute` 瀑布，工具自己的 `finalizeContent`，最后是只读的 `tools/result` 通知。权限、沙箱、审批、结果改写都只从这几个点插入，工具本身只负责“给定合法参数，怎么产出结果”。

三句话概括。第一，工具必须在注册时声明输出契约，`execute` 返回规范 JSON 值，模型看到的文本是对它的纯函数投影。第二，调度器允许执行并发，但策略判定、结果落盘、上下文顺序始终保持模型发出调用的原始顺序，并发默认关闭、显式声明才打开。第三，PTC 复用同一条流水线，只是把发起者从模型换成一段程序。

## 注册时就把不合格的工具挡在外面

`ToolRuntime.register()`（`packages/core/tools/src/index.ts`）在把定义放进注册表之前做三类校验。输出契约：`output` 必须存在，`render` 必须是函数，`presentationMeta` 若有必须是函数，`output.schema` 还要通过 `assertSupportedJsonSchema`，否则直接抛 `TypeError`。`timeoutMs` 若声明必须是正的有限数，避免一个 `NaN` 或负数在超时策略里造成难以调试的行为。名字：`run_code` 是 PTC 传输通道的保留名，任何插件都不能注册或覆盖。这三项都在注册时抛错，而不是执行时才暴露，是把问题尽量前移的做法。

返回的 disposer 走 `this.layers.effect(...)`，落在按 scope 分层的存储里，查找时最具体的 scope 胜出，scope 内的注册会遮蔽同名全局注册。围绕它还有两个配套 API：`restrict()` 对某个 scope 的全局工具集做白名单或黑名单过滤，`guard()` 注册一个单调检查函数。三者分工是：`register` 决定工具存在不存在，`restrict` 决定这个 scope 能不能看见，`guard` 决定看见了能不能真的跑。

`ToolDefinition` 上真正影响执行的字段主要有 `output`、`execute`、`finalizeContent`、`timeoutMs`、`isConcurrencySafe`。`presentCall` 和 `presentResult` 只服务 UI，不在流水线里，后面单独说。

## 值与展现分离

`execute()` 不直接返回给模型看的文本，而是返回一个必须满足 `output.schema` 的规范 JSON 值，模型看到的内容由 `output.render(args, value)` 生成。这样分开有两个直接收益。一是 PTC 里模型写的程序拿到的是结构化的 value，可以直接取字段判断，而不是解析一段格式化文本。二是 `render` 是纯函数，历史结果在会话重放时可以重新渲染，不必重新执行工具。

这个设计的代价是每个工具都要多写一份 schema 和 render，对简单工具是额外负担；换来的是执行结果、模型呈现、程序化调用三者的口径统一。

## 并行只在被证明安全时才发生

调度器用 `executionMode` 判断一次调用能否并行，规则是故意收紧的：工具未声明 `isConcurrencySafe`、声明后抛异常、返回值不严格等于 `true`，一律归为 `exclusive`。`read` 工具声明 `isConcurrencySafe: () => true`，因为它纯读取、无副作用；`edit`、`write` 这类写文件工具则不声明，走独占路径。这不是遗漏，是默认拒绝并发。

`packages/core/agent-loop/src/tool-calls.ts` 的 `executeToolCalls` 把一个 assistant step 里的一批调用按连续同质分组。队首是 `exclusive`，这一组就只有它自己；队首是 `parallel`，先把从当前位置到末尾的所有调用都作为候选。候选不等于真会一起跑：`runGroup` 里的 `fillPool` 每次启动下一个调用之前都会再问一次 `executionMode`，一旦发现下一个变成非并行就停止填充，已经在飞的继续跑完，新的不再加入。注册表状态可能在两次调用之间变化，比如前一个调用触发了权限降级，所以“是否并行”是每次启动前重新判定的，不是一次性决定。池容量由 `maxParallelToolCalls` 限制，默认值是 10。

并发执行的另一半约束是提交顺序。`slots` 按调用在这一批里的原始下标存放结果，`commitReady` 用 `while (committed < group.length)` 加 `if (slot === undefined) break`，只有下一个待提交的槽位已经就位才前进。调用 3 先跑完，也要等调用 1、2 落盘之后才能落盘。这两行就是模型侧上下文顺序一致的全部机制。

后面会看到，写入类工具在同一批里其实不会并发，所以乐观并发控制真正防的是跨调用、跨会话的过期写入，而不是同批竞争。这个判断是从调度规则推出来的，不是原课程明说的。

## 三段瀑布加一个单调守卫

`prepareExecution` 里，`createExecution` 先分配调用身份并对参数做无损快照；若调用方已经取消，直接以“派发前中止”的结果收尾。然后 `tools/pre-execute` 瀑布运行，默认回落值是 `allow`，监听器可以返回 `allow`、`deny` 或 `ask`。`ask` 交给 `serviceAsk`，也就是审批服务去问人。只有前面都放行，才调用 `guardReason(exec)` 遍历所有通过 `ctx.tools.guard()` 注册的守卫。任一被拒，都产生一条 `isError: true` 的结果，内容是 `Error: <reason>`，工具体从未被调用。

守卫的类型签名是 `(execution) => string | undefined`：返回字符串是拒绝理由，返回 `undefined` 是没有意见，没有“强制放行”这个选项。这样任何守卫都不能翻转别的守卫的拒绝。把它单列一条机制，而不是塞进 `tools/pre-execute`，原因在顺序上：守卫检查的是已经通过扩展策略的调用，是最后一道只能收紧的闸。

第二段 `tools/execute` 是环绕式瀑布，监听器可以在 `next()` 前后插入逻辑，比如计时和重试，`next()` 最终落到 `dispatchToolBody`，也就是工具体的 `execute()`。执行中通过 `deferContext()` 收集的附加上下文会在这里合并进结果。

第三段 `tools/post-execute` 在结果产出后运行，可以 `accept`、`replace`（替换部分展现内容）或 `block`（把结果转成纠正性错误反馈）。spill 策略把过大的文本结果换成“预览加定位符”，就从这里介入。

三段之后，`finishScheduledExecution` 先对结果做一次无损 JSON 快照，再调用工具自己的 `finalizeContent`，最后触发只读的 `tools/result`。`finalizeContent` 的 JSDoc 要求它是全函数、不能抛异常，因为它是结果确定之后唯一还能碰内容的钩子，它出错没有下游兜底。另外，注册表在调用开始时就快照了这个回调，即便执行中工具被注销或替换，这次调用仍用开始时捕获的那个收尾。

`ask` 与 `block` 看起来都是拒绝，性质不同。`ask` 在执行之前，结果只有允许一次或拒绝，工具体不会被调用；`block` 在工具体已经执行完之后，副作用可能已经发生，只是把结果换成纠正性反馈。所以能提前拦截的判断应该放在 `pre-execute` 或守卫，`post-execute` 只留给必须看到结果才能判断的场景，比如超长结果需要 spill、内容需要脱敏。

## 呈现为什么不进流水线

`presentCall` 和 `presentResult` 告诉 UI 一次调用或结果该渲染成什么样，要求是只依赖 `args`（以及 `presentResult` 依赖的 `result`）的纯函数。`bash` 是个直观的例子：后台运行渲染成 `card: 'generic'`，前台运行渲染成带退出码信息的 `card: 'terminal'`，无论渲染成什么，给模型的规范值不变。

分离的价值在重放。实时执行和重放历史日志用同一批纯函数渲染，得到同样的卡片，重放时也不会把 `bash` 再跑一遍。`edit` 的 `presentResult` 从 `result.meta`（随会话持久化的不透明展现数据）里取结果时算好的 diff 数组，而不是重读文件比对，`meta` 存在的目的就是让“结果时算一次，之后随便重放”成立。

## PTC：另一条分发路径

PTC 即 Programmatic Tool Calling，早期叫 Code Mode，现在包位于 `packages/ptc-runtime/*`，模型可见的工具名仍是 `run_code`。`ctx.tools` 的呈现模式配置是 `'native' | 'ptc' | 'both'`。设为 `ptc` 或 `both` 时，模型看到的是一份生成的 SDK 说明加一个可直接调用的 `run_code`，参数是一段程序体。程序里每次 `await tools.name(args)` 并不是本地函数调用，而是重新进入调度器，走完整的 `prepare`、`dispatch`、`finalize`，策略、沙箱、审批检查一样不少，只是发起者变成了正在运行的程序。

每个子调用都记一对 `tool/ptc-dispatch-start` 和 `tool/ptc-dispatch` 事件，便于重放时重建程序内部到底发起了什么；但子调用不进入模型历史，进入历史的只有 `run_code` 自己的最终结果。价值就在这里：模型可以在一次调用里串联多个工具、做条件判断和循环，中间结果不占上下文窗口。程序内部子调用的并发上限是 `maxParallelSubCalls`（属于 `ToolRuntime` 配置），与外层的 `maxParallelToolCalls` 是两个独立的配置，默认值恰好都是 10。

执行后端方面，当前默认是 `packages/ptc-runtime/ptc-runtime-node` 的 `NodePtcRuntime`，`isolation` 为 `'process'`，即独立 Node 进程，并注入 `fs`、`subprocess`、`sandbox`、`sandboxPolicy` 四个服务，与 `bash` 同一组，每次 `run` 也从 `ctx.sandboxPolicy` 解析策略。早期后端是同进程 worker 线程，只做资源约束，明确说明信任等级与直接跑 bash 相当。

`PtcRuntime` 抽象类上 `isolation` 字段的 JSDoc 有一句要点：它是描述性标识，不是准入条件，不是安全承诺，公认取值如 `'worker-thread'`、`'process'`、`'container'`。区别不在名字，在有没有真正接入沙箱：早期后端没有接入，当前后端接入了。所以不能拿 `isolation` 的字面值来推断安全等级。

## 小结

- 注册时校验输出契约、超时和保留名，执行时依次穿过 `pre-execute`、守卫、`execute`、`post-execute`、`finalizeContent`，拒绝越早越安全。
- 并发是显式授予的：只有严格返回 `true` 才并行，池按实时状态收缩，结果按原始顺序提交。
- PTC 复用同一条流水线，隔离的强弱取决于后端是否接入沙箱，而不是 `isolation` 的名字。
