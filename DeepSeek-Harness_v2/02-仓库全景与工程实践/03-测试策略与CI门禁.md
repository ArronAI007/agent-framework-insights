# DeepSeek Harness 的测试与 CI：绿色的单测，怎么才算真的能用

这一篇要回答的问题是：dsh 怎么避免"单测全绿、产品却坏了"，测试为什么要分层，CI 的门禁又怎么编排才不至于变成没人敢改的 YAML 黑箱。

结论有三点。第一，测试分成七层 Vitest 配置，每层验证不同维度的"真实性"，不能合并；核心哲学是尽量用真实实现、对着真实模型跑、检查外部世界而不是 agent 的自述。第二，CI 的检查项依赖图和并发调度写成 TypeScript 程序 `scripts/run-gates.ts`，YAML 只负责触发具名模式，并在 `all-checks-passed` 里汇总 required jobs。第三，本地 lefthook 只做几秒内能完成的快反馈，完整矩阵全部留给 CI。

材料里的层数和门禁数量在迭代中变过（测试层从五层变成七层），具体断言以仓库里的 `docs/testing.md` 为准。

## 为什么必须分层

只跑一层能过就行的单测，最典型的坑是"绿色的单测，坏掉的产品"：所有子函数都被 mock 到位，单测全绿，但 Loader 装配、进程间协议、构建产物的模块解析这些真实的组装路径一次都没被跑过，到用户手上才炸。反过来，每次提交都跑真实调用 LLM API 的端到端测试，本地开发和没有密钥的贡献者会被挡在门外。两个极端都不可接受，所以测试要分层，每层验证不同的真实性，而不是简单叠加断言。

`docs/testing.md` 的 Tiers 一节列出七层，每层对应一个独立的 vitest 配置：

- Unit（`pnpm run test`）：放在被测代码旁边的 `tests/**` 里，另含 `scripts/**/*.spec.ts`。仓库要求每个 registry 都有 HMR 安全性测试，销毁贡献插件的 fiber，断言清理正确执行，这直接对应 Cordis 的热重载语义。
- Coverage gate（`test:coverage`）：真正卡 CI 的一层，`packages/*/*/src` 下逐文件 100%。
- Real-API e2e（`test:e2e`）：带密钥对着真实 provider API 跑，每个套件没有对应密钥就自动跳过，无密钥的 CI 因此仍然是绿的。
- Owner-local expected output（`test:expected`）：不需要密钥、也不需要录制会话，直接对构建产物的 CLI 或进程断言确定性输出。它填的是 snapshot 录制成本高与 e2e 需要真实密钥之间的中间地带。
- Performance benchmarks（`test:bench`，Linux 上的 required PR gate `node 24 / benchmarks`）：在 `benchmarks/` 下用合成输入强制执行耗时、堆内存和随规模增长的预算，计时代码在纯 Node 下跑，不走 TSX。它让性能预算第一次成为会挡 PR 的门禁。
- Snapshot（`test:snapshot`）：用一个顶层场景已录制的最高父代内容提供用户输入和模型回放，再把它当作期望的持久化结果。进程场景都从 `dsh` 启动：headless 管一次性行为，SDK 管持久控制，ACP 管自动化协议行为。
- Web browser snapshot（`test:web`，required Linux PR gate）：Chromium 对比会话驱动的输出和纯 UI 输出。CI 里强制只读 `DSH_SNAPSHOT=replay`，永不写期望输出，录制和刷新只能在本地做，每个 diff 都要人工审查。

各层解决的问题不同，所以配置也是分开的：`vitest.config.ts`（unit 与 coverage 共用，coverage 多传 `--coverage`）、`vitest.e2e.config.ts`、`vitest.expected.config.ts`、`vitest.bench.config.ts`、`vitest.snapshot.config.ts`、`vitest.web.config.ts`。

## 覆盖率门禁的写法

覆盖率阈值是硬编码的：

```typescript
thresholds: coveragePartitionMode ? undefined : {
  perFile: true,
  statements: 100, branches: 100, functions: 100, lines: 100,
},
```

`perFile: true` 是关键，它防止一个测得很充分的大文件把一个几乎没测的小文件的平均分拉上去。外面那层 `coveragePartitionMode` 判断，是因为覆盖率门禁现在可以拆成多个并发分区跑，分区内不单独判定阈值，汇总阶段才做最终判定。配置里的注释是"100% or it doesn't merge"。

豁免是显式且有条件的。以 `pwsh-local` 为例，它的 run、start、lifecycle 套件在没有真实 `pwsh` 的机器上会自动跳过，覆盖率远低于逐文件 100%。配置的做法是用 `spawnSync` 探测 `pwsh`，探测不到时才把 `packages/shell/pwsh-local/src/index.ts` 和 `packages/shell/pwsh-sandbox/src/**/*.ts` 列入排除，CI runner 装了 `pwsh`，所以仍然强制满覆盖。豁免不是偷懒，而是承认覆盖率依赖一个本地不一定具备的外部程序，并把豁免范围限制在恰好缺这个程序的环境里。

另外，`docs/testing.md` 对覆盖率缺口的态度值得记住：未覆盖的行往往是门禁在提示删除的死代码，而不是要补的测试。e2e 配置则相反地放宽，测试超时 120 秒、重试 2 次，因为共享的内部密钥会遇到并发配额造成的偶发失败，而且 e2e 不计覆盖率，覆盖率门禁由 unit 套件负责。

## 四条测试哲学，各自落在哪里

`docs/testing.md` 的措辞克制，但每一条都对应仓库里可验证的机制。

"We are DeepSeek, do not ration real-API tests." 无密钥的测试只能证明管线通了，只有带密钥的运行才能证明 agent 对着真实模型能工作，覆盖写文件的 prompt、多轮对话、工具调用和流中取消。价值最高的是 smoke test：启动真实示例、发一个 prompt、检查世界的变化，它们能抓住 mock 永远抓不住的"绿色单测、坏掉的产品"，文档里引的是 postmortem 0001（ACP 默认导出丢掉了 inject）这次真实事故。

"Prefer the real implementation over a mock." 只在昂贵或不确定的边界上 mock（LLM 适配器、网络、时钟），下游全部保持真实。桥接层的工具调用测试保留真实的工具注册表和管线，脚本化的 `MockAdapter` 是唯一的替身，`makeBridgeHarness()` 挂载真实的循环、会话存储、工具注册表和 JSONL 持久化。也就是说测试里被替换的只有"模型会返回什么 token"这一个不确定点。

"Verify the world, not the self-report." e2e 断言要重新执行命令或重新读文件，而不是对 agent 自己的输出做关键词检查，否则一个作弊的 agent 也能通过；并且要断言没被触碰的文件字节级不变。这条规则专门防假阳性。

"Test the real entry path." 真实入口指发布出去的构建产物本身：包的 `bin` 在纯 `node` 下运行构建出的 `lib/bin.js`，暴露 tsx 会掩盖的问题，例如 settle 竞态、模块解析、被吞掉的加载失败。同时要断言真的缺失配置时进程以非零码退出。这类 `built-lib.e2e.ts` 测试现在分布得更广，`packages/experimental/*`、`packages/lsp/lsp-stdio`、`packages/api/remotes` 下都有。材料里还有一个小提醒：`docs/testing.md` 原文举的例子路径 `packages/examples/*/tests/built-bin.e2e.ts` 已经过期，实际是 `apps/cli/tests/built-bin.e2e.ts`。文档的例子会滞后于代码，路径类信息要自己核对。

## GitHub Actions：一个汇总门禁

`.github/workflows/ci.yml` 里，PR 真正必须全绿的 job 由 `all-checks-passed` 的 `needs` 列出：`node-24`（静态检查）、`node-24-coverage`、`node-24-bench`、`node-24-consumers`（快照、构建产物验证和 Playwright 浏览器快照）、`node-compat`（Node 双矩阵兼容）、`python-sdk`（无密钥的 SDK 套件）、`python-runtime`（单文件可执行体的发布形态 smoke）、`windows-build` 和 `windows-native-tests`。它的判定很简单：任一 needed job 的结果是 `failure`、`cancelled` 或 `skipped` 就失败。

这里有两处有意思的设计。一是 Windows 被拆成 build 和 native-tests 两个独立的 required job，另有一个不在 required 列表里的观察窗 `windows-coverage`，跑 PR 但不参与合并判定。二是 CI 有一个自托管失败转移开关 `DSH_CI_FAILOVER_LINUX`，`all-checks-passed` 这个纯汇总 job 也要跟随同一个开关重新定位到备用 runner 池，目的是自托管池故障时，连"这个 PR 算不算全绿"的判断本身也不会卡住。`ci-master.yml` 里 master push 触发的 Wine 演练、`serial-linux-selfhosted`、`serial-macos`、`serial-windows` 则是不参与合并判定的自愈演练，用来反复验证失败转移池的可用性。

## 用程序而不是 YAML 编排门禁

每个 CI job 的具体检查内容不写在 YAML 里，而是委托给 `scripts/run-gates.ts` 的具名模式，比如 `ci-static`、`ci-coverage`、`ci-bench`、`ci-snapshot`、`ci-artifacts`、`hygiene`、`doc-sync`。`gatesForMode()` 根据模式返回一组 `Gate`，每个 `Gate` 是带 `id`、`command`、`needs`、`allowFailure` 的普通对象，调度器 `runGates()` 按依赖图做有界并发，并发度可用 `DSH_GATE_CONCURRENCY` 覆盖。例如 `ci-static` 展开为共享静态门禁、构建、文档同步、`verify-module-graph` 和 `knip`。

这样做的动机是：如果全写成 YAML 的 `run` 步骤，"这次到底跑了哪些检查、依赖怎样、并发怎么控"会散在几十个 job 里，改一次门禁要到处改。写成程序后，依赖关系、并发策略和失败汇总都是可以本地直接运行、写类型、写测试的普通代码，要改"覆盖率门禁应在哪些检查之后跑"，只需改一个 `needs` 数组，不用理解 Actions 语法怎么和自定义 shell 纠缠。

## 本地 lefthook 与 GitLab CI

`lefthook.yml` 开头就说明了分工：本地检查点要快，全仓库的门禁矩阵归 CI。`pre-commit` 只做和本次改动直接相关、几秒内能完成的事：对 staged 的 `*.i18n.yaml` 做翻译配对校验、对 staged 文件跑 oxlint 自动修复并重新暂存、重新生成第三方 notice、空白检查、vendor manifest 守卫。`pre-push` 只跑一项完整的 `pnpm run typecheck`，拦住"类型错误推上去被 CI 打回"这种最常见的浪费。全仓库 100% 覆盖、Windows 矩阵、Playwright 浏览器快照这些开销大的检查，本地 hook 不试图复制。

`.gitlab-ci.yml` 和 GitHub Actions 职责完全不重叠：它只在打 `python-v*` 格式的 tag 时触发，分 `build` 和 `publish` 两个 stage，校验 tag 版本与 `package.json` 一致，构建单文件可执行体，用 `smoke-python-runtime.py` 做发布形态 smoke，最后用 `twine upload` 发布 Python SDK wheel 和五个平台的 runtime wheel（linux x64 与 arm64、macOS arm64 与 x64、windows x64）。GitHub Actions 管每次 PR 与 push 的正确性门禁，GitLab CI 管 tag 触发的一次性发布动作。

## 我的看法

以下是基于材料的判断。逐文件 100% 覆盖加上 `perFile` 是很强的约束，而配套的 postmortem 与"未覆盖行往往是死代码"的态度，让它更像一种删除死代码的压力，而不是单纯的数字指标，这一点材料里有明确文字支持。代价也能从材料里看到：门禁数量增长快（新增 bench、Windows 拆分为两个 required job、分区并发覆盖率），CI 编排因此复杂到需要自托管失败转移开关；豁免条件（如 `pwsh` 探测）意味着本地绿并不等于 CI 绿。材料自己也提醒，lefthook 全绿不等于 CI 会全绿。

## 小结

- 七层测试各验证不同的真实性，哲学是真实实现优先、对真实模型跑、检查外部世界、测发布出去的产物，每条都有具体机制和真实事故支撑。
- 门禁的依赖图与调度写在 `scripts/run-gates.ts` 里，GitHub Actions 只触发具名模式并用 `all-checks-passed` 汇总 required jobs。
- lefthook 管快反馈，CI 管全覆盖，GitLab CI 专管 Python wheel 发布，三者分工互补。
