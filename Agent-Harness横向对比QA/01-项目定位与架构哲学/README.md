# 模块一：项目定位与架构哲学

> 返回[总览](../README.md)。

**Q1. 如果只用一句话向我介绍这五个开源 Agent Harness 项目，你会怎么说？**

- **PI**：核心足够小、可以单独当引擎复用的极简终端编码 Agent。
- **DeepSeek Harness**：把"万物皆插件"这条哲学贯彻到底、依赖 Cordis 元框架的通用 Agent Harness。
- **Hermes Agent**：一个自我进化、经过大量真实生产故障打磨的多平台常驻个人/团队 Agent。
- **OpenHarness**：一个几乎逐工具复刻 Claude Code 的 Python 实现，外加基于它长出来的个人 Agent App `ohmo`。
- **OpenClaw**：用单一常驻 Gateway 把模型、工具、十余种消息渠道、四端原生 App 统一到同一套信任模型下的助理平台。

**Q2. 这五个项目里，哪个"最不像传统框架"？为什么？**

DeepSeek Harness 最不像——它没有自己发明一套扩展范式，而是把 Cordis（一个"万物皆服务、按名字索引"的依赖注入元框架）的源码直接 vendor 进仓库，运行时几乎每一层能力都是挂在 Cordis 这棵插件树上的普通节点，连 Agent 循环本身都是插件。换句话说，dsh 的"核心"薄到几乎不存在特权代码，这在五个项目里是唯一一个把"框架"本身外包给第三方元框架、自己只负责组装的案例。

**Q3. 这五个项目对"核心该做多大"这个问题，分别给出了怎样不同的答案？**

- PI：核心够小即可，扩展交给 TS Extension/Skills。
- dsh：核心几乎为零，一切是插件（Cordis 服务）。
- Hermes：核心是一个持续膨胀、靠机械重构减重的巨型类，没有刻意控制核心边界。
- OpenHarness：核心对齐 Claude Code 的工具集，边界由"复刻对象"决定，而不是自己设计。
- OpenClaw：核心边界写进了产品文档——"两层两条门槛"，核心的每个工具/prompt 行/配置项都要打到每次模型请求上，所以审查最严，官方明确要求"持续给核心瘦身"。

**Q4. 如果让你给这五个项目按"工程成熟度/生产打磨程度"排序，你会怎么排，依据是什么？**

不存在一条绝对客观的排序，但可以按"是否有真实生产故障沉淀下来的痕迹"这条线索粗排：Hermes 和 OpenClaw 的文档/AGENTS.md 里大量出现"这条规则来自某次真实故障编号""这是真实事件驱动的失败模式"这类表述，说明它们经历过较长的生产周期；dsh 的测试覆盖率规则（逐文件 100%）和治理规则也很严格，但更偏"设计阶段就定好规矩"而非"故障驱动"；PI 和 OpenHarness 相对更偏"架构展示"性质，代码整洁但历史包袱较少。这条排序本身也是一个好的追问点——面试官更想听的是你怎么找证据支撑排序，而不是排序本身。

**Q5. 这五个项目中，哪个明确表达了"复刻已验证产品"而非"另起炉灶"的设计取向？这种取向有什么优劣？**

OpenHarness——`pyproject.toml` 直接自称"Open-source Python port of Claude Code"，工具协议、权限模型、Skills/Plugins 规范都尽量贴身对齐 Claude Code。优势：不需要从零验证工具协议设计是否合理，站在一个已经被市场验证过的产品肩膀上；劣势：创新空间受限于复刻对象的设计选择，一旦复刻对象升级，跟随成本会持续存在；另外它也不是纯复刻，围绕核心长出了 `ohmo` 这类原创部分，说明"复刻"和"创新"可以在同一个项目里分层共存。

**Q6. 这五个项目里，哪个的"产品哲学文档"写得最系统、最像一份可执行的工程决策依据？**

OpenClaw 的 `VISION.md`——"两层两条门槛"（核心严审 vs 插件宽松）、"Recurring demand defines interfaces"（多个 PR 反复实现同类能力时该抽象成契约而不是持续接受重复实现）、Code Plugin vs Bundle-style Plugin 的执行模型区分，都是可以直接拿来做代码评审依据的具体规则，而不是空泛的价值观陈述。Hermes 的 Footprint Ladder（六级扩展面决策框架）是另一个可比对象，但更聚焦"新能力该加在哪一层"这一个问题，覆盖面不如 VISION.md 广。
