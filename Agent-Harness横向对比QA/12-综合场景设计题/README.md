# 模块十二：综合场景设计题（开放式）

> 返回[总览](../README.md)。

**Q1. 如果让你设计一个新的 Agent Harness，你会怎么组合这五个项目的设计？**

一个合理的组合思路：核心循环参考 PI 的"有状态外壳 + 无状态纯循环"分层，从设计之初就控制好复杂度，避免重蹈 Hermes 那种"巨型类靠机械重构减重"的覆辙；扩展机制参考 OpenClaw 的 Code Plugin/Bundle-style Plugin 二级信任模型，同时用 VISION.md 那种"两层两条门槛"的产品哲学控制核心边界；多智能体参考 Hermes 的"轻量委派 + 持久化编排"双轨制；安全模型参考 Hermes/OpenClaw 那种"诚实分层、承认哪层是真边界哪层是启发式"的态度；协议层如果需要服务多语言原生客户端，参考 OpenClaw 的 TypeBox 单一数据源代码生成方案。

**Q2. 场景：你需要给一个多人共享的团队 Agent 加"防止越权操作"的能力，你会参考哪几个项目的哪些机制？**

参考 OpenClaw 的"沙箱/工具策略/提权"三层边界模型，先明确每一类操作分别属于哪一层；参考它的设备配对信任模型，给不同成员/设备分配不同的信任等级；参考"审计留痕不等于授权"这条原则，确保审批决策有独立于日志系统之外的、真正的授权判定逻辑；如果涉及代码执行，参考 dsh 的自研沙箱内核或 OpenHarness 的外部沙箱 CLI 包装方案做进程边界隔离。

**Q3. 场景：你的 Agent 需要长期运行超过一天的自动化任务，中途可能重启，你怎么设计恢复机制？**

参考 OpenClaw 的 restart-recovery 设计思路：用多种独立信号检测"任务是否在上次运行时被中断"，设置一个有限的重试预算而不是无限重试，超过预算后用"墓碑"标记这个任务已经放弃自动恢复、转人工介入，同时配合"崩溃循环熔断器"防止一个必然失败的任务反复消耗资源重启。同时参考 OpenHarness 的会话快照"每轮落盘"策略，确保恢复点的粒度足够细，不会因为重启丢失太多已完成的进度。

**Q4. 场景：你需要让 Agent 同时服务 CLI、Web、移动端三种前端，你会怎么设计协议层？**

先做一层协议抽象决策：如果暂时只涉及 TypeScript 生态（Web + Node CLI），参考 Hermes 的单进程 Gateway + JSON-RPC 协议即可；如果确定需要 Swift/Kotlin 原生移动端，一开始就采用 OpenClaw 的"协议 schema 单一数据源 + 编译期代码生成"方案，避免后期补做代码生成管线时要回头修复大量手写类型定义不一致的问题。协议之外，参考架构里"Gateway 是单一控制平面"的思路，让三种前端都是同一个后端进程的客户端，而不是各自维护独立的业务逻辑副本。

**Q5. 场景：如果你只有两周时间给一个现有 CLI Agent 加"记忆"能力，你会参考哪个项目的哪个子集？**

优先参考 OpenHarness 的 `CLAUDE.md`/`MEMORY.md` 方案——它足够轻量（沿目录树查找 + frontmatter 文件 + 启发式相关性打分），不需要引入新的存储引擎或复杂的检索基础设施，两周内可以落地一个"发现 + 注入 + 基础检索"的最小可用版本。如果时间更紧张，甚至可以先只做"发现 + 全量注入"，把"按相关性筛选"这类更复杂的机制留到后续迭代——参考 OpenClaw"记忆是互斥插件槽位、今天多个选项、未来收敛"这条产品路线思路，允许自己先上线一个简化版本，而不是一开始就追求完整的记忆系统。

**Q6.（反问）这五个项目里，你认为哪个的架构决策五年后最可能被证明是错的？为什么？**

这是一道没有标准答案、专门考察候选人独立判断能力的开放题。一个可能的回答方向：dsh 自建 Linux Landlock 沙箱内核这类"自己造轮子"的决策，长期看维护成本可能会显著高于依赖一个逐渐成熟的社区标准方案，如果未来出现被广泛采纳的跨平台沙箱标准，dsh 现在的自研方案可能会变成技术债；也可以反过来论证——正是因为自研，dsh 才能不受外部方案的发布节奏和设计取舍限制，长期看反而是更可控的选择。面试官更想看到的是候选人能不能给出有理有据的论证，而不是背出一个"正确答案"。
