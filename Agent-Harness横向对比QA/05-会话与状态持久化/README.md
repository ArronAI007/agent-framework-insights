# 模块五：会话与状态持久化

> 返回[总览](../README.md)。

**Q1. 为什么有的项目选 SQLite，有的选 JSON/JSONL？取舍是什么？**

JSON/JSONL（PI、OpenHarness）的优势是简单、可读、可 diff、天然支持"追加即分支"；代价是复杂检索（全文搜索、按时间/标签过滤）需要额外自建索引机制。SQLite（Hermes、OpenClaw）的优势是天然支持事务、索引、全文检索（FTS5）、并发访问控制；代价是数据本身不再是人眼可读的文本，出问题时排查门槛更高。选择哪一种本质上取决于项目对"检索能力"和"简单直观"这两个需求的权重分配。

**Q2. OpenClaw 为什么在 AGENTS.md 里明文禁止新增 JSON/JSONL 运行时存储？**

因为一旦允许"每个新功能都可以顺手加一个 JSON 文件存状态"，很快会出现大量分散的、彼此不一致的持久化实现，每个都要单独处理并发写入、迁移、备份问题。强制所有核心运行时状态和缓存收敛到 SQLite，并且只能通过 Kysely 这层统一的查询构造器访问，是用一条强规则换取"所有状态管理都遵循同一套事务/迁移/并发语义"的一致性，属于"规模大到一定程度后必须的治理手段"。

**Q3. dsh 的事件溯源（event sourcing）会话表示相比"直接存历史消息数组"有什么好处？**

事件溯源存的是"发生了什么事件"而不是"当前状态是什么"，好处是可以完整重放整个会话的演变过程，压缩也可以用"追加一个 replace 事件"而不是"物理删除历史"来实现，天然保留审计轨迹。代价是读取当前状态需要额外的投影（Surface）计算，不像直接存消息数组那样"读出来就是当前状态"。

**Q4. Hermes 的 SessionDB 为什么要用 mixin 拆分 search/schema/portability？**

因为把全文检索（FTS5 + 自研 CJK 分词）、schema 迁移、导入导出这几类关注点全部塞进一个类里，会让这个类变得难以独立测试和维护；拆成 mixin 让每一类关注点可以独立演进、独立测试，同时依然可以组合出一个完整的 SessionDB 类。这是"关注点分离"原则在一个体量很大的持久化模块上的具体落地。

**Q5. 会话裁剪（pruning）、resume、restart-recovery 这几个概念分别解决什么问题？**

- **裁剪（pruning）**：会话历史增长过大时，按规则删除/归档不再需要的部分，防止存储无限膨胀。
- **resume**：把一个之前中断或结束的会话重新加载回来继续对话，通常需要修复中断造成的状态不一致（比如 OpenHarness 的 `sanitize_conversation_messages()` 专门修复孤立的 `tool_use` 块）。
- **restart-recovery**：Gateway/守护进程本身重启后，怎么恢复中断的会话和后台任务，通常有一个有限的重试预算和"墓碑"标记机制防止无限重试。

**Q6.（陷阱题）"session"和"main session"是一回事吗？（以 OpenClaw 为例）**

不是同一个概念的两种叫法。"session"是泛指的会话实体，一个系统里可以同时存在很多个；"main session"是一个更具体的概念，特指长期存在的默认会话（区别于临时会话或子会话）。如果候选人把两者混为一谈，说明他没有区分"会话"这个通用数据模型和"main session 承担的特殊角色定位"这两层含义——这正是课程写作时特意强调要讲清楚的一点。
