# 模块十：通信协议、多端与部署形态

> 返回[总览](../README.md)。

**Q1. 单进程多前端共享一套协议这种设计解决了什么问题？**

如果每种前端（CLI、Web、桌面 App）各自实现一套和后端通信的协议，不仅重复劳动，还容易出现"同一个功能在不同前端表现不一致"的问题。让所有前端共享同一套协议契约（比如 Hermes 的 JSON-RPC 网关协议、OpenClaw 的 WS 协议），意味着新增一种前端只需要实现协议的客户端一侧，而不需要重新设计一套通信语义，也保证了多前端之间行为的一致性。

**Q2. OpenClaw 为什么要用 TypeBox 作为协议单一数据源，再生成 Swift/Kotlin？**

因为 OpenClaw 要同时服务 TypeScript 后端和 Swift（macOS/iOS）、Kotlin（Android）原生前端，如果协议类型定义在三种语言里各自手写一份，任何一次协议变更都要在三个地方同步修改，极易出现遗漏和不一致。用 TypeBox 定义协议 schema 作为唯一数据源，编译期自动生成 JSON Schema 再派生出 Swift/Kotlin 类型，把"协议是单一数据源"这条原则贯彻到了代码生成层面，`protocol:check` 还会用 `git diff --exit-code` 防止生成产物和源头定义产生漂移。

**Q3. dsh 的 Host/Client 类型与构建物理分离是为了解决什么问题？**

dsh 的 Node 宿主进程（Host）负责跑 Agent 循环、工具执行、持久化，浏览器端（Client）是一整套插件化的 UI 组件，两者物理上运行在完全不同的环境（Node vs 浏览器），如果不做类型隔离，Host 端的类型定义很容易意外泄漏进 Client 的构建产物里，反之亦然。用 Typert 在编译期生成类型安全的 RPC 契约，让两侧各自维护自己的类型系统，只通过生成的 RPC 契约通信，从根本上防止类型系统互相污染。

**Q4.（陷阱题）OpenHarness 的 Textual 备用界面既然写得很完整，为什么没有被接入主入口？这说明了什么？**

课程写作时用 grep 验证过，`ui/textual_app.py` 虽然测试齐全、代码完整，但确实没有被 `cli.py`/`run_repl` 实际引用——它是一份写得很完整、却处于"孤儿"状态的正交实现。这说明一个仓库里"存在某个功能的完整代码"和"这个功能真的在被使用"是两回事，候选人如果只根据代码目录结构就断定某个模块是"当前主力实现"，容易得出错误结论——验证一个模块是否真的被调用，永远应该落到"有没有被实际 import/引用"这个具体证据上，而不是"看起来功能完整就该是在用的"。

**Q5. Gateway 模式（单一常驻控制平面）相比"每次命令起一个新进程"有什么优劣？**

优势：长期存活的连接（比如 WhatsApp 会话）不需要每次都重新建立；多个客户端可以共享一致的状态视图；后台任务（cron、消息监听）可以持续运行而不依赖某次命令行调用的生命周期。劣势：需要额外设计配对/信任模型来管理"谁能连接这个常驻进程"，并发写入、进程崩溃恢复这类问题也变得更复杂，不像"一次性进程"那样天然没有状态残留问题。OpenClaw 和 Hermes 都选择了 Gateway 模式，说明这是"个人/团队常驻助理"这类场景下的主流答案，但代价是更高的工程复杂度。

**Q6. 如果要给一个 CLI 工具增加一个 Web UI，你会参考这五个项目里的哪种协议设计？**

比较务实的参考是 Hermes 的"单进程多平台 Gateway + 共享 JSON-RPC 协议"或 OpenClaw 的"WS 协议 + TypeBox 单一数据源"——两者的共同点是先把协议契约独立出来，Web UI 只是这套协议的又一个客户端，而不是给 Web UI 单独发明一套通信方式。如果项目规模较小、暂时不需要跨语言客户端，Hermes 的 JSON-RPC 模式足够；如果未来有明确的多语言原生客户端需求，OpenClaw 的编译期代码生成模式能省下大量后续重复劳动。
