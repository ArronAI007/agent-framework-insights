# 模块九：长期记忆与个性化

> 返回[总览](../README.md)。

**Q1. 为什么会话持久化不能替代"长期记忆"？两者的本质区别是什么？**

会话持久化解决的是"这一个会话的历史怎么存、怎么恢复"，本质上是单个会话生命周期内的状态管理；长期记忆解决的是"跨越多个会话、甚至跨越很长时间周期，哪些信息应该被沉淀下来、影响未来的行为"，本质上是超越单次会话边界的知识/偏好积累。一个只做会话持久化的系统，每次开新会话都是"从零认识用户"；只有独立于会话之外的长期记忆层，才能让系统"越用越懂你"。

**Q2. OpenHarness 的三条正交记忆路径（项目/team/agent）分别解决什么问题？**

**项目记忆**（默认自动注入，对应 `CLAUDE.md`/`MEMORY.md`）解决"这个项目/仓库层面有哪些约定该被所有会话共享"；**team 记忆**（仅打了 scope 标签，没有同步机制）解决团队层面的信息标记，但课程验证时发现它目前还没有真正的跨会话同步实现；**agent 记忆**（每个 coordinator 子代理类型的私有仓库，仅手动触发）解决"某一类特定角色的子代理该积累哪些专属经验"。三者互不干扰，也说明"记忆"不是一个单一维度的概念，而是需要按"归属范围"拆成多个独立的存储路径。

**Q3. OpenClaw 为什么把记忆设计成"互斥插件槽位"？**

因为记忆系统涉及复杂的检索、存储、一致性问题，如果允许多个记忆插件同时生效，很容易出现"同一个事实在两套记忆系统里各存一份、互相冲突"的问题。把记忆限定成同一时刻只能有一个插件生效的互斥槽位，从架构层面直接排除了多套记忆并存导致数据不一致的可能性；官方也明确表态"今天提供多个记忆选项，未来计划收敛到一个推荐默认路径"，说明这是一个刻意的、承认当前是过渡状态的设计。

**Q4.（陷阱题）"Active Memory"是不是一直在后台运行、主动往上下文里塞记忆？**

不是。课程写作时验证发现，"Active Memory"实际上是一条**只在升级场景下才启用**的深度召回通道，不是持续运行的后台功能——名字里的"Active"容易让人误以为它一直在主动工作，但真实机制是分层的：日常场景走零模型调用的检索通道，只有满足特定升级条件时才会触发这条更"主动"、开销更大的深度召回通道。

**Q5.（陷阱题）"Dreaming"机制是不是会生成新的记忆内容？**

不是。课程写作时验证发现，"Dreaming"是一条三阶段（浅睡眠/REM/深睡眠）的、由确定性评分把关的批量巩固流水线，作用是对已有记忆做整理和巩固（去重、合并、提炼重要性），而不是凭空生成新的记忆内容。这个名字非常容易引发"它在做梦、在创造新东西"这类联想，但代码层面的真实行为其实更接近"整理房间"而不是"做梦创作"。

**Q6. 个性化系统该用规则匹配还是模型驱动抽取？各有什么取舍？（以 OpenHarness 为例）**

OpenHarness 的个性化系统（`personalization/extractor.py`）课程验证发现是**纯正则模式匹配**（识别 SSH 主机、IP、conda 环境这类结构化信号），不是模型驱动的语义抽取。规则匹配的优势是确定性强、成本几乎为零、不依赖额外的模型调用；劣势是只能捕捉"长得像某种已知模式"的信息，抓不住需要语义理解才能识别的偏好（比如"用户不喜欢冗长的解释"这类模糊表达）。真正的语义级记忆抽取在 OpenHarness 里是另一套独立机制（`services/memory_extract/`），说明"规则匹配"和"模型驱动抽取"往往是互补关系，而不是二选一。
