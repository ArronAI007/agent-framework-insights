# 模块六：上下文管理与压缩

> 返回[总览](../README.md)。

**Q1. 上下文压缩要解决的根本问题是什么？**

模型的上下文窗口有硬性长度上限，长时间运行的会话历史迟早会超限；压缩要在"尽量保留对完成任务仍然关键的信息"和"把 token 占用降到窗口允许范围内"之间做取舍，本质上是一种有损但要尽量减少信息损失的摘要/裁剪过程。

**Q2. 列举五个项目各自的压缩触发条件。**

- PI：接近上下文窗口上限时做分支摘要。
- dsh：Compaction 触发后连带做 Checkpoint 持久化存档。
- Hermes：结构化摘要模板 + 运行时迭代式摘要更新。
- OpenHarness：每轮对话直接检查是否接近 `auto_compact_threshold_tokens`，触发四级级联压缩。
- OpenClaw：双触发条件（容量阈值 + 安全网守卫质量审计），后者是在容量还没超限时，也可能因为"内容质量已经不适合继续留在上下文里"而提前触发。

**Q3. Hermes 的 `trajectory_compressor.py` 和运行时压缩器是什么关系？**

两者是完全独立的两套系统，服务的目标完全不同。运行时压缩器（`context_compressor.py`）服务于"让当前会话能继续在窗口限制内运行下去"；`trajectory_compressor.py` 服务于"把会话轨迹压缩成适合喂给模型训练管线的数据格式"，是 Nous Research 作为模型训练机构，把"Agent 产品"和"训练数据生产线"合流思路的具体体现——这是 PI、dsh 都没有的模块，也是候选人容易漏答的一个知识点。

**Q4. OpenClaw 的 `owns`/`delegate` 两种压缩归属模式分别在什么场景下使用？**

`owns` 模式下，触发压缩的这一方自己负责执行完整的压缩流程并对结果负责；`delegate` 模式下，触发方把压缩工作委托给另一个更适合的角色执行（比如子会话的压缩委托给主会话统一处理，避免多处并发压缩同一份历史导致冲突）。这条设计和第五模块讲的"写者声明"机制背后是同一类考虑——常驻多客户端系统必须明确"谁对这个操作负最终责任"，不能让多方各自决定各自触发。

**Q5. 压缩失败了应该怎么处理？各项目怎么做？**

比较成熟的做法是"失败隔离"而不是"静默重试或吞掉错误"——OpenClaw 的压缩系统在失败时会把这次失败标记为 quarantine（隔离），不会让一次坏的压缩结果污染后续会话状态；OpenHarness 的四级级联压缩也设计了"压缩失败或压缩后仍然超限"的兜底路径。相比之下，如果压缩失败被静默吞掉、会话继续用一个损坏的压缩结果运行，往往会导致更难排查的下游错误——这是候选人容易忽略、但生产系统里必须认真处理的边界情况。

**Q6.（陷阱题）压缩是不是应该做的越激进越好（尽量多删）？**

不是。压缩越激进，信息损失的风险越大，可能删掉后续任务仍然依赖的关键上下文（比如之前约定的文件路径、用户明确提出的约束条件）。OpenClaw 专门设计了"安全网质量审计"这一层，就是为了在压缩之后再检查一遍"这次压缩有没有把不该丢的东西丢掉"，这说明业界的共识是压缩本身也需要质量把关，而不是单纯以"腾出更多窗口空间"为唯一目标。
