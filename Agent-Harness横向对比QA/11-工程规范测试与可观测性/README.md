# 模块十一：工程规范、测试与可观测性

> 返回[总览](../README.md)。

**Q1. "不要写镜像实现测试"是什么意思？为什么重要？**

"镜像实现测试"指的是测试代码只是把被测函数的实现逻辑原样翻译成断言（比如实现里怎么算的，测试就怎么断言），这种测试在实现被重构时会跟着一起改，本质上没有独立验证任何行为契约，是一种虚假的安全感。真正有价值的测试应该断言"外部可观察的行为"，而不是"内部实现细节"——这样实现方式变了，只要行为契约不变，测试依然应该通过。OpenClaw、Hermes 的工程规范里都强调了这一点。

**Q2. Crabbox/Testbox 这种隔离测试环境解决了什么问题？（OpenClaw）**

有些测试场景（需要真隔离、清洁安装、打包验证、Docker、桌面/平台行为）没办法在开发者本地环境里可靠复现，也不适合直接在共享 CI 环境里跑（可能污染共享状态、消耗过多资源）。Crabbox（更轻量的 CLI 隔离环境）和 Testbox（挂载凭证的托管测试环境，用于需要真实凭据的场景）提供了按需申请、任务专属、用后即焚的隔离执行环境，把"需要强隔离的证明"和"日常开发迭代"这两类需求分开处理。

**Q3. dsh 为什么要求"每文件 100% 测试覆盖率"，这是不是意味着测试质量一定高？**

要求 100% 覆盖率的动机是希望不留任何"完全没被测试触碰过"的代码路径，尤其是在一个"万物皆插件"的架构里，任何一个未被测试覆盖的插件都可能在生产环境第一次被触发时才暴露问题。但覆盖率本身只衡量"代码有没有被执行过"，不衡量"断言是否真的验证了正确的行为"——一个覆盖率 100% 但断言薄弱（甚至没有断言）的测试套件，依然可能漏掉真实缺陷。这道题的关键点是：覆盖率是必要不充分条件，不能和"测试质量高"划等号。

**Q4.（陷阱题）CI 全绿是不是等于代码没问题？**

不是。CI 全绿只能说明"CI 里配置的检查项都通过了"，而 CI 能覆盖的永远是已知的、被明确写进检查脚本里的场景。真实生产环境里出现的很多问题（并发时序问题、特定平台的边界行为、未被测试覆盖的输入组合）不会被 CI 捕捉到。Hermes 的工程文化里强调"不写变更检测器测试"，OpenClaw 强调"trusted development proof runs locally...需要额外用 Crabbox/Testbox 做隔离证明"——这些规则背后的共同逻辑是：CI 全绿是一个必要的门槛，不是"代码正确"的证明。

**Q5. Autopilot 快照 + 静态站点这种可观测性方案的优势和局限是什么？（OpenHarness）**

优势是几乎零运维成本——快照挂在"任何会改变任务卡片状态的操作"尾部触发导出，不需要独立的调度器，前端甚至可以直接发布成 GitHub Pages 静态站点，没有常驻服务开销。局限是它不是实时推送——前端页面只在挂载时拉取一次数据，没有轮询或 WebSocket 更新机制，用户需要手动刷新才能看到最新状态；另外课程写作时还发现一处真实的实现缺陷：导出逻辑会无条件覆盖 `index.html`，导致本地手动构建的完整仪表盘会被下一次任意状态变更静默替换回极简 fallback 页——这提醒我们"轻量方案"往往伴随着"精细度不足"的代价，两者需要权衡。
