# 模块三：多模型 / Provider 抽象与 Failover

> 返回[总览](../README.md)。

**Q1. 统一多模型接口常见的设计模式有哪些？五个项目分别属于哪一种？**

- **完整适配器模式**（每个 Provider 一层完整实现）：PI 的 `pi-ai`。
- **Seam/双实现对照验证模式**（同一接口至少两个独立实现互相校验）：dsh 的 `packages/llm/*`。
- **元数据驱动 + 少数原生 Adapter 混合**（大多数 Provider 靠声明式配置描述差异，协议差异大的厂商才写原生代码）：Hermes、OpenClaw 都属于这一种。
- **Protocol + 具体客户端组合/复用**：OpenHarness 的 `SupportsStreamingMessages` Protocol，Copilot 客户端甚至靠 monkeypatch 复用 OpenAI 客户端而非独立重写。

**Q2. OpenClaw 的两阶段 Failover 具体分哪两阶段？为什么要拆开？**

第一阶段是**认证 profile 轮换**——同一个模型能力可能有多个认证凭据（比如多个 API Key/多个订阅），先在凭据层面尝试切换；第二阶段才是**模型降级**——凭据层面都试过仍失败，才降级到备选模型。拆开的原因是两类失败的根因完全不同：前者往往是配额/认证问题，换一个凭据就能恢复，没必要连带牺牲模型质量去降级；只有确认凭据层面都不行了，才值得付出"换一个能力更弱的模型"这个代价。OpenClaw 还在这之外单独设了一层 operation 级别的重试，与 Failover 完全解耦。

**Q3. OpenHarness 的 Copilot 客户端为什么选择 monkeypatch 而不是独立实现？**

因为 GitHub Copilot 的接口在很大程度上是 OpenAI 兼容协议的变体，独立实现一整套客户端意味着要重复维护一份和 OpenAI 客户端高度重叠的代码；用组合/monkeypatch 的方式复用已有的 OpenAI 客户端、只覆盖差异部分（比如认证方式），能显著减少重复代码和后续同步维护的成本。这是一个"能复用就不重写"的典型工程判断，但也带来一个隐性风险：如果被复用的 OpenAI 客户端后续改了内部实现细节，monkeypatch 的部分有断裂的可能，比继承/组合的正式接口更脆弱。

**Q4. dsh 用"双 Provider 对照验证"这种测试方式解决什么问题？**

如果只有一个 Provider 实现，很容易把"这个 Provider 恰好这么处理"的偶然行为，误当成"这层 seam 抽象本该长这样"的必然设计。同时维护两个独立的 Provider 实现（`llm-deepseek`/`llm-pi-ai`）并让它们对照跑同一套契约测试，能尽早暴露出"这层抽象其实偷偷依赖了某个 Provider 的特定行为"这类设计缺陷。

**Q5. Hermes 为什么只对协议差异特别大的几家（Anthropic/Bedrock/Gemini/Codex）写原生 Adapter，其余走 Profile 元数据？**

因为大多数 Provider 只是在"认证方式、请求字段命名、返回格式"这些细节上有差异，本质上都能收敛到 OpenAI 兼容协议的变体上，用一份声明式的 Profile 元数据描述这些差异即可，不值得为每一家都写一整层适配代码；但 Anthropic、Bedrock、Gemini、Codex 这几家的协议形态（比如流式格式、工具调用的表达方式）和主流的 OpenAI 兼容协议差异太大，元数据描述不了这些结构性差异，只能落到代码层面单独写。这是"能声明就不写代码，写代码只留给声明描述不了的地方"这条工程原则的具体案例。

**Q6.（陷阱题）是不是 Provider 数量越多的项目，抽象层就设计得越好？**

不是。OpenClaw 用 grep 实测出 154 个 extension 目录里有 79 个声明了 `providers`——数量最多，但这只说明生态覆盖广，不直接等价于"抽象层设计得好"。抽象层设计好坏的真正衡量标准是：新增一个 Provider 需要写多少代码、Failover 逻辑是否和具体 Provider 实现解耦、协议差异是靠声明式元数据还是靠到处写 if-else 分支吸收。数量是生态成熟度的信号，不是架构质量的证明——这条区分本身就是一道好的追问：候选人如果只会用"数量多"来评价好坏，说明他没有深入到具体的契约设计层面。
