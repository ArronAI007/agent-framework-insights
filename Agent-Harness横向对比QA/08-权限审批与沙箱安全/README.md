# 模块八：权限、审批与沙箱安全

> 返回[总览](../README.md)。

**Q1. "沙箱"、"工具策略"、"提权"这三个概念的边界在哪？（以 OpenClaw 为例）**

**沙箱**是执行环境层面的隔离（文件系统、网络访问的物理边界）；**工具策略**是决定"这个工具调用允不允许发起"的准入判断（发生在进入沙箱之前）；**提权**是在沙箱边界内，某些操作需要额外的、更高权限的批准才能突破默认限制的逃生通道。三者分别对应"能不能跑""该不该跑""跑的时候能不能突破默认限制"三个不同阶段的问题，OpenClaw 专门写了一篇文档区分这三者，正是因为它们太容易被混为一谈。

**Q2. dsh 为什么要自己手写一个 Linux Landlock 沙箱内核，而不是直接用现成方案？**

因为要覆盖多平台（Linux/macOS/Windows）并且希望沙箱层完全自持、可审计、可打补丁，而不是依赖一个外部黑盒方案——这和 dsh"把 Cordis 生态源码 vendor 进仓库"的整体工程哲学是一致的：宁可自己多写代码，也要保证关键基础设施完全在自己掌控之中，不受外部依赖的发布节奏和实现细节变化影响。

**Q3. Hermes 的"三层不等分量防御"具体指哪三层？为什么说它们"不等分量"？**

七种可插拔终端后端的沙箱隔离（OS 级边界）、网络出口隔离（OS 级边界）、批准模式（启发式门控）。前两层是真正的安全边界——`SECURITY.md` 明确承认这一点；批准模式只是一道"防合作模式下误操作"的门控，不是"防对抗性绕过"的边界，文档也明确承认了这一点。三层"不等分量"指的正是：不能因为都叫"安全机制"就默认它们提供同等强度的保护，诚实区分哪层是真边界、哪层只是启发式提醒，本身就是一种工程诚实。

**Q4. OpenHarness 的默认沙箱后端和 Docker 后端之间是什么关系？**

不是"Docker 是默认、其他是备选"这种直觉关系——课程验证发现默认后端实际是包装 Anthropic 官方 `srt` CLI（Linux 上用 bubblewrap，macOS 上用 sandbox-exec），Docker 是第二个、需要用户显式开启的可选后端，两者靠简单的字符串比较来分发，而不是共享一个统一的抽象接口。这也是一个"望文生义会出错"的案例——如果只看到项目里有 Docker 相关代码就默认它是主力方案，会得出错误结论。

**Q5.（陷阱题）审计日志（audit log）能不能被当作"这个操作已经被批准过"的证明？**

不能。OpenClaw 的 `AGENTS.md` 明文写着"opt-in provenance is never authorization"——留痕（有记录）和授权（被批准过）是两件完全不同的事，审计日志只是记录"发生了什么"，不能反过来被下游逻辑当成"这件事被批准过"的凭证。如果一个系统设计里把"有审计记录"当成放行的依据，就是把留痕和授权错误地等同起来，这是审计系统设计里一个真实存在、也很危险的陷阱。

**Q6. 云端沙箱能力应不应该做成核心项目的插件？OpenClaw 是怎么选的，为什么？**

OpenClaw 明确选择"不做"——VISION.md"What We Will Not Merge"一节直接点名"Cloud-based sandbox providers as OpenClaw plugins"是不会被接受的，云沙箱能力被导流到一个独立项目 Crabbox 里实现。理由是核心不应该为每个云沙箱厂商都维护一份插件适配，这会持续膨胀核心的维护面；把这类"提供商众多、接口差异大、变化频繁"的能力独立成另一个项目，是控制核心复杂度的一种取舍。

**Q7. 如果一个 Agent 系统完全不做沙箱、只靠权限审批，会有什么风险？**

权限审批本质上是"进程内的决策"，判断依据往往来自模型自身的行为或预设规则，一旦审批逻辑本身被绕过或存在漏洞，工具执行就没有第二道边界兜底；沙箱提供的是"进程边界隔离"这个物理层面的兜底，即使审批逻辑出了问题，沙箱依然能限制实际造成的破坏范围。只靠审批不做沙箱，相当于只有软件层面的门锁、没有物理围墙——理论上审批做得足够严谨也能防住大部分风险，但少了一层独立于审批逻辑本身的兜底防线。
