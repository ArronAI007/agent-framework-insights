# 模块七：多智能体协作与任务编排

> 返回[总览](../README.md)。

**Q1. 子代理委派有哪两种典型实现路径？分别在什么场景下适用？**

一种是**轻量、进程内、上下文零成本的并行委派**（比如 Hermes 的 `delegate_task`）——适合"父任务只需要看到子任务的最终结果摘要，不需要观察中间过程"的场景，委派开销小；另一种是**持久化的任务看板/编排系统**（比如 Hermes 的 Kanban、OpenHarness 的 Coordinator）——适合需要长期跟踪、可能跨会话持续存在、需要人工介入查看进度的复杂任务编排场景。

**Q2. Hermes 的 delegate_task 和 Kanban 为什么并存而不是二选一？**

因为它们解决的是两类不同粒度的问题：`delegate_task` 面向"这一轮对话里，我需要一个子任务帮我并行做点事，做完汇报结果就行"；Kanban 面向"一个需要持久化状态、可能横跨多轮甚至多天、需要被人查看和干预的复杂工作流"。用同一套机制强行覆盖两种场景，要么轻量场景被迫承担不必要的持久化开销，要么复杂场景缺乏足够的状态追踪能力——课程里明确强调这两套机制"边界清晰、互补而非替代"。

**Q3. OpenHarness 的 Swarm/Coordinator/Bridge 三者关系是什么？是不是一个依赖另一个？**

不是线性依赖关系，而是三个独立发展的子系统：**Swarm** 是机制层，提供 Team/Worktree/Mailbox 这类"怎么把一个队员跑起来"的执行原语；**Coordinator** 是经验层，通过环境变量驱动的行为分支，把"怎么编排团队"这套经验直接写进系统提示里；**Bridge** 是一个独立的、"驱动一个 OpenHarness 会话"的编程接口，课程写作时用 grep 验证过，在这份代码快照里 Bridge 与 Swarm/Coordinator/Tasks 之间**没有直接的调用耦合**，甚至独立实现了一套自己的进程跟踪逻辑，而不是复用 Swarm 已有的 `BackgroundTaskManager`。这是一个很好的例子，说明"看起来应该相关的模块，实际读代码验证后可能完全独立"。

**Q4.（陷阱题）OpenClaw 代码里"delegate"这个词出现在几个不同概念里？分别是什么？如果面试者说"delegate 就是任务委派"，你会怎么反驳？**

至少三个完全正交的概念共享"delegate"这个词：**multi-agent 路由**（一条消息该分发给哪个会话，和"任务委派"无关）、**delegate 身份模式**（`delegate-architecture.md` 讲的其实是一种组织意义上的"具名委托人"身份模式，不是任务委派机制）、`sessions_spawn` **任务委派**（这才是真正对应"把一个子任务派发出去"的机制）。如果面试者只说"delegate 就是任务委派"，说明他大概率是从文档标题望文生义，而没有真的去读 `delegate-architecture.md` 的具体内容——这正是课程写作时真实踩过的坑，也是这道题存在的原因：验证比信任标题更重要。

**Q5. Worktree 隔离在多智能体并行编辑场景下解决了什么问题？**

多个子代理如果同时在同一份工作目录里并行修改文件，会互相覆盖对方的改动。用 `git worktree` 给每个子代理分配一份独立的工作树，让它们各自在物理隔离的目录里编辑，最后再统一合并/审阅，从根本上避免了"两个进程同时写同一个文件"这类并发编辑冲突。

**Q6. 什么是"yield/handoff"？为什么需要这个机制？**

"yield/handoff"描述的是子代理什么时候把控制权交还给谁、以及交还时结果怎么合并回主会话这套协议。没有这套协议的话，子代理执行完之后"该由谁来消费这个结果、什么时候消费"是模糊的，容易出现结果丢失或者重复处理的问题；显式的 yield/handoff 协议把这个交接点标准化，明确了控制权转移的时机和数据契约。

**Q7. 如果要设计一个新的多智能体协作系统，你会从这五个项目里各借鉴什么？**

一个合理的组合是：借鉴 dsh/Hermes 的"轻量委派 vs 持久化编排"两套并行机制的分层思路；借鉴 OpenHarness Swarm 的 Worktree 隔离手段处理并行编辑冲突；借鉴 Coordinator 的"把编排经验写进系统提示"这一层，降低模型临场决策的不确定性；借鉴 OpenClaw 的教训——如果你的系统里也有"delegate"这类容易一词多义的核心术语，一定要在文档和代码里给不同概念起不同的名字，避免未来维护者混淆。
