# 模块二：Agent 核心循环执行模型

> 返回[总览](../README.md)。

**Q1. 五个项目的核心循环分别是怎么组织的？"心脏"在哪一层？**

| 项目 | 组织方式 |
|---|---|
| PI | `agent.ts`（有状态外壳）+ `agent-loop.ts`（无状态纯函数），刻意设计的引擎分层 |
| DeepSeek Harness | `ReactLoopAgent` 的 `kick → turn → step` 三级生命周期 |
| Hermes Agent | `class AIAgent`（巨型外壳）方法转发到自由函数，减重式机械抽取 |
| OpenHarness | `QueryEngine`（壳）+ `run_query()`（心脏，单个 `while` 循环） |
| OpenClaw | Gateway `req:agent` 驱动 `runEmbeddedAgent`，写者声明防并发写冲突 |

**Q2.（追问/陷阱题）Hermes 的"AIAgent 巨型外壳"是不是等价于 PI 的"agent.ts 有状态外壳"？区别在哪？**

不等价，这是一个容易被面试者忽略的关键区别。PI 的分层是**刻意设计**的：`agent.ts` 持有状态，`agent-loop.ts` 是纯函数，两者的边界从一开始就是架构决策的一部分。Hermes 的 `AIAgent` 巨型外壳则是**历史包袱驱动的机械重构**——真正的初始化逻辑被抽到 `agent/agent_init.py`，循环体抽到 `agent/conversation_loop.py`，但抽出去的新函数依然直接读写旧对象的上百个属性，本质上还是同一个巨大状态的一部分，只是物理上挪了个文件。课程写作时特意强调过："不必假装它变成了纯函数引擎"——把方法体搬到自由函数里是合理的减重手段，但如果新函数依然直接操作旧对象状态，就不该包装成一套它并不具备的"无状态契约"。这条区分本身就是候选人是否读过真代码、而不是只看了架构图的试金石。

**Q3. dsh 的 kick/turn/step 三级生命周期具体划分了什么职责？**

`kick` 负责启动一次会话级的驱动（比如响应一条新的用户输入）；`turn` 是一轮"模型 → 工具 → 模型"往返的边界；`step` 是 `turn` 内部更细粒度的单次动作执行。三级划分让"什么时候该检查压缩""什么时候该判断整个会话该不该继续"这类不同粒度的决策，各自落在恰当的层级上，而不是全部堆在一个函数里。

**Q4. OpenHarness 为什么选择"单层线性铺开"而不是像 dsh 那样拆多层状态机？**

`run_query()` 把压缩检查、图片预处理、模型请求、工具执行按顺序依次铺开在一个 `while` 循环里，这个选择的代价和收益都很直接：代价是单个函数体量偏大（挂了不少辅助函数），收益是"一次循环内到底按什么顺序做了什么事"一眼就能看全，不需要在多层状态机之间来回跳转去拼出完整时序。这是一种"用文件体量换认知连续性"的取舍，是否合理取决于团队更看重哪一边。

**Q5. OpenClaw 的"写者声明（writer-claim）"机制解决的是什么问题？为什么其余四个项目都不需要类似机制？**

OpenClaw 的 Gateway 是一个要同时服务多个客户端（CLI/Dashboard/TUI/原生 App）的常驻进程，同一个会话有可能被多个来源并发触发写入。写者声明机制确保同一时刻只有一个"写者"对会话事务写入拥有权威，避免并发写导致的状态错乱。其余四个项目要么是单一 CLI 进程（PI/OpenHarness 默认场景），要么虽然是常驻服务但主要面向单一操作者驱动会话，并发写冲突的概率和后果都小得多，所以没有发展出对应的显式声明机制——这也说明"要不要做这层防护"本质上是由"有没有真实的多写者并发场景"决定的，不是纯技术偏好。

**Q6. 循环终止条件一般有哪几种？举例说明。**

以 OpenHarness 的 `run_query()` 为例，四种终止路径是：模型不再要求工具（正常完成）、模型返回空消息（异常但可恢复）、不可恢复的 API 错误（异常终止）、达到 `max_turns` 上限（硬性熔断，防止模型陷入无限重复调用同一工具的死循环）。这四类大致可以泛化成"正常完成 / 可恢复异常 / 不可恢复异常 / 硬性上限熔断"，五个项目基本都能对应到这个框架，区别只在具体阈值和恢复策略的精细程度。
